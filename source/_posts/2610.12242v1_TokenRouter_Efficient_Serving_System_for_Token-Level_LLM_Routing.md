## 0. 一句话结论

论文解决的是"token 级路由（token-level routing）算法已被证明有收益、但现有 LLM 服务系统跑不动它"这一问题：SGLang、vLLM 等建立在单模型同步假设上，token 级路由会带来步级失同步（step desynchronization）与频繁的批次准入延迟（batch admission delay）。TokenRouter 的核心思路是"请求中心编程、模型中心执行"——开发者只写 route/send/receive 三个按单请求视角描述路由的函数，运行时为每个 LLM 启动一个自治子服务器（subserver），用三段解耦循环异步执行、靠 handoff-resume（交接-恢复）机制保持请求状态，并用延迟批处理（delayed batching）把稀疏到达聚成大批，其最优阈值 $B^*$ 由离散时间马尔可夫链（Discrete-Time Markov Chain, DTMC）吞吐模型解析求出。在论文报告的五种路由算法、三种负载、四组模型对上，吞吐比"更强基线"高 2.01–64.15×（Abstract、§5.2），消融与模型-实测对照支持各组件确有效用；但区间两端点高度依赖比较对象（对最强的 R2R 官方实现仅约 2.0–2.6×），结论应限定在论文覆盖的 A100 单机、并发 1–16、至多 3 个合作模型的范围内。

## 1. 论文具体想解决什么问题？

**研究背景与具体任务。** 大模型服务通常把请求分派给规模、专长不同的模型，以推进成本-质量帕累托前沿（Pareto frontier）。session 级与 query 级的粗粒度路由已在生产系统（如 ChatGPT、Cursor）与学术系统（如 RouteLLM）中广泛使用，但一旦路由完成，整段回复由单一模型生成。新近算法工作把粒度推到 token 级：R2R 只把约 5% 的 token 路由到 32B 模型即可逼近其质量，而 query 级路由需要把约 40% 的请求整单交给 32B；token 级路由还能让专长互补的模型在同一段回复内协作，并提供连续可调的成本-质量工作点（§1）。问题是：这类算法的收益依赖**每个解码步都可能切换模型**的执行模式，而现有服务系统并不支持。论文的任务因此落在系统层：**为 token 级路由推理设计一个高效、对开发者友好的服务系统**，使算法收益在真实系统上兑现，而不改动算法本身。

**现有方法通常如何处理。** vLLM、SGLang 等服务系统面向单模型：同一批活跃请求在每一步解码保持同步推进，连续批处理（continuous batching）、分页 KV 缓存（paged KV cache）等机制都以"请求不离开本模型"为前提（§2）。多模型场景下，speculative decoding 虽然也协调两个模型，但草稿生成与目标验证是固定、可预测的周期性模式；token 级路由则是数据依赖的随机模型访问（§2、§4.2）。

**现有方法具体在哪些条件下表现不好。** 论文在 §1 给出三条：

1. **步级失同步（step desynchronization）**：不同 LLM 每步延迟差异很大，把请求保持在同一个同步批次里意味着每步都要等最慢的模型，快模型被迫空转；
2. **批次准入延迟（batch admission delay）**：token 级路由导致频繁的模型切换，一个被路由的请求到达目标模型时，对方常常正在处理上一批，请求只能等到下一批才开始执行，产生气泡并使批次碎片化；
3. **实现复杂度**：现有系统没有暴露"逐步路由决策"的编程接口，在其内部实现 token 级路由需要大规模修改代码库，还要与连续批处理、前缀缓存（prefix caching）等紧耦合特性小心协调。

**支撑问题判断的证据。** 前两条的直接展示是 Fig. 4 的四种调度策略对照：Step-Sync 用步屏障（平均延迟 13.33 个 SLM 批单位）、Model-Sync 一次只跑一个模型（13.00）、Eager-Async 一有请求就到就处理（10.83），TokenRouter 的延迟批处理把平均延迟降到 8.67——注意这是**示意性时间线**（以 SLM 批为单位），不是硬件实测。真正的实测证据在 Table 10：作者自建的、无状态保持的 SGLang 基线（Std. Serving）在 SLM 侧每个解码步中，前缀匹配 7.78 ms（20.94%）、锁缓存节点 6.49 ms（17.47%）、释放锁 5.13 ms（13.81%）、更新 RadixCache 12.12 ms（32.62%）合计约 84.8% 的时间花在与路由状态保持无关的记账上，SLM 推理本身只占 1.56 ms（4.20%）。也就是说，论文观察到的现象是"系统侧开销吞掉了路由算法的收益"，且这一归因有单点实测支撑；但失同步与准入延迟的因果演示仍以示意图为主（审稿人判断）。

**作者认为问题产生的原因。** 根因是"单模型同步假设"：请求进入批次后被假定不会离开，返回的 token 被当作全新请求处理，于是每次切换都要重做前缀匹配与 KV 缓存分配。TokenRouter 的对策是把"路由算法描述"与"系统执行优化"彻底解耦：算法只在单请求视角描述流动，系统以状态保持的异步跨模型调度执行。

**论文最终要验证的核心假设。** 若把每个合作 LLM 当作自治子服务器独立推进、请求以消息在子服务器间异步迁移（迁移只需追加 token，不重建服务状态）、并用延迟批处理把稀疏到达聚成大而满的同模型批次，则：（a）token 级路由的算法收益能在真实系统上兑现为吞吐与延迟优势；（b）该优势随输出长度与并发扩大而保持；（c）系统可作为标准单模型服务器的替代品（drop-in replacement），不要求算法作者理解底层调度。

**三类问题的区分：**

- **领域早已存在的一般问题**：LLM 服务中的批调度与 KV 内存管理、多模型协同的选择策略；
- **本文发现的新观察**：token 级路由在单模型同步假设下产生的两类系统级病态（失同步、准入延迟），以及"把返回 token 当新请求"造成的可量化开销（Table 10 的逐项分解）；
- **本文实际解决的具体子问题**：在 8×A100-80G 单机（另有跨节点变体）上，为 5 种已有 token 级路由算法提供统一运行时，在并发 1–16 的负载下把吞吐与端到端延迟做到显著优于官方实现与自建 SGLang 基线，同时保持算法本身的输出行为。

## 2. 创新点是什么？

**总括。** TokenRouter 不是新路由算法，而是服务系统设计。技术增量可概括为：把各种 token 级路由算法共享的执行生命周期（选下一个模型 → 转移请求状态 → 接收 token/分布，§2 末段）显式化为 route-send-receive（路由-发送-接收）编程接口，并在接口之下用三段解耦循环异步执行 + handoff-resume（交接-恢复）接管跨模型切换、用延迟批处理（delayed batching）+ DTMC（离散时间马尔可夫链）阈值模型接管批调度，另配四项 token 路由特有的工程适配。四个创新点中研究成分最强的是 DTMC 吞吐建模，其余多为已有执行模式的显式化与工程改造；论文未使用"首次提出"表述，其自我定位是"把算法层面的理论收益转化为对成熟单模型服务系统的实际加速"（§1 末段）。

**创新点 1：route-send-receive 接口与"请求中心编程、模型中心执行"（request-centric programming, model-centric execution）原则。** 新增的是三个由开发者实现的函数：route 在每个解码步后决定每个请求是本地继续还是委派给某个 peer（对端）模型，send 在委派时打包要转移的请求状态，receive 在对端把状态接回本地请求继续解码（§3.2；三函数语义在 §3 完整展开）。与最接近做法的差异：现有服务系统不暴露逐步（per-step）路由接口，speculative decoding（投机解码）的接口是固定草稿-验证模式；论文观察到各种 token 级路由算法实际共享同一执行生命周期（§2 末段），本接口即对该生命周期的显式抽象——属抽象与 API 设计，不是新的路由思想。它对应 §1 的"实现复杂度"挑战；证据一句带过：5 种路由信号互不相同的算法都在同一运行时上以 scheduler 子类实现（§4.1、Appendix C）。

**创新点 2：三段解耦循环异步执行 + handoff-resume。** 在标准单模型服务器的两个异步循环（client-server 与 decoding）之外新增第三个 inter-model（模型间）循环，使被委派的请求可以离开本地批、在对端处理期间本地照常推进；对端返回后经 handoff-resume 把请求状态原样接回本地批（§4.2；机制展开见 §3）。与最接近做法的差异：朴素做法把返回请求当全新请求、重做前缀匹配与 KV 缓存分配——作者自建的无状态保持基线正是如此（§4.2）。属工程机制设计（在已有系统结构上增加循环与状态机），不是新研究思想。它对应 §1 的步级失同步（step desynchronization）挑战；证据一句带过，指向 §4.3 的 Table 6 逐项消融。

**创新点 3：延迟批处理 + DTMC 吞吐模型求最优阈值 $B^*$。** 子服务器不再"有请求就发批"，而是缓冲到达请求、攒到阈值 $B_i$ 才发批，用少量等待换取更大更满的同模型批次；阈值不手调，而是把系统建成有限状态 DTMC、由稳态分布解析求出吞吐最优的阈值向量（§4.3、Appendix D；模型与公式见 §3）。与最接近做法的差异：一到就发批的模式造成大量批次准入延迟，固定或人工阈值无法随并发与路由概率自适应；DTMC 建模在排队论中不是新范式，针对 token 级路由到达过程与延迟批处理的这套具体建模是本文增量，是三个机制里研究成分最强的。它对应 §1 的批次准入延迟（batch admission delay）挑战；证据一句带过：R2R 上模型预测的最优阈值与实测一致（§4.3，Fig. 10）；论文自认几何分布假设的边角情形留待未来工作（§6）。

**创新点 4：四项 token 路由特有的工程适配（Appendix B）。** 共享 GPU 上多模型 KV 缓存的联合分配（避免人工预留导致的 OOM 或闲置）；extend 模式 CUDA graph 捕获（token 路由下 peer 返回全是 extend 批）；进程内路由（route 每步每请求都调用，跨进程会引入每 token 一次 IPC 往返）；全局状态跟踪（延迟批处理阈值依赖系统级活跃请求数，各子服务器经 peer 消息通道捎带控制消息同步计数，无需中心协调者）。四项均属工程实现改进，服务于同一效率目标；证据一句带过，指向 §4.3 的 Fig. 1a 增益分解与 Table 6——单项最大工程增益来自 extend CUDA graph。

## 3. 作者如何解决？

**直觉。** TokenRouter 把一件事拆成两半："路由算法是什么"由开发者用三个函数描述，"如何高效地把它跑起来"由运行时（runtime）接管。运行时把每个参与协作的 LLM 变成一个自治的子服务器（subserver）：请求像内部消息一样在子服务器之间投递，每个子服务器只管一件事——尽快把自己模型上的批次跑满，跑满后按路由规则把请求寄出去；谁的模型慢，就只是谁自己慢，不需要全局同步。这样算法作者不需要理解批调度与异步执行，系统则获得对跨模型执行与批调度的完全控制权（§1）。核心思路之所以可能解决问题，是因为 §1 观察到的两类病态都源于单模型同步假设——"同一批请求每步同步推进"造成失同步，"离开再返回的请求被当新请求"造成重复记账；把执行拆成按模型自治的子服务器、把请求状态保留在子服务器内部之后，这两个假设都不再必要（§4.1–§4.3）。

**输入与外部接口（执行者：Server Interface，固定流程）。** 客户端通过一个与标准单模型服务器（vLLM/SGLang）完全一致的外部接口发送请求（OpenAI 风格协议），接口把请求转发给指定的入口子服务器（entry subserver），此后整段路由生命周期都不需要客户端介入；因此对客户端而言，背后有几个 LLM 参与路由是透明的（§4.1）。这是论文"可作为标准单模型服务器的替代品（drop-in replacement）"说法的落点。

**子服务器内部结构与三段解耦循环（执行者：运行时，固定策略）。** 每个子服务器持有一个调度器（scheduler）、一个带私有 KV 缓存池的 LLM runner，以及由用户三个函数构成的 router/sender/receiver 三件套；内部布局对每个模型完全一致，增加一个 LLM 只需再起一个子服务器（§4.1）。标准单模型服务器内部有两个异步循环——client-server 循环（请求准入与响应流式返回）与 decoding 循环（请求调度与模型执行）；TokenRouter 在其上增加第三个 inter-model 循环，负责在子服务器之间收发 peer（对端）请求（§4.2）。三段循环的分离就是图 1 的主体，也是"请求可以离开本地批、在对端处理时本地不空转"的结构性前提。

![图 1：TokenRouter 系统总览：路由粒度与三段循环](/images/dailypaper/2026-10-09/2610.12242_fig1.png)

**图 1**（论文 Fig. 2）：(a) 三种路由粒度——session 级做 1 次决策就不换、query 级每条 query 1 次决策、token 级每个 token 都可能换，粒度越细，"每个解码步都可能切换模型"的执行要求越高，这是理解"为什么单模型同步系统不适用"的前提。(b) 系统架构——客户端只看到 Server Interface（等价于单模型服务器）；其下若干 Subserver，每个由 Scheduler、LLM Runner（含私有 KV 缓存池）与用户实现的三个路由函数组成；图中三种颜色的箭头对应三段解耦循环：紫色是 client-server 循环（请求进出与流式返回）、蓝色是 decoding 循环（调度与执行）、黑色是 inter-model 循环（peer 消息收发）。**为什么需要它**：没有第三段循环，跨模型交接只能靠同步等待（退回 Step-Sync）；三段解耦是后续所有机制（pending 状态、延迟批处理）的结构基座。

**请求的流转：三个函数描述路由语义（§2 创新点 1 的展开；执行者：用户代码，逐请求、逐解码步）。** 所有 token 级路由算法共享同一生命周期：请求在某个模型上解码 → 算法决定去留 → 若委派则转移状态 → 对端接收后继续解码，循环往复直至结束：receive → decode → route → send → peer receive → peer decode → peer route → …（§3.1）。TokenRouter 只要求开发者填三个函数（§3.2）：

- **route(result)**：每个解码步之后调用，输入是该步的前向结果（hidden states（隐状态）、下一 token 的 logits（未归一化得分）、采样出的 token 等），为批内每个请求输出一个目标索引——0 表示本地继续解码，非零指向对应的 peer 模型。它决定"何时切、切给谁"。
- **send(req)**：当 route 决定委派时调用，构造一个 PeerReq（peer 请求消息），携带请求 ID、peer 尚未见过的 token 后缀、请求是否已结束的状态字段、算法自定义字段，以及位置锚点 req.loc（接收方据此决定最少要回传哪个后缀；刚采样的 token 是否算进后缀由算法决定——例如 R-Stitch 故意丢掉刚生成的不确定 token，让大模型从该位置重生成）。它决定"转移什么状态"。
- **receive(peer_req)**：PeerReq 到达时调用，把它转换成接收方的本地请求格式以继续解码；默认行为是接受全部转移 token（对多数算法足够），只有交接语义特殊的算法才需要覆写（例如恢复解码前附加额外状态）。它决定"如何接受回传"。

论文用 R-Stitch 的小模型侧示例展示三者配合（论文 Fig. 3）：route 把归一化熵超过阈值的高熵 token 交给 LLM，send 丢弃刚解码的不确定 token、只传输 peer 未见过的后缀，receive 走默认全接受；大模型侧结构相同，只是把 route 的条件换成低熵才发回 SLM。五种被测算法的路由信号各不相同（CITER 用置信度、R2R 用预测分歧、R-Stitch 用熵、Co-LLM 用延迟得分、ME 用集成权重，Table 1），但都只用到这三个函数（Appendix C）。

**跨模型交接：三段循环与 handoff-resume（§2 创新点 2 的展开；执行者：调度器 + 固定状态机）。** 被委派的请求离开本地批后，本地其余请求按自己的节奏继续执行；对端返回后，调度器把请求恢复回本地批。恢复的关键是引入一个中间状态 pending（介于 running 与 finished 之间）：交接时把请求标记为 pending，调度器跳过它、但保留其全部服务状态（包括 KV 缓存）；对端输出返回后按结果把 pending 切回 running 或 finished，未结束则直接把新 token 追加进请求并重新入批，**跳过前缀匹配与 KV 重分配**——交接开销因此近似于一次 token 追加（§4.2）。为什么这样设计：朴素做法把返回请求当作全新请求，每次切换都要重做前缀匹配与 KV 缓存分配；作者自建的无状态保持基线（每个 LLM 一个 SGLang server、每次只返回一个 token、由外部 dispatcher 转发）正是这种反例，Table 10 对它逐项量化了该开销（详见 §4.3）。论文在 Table 6 给出依据：移除异步执行后吞吐显著下降（详见 §4.3）。

**批调度：延迟批处理（§2 创新点 3 的展开之一；执行者：调度器，固定策略）。** 解耦异步执行后，子服务器面对的是稀疏且不规则的到达流，"一到就发批"会让后到的请求等当前批跑完才能入批——这就是批次准入延迟（batch admission delay，请求到达子服务器到开始执行的等待）。延迟批处理的做法是：调度器缓冲到达的请求，只有当缓冲数攒到阈值 $B_i$ 才启动新批（图 2 给出 LLM 子服务器 $B{=}2$、SLM 子服务器 $B{=}1$ 的例子）。为什么这样设计：论文给出的 Eager-Async 反例是 request 3 的 token 3 必须等 request 2 的 token 2 解码完才能开始，准入延迟从时刻 2 拉到 4.5；延迟批处理让先到的请求多等一点、后到的请求几乎不用等，从而降低平均准入延迟，批也更满（§4.3）。

![图 2：四种调度策略示意对照](/images/dailypaper/2026-10-09/2610.12242_fig2.png)

**图 2**（论文 Fig. 4）：四条时间线（横轴为 SLM 批单位的逻辑时间）对照四种调度策略：(a) Step-Sync 在每一步设屏障（barrier，虚线），三条请求必须等最慢的 LLM 批结束才能进入下一步，平均延迟 13.33；(b) Model-Sync 一次只激活一个模型，非活动模型的请求停摆，13.00；(c) Eager-Async 只要 peer 请求到达就处理，但正在跑批时新请求只能等——图中 request 3 的 token 3 因为要等 request 2 的 token 2 解码完，准入延迟从时刻 2 拉到 4.5，平均 10.83；(d) TokenRouter 保留异步（优于 a/b）但延迟发批（LLM $B{=}2$、SLM $B{=}1$，即攒够 2 个 LLM 请求才发批），先到的请求多等一点、后到的请求几乎不用等，平均降到 8.67。**为什么需要它**：这张图把两类病态的机理讲清楚——失同步是 (a)(b) 的病，准入延迟是 (c) 的病，(d) 是二者的折衷；浅蓝/灰/虚线分别代表 SLM 批、LLM 批与屏障。需要强调：这是**示意性对照**（数值以 SLM 批为单位），不是硬件实测。

**最优阈值：DTMC 吞吐模型（§2 创新点 3 的展开之二；执行者：离线求解，运行时取用）。** 阈值 $B_i$ 存在严格权衡：太小则准入延迟大，太大则请求滞留队列、另一个模型反而闲置（§4.3），因此论文不手调，而是解析求解。模型把系统建成有限状态的离散时间马尔可夫链（DTMC）：状态 $\mathbf{s}=(k_0,b_0,r_0,\dots,k_{M-1},b_{M-1},r_{M-1})$ 记录每个模型的等待请求数 $k_i$、在跑批大小 $b_i$ 与剩余执行时间 $r_i$（Eq. 4–5）；引入时间量子 $\delta$ 使状态有限（Eq. 6–7）；以"批完成事件"为状态转移时刻，下一状态的分布只依赖当前状态（Markov 性），转移概率由路由概率矩阵 $\mathbf{P}=[p_{ij}]$ 与各模型单步延迟 $L_i$ 决定（Eq. 11–15）。模型假设路由概率平稳、请求间独立、同一模型连续停留的步数服从参数 $1-p_{ii}$ 的几何分布（Appendix D.1）。由稳态分布 $\boldsymbol{\pi}_{\mathbf{B}}$（Eq. 16），稳态提交 token 吞吐写作"平均每次状态转移提交的 token 数 ÷ 平均转移时间"（Eq. 21）：

$$T(\mathbf{B}) = \frac{\sum_{\mathbf{s}\in\mathcal{R}_{\mathbf{B}}}\sum_{i\in\mathcal{A}(\mathbf{s})}\sum_{j=0}^{M-1}\pi_{\mathbf{B}}(\mathbf{s})\,b_i c_{ij} p_{ij}}{\sum_{\mathbf{s}\in\mathcal{R}_{\mathbf{B}}}\pi_{\mathbf{B}}(\mathbf{s})\,\tau(\mathbf{s})},$$

其中 $\mathcal{R}_{\mathbf{B}}$ 是阈值取 $\mathbf{B}$ 时的可达状态集（用 BFS（广度优先搜索）枚举，Appendix D.2.1），$c_{ij}$ 是请求从模型 $i$ 路由到 $j$ 时提交的 token 数，$\mathcal{A}(\mathbf{s})$ 是在下一次转移中完成的批的集合，$\tau(\mathbf{s})$ 是状态的保持时间。为避免"所有模型都攒不满一批"的死锁，模型施加可行性约束 $\sum_{i=0}^{M-1}(B_i-1) < N$（Eq. 22），在该可行集内解 $\mathbf{B}^{\star}=\arg\max_{\mathbf{B}} T(\mathbf{B})$（Eq. 24）。以 R2R 的实例化为例：$\mathbf{P}=\begin{bmatrix}1-p & p\\ 1 & 0\end{bmatrix}$（SLM 每条自己生成的 token 以概率 $p$ 转给 LLM，LLM 每生成一个 token 必回 SLM）、提交矩阵 $\mathbf{C}=\begin{bmatrix}1 & 0\\ 1 & 0\end{bmatrix}$，实验中 $p=0.35$、$L_0{=}6.0\,$ms、$L_1{=}27.9\,$ms、$\delta{=}0.1\,$ms（Appendix D.4，Eq. 25 附近）。模型预测的最优阈值与硬件实测是否一致，由 §4.3 的 Fig. 10 回答。

**四项工程适配（§2 创新点 4 的展开；执行者：运行时，启动期配置与固定策略）。** Appendix B 逐项给出 token 路由打破的单模型假设与对应修补：

1. **KV 缓存内存自动分配**：单模型服务器假设一个模型独占 GPU 上的整块 KV 预算，而 token 路由让多个模型共置同一 GPU 争用预算——预留过多会在满并发时 OOM（显存不足），过少则容量闲置。运行时按各模型的权重占用与每 token KV 单元大小，在可配置的共享预算下计算可容纳的最大公共 KV token 容量，并在启动前分配（Appendix B）。
2. **extend 模式 CUDA graph**：单模型服务器只给 decode 批抓 CUDA graph（每步形状稳定），而 token 路由下 peer 返回全部是 extend 批（把对端新产生的 token 拼接进已有序列继续处理的批次），交接路径由 extend 主导。TokenRouter 对一定范围的 extend 批大小与 token 长度抓图，超出范围回退到普通路径——常见情况落在抓图范围内，交接路径上的 kernel 启动开销被消除，长 extend 仍能正确服务（Appendix B）。
3. **进程内路由**：route 在每个请求的每次前向之后都要调用，比 query 级路由高频几个数量级；跨进程运行会引入每 token 一次 IPC（进程间通信）往返，并让路由与下一步解码串行。因此 router 与调度器、LLM runner 同进程同 GPU，每次路由决策只是进程内的张量运算（Appendix B）。
4. **全局状态跟踪**：延迟批处理阈值依赖系统级活跃请求数，所有子服务器必须对该计数保持一致，否则 $B^*$ 会按过期的并发值选取、偏离最优。论文不加中心协调者，而是把"新准入/新完成请求"作为控制消息叠加在 peer 消息通道上捎带传输（Appendix B）。

**哪些由路由算法决定、哪些由运行时固定控制。** 路由语义（何时切、切给谁、传什么后缀、如何接受回传）完全由用户实现的 route/send/receive 决定——其中可能包含算法自己的学习组件（如 CITER 训练出的 router）；批调度、异步执行、KV 内存分配、CUDA graph 捕获、全局计数等全部由运行时按固定策略控制。这正是"请求中心编程、模型中心执行"的分工（§3.1）。

**是否需要训练。** 系统本身无需训练，方法部分（§3–§4、Appendix B/D）全部是接口设计、工程机制与解析模型，没有引入新的可训练参数。评测中的部分路由算法带有各自的训练成分：CITER 需训练其 router，Co-LLM 需微调 Qwen3-0.6B；各自的阈值/权重为 CITER $\tau{=}0.98$、R-Stitch $\tau{=}0.03$、Co-LLM $\eta{=}0.15$、ME 集成权重 0.5/0.3/0.2（§5.1）。这些属于**直接使用的现有算法**，不是本文贡献。

**推理阶段发生了什么变化（相对单模型服务器）。** 三点：(a) 三段循环解耦——请求在对端处理时本地照常推进（§4.2）；(b) handoff-resume——离开的请求标记 pending，返回时直接追加 token 回批，跳过一次前缀匹配与 KV 重分配（§4.2）；(c) 延迟批处理——每批攒到 $B_i$ 才启动，$B_i$ 取模型推出的吞吐最优 $B^*$（§4.3、Appendix D）。此外外部接口不变，仍是单端点（§4.1）。

**最终输出。** 与单模型服务器相同的 token 流；对客户端而言，背后有几个 LLM 参与路由是透明的（§4.1）。

## 4. 解决得怎么样？

#### 4.1 实验设置

**路由算法与模型对。** 评测五种 token 级路由算法：CITER、R2R、R-Stitch、Co-LLM、ME（Table 1）。前四种在 Qwen3-0.6B 与 Qwen3-32B 之间路由，ME 在 Qwen3-0.6B、Qwen3-8B、Qwen3-32B 之间路由（§5.1）。另外每种算法还用**各自原始论文的模型对与数据集**复测（Table 4）：R2R 用 DeepSeek-R1-Distill-Qwen-1.5B/32B + AIME、CITER 用 Qwen2-1.5B/72B + CommonsenseQA、Co-LLM 用 LLaMA2-7B(tuned)/70B + GSM8K、R-Stitch 用 L1-1.5B-Short/QwQ-32B + AIME。

**硬件与部署。** 全部实验在一台 8×A100-80G 上运行。两模型算法：小模型占 1 GPU，大模型占 2 GPU（张量并行 tensor parallelism，TP=2），两个模型通过 CUDA MPS 共享 2 块 GPU（"重叠部署"）；ME 每个模型占 1 GPU（§5.1）。附录另测非重叠部署（小/大模型占不同 GPU，Appendix A.3.1）与跨节点部署（两节点经 RoCE 3.7 GB/s 互联，Appendix A.3.2）。

**基线。** 两个：(1) **Official Code**——算法官方开源实现（R-Stitch 未开源，记为 N/A；Co-LLM 官方用 per-model vLLM 服务器带连续批处理，CITER 与 R2R 官方是无连续批处理的推理引擎）；(2) **Std. Serving**——作者自建的标准 SGLang 基线：每个 LLM 一个 SGLang server、每次只返回一个 token、由外部 dispatcher 在服务器之间转发，代表"成熟单模型系统 + 外部路由胶水"的朴素做法（§5.1）。Table 2/5 中还列出 LLM-only 参照行（只部署大模型、不路由）。

**负载。** 三种：(1) Low-effort reasoning（短输入短输出）：AIME2024 提示（约 100 token），最大输出 2048；(2) High-effort reasoning（短输入长输出）：AIME2024，最大输出 8192，只保留 Qwen3-32B 解答超过 8192 token 的题；(3) Agentic（多轮）：SWE-Smith 轨迹，输入约 8192 token，最大输出 1024（§5.1）。

**指标与协议。** 吞吐 = 生成输出 token 总数 / 总耗时；同时报端到端请求完成延迟与 TTFT（首 token 时间，time-to-first-token）。注意协议差异：对推理引擎（Official Code）是打包一批 $N$ 个请求一起处理；对服务系统（Std. Serving、TokenRouter）是启动 $N$ 个 worker、每个 worker 完成上一个请求立刻发下一个（闭环）。主要并发点为 4（Fig. 5/6）与 8（Fig. 1a）；附录补并发 1（Fig. 8/9、Table 5）。

**各实验分工。** 主实验（§5.2）回答"比现有系统快多少"；§5.3 与 Appendix A.2 的消融回答"增益来自哪个组件"；Appendix A.3 回答"部署方式（重叠/非重叠、单节点/跨节点）影响多大"；Appendix A.4 回答"与自建基线的差距从何而来"（延迟分解）；§5.4 回答"对成本-质量帕累托前沿的推进"；Appendix D.4 回答"DTMC 模型能否预测最优阈值"。

**并行策略（Table 7）。** 给 LLM 加张量并行远比给 SLM 加有效：两 GPU 设置下 LLM 的 TP 从 1 提到 2，N=1 时吞吐 +40.6%、N=4 时 +22.8%；此后 SLM 的 TP 从 1 提到 2 只再带来 0.8%/0.4%。因此全文默认 LLM TP=2、SLM TP=1（§5.3）。

**部署变体（Appendix A.3）。** 非重叠部署（LLM 独占资源）平均再提升 6.43%；跨节点部署吞吐与同资源单节点相当（略有下降），相对各自官方实现仍高 1.93–32.81×（N=1/4，Table 8/9）。

**帕累托前沿推进（§5.4，Fig. 7）。** 在 AMC23 上、Qwen3-0.6B/32B 模型对、贪心解码、最大输出 8192、所有请求并发发出（SLM/LLM 显存份额在各系统间对齐）的设定下，TokenRouter 的吞吐-准确率曲线整体位于官方 R2R 曲线右上方（图 5）；图中还并列了 RouteLLM 的 query 级路由变体（QR-MF、QR-BERT、QR-LLM、QR-SW）与 SLM/LLM 两个端点（星标）。论文据此主张：token 级路由在新一代框架（如 SGLang）上比 query 级路由更具竞争力（§5.4）。**审稿人视角的保留**：该结论来自单一数据集（AMC23）与单一模型对，且曲线为点值、无方差，见 §5 质疑四。

**图 5**（论文 Fig. 7）：横轴为吞吐（tokens/s）、纵轴为准确率。蓝色菱形为 TokenRouter、紫色圆点为官方 R2R 实现，两者都是随"每 token 走大模型的比例"变化得到的曲线（从左上高准确率低吞吐，向右下低准确率高吞吐移动）；红色三角是 RouteLLM 的 query 级路由各变体（QR-*），黑星是只用 SLM 或只用 LLM 的两个端点。"推进帕累托前沿"的含义就在这张图上：在相同的准确率水平（纵坐标）下，TokenRouter 曲线位于所有其他曲线（含官方 R2R 与 query 级路由）右侧。**为什么需要它**：前面几张图比较的是"同一算法的不同服务实现"，这张图回答的是更上层的叙事问题——高效服务让 token 级路由在整条成本-质量权衡曲线上追平/超越 query 级路由。

#### 4.3 机制证据

**结论先行。** 本文的证据链分成两层：效果层（Fig. 5/6、Table 2/3——"更快"）与机制层（Table 6/Fig. 1a 的组件消融、Table 10 的延迟分解、Fig. 10 的模型验证——"为什么快"）。机制层证据在同类系统论文中属于比较扎实的一档，但仍有明确边界（等价性未验证，见质疑三；模型验证范围窄，见质疑二）。

**组件消融（Table 6、Fig. 1a）。** 每个组件移除后吞吐按预期方向下降：N=8 时完整系统 372.48 → 去延迟批处理 296.86 → 去异步执行 230.79 → 去扩展 CUDA graph 约 132.78，且 base 132.78 与官方 R2R 134.89 基本持平——这个"base≈官方"的控制很有价值，它使 2.76× 的整体增益可以归因到四个具体改动，而不是"换了起点"。局限：消融是逐层累加式的，组件间交互（例如 CUDA graph 与异步执行的叠加效应）未被单独分析；N=1 时异步与延迟批处理增益为零（73.02 不变），这与机制解释一致（无批可攒、无跨模型并发），但也说明两项机制的收益完全依赖并发负载。

**延迟分解（Table 10，Appendix A.4）。** 对自建 Std. Serving 基线剖析 2048-token 生成最后 128 步的 SLM 侧单步耗时：前缀匹配 7.78 ms、锁缓存节点 6.49 ms、SLM 推理 1.56 ms、释放锁 5.13 ms、更新 RadixCache 12.12 ms、其他 4.08 ms。与"没有状态保持 → 每次返回被当作新请求 → 重做前缀匹配与 KV 记账"的解释吻合，是"handoff-resume 为什么必要"的直接证据。局限：只剖析了一个算法场景（R2R）与自建基线，未对官方实现做同样分解。

**DTMC 模型验证（Fig. 10，Appendix D.4）。** 在 R2R（$p{=}0.35$、$L_0{=}6.0\,$ms、$L_1{=}27.9\,$ms）上，模型预测吞吐与实测吞吐在 N=2/3/4 上给出相同的阈值排序与最优位置：N=2 两者最优都在 $B{=}2$（预测 110.3 vs 实测 122.3），N=3 都在 $B{=}2$（158.1 vs 169.0），N=4 都在 $B{=}3$（207.9 vs 197.4）（图 6）；图中 n/a 格恰好是违反可行性约束 $\sum_i(B_i-1)<N$ 的配置（分析者按 Eq. 22 核对一致）。两点保留：绝对数值存在最高约 ±11% 的系统性偏差（模型不是精确校准的，只保证"选哪个 B 最优"这一用途）；验证只覆盖两模型、单算法、并发 ≤4 的情形。

![图 6：DTMC 吞吐模型与实际测量对照（R2R）](/images/dailypaper/2026-10-09/2610.12242_fig6.png)

**图 6**（论文 Fig. 10）：左"Theoretical"为模型预测、右"Practical"为硬件实测，行是并发 $N\in\{2,3,4\}$，列是 LLM 子服务器的阈值（图注写 $B_1$、坐标轴写 $B_2$，指同一对象）；格内为吞吐（token/s），星号标出每行跨阈值的最优，n/a 为不可行配置。**为什么需要它**：它是"数学建模"这一创新点的唯一实证——浅色→深色按吞吐着色，左右两图同行为同一 $N$，可以看出深浅分布与星号位置一致，而绝对色深略有出入（对应上面提到的 ±11% 偏差）。

**替代解释的排除程度。** 增益来源已被分解为四块且各有单独证据，基本排除了"靠更大的基础模型/更多的算力预算"（base≈官方、同硬件、同算法配置）；但尚不能排除：(a) 与官方实现对比时，CUDA graph 优化本身可能利用了官方 R2R 引擎未做 kernel 融合的事实，而非 TokenRouter 的架构设计；(b) 不同 `B` 选择对最终数字的敏感性（除 Fig. 10 的低并发验证外无扫描数据）；(c) 输出序列本身是否与不路由/官方实现完全一致。

**对 §2 创新点逐一核对**：接口抽象（创新点 1）无法直接消融，只有 5 种算法的覆盖广度作替代证据（Appendix C）；异步执行与延迟批处理（创新点 2、3 的调度侧）有 Table 6 的移除对照；DTMC 阈值模型（创新点 3 的建模侧）有 Fig. 10 的预测-实测最优阈值一致作证；四项工程适配（创新点 4）各有 Fig. 1a 与 Table 6 的分解与消融——但每项证据都带有上文与 §5 所述的边界（输出等价性未验证、模型外推范围窄、$B^*$ 未披露）。

#### 4.4 成本与适用范围

**成本侧（论文报告）。** 系统本身无训练成本；推理阶段：吞吐增益 2.01–64.15×、端到端延迟降低 2.03–63.64×，TTFT 与官方实现持平或略好（Table 2/5）；单用户速度在并发 16 时仍保有并发 1 时的 51.7%（官方 R2R 为 31.3%，Fig. 1b）。额外开销与复杂度：多子服务器进程 + ZeroMQ IPC 通道 + 共享 GPU 的 KV 联合分配 + extend 范围 CUDA graph 捕获（Appendix B/C）；跨节点部署吞吐比同资源单节点略降（Table 9，N=4 时 CITER 308.36→277.56，约 −10%）；非重叠部署反而平均 +6.43%（Appendix A.3.1）。

**论文未报告的成本项。** DTMC 求解 $B^*$ 的耗时与内存（仅说明用 BFS 枚举可达状态，Appendix D.2.1，未给复杂度）；主实验各场景实际采用的 $B^*$ 数值；GPU 时耗/能耗对比；失败率。

**适用范围。** 结论适用于：(a) 遵循"选下一个模型 → 转移请求状态 → 接收 token/分布"生命周期的 token 级路由算法（论文的抽象本身以该生命周期为界，§2）；(b) 至多 3 个合作模型（ME 是验证到的上限）；(c) 单机 8×A100-80G，并发 1–16（跨节点变体亦验证）；(d) 模型规模覆盖 0.6B–32B（标准设置）与 1.5B–72B（各算法原始设置）。**仍未解决/未验证**：违反几何分布假设的路由模式（§6 自认的开放问题）；>3 模型与更高并发下的调度与模型有效性；服务输出与官方实现的逐 token 等价性；生产环境（多租户、真实到达过程、尾部延迟）表现。

## 5. 最容易受到审稿人质疑的地方

#### 质疑：摘要头条"2.01–64.15×"的口径依赖比较对象的选取，存在选择性呈现的风险

- **原文依据**：Abstract 与 §5.2 报"relative to existing systems/stronger baseline 2.01–64.15×"；§5.1 承认基线异质——CITER、R2R 官方是"无连续批处理的推理引擎"，Co-LLM 官方用 per-model vLLM，R-Stitch 无官方代码，Std. Serving 是作者自建、且被 Table 10 证明有 ~85% 的记账开销。按 Fig. 5 柱值反推（分析者推断）：64.15× 的上限来自 CITER high-effort（288.7 vs Std. Serving 4.5 token/s），而对论文最引以为豪的效率型算法 R2R，全部三个负载的增益只有约 2.0–2.6×（如 agentic：151.2 vs 官方 75.1）。
- **为什么重要**：它决定读者对"真实收益"的认知。最大数字来自官方实现本就极弱（个位数 token/s）的算法，如果读者把 64.15× 当作"相对成熟系统的加速"，会显著高估；而对最接近生产形态的比较（自建 SGLang 基线），论文自己提供的分解说明大头来自常规工程优化（CUDA graph 1.71×）。
- **当前能够得出的判断**：数据本身透明（Fig. 5、Table 2/6 都能复核），问题在呈现层的取舍——摘要与结论只给全局最大区间，不区分基线强度；"vs 官方研究代码"与"vs 具备连续批处理的自建系统"两类口径被合并。属于"结论被（呈现方式）夸大"，而非数字造假。
- **如何验证或补强**：按基线分层报告（vs 官方实现 / vs Std. Serving / vs base 实现各自 min–max 与出处组合）；公布区间两端点的具体算法-负载归属；对 R2R 单独强调 2.0–2.6× 这一更保守的数字。
- **严重程度**：主要问题。

#### 质疑：DTMC 吞吐模型的假设强、验证范围窄，且主实验使用的阈值 $B^*$ 从未披露

- **原文依据**：模型依赖"路由概率平稳、请求间独立、同一模型连续停留步数服从几何分布（参数 $1-p_{ii}$）"（Appendix D.1）；§6 自认几何假设的边角情形留给未来；Appendix D.4 的验证只有 R2R 一种算法（$M{=}2$、$p{=}0.35$、$N\le 4$）；Fig. 10 显示绝对吞吐的预测-实测偏差最大约 ±11%；§5 全部主实验、Table 6 消融、Fig. 1 分解均未列出任何场景实际使用的 $B^*$ 数值。
- **为什么重要**：这是论文三大贡献之一的实证基础。如果主实验并非逐场景使用模型推导的 $B^*$（论文没有说明），那么"optimal hyperparameters derived from a mathematical throughput model"只是理论主张；反之，如果确实使用了，读者又无法复核这些值以及模型在 ME（每 token 都可能换模型，几何假设最可疑）、长输出、高并发下是否仍给出最优。
- **当前能够得出的判断**：可确认"模型能预测 R2R 在 $N\le4$、$M{=}2$ 时的最优阈值"；不能确认其外推到 ME、跨模型对与更高并发仍成立。主实验的 $B^*$ 取值属于"论文未报告"，无法核对。
- **如何验证或补强**：披露各场景 $B^*$ 与选取流程；对 ME（3 模型）与 R-Stitch（对称切换）重复 Fig. 10 式验证；给出阈值敏感性扫描（固定 vs 最优 $B$ 的吞吐差）；报告 DTMC 求解开销随 $N$、$M$ 的增长。
- **严重程度**：主要问题。

#### 质疑：异步执行与延迟批处理改变了解码时序，但"服务结果与算法原语义一致"未被直接验证

- **原文依据**：§4.2 的异步三段循环与 §4.3 的延迟批处理都改变请求在何时、与谁一起被解码；论文只论证吞吐/延迟，没有给出任何"TokenRouter 与官方实现产生相同 token 序列/路由决策序列"的对照实验；§5.4 的 Fig. 7 仅以准确率-吞吐曲线形式呈现质量。
- **为什么重要**：服务系统的基本契约是"承载算法而不改变其行为"。批组成与执行时序变化会改变浮点归约顺序与 kernel 选择，在非贪心解码下可能改变采样结果，进而改变后续路由轨迹——哪怕概率极小，也需要证据而不是默认。若输出不一致，§5.4"推进帕累托前沿"的准确率数字与官方 R2R 的对比就失去同基准前提。
- **当前能够得出的判断**：当前材料无法确认逐 token 等价性；Fig. 7 显示 TokenRouter 曲线与官方 R2R 曲线位于同一准确率区间（约 0.5–0.77），这构成弱证据但非直接验证。
- **如何验证或补强**：固定请求与随机种子，逐一对比各系统输出的 token 序列与每步路由决策；给出不同 $B$ 与不同并发下准确率的差异（把调度不变量当作实验假设检验）。
- **严重程度**：主要问题。

#### 质疑：评测规模与硬件覆盖有限，"drop-in replacement / 生产收益"的表述缺少对应证据

- **原文依据**：全部实验在单台 8×A100-80G 上（跨节点仅附录小规模，Appendix A.3.2）；并发上限 16（Fig. 1b）；合作模型数上限 3（ME）；帕累托结论仅基于 AMC23 单数据集（§5.4）；所有结果为单次运行点值，无方差、置信区间或显著性检验（Table 2/3/5–10 均无）。
- **为什么重要**：摘要的"drop-in replacement for standard single-LLM servers"是关于部署与兼容性的强主张，但：没有真实生产轨迹、没有多租户/多副本、没有 H100 等其他硬件、没有并发 32+ 的数据（延迟批处理在极高并发下收益可能反转，因为准入延迟的绝对值会上升）；缺少方差也意味着无法判断小差距（如 1.99×、2.01× 这类端点）是否稳定。
- **当前能够得出的判断**：在论文覆盖的条件下（A100 单机、并发 ≤16、≤3 模型、数学推理与 agentic 轨迹）证据方向一致；超出该范围的结论属于外推，当前材料不足以支持。
- **如何验证或补强**：并发 32/64/128 的扫描；真实到达过程回放；H100 等不同硬件的重复；≥4 模型的调度验证；报告 p50/p99 与多轮运行的方差。
- **严重程度**：次要问题。

#### 质疑：核心动机图（Fig. 4）的量化对比是示意性模拟，机制归因的实测证据只覆盖"自建基线"一种做法

- **原文依据**：Fig. 4 四种策略对照以"SLM batch units"为时间单位（平均延迟 13.33/13.00/10.83/8.67），是简化模型下的示意，不是硬件测量；正文的真实剖析只有 Table 10（自建 Std. Serving、R2R 场景、2048-token 生成的最后 128 步、SLM 侧）。
- **为什么重要**：它影响"问题有多严重、解法有多少收益"的量化可信度。若读者把 13.33→8.67 当实测，会高估两类病态的实际代价；同时，"每次切换当新请求"的 ~85% 记账开销只在一个算法、一个基线实现上得到验证，官方实现（如 R2R 的高效切换路径）为什么不需要类似机制、以及强制同步模式在真实系统中的代价，论文没有测量。
- **当前能够得出的判断**：论文未把 Fig. 4 数值作为实测证据引用（这一点处理尚可），但缺少"同步/半同步策略真实开销"的对照实验；机制归因的实测面偏窄。
- **如何验证或补强**：在真实硬件上实现 Step-Sync / Model-Sync / Eager-Async 三种执行模式并与 TokenRouter 对比吞吐与延迟；把 Table 10 式的分解扩展到 CITER、Co-LLM 官方实现。
- **严重程度**：次要问题。

## 6. 审稿式总评

> 作者发现 token 级路由算法的收益在现有单模型同步服务系统上被两类系统级病态（步级失同步、批次准入延迟）与"无状态切换"的记账开销吞掉，因此提出 TokenRouter：用 route-send-receive 接口把算法描述与执行优化解耦，用三段循环异步执行 + handoff-resume 保持请求状态，用延迟批处理聚批并以 DTMC 模型推出最优阈值。实验在 5 种算法、3 种负载、4 组模型对（0.6B–72B）与各算法原始设置下表明，吞吐最高提升 64.15×、且 base≈官方的控制显示增益来自四个可分解的具体改动；其中组件消融（Table 6）、延迟分解（Table 10）与阈值模型验证（Fig. 10）证据较强，但头条数字的口径选择性、DTMC 假设的窄验证与主实验 $B^*$ 未披露、服务输出等价性未验证仍缺少充分支持。本文最有价值的部分是"请求中心编程、模型中心执行"这一接口抽象与 Tri-loop + handoff-resume + delayed-batching 的完整工程闭环，把一个新兴算法方向的系统支撑补齐了一大块；最大的审稿风险是把"对未优化研究代码的加速"与"对成熟系统的加速"混在一个区间里呈现，以及对模型外推范围的低调处理。

- **问题定义清晰度**：强——三类挑战（失同步、准入延迟、实现复杂度）在 §1 界定明确，且每类都有对应的失败场景描述（Fig. 4）与部分实测（Table 10）。
- **创新性证据**：中——接口抽象与异步机制多为已有执行模式的显式化/工程组合，论文自己以"complementary"而非"首次"定位；DTMC 建模是实打实的增量但已有应用范式；组件消融充分，然"接口不可替代性"类证据天然缺失。
- **方法可信度**：强——机制与证据链自洽（base≈官方的控制、逐项消融、延迟分解、模型-实测最优阈值一致），假设均显式声明并标注边界（§6 限制、Appendix D.1 假设）；输出等价性未验证属于其外沿边界（质疑三）。
- **实验支持力度**：中——覆盖面广（算法×负载×模型对×原始设置×部署变体），方向性结论一致；但全部为单机、单次运行点值，无方差/置信区间，区间端点又依赖比较对象选择（质疑一、四），因此不宜按"无保留的强"理解。
- **可复现性**：强——官方代码已发布（GitHub thu-nics/TokenRouter，仓库标注 NeurIPS'26 官方实现，本次已核验可访问），系统构建于 SGLang 0.5.1，实现细节（ZeroMQ IPC、内存联合分配、CUDA graph 范围）与全部模型公式在 Appendix B–D 给出；扣分项是主实验 $B^*$ 未披露与对 A100/CUDA graph 的硬件依赖，精确复现仍需与作者对齐配置。
- **综合阅读价值**：高——对一个正在升温的方向（token 级路由/多模型协同解码）给出了第一个较完整的服务系统设计与系统-算法联合测量，抽象（route-send-receive）可复用，测量方法（base≈官方的消融设计、DTMC 验证）也可借鉴；对做推理服务、模型路由与多模型协同的读者都值得精读，但引用其加速倍数时应按基线分层折算。
