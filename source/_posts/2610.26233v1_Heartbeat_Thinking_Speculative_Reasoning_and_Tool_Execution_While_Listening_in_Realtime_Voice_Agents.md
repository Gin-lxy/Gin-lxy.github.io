## 0. 一句话结论

论文要解决实时语音智能体在用户说完之前无法可靠完成推理与工具调用的问题；它提出 Heartbeat Thinking，用固定间隔、可重叠的 Thinker 调用让旧调用和已派发工具跨过语音更新继续完成，并在 VAD 端点把已完成准备快照交给独立的 Responder。三个基准上投机工具覆盖率均高于 SHANKS 式窗口基线，FDBench v3 上最终响应延迟从 6.90 s 降到 4.39 s（−36.4%）；但默认配置下 SpeechFCEval 准确率与 AudioCRAG 正确率反而略降，质量收益是基准与模型配置依赖的，尚不能支持“更快且普遍更强”。

## 1. 论文具体想解决什么问题？

实时语音智能体（realtime voice agent）要在用户说完后尽快回答，而答案往往依赖外部工具：查订单、检索知识库、调用业务 API。级联流水线（cascaded pipeline）的默认做法是等语音结束、拿到最终转写，再开始推理和工具调用；但用户在前半句就可能给出可操作的信息，例如在描述配送问题时已经报出订单号。把这部分工作提前到“听”的阶段，是降低端到端延迟的直接机会（§1）。

已有的提前准备大致有三类：在部分转写上做前缀推理（LiveMind）、起草候选回复（PredGen）、把推理与工具调用交织进语音块（SHANKS）。它们共同的问题是计算的生命周期仍被输入更新绑住。SHANKS 把每个生成回合限制在一个语音块内，是典型的按块截断（chunk-bounded）方案，工具调用的参数可能还没写完就被截断；投机交互智能体（Speculative Interaction Agents, SIA）在收到新事件时中断正在进行的生成，是收到更新即中断（interrupt-on-update）的思路，调用可能在真正发出前就被打断；Stream RAG 并行检索并判断中间结果能否服务最终请求（§1、§2、Appendix F）。当自动语音识别（automatic speech recognition, ASR）每几百毫秒更新一次时，频繁更新会让“完整构造一个工具调用”所需的不间断时间变得很短。另一类问题是结果时效性：用户后来补上预算或改变意图，早期检索可能已经不再适用。

论文把问题重新表述为一个调度问题：不是“要不要提前做”，而是“如何让一次推理或工具调用跨过若干次输入更新完成，并在端点（endpoint）决定哪些已完成结果仍然适用”。支撑这一判断的证据主要是概念性的图 1 和 Table 1 的窗口基线：Window Thinking 在 SpeechFCEval/FDBench/AudioCRAG 上仍能拿到 33.13%/34.67%/20.05% 的投机工具覆盖率（speculative tool coverage, STC），说明它确实提前做了工作；但其最终响应延迟 6.90 s 只比非投机基线（8.08–8.52 s）好约 1.2–1.6 s，说明被窗口截断的工作没有充分转化为端点后的节省（审稿人判断；论文没有直接测量截断率）。

![图 1：三种推理与工具调用的时间线](/images/dailypaper/2026-10-23/heartbeat_fig1.png)

**图 1**（论文 Fig. 1）：这张图把三种时间线并排放在同一条语音时间轴上，用来对比“计算什么时候开始、什么时候被允许结束”。级联方案把推理和工具调用全部推迟到语音结束；SHANKS 在语音块内推理，但每次生成被块边界限定，工具调用参数可能在边界处被截断；Heartbeat 让多个 Thinker 调用在时间上重叠，新语音启动新调用，旧调用继续运行，因此一个完整的工具调用可以跨过若干次语音更新形成，并在端点前进入 pending 状态等待交接。读图时应抓住的不是“越早开始越好”，而是“开始之后能不能不被下一次输入更新打断”，这正是论文把调度而不是模型能力当作核心变量的原因。

核心假设有两部分：(i) 让新语音触发新的思考器（Thinker）调用、同时允许旧调用和已派发工具继续跑，会增加端点时可用的已完成准备；(ii) 在端点用一个独立的响应器（Responder）校验并复用这些准备，会减少说话结束后的剩余工作。论文没有提出新的学习算法，也没有训练任何模型；它验证的是推理时的调度与接口设计。需要区分：领域中一般的“语音代理延迟高”是旧问题；本文的新观察是把瓶颈定位到“生成生命周期与输入更新窗口的耦合”；实际解决的是三个基准上的函数调用、意图跟随与检索问答准备，而不是通用的“边听边理解”。

## 2. 创新点是什么？

真正的技术增量是推理时的调度语义与准备交接接口，不是新模型、新训练目标或新的解码算法。以下三点分别对应“让旧工作完成”“让后续调用接上已完成结果”“让端点在一致快照上切换”。

第一，可重叠的心跳调度（overlap-preserving heartbeat scheduling）。系统每 Δ 秒启动一次思考器（Thinker）调用，最多 K 个并发；槽满时跳过触发而不是排队；新调用读取最新部分转写与共享状态（shared state），但不打断旧调用。与 SHANKS 的块边界截断、SIA 的更新即中断相比，关键差别是把“下一次输入更新”从生成截止时间改成了“再开一个调用”的触发条件。这是新的调度策略，但周期触发、并发上限、异步工具都是已有系统原语的新组合，不是新学习算法。证据见 §4.2 的 STC 与延迟对比；组件级消融缺失，见 §4.3。

第二，外部共享准备记录（shared preparation record）。每次 Thinker 完成后，推理记录、工具请求和按 tool-call ID 关联的返回结果写入共享状态；后续调用可以用已完成结果补齐缺失参数、发起依赖调用，即使转写没有新内容。与 AsyncReasoning 的模型内部状态、AsyncLM 的 token 流接口相比，这是一个模型外部的接口，因而允许 Thinker 与 Responder 使用不同模型。它更像接口设计与工程组合，而不是新的推理机制。证据见 §4.3 的 Table 10；论文没有单独消融“去掉依赖链”会怎样。

第三，端点快照与 Responder 复用/校验（endpoint snapshot and responder reuse）。语音活动检测（voice activity detection, VAD）判定说话结束后，系统停止新调用、取消未完成的 Thinker 与投机工具任务，把交接（handoff）时刻已完成的准备做成快照交给 Responder；Responder 用 ReAct 对照完整请求，丢弃被后续语音否定的解释，复用工具名与完整参数都匹配的已完成调用，缺失的调用由自己补做。与 SHANKS 的 call-after-listen 配置相比，这里把“投机准备”和“正式响应”显式分成两个阶段，并加了一道校验。证据是 §4.2 的延迟与混合的质量结果；它是否比直接让一个模型从头做更好，仍取决于结果复用是否正确（§4.3）。

## 3. 作者如何解决？

直觉上，Heartbeat 把“听”看成一条可以超前的流水线：不让 ASR 的每次更新成为正在生成内容的截止时间，而是让每次更新启动一份新的、独立的准备工作；到说话结束，再从所有已完成的准备中挑出仍然适用的部分，交给负责正式回答的模型。这样做的代价是可能做重复工作，收益是把等待从“说完之后”挪到“说话期间”。

输入是流式 ASR 的部分转写（partial transcript）x[0,t]、对话历史 H（含之前的工具调用与结果）和工具模式（tool schema）集合 T；当前话语在 T_end 结束。系统有两个语言模型角色：Thinker 在听的过程中周期性地产生暂定推理与工具请求；Responder 在端点被触发，负责最终回答。两者都接收 H 与 T，但可以是不同模型；共享状态保存当前轮已完成的 Thinker 输出、工具请求及其返回结果。整个方法不需要训练，只有调度器、共享状态和提示词（Appendix A、G）。

心跳调度的细节决定了很多性质。每隔 Δ（实验取 500 ms）检查一次：如果当前活跃的 Thinker 调用少于 K（实验取 2），就启动一个新调用；如果 K 个槽都占用，这次触发被跳过，而不是排队。新调用在启动时刻 t_k 读取 H、T、最新部分转写、之前已完成的 Thinker 输出，以及当时已经返回的工具结果；新语音和新结果只进入后续调用，不会注入正在生成的调用。Thinker 的输出有三种：空操作（noop，没有新解释也没有可执行的新调用）、只带推理的 think、带结构化工具请求的 think。一个 think 完成后，先把推理记录写入共享状态，再异步派发工具；工具并发与 Thinker 并发分开控制，派发不设上限，由执行后端排队；结果按唯一 tool-call ID 关联回请求。提示词要求后续调用不要重复“工具名与完整参数都相同”的 pending 或已完成调用。

共享状态是后续调用能“接着做”的关键。因为结果已经落在外部记录里，后来的调用可以在转写没有变化时，用返回结果补齐之前缺失的参数，或发起依赖前一个结果的调用。教学简化示例：用户先说“帮我看看明天去上海的航班”，几秒后补一句“要下午的”；早期调用可以先查航班，后续调用读到结果后再按“下午”约束发起新的查询；端点时 Responder 只复用参数与最终请求完全匹配的已完成调用。这个例子只用于说明依赖链，不是论文实验数据。

端点是 VAD 触发的。设交接时刻为 c，准备输出 r_j 的可用时间为 a_j，Responder 拿到的是满足下式的快照：

$$
\mathcal{R}_c=\{r_j:\ r_j\ \text{已完成，且可用时间}\ a_j\le c\}
$$

其中“完成”既包括已完成的 Thinker 记录，也包括已经返回的工具结果；一条已完成的记录可能包含尚未返回结果的工具请求。c 之后返回的投机输出会被丢弃，未完成的 Thinker 与投机工具任务（包括排队中的调用）会被取消。Responder 收到最终转写、H、T 和这份快照后，按 ReAct（Reasoning and Acting，推理-行动循环）的方式检查准备是否与完整请求一致：被后续语音否定的解释要丢弃；工具名与完整参数都匹配的已完成调用可以直接复用；没有可用结果的必需调用（包括交接时仍在 pending 的调用）由 Responder 自己发起。最终回答送入语音合成（text-to-speech, TTS），对话与保留的工具记录带入下一轮。图 2 把角色、共享状态和端点的关系画成架构与时间线。

![图 2：Heartbeat 架构与执行时间线](/images/dailypaper/2026-10-23/heartbeat_fig2.png)

**图 2**（论文 Fig. 2）：上半部分把系统分成三层：听、异步心跳、响应交接。语音流经 ASR 变成部分转写，和对话历史、工具模式一起进入按 Δ 触发的 Thinker；Thinker 读写共享状态，工具结果异步回到共享状态；端点是 VAD 触发的切换，Responder 只读取交接时刻已完成的快照。下半部分的时间线显示多个 Heartbeat 调用在用户说话期间重叠：较早的调用不会因为下一次触发而被杀死，工具结果可以在后续调用之间传递；到 T 时刻，Responder 才开始，未完成的工作被取消。读图时应理解：共享状态是三个组件之间唯一的耦合面，调度器决定何时开始，模型决定做什么，VAD 决定何时切换。图中的 Response context 部分在截图里被裁切，但正文 §3 与 Appendix A.3 说明了 Responder 的输入与复用规则。

分工可以这样理解：模型决定“做什么、调用什么、参数是什么”；调度器决定“何时启动、何时跳过、何时取消”；VAD 决定“何时从准备切换到回答”；Responder 决定“哪些结果可用、哪些要重做”。固定流程不参与语义判断，模型不控制调度。这样设计的原因是：取消未完成工作可以避免 Responder 等待；快照可以避免交接过程中状态继续变化；外部记录可以让两个角色独立选模型。代价是取消会浪费已经投入的计算，固定间隔会在没有新信息时也触发调用，论文在 Limitations 中承认没有做自适应调度。

## 4. 解决得怎么样？

### 4.1 实验设置

三个基准分别回答不同问题，且都不是本文新提出的基准。SpeechFCEval 测函数调用，包含 Speech-ACEBench 单/并行、Speech-BFCL 单/并行和 SmartInteract 五组，共 1,914 条（208+88+578+372+668），论文使用完整测试集；FDBench v3 测口语不流畅条件下的意图跟随，含 100 条录音、79 个场景、12 位说话人，评价轮次切换、工具选择、参数准确、回答质量和任务成功；AudioCRAG 测基于知识检索的口语问答，含 1,312 条样本，STC 在这里是“样本级”的检索复用比例，而不是函数调用级（§4.1、Appendix B）。

默认系统：Thinker 为 Qwen3.6-35B-A3B，Responder 为 DeepSeek-V4-Flash（0731），Δ=500 ms，K=2；ASR 为 Qwen3-ASR-1.7B，TTS 为 Qwen3-TTS-12Hz-1.7B-Base；VAD 最小语音 200 ms、最小静音 800 ms、padding 500 ms；全部实验使用 NVIDIA H200（Table 4、Appendix B）。论文还分别替换 Thinker（Qwen3.5-9B、GLM-4.7-Flash、Gemma-4-26B-A4B-it）和 Responder（Qwen3.5-397B-A17B、Qwen3.8-Flash-Next）做模型对比（Tables 2–3、6–9）。

基线有四类：Speech-to-Speech、Pipecat、LiveKit 三个非投机系统，以及 SHANKS-style Window Thinking。Window Thinking 使用与 Heartbeat 相同的更新节奏，但丢弃在窗口之后到达的输出（论文没有报告窗口长度的具体设置），因此它是“是否允许进行中的工作完成”的关键对照；三个非投机基线不做投机，STC 按定义为 0，主要用于延迟和质量参照。论文没有把 SIA、Stream RAG 作为实际基线，尽管在 related work 中讨论了它们（§4.1、Appendix F）。

指标有三类。STC 是参考调用中被“已完成的、匹配的投机调用”覆盖，且结果进入 Responder 上下文、Responder 没有重复该调用的比例；AudioCRAG 改为样本级复用比例。它是召回式指标：只奖励被覆盖的参考调用，不惩罚错误或被后续语音否定的投机调用，也不要求最终答案正确。任务质量用 SpeechFCEval 的函数名/参数准确率、FDBench 的 Quality 与 Pass@1、AudioCRAG 的正确率。延迟用 Correct Tool Call Latency（第一个匹配最终请求的工具调用发起时刻，相对语音结束）和 Final Response Latency（最终语音回答的起始时刻），两者都以对齐后的语音端点为 0，负值表示发生在说话结束之前；先在每条录音内平均，再让录音等权（§4.1、§B.2、Table 5）。

延迟口径有两个重要条件：Correct Tool Call Latency 只在存在匹配调用时计算，而且投机调用必须在完成后进入 Responder 上下文才算；Final Response Latency 从语音端点算到最终回答的语音起始；按口径，VAD 的 800 ms 最小静音等待落在测量区间内，测量包含 TTS 起始，但不包含网络与真实电话链路。延迟实验单独使用“两个模型都关闭 thinking”的配置（§B.2），主质量实验是否使用相同 thinking 设置，论文没有明确说明（当前材料无法确认）。

论文没有报告：训练种子、置信区间、显著性检验、GPU 数量/小时、token 总量、实际 Thinker 调用次数、被跳过的触发比例、noop 比例、工具调用总数、取消浪费比例。这些缺口会影响 §4.3 与 §4.4 的判断。

### 4.2 关键结果

先看默认配置。Table 1 中，SpeechFCEval 的 STC 从 Window Thinking 的 33.13% 升到 43.69%（+10.56 pp），FDBench v3 从 34.67% 升到 50.67%（+16.00 pp），AudioCRAG 从 20.05% 升到 62.42%（+42.37 pp）；三个增益都相对 Window Thinking，而不是相对非投机基线。质量则不一致：SpeechFCEval 准确率 66.85% 对 67.95%（−1.10 pp）；FDBench Quality 72.0%→77.0%、Pass@1 57.0%→65.0%；AudioCRAG 正确率 57.24%→55.49%（−1.75 pp）。在 FDBench 上，Heartbeat 的 Quality 77.0% 仍低于 Speech-to-Speech 84.0%、Pipecat 78.0%、LiveKit 77.6%，Pass@1 65.0% 低于 Speech-to-Speech 75.0% 与 LiveKit 67.0%；在 AudioCRAG 上，55.49% 低于三个非投机基线（56.48–59.45%）和 Window（57.24%）（Table 1）。论文在 §4.2 只点出 FDBench 的 Pass@1 低于两个非投机基线，没有点出 Quality 也低于三个非投机基线（审稿人核对 Table 1）。

换 Responder 后，STC 的优势仍然存在，质量的方向则随模型变化。SpeechFCEval 上，Heartbeat 对 Window 的准确率在 Qwen3.5-397B-A17B 下是 69.70% vs 67.27%，在 Qwen3.8-Flash-Next 下是 64.30% vs 57.14%，在默认 DeepSeek-V4-Flash 下是 66.85% vs 67.95%；AudioCRAG 上分别是 55.95% vs 55.79%、56.17% vs 53.35%、55.49% vs 57.24%；FDBench Quality 上分别是 77.0% vs 76.0%、74.0% vs 76.0%、77.0% vs 72.0%（Tables 2–3、9）。把三个基准的主质量指标放在一起，9 个（基准、Responder）组合中有 6 个高于 Window、3 个低于（审稿人根据 Tables 2–3、9 统计）。摘要里“SpeechFCEval 和 AudioCRAG 略降”只描述了默认 Responder 的情况。

换 Thinker 后，“覆盖更高”不等于“质量更好”。SpeechFCEval 上 Gemma-4-26B-A4B-it 的准确率 68.58% 高于默认 Qwen3.6 的 66.85%，但 STC 42.71% 略低于 43.69%；FDBench 上 GLM-4.7-Flash 的 Quality 达到 84.0%，Pass@1 只有 55.0%；AudioCRAG 上 Gemma 的 STC 74.70%，正确率 55.87%，仍低于 Window 的 57.24%（Tables 6–8）。这说明准备阶段的覆盖与最终回答质量由不同环节决定，不能用一个指标替代另一个。

延迟结果只在 FDBench v3 上报告。Correct Tool Call Latency 方面，Heartbeat 为 −4.37 s，Window 为 −2.74 s，三个非投机基线为 2.45–3.52 s；负值表示工具调用在说话结束前就已发起（图 3、Table 5）。

![图 3：正确工具调用的发起时刻](/images/dailypaper/2026-10-23/heartbeat_fig3.png)

**图 3**（论文 Fig. 3）：这张柱状图把“工具调用起点”放在以语音结束为 0 的时间轴上。Heartbeat 的 −4.37 s 意味着平均在用户说完前 4.37 秒就发起了最终匹配的调用，Window 是 2.74 秒；三个非投机基线都在说完后 2.45–3.52 秒才发起。读图时要注意两点：它测的是发起时刻而不是完成时刻，而且只统计最终匹配、完成后进入 Responder 上下文的调用，因此均值是条件均值。它说明提前量来自“旧调用没有被下一次 ASR 更新杀死”，而不是来自更快的模型。

Final Response Latency 方面，Heartbeat 为 4.39 s，Window 为 6.90 s，相对降低 36.4%；相比最快的非投机基线 Pipecat 的 8.08 s 低 45.7%（图 4、Table 5）。这两个数字都来自 FDBench v3（共 100 条录音；论文未报告实际进入延迟统计的样本量），且两个模型都关闭 thinking。

![图 4：最终响应延迟](/images/dailypaper/2026-10-23/heartbeat_fig4.png)

**图 4**（论文 Fig. 4）：这张图测的是用户真正感知到的最终回答起点。Heartbeat 4.39 s，Window 6.90 s，非投机基线 8.08–8.52 s。它把准备阶段节省的时间换算成“说话结束后还要等多久”，是论文最主要的用户体验指标；但只在 FDBench v3（共 100 条录音）上测，且延迟配置关闭了 thinking，不能直接外推到质量实验的全部配置。读图时应把 36.4% 理解为“相对 Window 的均值差”，而不是对所有工具负载、所有模型的普遍保证。

### 4.3 机制证据

最干净的机制证据是 Window Thinking 对照。它和 Heartbeat 使用相同的 Δ、K、模型和更新节奏，唯一区别是窗口之后到达的输出被丢弃。FDBench 上这一改动带来 STC +16.00 pp 和最终响应延迟 −2.51 s（6.90→4.39），方向与“允许进行中的工作完成会增加可用准备”一致（Table 1、Table 5）。这是效果证据，也是目前最强的机制证据；但它是一个“打包”对照：Window 同时改变了多少调用的结果能进入交接、Responder 要重做多少调用、哪些结果进入上下文，论文没有把这三者拆开。因此它支持“重叠并保留完成工作这个组合有效”，不支持“共享状态依赖链”或“端点快照”各自独立必要。

论文没有做 Δ、K、异步工具派发、共享状态依赖链、取消策略的消融。Table 10 给出按信息时机的分析：早期信息组 73.3% 的录音在说话结束前发起了与最终请求一致的调用，晚期信息组 49.2%，显式改口组 70.6% 在结束前发出了修正后的调用（Table 10、Appendix D）。这证明系统能在说话过程中吸收晚到约束和改口，但它是“发起时刻”指标，不要求调用完成、进入上下文或被 Responder 复用，也没有和 Window 做同样的分组对比；所以它是能力证据，不是相对优势证据。

质量侧的机制证据更弱。AudioCRAG 上 STC 从 20.05% 升到 62.42%，正确率却从 57.24% 降到 55.49%，缺失回答率从 14.33% 升到 16.84%；FDBench 上 4.0% 的录音在工具调用参数正确的情况下，最终答案仍使用了错误或过期的结果（§4.2、Appendix D）。论文用“正确调用”和“正确使用结果”的区分来解释，这是合理的，但没有进一步分析哪些复用导致了错误、Responder 在什么条件下会误用旧结果。它说明瓶颈在 Responder 的解释与复用，而不是调度器；但这是相关性证据，不是因果分解。

替代解释也不能完全排除。Heartbeat 在听的过程中可能比 Window 做了更多有效推理（因为旧调用不被丢弃），也可能发起了更多工具调用；论文没有报告每个 utterance 的调用数、token 数或工具执行数，因此无法判断覆盖/延迟增益中有多少来自“更多计算”，多少来自“更聪明的调度”。Window 使用相同节奏，部分控制了 Thinker 侧的调用次数，但 Responder 侧重做调用的数量不同，且没有披露。结论应限定为：在论文的配置和三个基准上，允许跨更新完成工作会提高已完成准备的覆盖率，并在 FDBench 上降低最终响应延迟；至于每个设计是否不可替代，当前材料无法确认。

### 4.4 成本与适用范围

成本方面，论文只报告了调度参数和硬件类型：Δ=500 ms、K=2，意味着整个说话期间最多同时跑两个 Qwen3.6-35B-A3B 的 Thinker 调用；每次调用读取增长中的部分转写和共享状态。论文没有报告每条 utterance 实际启动了多少次调用、多少次因槽满被跳过、多少次返回 noop、总共消耗多少 token、用了多少 GPU 小时、每个对话轮的成本是多少（§3、Table 4、Appendix B）。它也没有报告取消时浪费了多少进行中的工作、Responder 重做了多少调用、工具后端承受了多少并发。唯一的具体成本线索是“所有实验使用 NVIDIA H200 GPU”（§B）。

延迟方面，只有 FDBench v3（共 100 条录音；论文未报告实际进入延迟统计的样本量）；SpeechFCEval 和 AudioCRAG 没有延迟结果。实验是离线录音回放，不含真实麦克风、网络抖动、电话链路、用户打断（barge-in）和 VAD 误触发；VAD 最小静音 800 ms 意味着端点本身有等待，论文没有分析假端点或过早取消的比例。作者在 Limitations 中承认延迟分析只覆盖 FDBench，需要更多工具负载来刻画覆盖、推理成本与延迟的权衡（Limitations、§B.2）。

质量与适用范围方面，默认配置下质量并非全面超过投机基线，也并非全面超过非投机基线；FDBench 和 AudioCRAG 上仍有质量差距。从论文描述看，三个基准的工具以检索/函数调用为主，论文唯一详细讨论的状态改变工具（state-changing tool）例子是 Appendix D 的购物车案例；论文没有报告系统测试下单、预订、改签等不可逆操作。4.0% 的结果误用和“修正检索不能撤销已加入购物车的商品”说明，投机执行改变状态的工具需要额外的提交/回滚协议，而本文没有提供。论文也没有报告语言覆盖、口音/噪声条件和真实用户研究，当前材料无法确认这些范围。

因此，本文能支持的范围是：在三个公开语音基准的离线回放上，用固定 500 ms 心跳和最多 2 个并发的 35B-A3B Thinker，Heartbeat 比 SHANKS 式窗口基线保留更多已完成的工具准备，并在 FDBench 上把最终响应延迟从 6.90 s 降到 4.39 s；它不能支持“普遍更快且更强”“对状态改变工具安全”“在真实电话环境中同样有效”这些更大的结论。

## 5. 最容易受到审稿人质疑的地方

#### 质疑：质量收益被摘要的选择性叙述放大，“更快且更能干”只在部分配置成立

- **原文依据**：摘要写 “faster and more capable voice-agent responses”；§4.2 的默认配置下 SpeechFCEval 66.85% < 67.95%，AudioCRAG 55.49% < 57.24%；Table 1 中 FDBench 的 Quality 77.0% 低于 Speech-to-Speech 84.0%、Pipecat 78.0%、LiveKit 77.6%，Pass@1 65.0% 低于 Speech-to-Speech 75.0% 与 LiveKit 67.0%；Tables 2–3、9 显示换 Responder 后 9 个主质量格中 6 升 3 降。论文 §4.2 自己写 “More retained preparation therefore does not consistently yield better final task performance”。
- **为什么重要**：这决定读者是否能把“覆盖/延迟提升”理解为“任务能力提升”，也决定部署时是否愿意用质量换延迟。标题和摘要的措辞会影响非专业读者的第一印象。
- **当前能够得出的判断**：STC 和 FDBench 延迟的方向性证据较强；质量收益是配置依赖的，默认配置下两个基准下降，且 FDBench/AudioCRAG 仍低于非投机基线。“faster and more capable” 应收缩为“在 FDBench 默认配置上更快且质量更高；其他基准质量 mixed”。
- **如何验证或补强**：报告全部 9 个质量格及置信区间；预先声明主指标；在同一模型、同一工具预算下与非投机基线比较；对 FDBench 的 Quality 低于三个非投机基线给出解释；增加人工评测，避免单一 LLM judge。
- **严重程度**：主要问题。

#### 质疑：没有算力账单，无法判断“用更多推理换更低延迟”是否划算

- **原文依据**：§3 与 Table 4 给出 Δ=500 ms、K=2；Thinker 是 35B-A3B；论文未报告实际调用次数、跳过触发次数、noop 比例、token 总量、GPU 数量/小时、每轮成本、工具调用总数与取消浪费；§B 只说 “All experiments use NVIDIA H200 GPUs”；Limitations 承认固定调度可能在信息很少时产生冗余推理。
- **为什么重要**：实时语音对成本和尾延迟敏感。若 Heartbeat 的覆盖/延迟收益主要来自“在听的时候多跑了很多次大模型”，那么它不是一个便宜的调度改进，而是一个用算力换体验的方案；读者需要知道交换比。
- **当前能够得出的判断**：无法确认。论文只证明了在给定配置下 wall-clock 延迟更低，没有证明单位任务的推理成本可接受，也没有和“同样多算力”的 Window/非投机基线比较。
- **如何验证或补强**：记录每条 utterance 的 Thinker 调用数、跳过率、noop 率、输入/输出 token、工具调用数与取消比例；报告 GPU 小时和每轮成本；做算力匹配对照（给 Window 相同的调用预算）；测试更低成本 Thinker 或自适应调度。
- **严重程度**：主要问题。

#### 质疑：关键基线是 SHANKS-style 复现，最近方法缺席，评审模型与 Responder 同源

- **原文依据**：§4.1 的 SHANKS 基线名为 “SHANKS-style Window Thinking”，论文没有说明是否直接运行 SHANKS 原系统，也没有报告窗口长度与实现细节，其定义是沿用 Heartbeat 的更新节奏但丢弃窗口后输出；Appendix F 讨论了 SIA 与 Stream RAG，但实验中没有它们；级联基线只写 “Qwen3-ASR with a text reasoning model”，没有点名文本模型，Speech-to-Speech 的模型也未说明；§B.2 用 DeepSeek-V4-Flash（与默认 Responder 同模型）作为 FDBench 的评审模型（LLM-as-a-judge）；延迟配置明确关闭两个模型的 thinking，主质量实验的 thinking 设置未说明。
- **为什么重要**：这会同时影响绝对排名和内部效度。自实现的窗口基线可能高估或低估 SHANKS 的真实表现；缺少 SIA/Stream RAG 使“相对最近方法更好”无法判断；评审模型与 Responder 同源可能产生 self-preference bias，尤其在 Quality/Pass@1 这类开放式评分上；thinking 设置不一致会让延迟与质量数字不可直接拼接。
- **当前能够得出的判断**：相对 Window 的内部对照（同调度、同模型、只改丢弃策略）有一定说服力；但“比非投机基线更好”“比 SHANKS 更好”“比 SIA/Stream RAG 更好”都不能从当前实验确认。Judge 偏差无法排除。
- **如何验证或补强**：使用 SHANKS、SIA、Stream RAG 的官方实现或复现；披露所有基线的模型、提示、解码参数与工具预算；用独立模型或人工评测做 judge 交叉验证；在延迟与质量实验中统一 thinking 设置，或分别报告两套配置。
- **严重程度**：主要问题。

#### 质疑：状态改变工具的投机副作用与结果误用没有量化

- **原文依据**：§4.2 报告 4.0% 的 FDBench 录音在参数正确的情况下使用了错误/过期结果；Appendix D 的购物车例子中，系统在听到 50 美元预算前就把 99.99 美元的咖啡机加入购物车，之后检索到 40 美元商品，但最终回答混用了两个结果，且“修正检索不能撤销已加入购物车的行为”；Table 10 的改口组只有 70.6% 在说话结束前发出修正调用，意味着约 29.4% 没有及时修正；从论文描述看，三个基准的工具以检索/函数调用为主，论文没有报告对不可逆操作的系统测试。
- **为什么重要**：语音助手越来越多地执行下单、预订、改签、转账等状态改变操作。投机执行在用户还没说完时就把动作发出去，可能造成真实副作用；取消只能停止未完成的任务，不能回滚已经执行的调用。4.0% 是答案一致性指标，不是有害动作率。
- **当前能够得出的判断**：论文承认结果误用，但没有量化错误动作率、回滚成功率或用户可见损害；也没有提供提交/中止协议。当前证据只支持“只读或低风险工具”的适用范围，不能支持“可用于交易型语音助手”。
- **如何验证或补强**：在基准中加入状态改变工具，记录投机执行导致的错误下单/错误预订率、回滚成功率和用户可见损害；设计“准备-提交”两阶段协议（投机阶段只读或预计算，端点后才提交副作用）；按工具风险等级做调度；报告改口场景下的副作用率。
- **严重程度**：主要问题。

#### 质疑：延迟指标是条件均值，且只在 FDBench v3 上测

- **原文依据**：§4.2 与 §B.2 说明 Correct Tool Call Latency “conditional on a matching call”，投机调用必须在完成后进入 Responder 上下文才算；论文没有报告每个系统的匹配调用数/录音数，也没有置信区间；Final Response Latency 只在 FDBench v3（共 100 条录音）上测，未报告实际进入统计的样本量，先在录音内平均再等权；延迟实验关闭 thinking，质量实验的 thinking 设置未说明。
- **为什么重要**：条件均值会在不同系统之间比较不同的子集：如果 Heartbeat 在更多录音上产生匹配调用，而 Window 只在容易的录音上产生匹配调用，二者的 −4.37 s 与 −2.74 s 就不可直接比较。100 条录音的等权平均也容易受少数场景影响；没有方差就无法判断 2.51 s 的差距是否稳定。
- **当前能够得出的判断**：方向可信（Heartbeat 的工具调用起点更早、最终回答更快，且差距较大），但精确幅度和跨基准泛化不确定。延迟结论应限定在 FDBench v3 与关闭 thinking 的配置。
- **如何验证或补强**：报告每个系统的条件样本量、匹配率、无条件延迟、按场景/说话人的分层结果和 bootstrap 置信区间；在 SpeechFCEval/AudioCRAG 上补延迟；测试不同工具延迟分布和真实网络条件；统一 thinking 配置。
- **严重程度**：次要问题。

## 6. 审稿式总评

作者发现实时语音代理的工具准备被“语音块边界/输入更新”绑住，导致用户在说完后还要等待；因此提出 Heartbeat Thinking，用固定间隔、可重叠的 Thinker 调用和外部共享准备记录，把推理与工具执行提前到倾听阶段，并在 VAD 端点把已完成快照交给独立的 Responder 复用与校验。实验在 SpeechFCEval、FDBench v3、AudioCRAG 上表明，STC 比 SHANKS 式窗口基线分别高 10.56、16.00、42.37 个百分点，FDBench 上最终响应延迟从 6.90 s 降到 4.39 s（−36.4%）；其中“覆盖增益跨基准、跨 Responder 稳定”和“FDBench 延迟下降”证据较强，但“质量普遍提升”“每个设计不可替代”“推理成本可接受”仍缺少充分支持。本文最有价值的部分是把“输入更新不是生成截止时间”这一调度语义讲清楚，并给出可操作的端点快照/Responder 复用协议与完整提示词；最大的审稿风险是质量收益的选择性叙述、缺失的算力账单，以及状态改变工具的副作用没有被量化。

- **问题定义清晰度**：强。§1 明确区分了级联、chunk-bounded、interrupt-on-update 三种时间线，并把问题收敛为“计算生命周期与输入更新窗口的耦合”；STC 的定义也在 §4.1 交代得具体。扣分点是摘要的“more capable”比实验覆盖更宽。
- **创新性证据**：中。可重叠心跳调度与端点快照是清晰的系统增量，且与 SHANKS/SIA 的差别一句话能说清；但它是推理时调度与接口组合，不含新学习算法，且没有 Δ/K/依赖链/取消策略的组件消融，无法证明每个设计都不可替代。
- **方法可信度**：中。架构、状态机、输出 schema、提示词和取消/快照语义都写得具体，Appendix G 可直接复用；但成本、实际调用次数、结果复用精度和状态副作用没有量化，质量的机制解释仍停留在相关性。
- **实验支持力度**：中。三个基准、四个 Thinker、三个 Responder 的覆盖面不错，STC 的优势一致，FDBench 延迟差距大；但质量结果 mixed、默认配置下两个基准下降，缺少置信区间/种子，延迟只在 FDBench v3 上测，且 judge 与 Responder 同源。
- **可复现性**：中。方法无需训练，提示词、调度参数、基准和模型名称都给了，理论上可复现；但没有代码，Window/SHANKS 的具体窗口实现、级联基线的文本模型、judge 配置与随机种子没有完整披露。
- **综合阅读价值**：高。对实时语音、流式 agent、tool-use 调度的读者，这篇把“何时允许一次生成结束”这个常被忽略的调度问题讲得很清楚，图 1/2 与 Appendix G 的提示词有直接参考价值；质量与成本的负面结果也值得作为批判性阅读材料。阅读时应把结论限定在 FDBench 的延迟和 STC 的覆盖增益上。
