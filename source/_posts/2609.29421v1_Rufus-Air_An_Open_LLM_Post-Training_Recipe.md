## 1. 作者发现了什么问题？

开放权重基座模型让更多团队可以做后训练，但**后训练配方本身被公开得太少**：论文里这一节常常写得像系统卡（system card），真正能复现的细节——数据构成、奖励怎么算、阶段怎么排、基础设施怎么调——恰恰披露最少（§1）。作者把 Tülu 3 列为少数把配方写清楚的例外，并以此说明"把配方完整写下来"本身值得作为贡献。

这篇报告的任务是：在公开基座 **GLM-4.5-Air-Base（106B 总参 / 12B 激活的 MoE）** 上，完整记录一份可复现的后训练流水线 **Rufus-Air**，涵盖数据、奖励设计、基础设施、阶段顺序与逐阶段结果，且**不新增人工标注、不自建蒸馏 teacher**，数据尽量使用公开数据集原样发行版（§1、§2）。作者自述这份报告介于研究论文与工程经验报告之间：**部分结论来自训练经验而非完整消融，正文明确标记**（§1、§6）。

作者从训练中总结了四条贯穿全文的判断（§1、§6）：

1. **SFT 是能力建设阶段，不是热身**：一个强 SFT checkpoint 已经建立起大部分能力，后续 RL 是精修而不是从零教起；
2. **难度过滤（difficulty filtering）让 prompt 保持在"可学习区间"**：训练前丢掉策略已经全会的、以及（多数阶段）从来不会的 prompt，过滤本身构成自动课程表；
3. **奖励可靠性决定阶段顺序**：奖励越难被 hack 的阶段越靠前，软性 judge/模型奖励靠后，从而缩短"可被博弈的奖励暴露在优化压力下"的时间。注意顺序跟踪的不是奖励形式而是 hack 暴露度——IF RL 用的是 rubric judge 却排在前面，因为指令跟随接近模型已有行为，judge 没什么可被利用的空间；
4. **基础设施是配方的一部分**，不是实现细节：on-policy 多轮 RL 的 token-in/token-out rollout、从 SFT 到 Agent 阶段一致的 chat template 处理、可支撑长轨迹的沙箱服务、以及大 batch + Rollout Routing Replay 的稳定性。

## 2. 作者如何解决？

核心思路：把后训练组织成**一条串行流水线**——`SFT → Reasoning RL → Coding RL → Instruction-Following RL → General Agent → Coding Agent → Search Agent → RLHF`，**每个阶段在上一阶段产出的 checkpoint 上训练**；能力上从基础到进阶，奖励上从"硬、可验证"过渡到"软、judge 或环境判定"，图 1 给出总览。

![Rufus-Air 流水线总览](/images/dailypaper/2026-09-27/2609.29421_fig1.png)

*原文图 1（§2.1）。八个阶段与其目标能力、奖励类型（图例：token supervision / rule-based verifier / hybrid verifier / reward model）。前半段建通用能力，中间三段接入工具环境，最后用 RLHF 塑形开放域质量；终点是 Rufus-Air 最终模型。*

**① SFT（§3.1）。** 混合集共 **9.01M 样本 / 44.5B 原始 token**，经掩码后 **27.0B token（60.8%）**参与损失，来自 **17 个公开数据集**（附录 C 列出许可与上游生成依赖），Rufus-Air **不重生成任何回复**（"regenerated by Rufus-Air is zero"）。六个能力类别的样本占比与 token 占比差别很大：Math 与 Coding Agent 合计 18.8% 样本但贡献 49.1% 训练 token（表 3、图 2）。训练 3 个 epoch，64 台 8×H200（512 GPU），batch 4096，AdamW，学习率 100 步线性 warmup 到 $5\times10^{-5}$ 后余弦退火到 $5\times10^{-6}$；按 chat template 计算序列长度上限 120K（打包后 128K）。训练损失从 0.84 降到 0.42（第 1 epoch 末）再到 0.34（图 3a），但**留出集分数在第一个 epoch 内就进入平台**（图 3b），所以最终采用平台内的 **checkpoint 3799** 而不是最后一步。去污染方面：用 8-gram 重叠测试串行筛除 3,529 条，又对最易泄漏的数学/知识基准（AIME 24/25/26 等）追加穷举 8-gram 与稠密检索两道检测，确认 68 对污染（58 条唯一样本），连同边界案例共**剔除 4,187 条**。

![SFT 训练动态](/images/dailypaper/2026-09-27/2609.29421_fig3.png)

*原文图 3（§3.1）。左：训练损失及 50 步滑动平均，每个 epoch 边界出现台阶式下降（重复数据效应）；右：AIME 25/26、GPQA、IFEval、IFBench 的留出评测，第一个 epoch 后基本走平，虚线为被选中的 checkpoint 3799。*

**② Reasoning RL（§3.2）。** 12.1 万条可验证单轮 prompt（Math 47.7% / Science 35.7% / Puzzles 16.7%，表 5），奖励全部为**程序可判定的二元信号**（Math-Verify 规范化比对、生成式 Python checker、模糊字符串匹配）。两道过滤最重要：**correctness filter**（强 teacher GPT-OSS-120B 至少拿到一次正奖励，保证题目有解）与 **learnability filter**（通过率 >0.8 的丢弃、零成功丢弃）；训练中用 DAPO 式动态采样在线维持组均奖励 $\bar r\in(0,0.8]$。优化用 GSPO（序列级重要性比与裁剪，长 MoE rollout 更稳），并加了一条"相对组内最短正确 rollout 的长度惩罚"以压住冗长。结果：GPQA 从 68.18 升到 73.50（+5.32），AIME 两届分别回落 2.81/2.60——作者当时把 AIME 当护栏（SFT 已在 90+，30 题下 3 点以内不到一题的量级），主目标看 GPQA（表 6）。

**③ Coding RL（§3.3）。** 4 个来源共 **29,405 题**（EvolveCoder 14,743 / Nemotron 9,393 / Dolci 3,109 / ADR 2,160，表 7），代码块提取后在沙箱执行测试，奖励二元（每题确定性抽 ≤50 个测试）。训练前做 LCB v6 泄漏检查（1,055 题无前缀哈希命中、无 ≥5 个 60-gram 重叠）与"热启动四采样全过则丢弃"的难度过滤。训练中 64K 响应预算下 11–28% 的样本被截断并掩码，于是**在第 23 步把响应预算扩到 128K 并从该 checkpoint 继续**，截断率降到 <0.1%，奖励从 0.26 继续爬到 0.42（图 4）。LiveCodeBench v6 pass@1 从 68.6 升到 **75.9**（+7.3，单阶段评测口径；训练曲线在 step 33 达到同值峰值），pass@8 仅 +2.3——作者总结的实践教训是"扩响应预算、去截断掩码"直接带来了后续上涨（表 8、图 4）。

**④ Instruction-Following RL（§3.4）。** 两个数据轴：**多约束单轮**（14K 条，每条 2–6 个原子约束，教师 Qwen3-235B-A22B 生成约束及对应 Python 校验函数）与**多轮对话式**（13K 段对话，平均 6.1 轮、2.7 条 rubric；用户侧由教师模型扮演并主动"下套"：叠加指令、中途改需求、插入干扰项，助手侧轮换多个开源模型避免风格偏置）。奖励是**rubric 二元奖励**：所有 rubric 全过才给正奖励；rubric 只描述"必须满足"的条件，作者特意**排除"可选/加分项"rubric**——他们观察到把可选 rubric 也挂上去后（每例十条量级），策略出现明显长度偏置，输出又长又冗余。三道过滤：去超长对话并对"应拒绝"样本降采样防过度拒答、教师在 4 次内至少过一次、策略通过率 >80% 的丢弃。用 GRPO 训练 90 步。结果：IFEval 90.5→94.5（+4.0）、IFBench 63.8→77.8（+14.0）、Multi-challenge 31.1→55.8（+24.7）、AdvancedIF 45.5→62.9（+17.4），GPQA 还 +3.2、AIME 25 仅 −1.2（表 9）。最终响应长度从约 5.4K 降到 3.6K token（图 5）。作者还报告一个课程现象：同样的 IF RL 跑在 Reasoning RL checkpoint 上比直接跑在 SFT 上收益更大——复杂指令需要先"想清楚"再答。

**⑤ General Agent（§3.5）。** 数据为 AgentWorldModel（AWM）的 10K 条单服务器 MCP 任务（1K 个人造环境，每环境约 35 个工具），经 correctness 与 difficulty 过滤留下约 **2K 条**。环境是"任务绑定一个合成数据库 + MCP server"的设定，工具读写数据库，奖励在 episode 结束时由**规则校验数据库状态**给出二元值（去掉了 AWM 原带的 LLM judge 奖励与格式奖励，后者被"把全部工具 schema 直接写进 system prompt"取代）。用 GRPO + DAPO 式动态采样 + R3 训练。结果：MCP-Atlas 34.95→42.75（+7.80）、Tau2-Retail 74.00→83.80（+9.80），轨迹长度从约 14K 涨到 16.5K token（表 10、图 6）——作者把增益解读为"合成 MCP 环境提供的通用工具编排先验"。

**⑥ Coding Agent（§3.6）。** 数据来自 Endless-Terminal、SETA-Env（4,500+ Harbor 格式环境）、Scale-SWE，过滤后约 **4K 条**。统一成 Harbor 任务格式（`instruction.md` + `environment` Dockerfile + `tests/test.sh`），工具面只有**一个 `execute_command`**（返回 stdout/stderr/exit code），文件读写、构建、跑测试都是 shell 命令；奖励是任务自带 verifier 的二元结果。工程上把每个容器镜像预烘成沙箱模板快照，rollout 时直接恢复。训练时把沙箱启动失败、verifier 超时、连接断开等**基础设施噪声标为 `aborted` 并从组内优势计算中剔除**，避免污染基线。结果：Terminal-Bench 2.1 38.76→40.17（+1.41）、SWE-bench Verified 65.60→67.80（+2.20）；作者明确标注**该阶段是"按可用算力训练、未训到收敛"**（表 11）。

**⑦ Search Agent（§3.7）。** 从 MiroVerse 抽出 36,614 条可验证问答（另留 4,069 条验证）。因为 rollout 贵，做了两遍强筛选：先删掉"关掉工具也能答对"的题（约占四分之一，防止奖励工具无关的捷径），再按初始策略 8 次 rollout 的正确数 $c$ 只保留 $0<c<4$ 的题目（其余极端值 15.5% 从未解出、31.4% 全对，组内优势为零），最终训练集约 **2.2K 题**。工具是 Web Search、Web Scrape（超长页面先摘要但保留人名/日期/数字原文）、沙箱 Python；训练最多 100 次调用、评测 200 次。奖励是**LLM judge（训练用 Qwen3-32B）在 [0,1] 上的连续分**，含部分正确加分；为防止"不查资料直接背答案"，正奖励要求**至少 2 次成功工具调用**，畸形调用按比例打折（最低 ×0.5），预算耗尽无最终答案罚 −0.1；早期那个"提交 boxed 答案就给格式分"的项因被策略钻空子而删除。优化上有一个关键的算法改动：GRPO 只用**组均值优势**、去掉标准差归一化（$G=16$）：

$$\widehat{A}_i=r_i-\mathrm{mean}(\{r_j\}_{j=1}^{G})$$

理由是 judge 奖励噪声大：若按组标准差归一化，"8 次里只对 1 次、但奖励差距 1.0"与"差距 0.1 的部分分"会得到同样的 +3.75 优势，是平衡组里成功样本的约 3.9 倍，等于把评分噪声放大成"真解出"量级的信号。同配置配对消融中，mean-only 在各次评测都领先（留出集 55.8–64.8 vs 49.7–58.7）。结果：BrowseComp 34.2→37.2（+3.0）、Seal-0 48.6→54.0（+5.4）、HLE-Verified 47.7→51.1（+3.4）（表 12）。轨迹分析（图 7、附录 E）显示工具调用数先降后升，且"变长"发生赢家一侧（赢家中位仍约 25 次调用，90 分位从 40 升到 54.5；>45 次调用的轨迹从 49 条增到 133 条、其中赢家占比从 24% 升到 43%）；附录 E 的评测轨迹进一步显示，BrowseComp 上错误答案的轨迹深度约为正确的两倍（92 vs 43 次迭代），超过约 50 次迭代后准确率降到 30% 以下，"更长"本身不是好事。

**⑧ RLHF（§3.8）。** 用**公开奖励模型 Skywork-Reward-V2-Qwen3-8B**（不新训 RM、不新标数据），在 HH-RLHF 的 **75,815 条** prompt 上做 on-policy GRPO（"RLHF"在这里指对学习到的奖励模型做 RL，而非直接用人类标注）。选 prompt 之前先做了数据对比（表 13）：Arena Human Preference 两侧分数都高、回复最长；HelpSteer3 分数区分度最大但 RM 打分不稳、训练时科学推理与指令跟随回退；HH-RLHF 回复最短、两侧绝对分都为负。由此得到三条负面结论：未过滤的 HH-RLHF prompt 会明显损伤编码与指令跟随（这正是加"有效性过滤"的原因）、HelpSteer3 的 prompt 对 RM 太难打准、指令跟随与 Agentic prompt 不适合这一阶段（RM 判不准复杂约束）。最终只取有效性过滤后的 75,815 条 HH-RLHF prompt，奖励为原始 RM 分数加一条线性长度惩罚（对正奖励的超长回复打折、负奖励不动）。结果：Arena-Hard v2 Hard Prompt 83.06→89.05（+5.99）、Creative Writing 38.56→52.97（+14.41），交付 checkpoint 为第 29 次迭代（表 14、图 8）。

**训练基础设施（§4）。** 两个自研组件都建立在开源栈上：**Rufus-Slime**（Slime 的改造版，Megatron-LM 训练 + SGLang rollout）负责 SFT 与全部 RL；**Rufus-Gym** 负责多轮 Agent rollout。图 9 给出 Agent rollout 栈：Data Sampler 产出 Task → Environment（每个 rollout 一个）经 Rollout Engine 生成 → 返回 `RolloutResult`（token 轨迹、奖励、类型化终止原因）给 Training Engine，环境内部是 Agent Loop（Inference Client + Tool Execution）加 Reward Service。

![Agent rollout 栈](/images/dailypaper/2026-09-27/2609.29421_fig9.png)

*原文图 9（§4.2）。Rufus-Gym 的 gym 式接口：同一契约兼容代码执行、网页检索、MCP 服务器等不同工具面；终止原因被类型化，训练器可区分"任务完成"与预算耗尽、上下文溢出、执行失败。*

被作者点名的几个"配方级"工程选择（§4.1、§4.2）：on-policy 多轮必须 **token-in/token-out**（直接传 token id，避免重分词漂移、chat template 反复套用改历史）；**Rollout Routing Replay（R3）** 缓存 rollout 时的 MoE 路由并在训练前向重放，消掉"同一 token 在 rollout 与训练时被路由到不同专家"造成的 log-prob 失配（与精度无关的那一部分差距）；并用**混合精度 rollout**（前三个 transformer 层 BF16、其余 FP8）配 BF16 参数更新，同时全程监控截断率（截断样本被掩码，比例升高等于每批可用梯度变少，Coding RL 正因此中途扩了响应预算）；沙箱不是容器而是 **Firecracker microVM**（自托管的 E2B runtime），可快照恢复、硬件级隔离；工具结果截断到固定 token 预算再入上下文；重试只对"确定未曾开始执行"的失败生效（agent 命令非幂等）；用 Ray 把环境 actor 分散到各节点，避免 CPU 密集的工具执行与奖励计算互相争抢。

**逐阶段进展（§5.2、表 2）。** 每个阶段都提升自己瞄准的指标，读法是"与上一行比"：SFT（对 GLM-4.5-Air 公开版）IFEval 88.33、IFBench 57.75、AIME 25/26 双升、GPQA 反而低 5.72；Reasoning RL 补上 GPQA（68.18→73.50）；Coding RL 把 LCB v6 推到 75.9；IF RL 是最大单阶段跃迁之一（Multi-challenge +24.7）；General Agent 抬 MCP-Atlas（+7.8）与 Tau2-Retail（+9.8）；Coding Agent 只加 +1.4/+2.2；Search Agent 三项检索 benchmark 各 +3.0/+5.4/+3.4；RLHF 把两个 Arena-Hard v2 分轨抬 +6.0/+14.4。**SFT-only checkpoint 在已测的 5 项上除 GPQA 外全部超过带 RL 的公开 GLM-4.5-Air**（IFEval +5.33、IFBench +24.15、AIME 25 +6.63、AIME 26 +3.50、GPQA −5.72；表 4），这是"SFT 是能力建设阶段"主张的直接证据；但该 checkpoint 未测多轮指令跟随，作者另据 IF RL 起点在 Multi-challenge 上仅 31.1 判断这一短板真实存在。

**代价与边界。** 成本是分层的：SFT 是作者能核算的各阶段中最大的单项（约 105 小时/epoch、3 epoch 共约 **13 天 / 832 node-days**，64 节点）；各 RL 阶段 8–32 节点；Agent 阶段的额外开销更贵——Coding Agent 的沙箱服务按**约一万个并发沙箱**规模运行、维护费约 **每月 1 万美元**量级，Search Agent 每次评测遍历 BrowseComp 1,266 题约产生 $10^{5}$ 次检索/抽取调用、按列表价几百美元，训练里每次 rollout 还要过一遍 LLM judge（§6）。作者主动列出的"配方未证明的东西"也很清楚：**阶段顺序是"能work的一种"而非最优**，没做顺序消融，也没试"分域专家 + 多教师 on-policy 蒸馏再合并"的替代路线；Coding Agent 按算力截断、未训到收敛，其 SWE-bench 增益（67.8）**没有保持到最终 checkpoint**（65.6），而 Terminal-Bench 2.1 最终是 42.7，但这两项在 Search Agent 后没再测，**无法归因到具体阶段**；没有任何一个 benchmark 全阶段贯通；LCB v6 与 Tau2-Retail 的阶段行与表 1 口径不同、不能直接比；Search Agent 的奖励门只检查"工具调用执行过"而不检查"答案依赖调用结果"，背答案顺带调工具的残余路径仍需靠轨迹审计（§3.7）。评测口径本身也要小心：Tau2-Bench 分数**随用户模拟器最多变动 23.7 点**（附录 F：GLM-4.5-Air 零售域在 Sonnet 4 下 57.0、Sonnet 5 下 80.7），作者因此强调跨论文比较必须对齐模拟器设置。

作者发现后训练配方普遍披露不足，因此在公开基座 GLM-4.5-Air-Base 上完整记录了八阶段流水线 Rufus-Air（数据、奖励、基础设施与逐阶段结果，全部基于公开组件与数据、无新增人工标注），并给出四条可迁移经验——SFT 是能力下限、难度过滤是自动课程表、奖励可靠性决定阶段顺序、基础设施属于配方本身；实验表明最终模型在除 Creative Writing 外的全部报告基准上超过官方 GLM-4.5-Air 后训练版、与同级开源模型各有胜负，但阶段顺序未经消融、Agent 阶段未训到收敛、跨阶段归因与评测口径（用户模拟器、harness）都留有明确的不确定性。
