## 0. 一句话结论

本文要解决的是"多 Agent 协作能力无法被单独评测"这一问题：作者在开源 MMORPG 引擎 Kaetram 上搭起沙盒，用 13 个高层 API 抽象掉低层操作、用回合制黑盒协议强制自然语言协调，再配 100 道人工标注任务（另 100 道 LLM 增强变体）与程序化 verifier，并新提出动作级指标 CCE 来量化"多少动作真正贡献了成功"。在当前证据下，"在论文自建的 200 题基准与给定黑盒协议下，四个前沿模型的长程协作成功率最高只有 52.0%、最好模型的贡献动作占比也只有 0.320"这一有边界的结论是站得住的；但 CCE 的绝对值依赖 LLM 因果判定与宽松纳入策略（论文自认是上界），"沟通量存在最优区间"等解释性结论目前只有 4 个模型的观测相关性支撑，尚无因果实验。

## 1. 论文具体想解决什么问题？

**研究背景与具体任务。** LLM Agent 正从单轮推理走向自主工具使用与多步执行，而软件开发、科研、复杂运营等真实任务需要多个各有所长的 Agent 朝共同目标协调，即 multi-agent collaboration (MAC)；作者认为要理解当前模型的强项与短板，必须有一套能把"协作能力"单独测出来的评测（§1）。

**现有方法通常怎么做。** 已有工作大致三条路线：社会模拟（Generative Agents、Project Sid、Agent Society 等）、具身与协作基准（RoCo、Collab-Overcooked、MINDAGENT）、Minecraft 平台（MineDojo、TeamCraft、MineLand），另有 TheAgentCompany 等职业场景评测（§2）。Table 1 上半区按"最大 Agent 数、是否黑盒、领域、API 工具数、是否非对称角色、是否可扩展、是否开放世界"逐项对比了这些平台。

**现有方法具体在哪些条件下表现不好（作者的诊断）。** §1 给出三条论证，并在 Table 1 下半区逐项对照：

1. **视界太短。** 多数已有基准的任务在 20 步以内（Table 1 中 MineLand、MINDAGENT 为 10+，MindCraft 为 20+），不足以考察"持续协调"——多轮之后计划是否走样、状态是否同步都测不出来。
2. **把低层操作控制与协作混在一起。** Minecraft 类环境要求精确 3D 导航、放方块、管背包，这些操作能力会直接进分数，稀释协作本身对分数的贡献；而 Overcooked、狼人杀这类接口干净的环境世界又太简单，撑不起多样、长程的协作任务（§3.1）。
3. **大规模社会模拟测的不是任务。** Project Sid、Agent Society 关注涌现的社会行为，而不是有明确目标、可用程序化 verifier 判定的具体任务（§1、§2）。

Table 1 还指出已有平台大多**不同时具备**黑盒交互（Agent 看不到彼此的观测、动作与内部状态）与非对称角色（各 Agent 技能、装备、目标不同），而作者认为这两点是真实协作的前提。

**一个被忽略的度量问题。** 即使任务设计得当，仅用 task success rate (SR) 也测不出协作质量：任务可能"一个 Agent 把活全干完、其余人闲着"却依然算成功（§3.5）。已有工作用 LLM-as-judge 给协作整体打 1–5 分，作者指出这类主观评分会随 judge 模型版本更新而漂移、无法复现（§3.5）。

**三类问题的区分（按规范要求）。**

- **领域早已存在的一般问题**：多 Agent 协作难以评测、现有基准视界短、缺少可判定的任务，这些是本文引用的多篇 survey 与 benchmark 已经反复讨论的。
- **本文的新观察**：论文不是先提出一个现象再立论，而是先造基准、再由基准测出一组经验事实——最强模型 52.0% SR、CCE 仅 0.320、沟通数量与成功率不相关、沟通失败可归为六类（其中"过时与冗余"占 37.7%）、oracle 沟通下仍有 40% 失败（§4.2–§4.5、§5）。这些是本文通过自建基准新测出来的。
- **本文实际解决的具体子问题**：不是提出更强的协作方法，而是造出一套可运行、可判定的评测装置（沙盒 + 高层 API + 回合制黑盒协议 + 人工任务与 verifier + 指标 CCE + 开源工具链）。

**作者认为问题产生的原因。** 根源是评测环境没有把"协作难度"与"操作难度、信息充分性"分离开，以及缺少客观的协作度量（§3.1、§3.5）。因此作者选择"中间地带"的设计目标：世界复杂到能支撑多样的长程协作场景，同时用高层 API 把低层操作抽象掉，让分数主要反映联合规划与协调决策。

**论文最终要验证的核心假设。** 把低层控制抽象掉、强制黑盒沟通、用"单个 Agent 不可能完成"的任务加程序化 verifier 判定，就能把协作能力作为一个独立维度测出来；并且当前前沿模型在这一维度上存在系统性缺口。

**需要指出的证据边界。** 作者对"已有基准不好"的判断主要是设计层面的论证与 Table 1 的能力清单对比，**论文没有报告"同一模型在 AgentWorld 与某个已有基准上"的对照实验**；因此"AgentWorld 更能隔离协作能力"目前是作者主张加部分消融支持（Table 3、Table 4），不是直接实验证明（审稿人判断）。

## 2. 创新点是什么？

**一段话概括真正的技术增量。** 本文不是新模型、也没有任何训练，增量是"一套评测装置 + 一个动作级协作指标"：把开源 MMORPG 引擎包装成高层 API 沙盒，用回合制黑盒协议和 100+100 道长程任务（含 Python verifier）构造可判定的协作评测，再用因果动作图把"协作质量"操作化为贡献动作占比 CCE。

**创新点 1：长程黑盒非对称协作基准 AgentWorld。**

- **新增了什么**：任务五要素格式——多 Agent 主目标、带非对称角色/技能/出生点/初始物品的 Agent 配置、轮数预算、任务特定文档、Python 成功判定函数（§3.2）；100 道人工标注主任务 + 100 道由 Claude Opus 4.5 生成的 augmented 变体（§3.3、§3.4 与脚注 3）；13 个高层 API 工具，一次 `attack_entity` 调用打通"寻路→战斗→拾取战利品"，`harvest_resource` 同理（§3.1）；回合制 round-robin 编排与全实验统一的黑盒协议（§3.1）。
- **与最接近的已有工作差在哪**：Table 1 显示 Overcooked 类最多 4 Agent、5 个工具、非黑盒、非开放世界；MineLand 有 200 题但视界 10+ 且不做定量评测；MineCraft 平台操作负担重；SmallVille 无定量评测。AgentWorld 的差异是"长视界 + 黑盒 + 非对称角色 + 开放世界 + 定量评测"这一组合同时成立（Table 1）。
- **属于哪类创新**：**已有组件的新组合 + 大量工程与数据构造**，而不是新算法。沙盒底座 Kaetram 是既有开源引擎（§3.1 脚注 2），不是作者从零构建；augmented 变体由现成 LLM 生成、变化限于目标数量、出生点、初始物品（§3.4 脚注 3、附录 D）。
- **如何对应前面的问题**：长视界 25–55 轮对应"协调测不深"，API 抽象对应"操作稀释协作"，程序化 verifier 对应"社会模拟没有可判定任务"。
- **原文提供的有效性证据**：Table 3 中 single-agent 基线（把所有角色和物品塞给一个 Agent）只有 28.6% SR，而多 Agent 默认设置为 52.0%，说明任务确实需要多个协调的 Agent；Table 4 的设计消融显示每个组件都承重——去掉非对称角色 54.3%→45.7%，轮数上限从 50 砍到 10 只剩 37.1%，随机化出生点影响最小（51.4%）。
- **移除后的变化论文报告了**，但有一点值得注意：**跌幅最大的是"去掉任务文档"（54.3%→29.4%）**。作者的解读是此时瓶颈从协作转移到信息搜集与时间压力（§4.4），这恰好提示：基准对"文档被正确提供"这一信息要素高度敏感，"分数反映协作"的前提是信息供给不变（审稿人判断）。

**创新点 2：CCE（Causal Collaboration Effectiveness）。**

- **新增了什么机制**：把一条轨迹里所有 Agent 的全部工具调用与 chat 消息建成**因果动作图**（Causal Action Graph，DAG，因果只能由前面的轮流向后面的轮次），从"直接完成目标的成功动作"出发做类 BFS 的反向追踪，累积出贡献集 $\mathcal{C}$，CCE 即贡献动作占比：

$$\mathcal{C}=\mathcal{S}\cup\mathrm{ancestors}(\mathcal{S})$$

$$\mathrm{CCE}=\frac{|\mathcal{C}|}{|\mathcal{T}|}$$

  其中 $\mathcal{T}$ 为全部动作集合，任务完全失败时定义 CCE $=0$（§3.5、Eq. 1–2、§F.1）。另有逐 Agent 的 PAC：

$$\mathrm{PAC}_i=\frac{|\mathcal{C}\cap\mathcal{T}_i|}{|\mathcal{T}_i|}$$

  用于暴露"某个 Agent 独自撑起高分"的伪协作（Eq. 3、§F.1.4）。
- **与最接近的方法差在哪**：相对 LLM-as-judge 的整体打分，本文把 judge 的任务降级为**二元因果判断**（"捕虾是否为后续转交虾的必要前提"），作者主张这比"给协作打 1–5 分"更客观、且更换 judge 模型版本时更稳定（§3.5）。
- **属于哪类创新**：**指标设计创新**——把"协作质量"操作化为动作级因果贡献比例，算法上是图遍历与 LLM 判定的组合。
- **如何对应前面的问题**：SR 只能回答"做没做到"，CCE 回答"多少努力真的有用"。
- **有效性证据**：人类一致性——从 2 个模型、11 道题的轨迹中抽 84 个动作级判断，人类标注与 GPT-4.1 judge 原始一致 82%（69/84），Cohen's $\kappa=0.64$，而两个 judge 模型之间的一致性也才 $\kappa=0.66$（7,298 个判断），即"人机分歧"与"机机分歧"同量级（§4.3）；judge 稳健性——用 GPT-4.1、Claude Sonnet 4、Llama-4 Maverick 三个不同家族的 judge 重算，四个 Agent 模型的排序完全不变，绝对值漂移不超过约 0.05（Table 6）；条件在成功任务上，CCE 提供了 SR 之外的信息（Claude 0.653 > Gemini 0.609 > GPT-5 0.571，§4.3）。

**创新点 3（较弱，属结果与资源贡献）：实证发现与开源。** 四个前沿模型的失败模式分析（§4.5、Table 5）与开源整套沙盒、任务定义、verifier、评测脚本、标注平台（§1 第四条 contribution）。这不是方法创新，但在"为社区提供可复用的评测基础设施"这一意义上是实质产出。

**什么不算创新（对照规范逐条核对）。**

- 单纯使用更大的基础模型：不适用，本文无训练、无模型改动。
- 更换数据集或评测指标：SR、PSR 是常规指标；augmented 变体由 Claude Opus 4.5 生成、只改目标数量/出生点/初始物品，属数据构造而非方法贡献（§3.4 脚注 3、附录 D）。
- 未解释作用的模块堆叠：13 个工具、回合制、非对称角色均有基线或消融对照（Table 3、Table 4），不属此列。
- 作者声称"首次提出"但未充分比较：论文全文没有使用"first"式措辞；**至于它是否构成"首次"，根据本文的 related work 与实验对比只能确认作者声称的差异，完整判断还需要更广泛的文献检索**（审稿人判断）。

## 3. 作者如何解决？

**直觉先行。** 本文要测的不是"会不会干活"，而是"会不会一起干活"。作者的做法可以类比成一次"实验室化的团队任务"：把受试者放进一个有真实资源依赖链的世界（伐木→制杖、采矿→熔炼→锻造），给他们一套"点一下就自动完成"的粗粒度操作按钮，让他们只能通过语言互相喊话——然后把"团队最终有没有把东西做出来"（SR）与"团队总共按了多少下按钮、其中多少下真的推动了成功"（CCE）分别记下来。前者的直觉是"操作被抽象掉之后，剩下的难度主要来自协调"；后者的直觉是"如果一个动作既没直接达成目标、也没有为后续任何达成目标的动作提供资源、位置或信息，它就是无效功"。

**（i）世界与抽象层（输入侧）。** 底座是开源 MMORPG 引擎 Kaetram：1056×768 的 2D 世界、9 种 biome、380+ 物品、144 种怪物（1 级到 250+）、70+ NPC、跨 8 种技能（lumberjacking、mining、fishing、foraging、crafting、smithing、fletching、cooking）共 1,531 个可采集资源点（§3.1）。关键设计是自建抽象层，暴露 **13 个高层 API 工具**（move、attack、harvest、craft、transfer、chat 等），把多步游戏机制压成单次函数调用；作者给出的理由很明确：让 Agent 的决策预算花在"做什么、和谁协调"上，而不是"怎么执行"（§3.1）。每回合 Agent 还会收到 (1) 附近地块、实体与自身状态的结构化文本观测，以及 (2) 任务特定文档（相关配方、怪物属性、资源位置）（§3.1）。

![AgentWorld 总览](/images/dailypaper/2026-09-28/2609.31590_fig1.png)

*原文 Figure 2，AgentWorld 总览。左侧 Game Environment 是带多种 biome 与资源的 MMORPG 沙盒；中间 Blackbox Multi-Agent Interaction 显示各 Agent 独立决策、只能看到自身状态与聊天消息，协调必须经由 chat 与 trade 这类显式动作；右侧列出 13 个工具中的 10 个代表性高层 API（move_character、attack_entity、craft_item、equip_item、sleep、chat、harvest_resource、transfer_items、enter_portal、complete），每个工具对应一类被抽象掉的多步游戏机制。该图解释了本文"复杂世界 + 高层抽象 + 黑盒通信"三件套如何把操作难度从分数里剥离。*

**（ii）回合制与黑盒协议（流程控制）。** Kaetram 原本实时运行，作者把它改成回合制以保证可复现：每一轮中所有 Agent 按固定顺序依次收到新观测、选择**恰好一个** API 工具调用、等动作结算后再轮到下一个（round-robin，§3.1）。这一步由环境固定实现，模型只决定"调哪个工具、传什么参数、发什么消息"。所有实验采用 blackbox 设置：Agent 拿不到其他 Agent 的内部状态、观测与动作历史，只能依赖经环境转发的显式 chat 消息（§3.1）。四个被测模型共用同一套 system/user prompt 与工具定义（附录 E）：system prompt 要求"每次响应必须且只能调用一个工具"并注入当前观测与聊天历史；user prompt 用 Jinja2 模板注入任务名、目标、次要目标、相关游戏知识、队伍成员名单（附录 E.1–E.2）。

**（iii）任务与标注。** 每道题由五要素构成（§3.2，示例见 Figure 3）。设计硬约束是"任何单 Agent 都不可能独占所需技能与资源"（§3.2）。作者举了几道真实任务：Task 67（Resource Caravan）要求 8 个 Agent 跨三种 biome，队长协调森林里的两支伐木队、山区矿工与接收两路材料的工匠；跨度从 Task 1（3 Agent 制作链）、Task 80（10 Agent 节日准备、并行烹饪与锻造）到 Task 100（16 Agent 全图大陆勘察）（§3.2）。标注由 5 名人类标注员按预设类别分布完成：定义互补角色、设定主目标与中间检查点、编写检查终局游戏状态的 Python verifier（可选检查轨迹）、为每个 Agent 整理任务相关文档；每道题用两个 LLM 做 pilot 试跑，把失败分为 system/task/agent 三类，反复修订到只剩 agent 错误才收录；轮数预算（25–55 轮）就是从 pilot 中"成功完成需要多少轮"校准来的（§3.3）。附录 C 介绍了配套的网页标注平台（Figure 6）：点选出生点的世界地图、8 项技能的滑杆、133 个物品的可搜索浏览器、带角色预览的装备槽。

![Task 86 的任务定义示例](/images/dailypaper/2026-09-28/2609.31590_fig2.png)

*原文 Figure 3（Task 86: Forge Vanguard）。目标为"挖 10 铁矿、8 煤，熔炼 6 铁锭，锻造 2 把重剑和 1 把斧"；10 个 Agent 沿 mine → smelt → craft 流水线分工（miner_1–3、smelter、smith_1–2、support_1–3、coordinator），每人有独立的技能等级、装备与初始库存。该图说明"非对称角色 + 资源依赖链"如何把多 Agent 协作变成硬性需求：任何单个角色的技能与库存都不足以独立完成目标。*

**（iv）augmented 变体。** 除 100 道人工题外，作者用 Claude Opus 4.5 按人工题的结构生成 100 道变体，变化集中在目标数量、出生点与初始物品（§3.4 脚注 3、附录 D）；人工抽检 10%（覆盖 gathering、construction、combat、crafting），报告 100% 保持多 Agent 协作需求、100% 保持目标语义、100% 保持角色非对称，90% 难度合适（附录 D）。

**（v）度量与判定流程（输出侧）。** SR 由每题自带的 Python verifier 检查终局状态（背包物品数、击杀数、存活情况等），全部检查点满足才算成功；PSR 是各检查点达成比例的跨任务平均，成功任务按 100% 计（§3.5）。CCE 的判定是离线流程（§F.2）：先让 LLM 从轨迹里挑出"最后直接完成目标的成功动作" $\mathcal{S}$，再从后往前逐轮询问"这一轮哪些动作因果上促成了已确定的贡献动作"，是则加边并入集，直至收敛；最后按上式算 CCE 与 PAC。判定用两条 prompt（附录 F.3），模型是 GPT-4.1、温度 0。为把 $O(|\mathcal{T}|^{2})$ 的配对查询降下来，作者用了三类优化：按资源类型/位置/通信通道做相关性剪枝、把多条因果查询批进一次调用、以及时间窗限制（§F.2）。设计约定：每个工具调用或 chat 消息各算一个动作、不做合并；所有贡献动作等权、与到成功节点的距离无关；chat 消息是"一等公民"动作（§F.1.2）。

**（vi）一次评测实际发生什么（按运行顺序）。**

1. **输入**：一道任务的 YAML（目标、各 Agent 的出生点/技能/装备/库存、轮数预算、任务文档）与 verifier 脚本；所有 Agent 收到同一份任务描述与自己那部分文档（附录 B、E）。
2. **循环**：环境按回合制轮询每个 Agent；模型收到观测 + 聊天历史，返回恰好一次工具调用；环境结算动作并把 chat 广播出去；直到预算耗尽或任务终止。
3. **判定**：verifier 读出终局状态给 SR/PSR；CCE 流程另起一次离线分析给 CCE/PAC。
4. **谁做主**：工具选择、参数、消息内容由模型决定；回合顺序、动作结算、观测生成、判定规则全部由环境固定。
5. **是否训练**：全程 training-free，没有任何模型训练或微调（§4.1）。
6. **输出**：SR、PSR、CCE、PAC 以及完整的动作/消息轨迹（作者把 6 条代表性轨迹可视化在 Figure 7–12）。

**（vii）瓶颈与开销。** 单题的模型调用量约为"Agent 数 × 轮数"，最大档位是 20 Agent × 55 轮；实测 Gemini 在主集上平均 26.4 轮、11.0 条消息，而 GPT-5 Mini 平均 131.3 个动作（§4.2、Table 2）。此外每题还要额外跑一遍 CCE 判定流程，其调用量与费用论文未报告（§F.2 只给了优化手段）。

**（viii）以 Task 01 为例看 CCE 怎么算。** Figure 5 展示三人（Lumberjack、Woodworker、Wizard）合作魔法法杖：Lumberjack 在第 2 轮把 logs 转给 Woodworker、第 4 轮转给 Wizard，Woodworker 用 logs 做 stick 再转给 Wizard，Wizard 最后 craft 出 staff。这条 27 个动作的轨迹里只有 12 个位于通向成功动作的因果路径上（含跨 Agent 的因果边），其余动作（图中以灰色虚线标出，如多次 sleep）不在任何因果路径上，于是 CCE = 12/27 = 44.4%（§3.5、Figure 5 图注）。这个例子的教学价值在于：CCE 的判据是"某动作是否为后续贡献动作提供了资源/位置/信息"，是二元判断而非印象分；同时作者采取**宽松纳入策略**（稍有帮助就算贡献），因此 CCE 应被读作真实有用动作比例的**上界**（§F.1.2、§4.3）。

## 4. 解决得怎么样？

### 4.1 实验设置

- **任务与数据**：100 道人工标注主任务 + 100 道 LLM augmented 变体，覆盖 8 个类别（combat、crafting、gathering、trading、exploration、survival、construction、coordination，§1），3–20 个 Agent，轮数预算 25–55、平均 38（§3.4、Figure 4）。
- **被测系统**：四个主模型 Gemini 3 Flash、Claude Haiku 4.5、GPT-5 Mini、DeepSeek R1-70B；Table 2 另列 Muse-Glimmer-30B 与 Gemma 4 26B A4B†（†表示暂定值）（§4.1、Table 2）。
- **公平性控制**：所有模型使用完全相同的 system prompt、user prompt 模板与 API 工具定义，同一回合制黑盒协议，每题每回合一次工具调用（§4.1、附录 E）。
- **基线（Table 3，均以 Gemini 3 Flash 为底模）**：random actions（无 LLM）、single-agent（所有角色与物品给一个 Agent）、no-communication（禁用 chat 与消息工具）、shared-plan-no-communication（先给一份人类写的共享计划再各自执行，不许沟通）、oracle communication（一个 Agent 能看到所有消息并统筹）。其作用是校准难度，并把"原始 LLM 能力"与"多 Agent 编排"分离开（§4.4）。
- **设计消融（Table 4，35 题子集）**：去掉非对称角色信息、把轮数预算从 50 砍到 10、随机化出生点、移除任务文档，四项分别回答"哪些设计组件是承重的"。
- **稳健性与机制实验**：Gemini 3 Flash 三次重复（温度 0.7，种子 42/819/314）回答运行间方差（§4.4）；三个 judge 模型重算 CCE（Table 6）回答指标稳健性；人类一致性研究回答"二元因果判断是否 well-posed"（§4.3）；沟通失败模式聚类回答"错在哪里"（§4.5、Table 5）。
- **每个实验各回答什么**：主实验给能力上限；基线给难度刻度与"任务是否真的需要协作"；消融给设计组件的作用；方差给稳定性（作者自己限定了结论强度）；judge 实验给指标可信度。

### 4.2 关键结果

**主表（Table 2，主集 100 题）。** Gemini 3 Flash 以 52.0% SR / 71.5% PSR / CCE 0.320 领先，其后是 Claude Haiku 4.5（45.0% / 62.7% / 0.294）、GPT-5 Mini（36.0% / 62.6% / 0.206）、DeepSeek R1-70B（20.0% / 43.5% / 0.125）。PSR 全线高于 SR，作者据此指出模型能开始协作、但在后段协调上失败（§5）。行为差异显著：Gemini 平均轮数最少（26.4），DeepSeek 发消息最少（7.5 条/Task），GPT-5 Mini 动作最多（131.3 次）且消息最多（44.1 条）（§4.2）。

**提升小、没有提升或方向相反之处（同样重要）。**

- **augmented 集全线下跌**，且量级很大：Gemini 52.0→24.0%、Claude 45.0→26.0%、GPT-5 36.0→21.0%、DeepSeek 20.0→10.0%（Table 2、§4.2）。更值得注意的是，Gemini 在变体集上的 CCE 只有 0.113，低于 Claude 的 0.179 与 GPT-5 的 0.145——**主集上的"最强模型"在变体集上并非最强**，说明结论对任务分布敏感。
- **oracle communication 只把 SR 从 52.0% 提到 60.0%**（Table 3）：沟通质量确实是瓶颈之一，但即使把沟通的协调问题几乎消掉，仍有 40% 失败，作者据此认为长程规划与资源分配存在内生难度（§4.4）。
- **shared-plan-no-communication（17.6%）比 no-communication（22.9%）更差**（Table 3）：给一份人类写好的固定计划反而拖累成绩，作者的解释是不能随执行修正的计划会在假设失效时把 Agent 卡死在依赖他人的步骤上，因此计划的价值依附于执行中修订它的能力（§4.4）。
- **条件在成功任务上，效率排序与 CCE 排序不同**：Claude 每任务效率最高（0.653），高于 Gemini（0.609），GPT-5 最低（0.571）（§4.3）。也就是说"谁成功得多"和"谁成功时浪费得少"是两个问题。
- **Table 2 附加模型带来一个未被讨论的对比**：Muse-Glimmer-30B 在 augmented 集上是 36.0% SR，高于 Gemini 的 24.0%；Gemma 4 26B A4B† 为 30.6%。但表注称这两个模型使用"100-task augmented v1 split"、Gemma 为暂定值，而表中同时给出 Main Set 与 Augmented Set 两列——两栏与"v1 split"如何对应，论文没有进一步说明，因此**这个反超不能作为可靠结论**（当前材料无法确认）。
- **方差与显著性**：三次重复的 SR 都是 54.3%（样本标准差 0.0），轮数标准差 2.07、聊天数标准差 0.18；作者明确声明"三次、单模型的分析不足以证明跨模型的稳定性或模型间差异的统计显著性"（§4.4）。换句话说，**Table 2 中 45.0% 与 36.0% 这类差距是否稳定，论文没有提供证据**。
- **平均掩盖差异**：类别间通过率差别极大。按 §4.2 的分模型区间，survival 最易（50–100%），coordination（0–50%）、construction（0–60%）与 trading（8–46%）最难；按 §3.4 的跨模型平均，survival 67–100%，coordination 12%、construction 20%。但 Figure 4(d) 实际画出的 7 个类别里，最低的两项是 Others（25%）与 Trading（21%），并没有出现 coordination 与 construction——文本与图在这一处对不上（§3.4、§4.2、Figure 4）。
- **"27% 的任务没有任何模型解出"** 只在 §5 结论中出现一句话，未给出表格或明细（论文未报告进一步拆分）。

### 4.3 机制证据

**哪些只是"方法有效"。** Table 2 主结果、Table 3 基线对比回答的是"分数是多少""任务难不难"，属于效果证据。

**哪些在解释"为什么"。**

- Table 4 消融是本文最接近机制的证据：去掉非对称角色、缩短视界、去掉文档都掉分（54.3→45.7 / 37.1 / 29.4），说明这些组件确实在影响成绩；作者据此论证设计目标"把协作能力从偶然难度源里隔离出来"（§4.4）。但**消融证明的是"组件影响分数"，不是"分数主要由协作能力决定"**——去掉文档的跌幅最大，作者自己解释为瓶颈转移到信息搜集与时间压力（§4.4），这反过来说明：一旦信息供给变化，测到的就不再是协作。
- oracle communication 是一条较干净的干预（Table 3）：它把信息可见性提高后成绩提升 8 个百分点，说明"沟通不充分"是可识别的一类瓶颈；但残余 40% 失败说明还有别的瓶颈，作者归因于长程规划与资源分配，**这一归因没有进一步的实验分离**（审稿人判断）。
- CCE 的可信度证据属于"为什么这个指标可以被相信"：人类一致性 $\kappa=0.64$（84 个判断）与两个 judge 模型之间的 $\kappa=0.66$（7,298 个判断）同量级（§4.3）；三族 judge 下模型排序完全不变、绝对值漂移不超过约 0.05（Table 6）。作者据此主张"把 judge 降级为二元因果判断"比整体打分更可复现——这是本文证据链中较强的一环。
- 沟通失败模式（Table 5、§4.5）：Gemini 轨迹中 61 条沟通错误被分为六类，最多的是 Stale & Redundant（23 条，37.7%），其后为 Misidentification（10 条，16.4%）、Factual Error（9 条，14.8%）、Premature Completion（7 条，11.5%）、Non-Material Output（7 条，11.5%）、Logical Inconsistency（5 条，8.2%）。作者推测根因是"对其他 Agent 状态的理解或预测不准"，这是**解释性主张而非因果证明**；且论文未报告总共检查了多少条消息、这 61 条如何被挑出（分母与抽样方式未报告）。

**替代解释能否被排除。**

- "沟通量与成功率无关/存在最优区间"（§4.2）：只有 4 个模型的观测相关性，未控制模型能力、任务类别、动作预算，**不能排除混杂**。
- CCE 的高低是否部分来自"轨迹长度或动作粒度"：论文把每个工具调用与 chat 各算一个动作、不加权，也未做粒度敏感性分析（论文未报告）。
- 分数是否主要反映协作而非信息要素：Table 4 的文档消融提示相反方向的风险，基准对此未做进一步隔离。

### 4.4 成本与适用范围

**代价（论文实际报告的部分）。**

- **训练成本**：无。本文是纯评测工作，不涉及任何训练（§4.1）。
- **人工与数据**：5 名标注员出题、逐题编写 verifier 与任务文档、每题用两个 LLM 做 pilot 校验、augmented 变体 10% 人工抽检（§3.3、附录 D）；**标注工时与开支论文未报告**（致谢提到标注者按当地标准获得报酬）。
- **评测推理量**：每题每回合每 Agent 一次调用，单题上限 20 Agent × 55 轮；实测平均动作数从 Gemini 的较少到 GPT-5 Mini 的 131.3 次/题（§4.2、Table 2）；200 题 × 6 个模型的总调用量与费用**论文未报告**。
- **指标开销**：CCE 需要对每条轨迹额外做 LLM 判定（GPT-4.1、温度 0），算法层面有剪枝/批处理/时间窗三项优化（§F.2），但**实际调用量与费用未报告**。
- **依赖**：开源引擎 Kaetram + 自建抽象层；CCE 判定依赖闭源模型（主 judge 为 GPT-4.1，稳健性实验另用 Claude Sonnet 4 与 Llama-4 Maverick）；被测对象为 4 个主模型加 2 个附加模型的 API。
- **系统复杂度**：模拟器宣称支持最多 1,000 个并发 Agent（§1），但评测时的实际并发与墙钟耗时论文未报告。

**改善了什么。** "协作能力"从一句口号变成了可运行的装置：任务可判定（verifier）、操作被抽象（13 个 API）、沟通被强制（黑盒 + chat 通道）、"多少努力有用"变成可复算的比率（CCE），且整套沙盒、任务、verifier 与标注平台开源（§1）。

**仍未解决。** oracle 沟通下仍 40% 失败；27% 的任务无任何模型解出（§5）；CCE 是上界估计；失败任务 CCE 记 0 使总体 CCE 混合了成功率与效率（作者用"条件于成功任务"的分析部分缓解）；沟通失败分析与"最优沟通区间"都停留在观测层面。

**结论适用于什么范围。** 只在以下边界内成立：本文的 100 道主任务与 100 道变体、给定的 prompt 与工具定义、单次运行、黑盒 round-robin 协议、4 个（+2 个）被评测模型。**不能直接外推到经过训练或微调的协作系统、其他任务分布或其他环境**——论文没有做这类实验。

## 5. 最容易受到审稿人质疑的地方

#### 质疑 1：CCE 的判定仍由 LLM 完成且采用宽松纳入策略，指标是"上界"，绝对值比较的证据不足

- **原文依据**：§3.5 与 §F.1.2（loose inclusion policy：稍有帮助即计为贡献）、§4.3（作者自述 CCE 最好读作真实有用动作比例的上界）、§F.3（判定 prompt 交给 GPT-4.1、温度 0）；人类一致性研究的规模只有 84 个动作级判断、来自 2 个模型在 11 道题上的轨迹（§4.3）。
- **为什么重要**：CCE 是本文第二号贡献，"不到 1/3 的动作有贡献""0.294 vs 0.320"这类说法都建立在它的数值意义上；如果纳入策略系统性偏松，绝对值的可比性会被削弱，而这些数字最容易在引用中被当成精确事实。
- **当前能够得出的判断**：排序层面的证据较强（三族 judge 下模型排序完全一致，漂移不超过约 0.05，Table 6）；但"上界有多松"、以及 84 个判断是否足以支撑"well-posed"，当前材料无法确认。另一个结构性问题是失败任务 CCE 记 0，使总体 CCE 主要由 SR 驱动，CCE 的独立信息只在条件于成功任务时才显现（§4.3）。
- **如何验证或补强**：报告 judge 调用总量、解析失败率与每条轨迹的判定成本；在一个子集上做人工全量标注，估计上界与真值的差距；对动作粒度（如把 chat 与工具调用分开计数）与"等权"假设做敏感性分析；对失败任务给出非零的效率定义或明确声明只在成功任务上比较。
- **严重程度**：主要问题。

#### 质疑 2："沟通量存在最优区间"等结论只是 4 个模型的观测相关性，没有控制变量

- **原文依据**：§4.2（GPT-5 Mini 消息最多 44.1 条却排第三、DeepSeek 消息最少 7.5 条垫底、Gemini 中等沟通 11.0 条最优；失败任务上 GPT-5 Mini 把 26% 的动作用于聊天；DeepSeek 平均拖到第 5 轮才发第一条消息，其他模型是第 1–2 轮），§4.5 与 Table 5（37.7% 的错误是过时与冗余信息）。
- **为什么重要**：这是摘要与结论中传播度最高的发现之一，直接影响"应该给 Agent 加多少沟通"这类实践判断；若混杂了模型能力、任务类别与动作预算，就不应表述成规律。
- **当前能够得出的判断**：论文用的是 "suggest" 级措辞，属合理推测而非已证结论；唯一接近受控干预的是 oracle communication（Table 3），但它改变的是信息可见性而不是沟通数量，不能替代"沟通量"的因果实验。
- **如何验证或补强**：在同一模型上做沟通预算/沟通策略的受控干预（限制消息长度、强制或禁止某类消息、固定行动数只改沟通频率）；跨更多模型与任务做回归，控制任务类别、Agent 数、总动作数。
- **严重程度**：主要问题。

#### 质疑 3：主实验缺少统计稳定性与推理配置披露，模型间排名是否可复现无法确认

- **原文依据**：§4.1 只说明"相同 prompt、相同协议"，未报告采样温度、top-p 等推理超参；§4.4 的重复实验只有 Gemini 3 Flash、只在 35 题子集、3 次运行，作者本人声明这不足以确立跨模型稳定性或模型差异的统计显著性；Table 2 每题只有单次运行，没有置信区间。
- **为什么重要**：论文的核心讯息是模型排序（52.0 > 45.0 > 36.0 > 20.0）与"最好的模型也只有 52.0%"，而 5–9 个百分点的差距在无方差信息时无法判断是否落在噪声内。
- **当前能够得出的判断**：模型间差距的方向（前沿模型普遍过半失败）证据较稳；但成对差距的显著性证据不足，这是论文自己承认的局限，结论表述应加限定。
- **如何验证或补强**：多温度/多种子重复并报告均值与置信区间；补报推理超参；对关键成对比较做检验（如配对 bootstrap）。
- **严重程度**：主要问题。

#### 质疑 4："把协作能力从操作能力中隔离出来"是设计主张，缺少直接验证；影响最大的组件反而是任务文档

- **原文依据**：§3.1 的设计目标、§4.4 消融（去掉文档 54.3%→29.4%，作者解读为瓶颈从协作转移到信息搜集与时间压力）、Table 1 的能力清单对比（没有同一模型跨基准的对照实验）。
- **为什么重要**：这决定读者能否把 SR/CCE 解读为"协作能力"；如果分数对文档的存在与质量高度敏感，那么跨团队、跨版本的分数就不完全可比。
- **当前能够得出的判断**：部分支持——single-agent 28.6% 对多 Agent 52.0% 说明协作是必需的，去非对称角色、缩短视界也掉分；但"分数主要反映协作"没有被直接测量，论文未报告文档长度/质量/呈现方式的敏感性实验，也没有与已有基准的对照。
- **如何验证或补强**：把文档消融细分（配方、怪物属性、资源位置分别移除）；报告文档长度与格式；在同一批模型上补一个已有基准的对照；设计"操作难度受控、协作结构变化"的任务对来直接分离两个因素。
- **严重程度**：主要问题。

#### 质疑 5：基准描述与图表存在若干不一致，影响表述准确性与复现

- **原文依据**：(a) 摘要与 Table 1 写作 "50+ rounds"/"Task Horizon 50+"，而 §3.3、§3.4 与 Figure 4(c) 明确是 25–55 轮、平均 38 轮；(b) §1 与 §3.4 声称任务覆盖 8 个类别，§3.4 还把 coordination 12%、construction 20% 的通过率归给 Figure 4d，但 Figure 4 的 (a)(d) 两个面板都只列出 7 个类别（Combat、Crafting、Gathering、Trading、Exploration、Others、Survival），(d) 中最低两项是 Others 25% 与 Trading 21%，图中没有 construction/coordination，也没有 12%/20% 这两个数；(c) Table 2 表注称两个附加模型使用"100-task augmented v1 split"，但表中同时给出 Main Set 与 Augmented Set 两列，Gemma 一行为暂定值，协议对应关系未说明；(d) Table 5 只报告 61 条沟通错误的分布，未报告被检查消息总数、抽样方式与是否只统计 Gemini。
- **为什么重要**：影响读者对基准规模、类别构成与难度分布的准确理解；(b) 会让"哪类任务最难"这一结论无法核对，(c)(d) 直接影响可复现性；这类不一致在评审中通常会被要求逐条澄清。
- **当前能够得出的判断**：属文本/图表层面的不一致与披露不足，不否定主要结论（主表数字与 §4.2 正文核对一致，Figure 4 的 (a)(d) 读数与本地保存的 arXiv 官方 SVG 资产一致），但需要修订澄清。
- **如何验证或补强**：统一视界表述；在图 4(a)(d) 中明确 8 类或说明 Others 的构成（coordination 与 construction 是否被并入）；补充附加模型的评测协议；补充 Table 5 的抽样与分母。
- **严重程度**：次要问题。

## 6. 审稿式总评

> 作者发现已有的多 Agent 评测视界太短、把低层操作与协作混为一谈、且缺乏客观的协作度量，因此提出 AgentWorld：在开源 MMORPG 沙盒上用 13 个高层 API 抽象操作、用回合制黑盒协议强制自然语言协调，配 100 道人工标注任务（另 100 道 LLM 变体）与 Python verifier，并新提出基于因果动作图的 CCE 指标。实验在四个前沿模型、200 道任务、统一 prompt 与黑盒协议下表明，最好的 Gemini 3 Flash 也只有 52.0% SR、CCE 0.320，oracle 沟通仅把成绩提到 60.0%，沟通失败以"过时与冗余"为主；其中"任务确实需要多 Agent 协作"（single-agent 28.6% 对 52.0%）与"CCE 的排序对 judge 选择稳健、并与人类判断同量级一致"这两处证据较强，但"沟通量存在最优区间""文档与长视界是承重墙"仍缺少充分支持——它们分别是 4 个模型上的观测相关性与单模型子集消融，且主实验没有方差、置信区间与显著性检验。本文最有价值的部分是它把一个含糊的口号（"协作能力"）做成了可运行、可判定、指标可复算的评测装置，并给出了清晰的负面结果；最大的审稿风险是核心指标 CCE 的绝对数值依赖 LLM 判定与宽松纳入策略（自认是上界），以及基准"隔离协作能力"这一主张缺少直接的验证实验。

- **问题定义清晰度**：强。三条问题（视界短、操作与协作混淆、缺少可判定任务与客观度量）在 §1、§2、§3.1、§3.5 逐条给出论证与 Table 1 对照，边界明确。
- **创新性证据**：中。组合式创新（长视界 + 黑盒 + 非对称 + 开放世界）与指标设计都有说服力，Table 3/Table 4 支持组件承重；但沙盒底座是既有引擎，变体数据由现成 LLM 生成，"是否首次"无法从本文确认，且缺少跨基准对照。
- **方法可信度**：中。协议统一、prompt 与任务全部开源、判定 prompt 公开，工程可信度高；扣分点在 CCE 的 LLM 判定与宽松策略、以及"隔离协作"缺少直接验证。
- **实验支持力度**：中。主表 + 5 个基线 + 4 项消融 + judge 稳健性 + 人类一致性覆盖面不窄，但单次运行、无显著性检验、消融只在 35 题子集与单模型上做，部分解释性结论只到相关性。
- **可复现性**：中。任务、verifier、prompt、标注平台开源，且 CCE 判定 prompt 与算法完整给出（附录 F）；但主实验的推理超参未报告、附加模型协议含糊、CCE 判定的调用量与费用未报告。
- **综合阅读价值**：高。对做 Agent 评测、多 Agent 系统或长程任务的研究者，这是一份设计取向清晰、负面结果明确、且工具链可复用的基准论文。
