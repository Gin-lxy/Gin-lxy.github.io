## 1. 作者发现了什么问题？

**背景。** LLM Agent 正从单轮推理走向自主工具使用与多步执行，许多真实任务（软件开发、科研、复杂运营）需要多个各有所长的 Agent 朝一个共同目标协调行动，即 multi-agent collaboration (MAC)。作者认为，要理解当前模型的强项与短板，必须有一套能把"协作能力"单独测出来的评测（§1）。

**已有 benchmark 具体哪里不好。** 作者在 §1 和 §2 把已有工作的问题归为三点，并在 Table 1 中逐项对比：

1. **任务视界太短。** 多数已有 benchmark 的任务只有 10 步左右（Table 1 中已有工作普遍在 20 步以内），不足以考察"持续协调"——多轮之后计划是否走样、状态是否同步，都测不出来。
2. **把底层操作控制与协作混在一起。** Minecraft 类环境要求 Agent 做精确的 3D 导航、放方块、管背包，这些操作能力会显著影响得分，稀释了"协作"本身对分数的贡献；而在 Overcooked、狼人杀这类接口干净的环境里，世界又太简单，撑不起多样、长程的协作任务（§3.1）。
3. **大规模社会模拟测的不是任务。** Project Sid、Agent Society 一类系统关注涌现的社会行为，而不是有明确目标、可用程序化 verifier 判定的具体任务（§1、§2）。

Table 1 还指出，已有平台大多**不同时具备**黑盒交互（Agent 看不到彼此内部状态）与非对称角色（各 Agent 技能、装备、目标不同），而作者认为这两点恰恰是真实协作的前提。

**一个被忽略的度量问题。** 即使任务本身设计得当，用 task success rate (SR) 单一指标也测不出协作质量：一个任务可能"一个 Agent 把活全干完、其他人闲着"却依然算成功（§3.5）。为此已有工作引入 LLM-as-judge 整体打分（如"给协作打 1–5 分"），但作者指出这类主观评分会随 judge 模型版本更新而漂移，无法复现（§3.5、§4.3）。

**核心判断。** 作者认为问题的根源是评测环境没有把"协作难度"与"操作难度、任务提示充分性"分离开，以及缺少客观的协作度量。因此他们选定"中间地带"（§3.1）的设计目标：世界要复杂到能支撑多样的长程协作场景，同时用高层 API 把低层操作抽象掉，让分数主要反映联合规划与协调决策；再配一个只用 LLM 做**二元因果判断**的图结构指标，把"多少动作真正推动了成功"量出来（§1、§3.5）。

**本文的新观察**（来自其自建基准上的实验，详见第 3 节），在论文摘要与 §5 中概括为：最强模型也只有 52.0% 成功率、CCE 仅 0.320（不到 1/3 的动作有因果贡献）、沟通数量与成功率不相关、以及沟通失败可归为六类模式。这些是作者通过本文基准**新测出来的经验事实**，而不是他们预先持有的假设。

## 2. 作者如何解决？

**核心思路。** 论文的产出不是新模型，而是一套**评测基准 + 度量指标**（training-free，全文不涉及任何模型训练）：选一个足够复杂、自带经济与技能系统的 MMORPG 世界（Kaetram 引擎，§3.1）；在其上盖一层高层 API，把寻路、战斗、采集等操作压缩成单次函数调用，使 Agent 的决策预算花在"做什么、和谁协调"上；用回合制、黑盒、非对称角色的协议强制 Agent 只能通过自然语言聊天来协调；再让人工标注出"单 Agent 不可能完成"的任务（§3.2–§3.3）；最后用任务自带的 Python verifier 给出硬性成功判定，用基于因果动作图的 CCE 给出协作质量（§3.5）。这样，前面的三个问题分别对应：长视界任务（25–55 轮）解决"协调测不深"，API 抽象解决"操作稀释协作"，CCE 解决"SR 测不出协作质量"。

下面按一次评测实际运行的过程展开。

**（i）沙盒世界与高层 API 抽象。** 世界基于开源 MMORPG 引擎 Kaetram：1056×768 的 2D 地图、9 种 biome、380+ 物品、144 种怪物（1 级到 250+）、70+ NPC、跨 8 种技能（lumberjacking、mining、fishing、foraging、crafting、smithing、fletching、cooking）共 1,531 个可采集资源点；模拟器可支撑最多 1,000 个并发 Agent（§1、§3.1、Table 1）。关键设计是自建的抽象层，暴露 **13 个高层 API 工具**，例如 `move`、`attack`、`harvest`、`craft`、`transfer`、`chat`：一次 `attack_entity` 调用在内部完成"寻路到目标 → 发起攻击 → 打完 → 拾取战利品"的全过程，`harvest_resource` 同理完成"走到资源点 → 采集 → 收进背包"（§3.1）。每个回合 Agent 还会收到 (1) 附近地块、实体与自身状态的结构化文本观测，以及 (2) 任务特定文档（相关配方、怪物属性、资源位置），后者正是消融实验中影响最大的组件（见第 3 节）。

![AgentWorld 总览](/images/dailypaper/2026-09-28/2609.31590_fig1.png)

*原文图 2，AgentWorld 总览。左侧是带多种 biome 与资源的 MMORPG 沙盒世界（Game Environment）；中间是黑盒多智能体交互（Blackbox Multi-Agent Interaction）：各 Agent 独立决策，只能看到自身状态、附近实体与聊天消息，协作只能靠 chat 与 trade 这类显式动作；右侧列出 13 个工具中 10 个代表性高层 API（move_character、attack_entity、craft_item、equip_item、sleep、chat、harvest_resource、transfer_items、enter_portal、complete）。该图说明本文"以复杂世界 + 高层抽象 + 黑盒通信"三件套来隔离协作能力的整体设计。*

**（ii）回合制编排与黑盒协议。** Kaetram 原本是实时游戏，作者把它改成**回合制**以保证可复现：每一轮中所有 Agent 按固定顺序依次收到新观测、选择恰好一个 API 工具调用、等待动作结算后再轮到下一个（round-robin，§3.1）。这一协议由环境固定实现（流程控制），模型只决定"调哪个工具、传什么参数、发什么消息"。所有实验都采用 blackbox 设置：Agent 拿不到其它 Agent 的内部状态、观测或动作历史，协调只能依赖经由环境转发的显式 chat 消息（§3.1）。所有被测模型共用同一套 system/user prompt 与工具定义（附录 E；system prompt 要求"每次响应必须且只能调用一个工具"，并附带当前观测与聊天历史；user prompt 用 Jinja2 模板注入任务名、目标、次要目标、相关游戏知识、队伍成员名单）。

**（iii）任务设计。** 每个任务由五要素构成（§3.2）：需要多 Agent 协作的主目标（如"为巫师制作魔法法杖"）；带**非对称角色**（不同技能、装备、库存、出生点）的 Agent 配置；限定交互轮数的轮数预算；任务特定文档；以及判定的 Python 函数。设计硬约束是"任何单 Agent 都不可能凭一己之力完成"。举几个论文中的真实任务：Task 67（Resource Caravan）要求 8 个 Agent 横跨三种 biome——队长指挥森林里的两支伐木队、山区的矿工，以及接收两路材料打造镐子的工匠；跨度为 Task 1（3 Agent 制作链）、Task 80（10 Agent 节日准备、并行烹饪与锻造）到 Task 100（16 Agent 全图大陆勘察）。

![Task 86 任务定义示例](/images/dailypaper/2026-09-28/2609.31590_fig2.png)

*原文图 3（Task 86: Forge Vanguard 的任务定义示例）。目标为"挖 10 铁矿、8 煤，熔炼 6 铁锭，锻造 2 把重剑和 1 把斧"；10 个 Agent 按 mine → smelt → craft 流水线分工：3 名 miner 采矿采煤、1 名 smelter 炼铁锭、2 名 smith 打剑、3 名 support 与 1 名 coordinator 做支援与协调，每人有独立的技能等级、装备、初始库存与出生坐标。该图说明"非对称角色 + 资源依赖链"如何把多 Agent 协作变成硬性需求。*

**（iv）标注与质量控制。** 5 名人类标注员按预设类别分布出题：定义互补角色、设定主目标与中间检查点、编写检查终局游戏状态的 Python verifier（可选检查轨迹）、为每个 Agent 整理任务相关文档（§3.3）。每道题都要用两个 LLM 做 pilot 试跑，把失败分为 system/task/agent 三类错误，反复修订直到只剩 agent 错误才收录；轮数预算（25–55 轮）也是从 pilot 中"成功完成需要多少轮"校准出来的（§3.3）。附录 C 介绍了配套的网页标注平台（Figure 6）：点击世界地图选出生点、8 项技能的滑杆、133 个物品的可搜索浏览器、带角色预览的装备配置。除 100 道人工题外，作者还用 Claude Opus 4.5 生成 100 道 augmented 变体（改目标数量、出生点、初始物品），并做了人工抽检（§3.4、附录 D，见第 3 节）。

**（v）度量：SR / PSR / CCE。** SR 由每题的 Python verifier 检查终局状态（如背包物品数、击杀数、存活情况）判定，全部检查点满足才算成功；PSR 是各检查点达成比例的跨任务平均，成功任务按 100% 计（§3.5）。而本文的核心新指标 **CCE（Causal Collaboration Effectiveness）** 想回答"多少动作真正有用"：把一次任务轨迹里所有 Agent 的所有动作（工具调用与 chat 消息各算一个动作）建成**因果动作图**（Causal Action Graph，DAG，边 $x \to y$ 表示"动作 $x$ 是 $y$ 的因果前提"，因果只能从前面的轮流向后面的轮次），先从轨迹与结果中找出直接完成目标的**成功动作** $\mathcal{S}$，再以类 BFS 的方式逐轮回扫，让 LLM 判断"这一轮里哪些动作因果上促成了已经确定的贡献动作"，累积出贡献集合 $\mathcal{C}$（§3.5、附录 F）：

$$\mathcal{C}=\mathcal{S}\cup\mathrm{ancestors}(\mathcal{S}),\qquad \mathrm{CCE}=\frac{|\mathcal{C}|}{|\mathcal{T}|}$$

其中 $\mathcal{T}$ 是全部动作集合；任务完全失败时定义 $\text{CCE}=0$。另有逐 Agent 的 PAC 指标：

$$\mathrm{PAC}_i=\frac{|\mathcal{C}\cap\mathcal{T}_i|}{|\mathcal{T}_i|}$$

用来暴露"高 CCE 其实由少数 Agent 撑起"的伪协作（§F.1.4）。反向追踪的具体算法见 §F.2：识别成功动作 → 初始化 $\mathcal{C}\leftarrow\mathcal{S}$ → 对前沿中的每个动作 $y$，对时间上不晚于它的每个 $x$ 询问 LLM"$x$ 是否因果上促成 $y$"，是则加边并把 $x$ 入集；为把 $O(|\mathcal{T}|^2)$ 的配对查询降下来，作者用三类优化：按资源类型/位置/通信通道做相关性剪枝、把多条因果查询批进一次 LLM 调用、以及时间窗限制（§F.2）。判定用的是两个提示词（附录 F.3，GPT-4.1、温度 0）：第一步只挑"最后直接完成目标的动作"，第二步逐轮问"哪些动作因果上 enable 了已知贡献动作"。

**为什么这样设计可能有效——以 Task 01 为例（教学简化）。** 图 5 展示了 CCE 在 Task 01（三人合作魔法法杖）上的计算：Lumberjack 在第 2 轮把 logs 转给 Woodworker、第 4 轮转给 Wizard，Woodworker 用 logs 做 stick 再转给 Wizard，Wizard 最后 craft 出 staff 完成目标。在由 27 个动作组成的轨迹里，只有 12 个位于通向成功动作的因果路径上（含跨 Agent 的紫色因果边），其余为"sleep"之类的无效动作，于是 CCE = 12/27 = 44.4%（§3.5、Figure 5）。这个例子的意义在于：CCE 只看"某动作是否为后续贡献动作提供了资源/位置/信息"，判据客观、二元，因此比"给协作整体打 1–5 分"更可复现；且作者采用宽松纳入策略（稍有帮助就算贡献），使 CCE 更应被读作真实有效动作比例的**上界**（§4.3、§F.1.2）。

![CCE 在 Task 01 上的计算示意](/images/dailypaper/2026-09-28/2609.31590_fig4.svg)

*原文图 5（Task 01 上的 CCE 示意）。横轴为回合 R1–R6，三行分别是 Lumberjack、Woodworker、Wizard；彩色实心节点是位于因果路径上的贡献动作，灰色虚线节点不贡献，紫色箭头是跨 Agent 的因果边（如 R2、R4 的 logs 传递，以及 sticks 由 Woodworker 转给 Wizard）；该任务 CCE = 12/27 = 44.4%。该图说明 CCE 如何把"协作"具体化为可追踪的跨 Agent 因果链。*

## 3. 解决得怎么样？

**实验条件。** 四个前沿模型——Gemini 3 Flash、Claude Haiku 4.5、GPT-5 Mini、DeepSeek R1-70B——在 100 道人工主任务与 100 道 augmented 变体上评测；所有模型使用完全相同的 system prompt、user prompt 模板与 API 工具定义，黑盒协议，报告 SR、PSR、CCE（§4.1）。Table 2 另附两个补充模型（Muse-Glimmer-30B、Gemma 4 26B A4B†），其说明指出它们使用 100 题 augmented v1 split 评测、Gemma 的结果为暂定值。

**主结果（Table 2）。** 主集上 Gemini 3 Flash 以 52.0% SR 领先，其后是 Claude Haiku 4.5（45.0%）、GPT-5 Mini（36.0%）、DeepSeek R1-70B（20.0%）；PSR 普遍高于 SR（43.5%–71.5%），CCE 从 0.125（DeepSeek）到 0.320（Gemini）。行为差异显著：Gemini 平均轮数最少（26.4），DeepSeek 发消息最少（7.5 条），GPT-5 Mini 动作最多（131.3 次）、消息最多（44.1 条）。augmented 集上全线下跌（Gemini 52→24%、Claude 45→26%、GPT-5 36→21%、DeepSeek 20→10%）。

**作者据此提炼的三个发现（§4.2–§4.3、§5）。** 其一，**沟通多不等于协作好**：聊天最多的 GPT-5 Mini（44.1 条）只排第三，且它在失败任务上把 26% 的动作花在聊天上；沟通最少、且平均拖到第 5 轮才发第一条消息的 DeepSeek 垫底（其它模型第 1–2 轮就开口），像是错过了早期协调窗口；Gemini 沟通中等（11.0 条）却成绩最好——作者推断存在"够用即可、别挤占行动"的最优沟通区间。其二，**绝大多数动作是无效功**：即便最好的 Gemini 也只有不到 1/3 的动作在因果路径上（CCE 0.320），DeepSeek 近 88% 的动作被浪费；不过条件在**成功任务**上看，Claude 的每任务效率最高（0.653，Gemini 0.609，GPT-5 0.571），即"Claude 成功时浪费更少"（§4.3）。其三，**难度按类别分化**：按 Figure 4(d) 的跨模型平均通过率，survival 最易（67–100%），coordination（平均 12%）与 construction（平均 20%）最难，反映紧耦合的多 Agent 同步与博弈式协商最难做（§3.4；§4.2 给出的分模型区间一致，如 coordination 0–50%）。

**基线、消融与稳健性是否支撑作者的解释（§4.4）。** Table 3 的基线以 Gemini 3 Flash 为底模：随机动作 5.7% SR，单 Agent（把所有角色和物品塞给一个 Agent）28.6%，完全禁言 22.9%，而"给一份人类写好的共享计划但不许沟通"反而降到 17.6%——比不许沟通还差，作者的解释是：不能随执行修正的计划会在假设失效时卡死，说明**计划的价值依附于执行中修订它的能力**；oracle communication（一个 Agent 能看到所有消息来统筹）把成绩从 52.0% 提到 60.0%，证明沟通质量确实是瓶颈之一，但**即便有 oracle 沟通仍有 40% 失败**，说明长程规划与资源分配本身内生的难度不可忽视（§4.4）。设计组件消融（Table 4，35 题子集）显示每个设计都起作用：完整配置 54.3%，去掉非对称角色 45.7%，轮数上限从 50 砍到 10 只剩 37.1%，随机化出生点影响最小（51.4%），而拿掉任务文档掉到 29.4%——作者解读为文档与长视界是"承重墙"：缺了它们，瓶颈会从协作转移到信息搜集与时间压力上，这与基准"隔离协作能力"的设计目标一致（§4.4）。三次重复（温度 0.7，种子 42/819/314）在主测试的子集上 SR 都是 54.3%（样本标准差 0.0），轮数标准差 2.07、聊天数标准差 0.18；作者自己声明：这一三次、单模型的分析不足以证明跨模型的稳定性或模型间差异的统计显著性（§4.4）——这一点值得注意，说明模型间的排名差异没有被论文做显著性检验。

**CCE 这个度量本身可信吗（§4.3、附录 A）。** 这是本文少数"用证据解释机制"而非仅报分数的地方，作者给了三条证据：(1) 与人类一致性——在 11 道任务、两个模型轨迹中抽样 84 个动作级判断，人类标注与 GPT-4.1 judge 的原始一致率 82%（69/84），Cohen's $\kappa = 0.64$（"substantial"），而两个 judge 模型之间的一致性也才 $\kappa=0.66$（7,298 个判断，84% 原始一致）——即"人—机分歧"与"机—机分歧"同量级，说明二元因果判断是**well-posed** 的，不是某个模型的artifact；(2) 换 judge 稳健——用 GPT-4.1、Claude Sonnet 4、Llama-4 Maverick 三个不同家族的 judge 重算 CCE，四个被测模型的**排序完全不变**，绝对值漂移不超过约 0.05（Table 6）；(3) CCE 与 SR 的关系——整体排名大体跟随 SR（因为失败任务 CCE 记 0），但条件在成功任务上能看到 SR 之外的差别（如 Claude 效率反超）——作者据此认为 CCE "adds nuance"（§4.3）。沟通失败的分析（§4.5、Table 5）把 Gemini 轨迹中 61 条错误信息分为六类，最多的是"Stale & Redundant"（37.7%，引用已完成的任务、重复已知状态），其次是角色指认错误（16.4%）与事实错误（14.8%），作者推测根因是**对其他 Agent 状态的理解或预测不准**。

**代价与未解决的问题。** 成本方面：本文无训练开销（纯评测），主要代价是 (a) 人工：5 名标注员出题、每题的 verifier 脚本与文档、双 LLM pilot 校验、augmented 变体的人工抽检；(b) 评测时每题都要跑 CCE 的 LLM 判定的多次调用（附录 F.2 虽给出剪枝/批处理/时间窗三项优化，但论文未报告判定的实际调用量或费用，属未报告信息）；(c) 更强的模型未必更"高效"——高 SR 与高动作数并存（GPT-5 Mini 主集 131.3 个动作）。未解决的问题包括：oracle 沟通下仍 40% 失败、27% 的任务所有模型都解不出、最好的模型 CCE 也仅 0.320（§5）；CCE 在失败任务上定义为 0，使总体 CCE 混合了成功率与效率，作者用"条件于成功任务"的补充分析部分缓解；宽松的纳入政策使 CCE 只是**上界**估计；augmented 任务由 LLM 生成、仅抽 10% 人工验证（附录 D 报告抽检中 100% 保持协作需求/目标语义/角色非对称，90% 难度适当）；此外结论只覆盖 4 个（+2 个补充）前沿模型在黑盒协议下的表现，**不能直接外推到训练过的 Agent 系统或其它环境**——论文未做此类实验。

**总评。** "结果显示有效"与"证据解释机制"需要分开看：基线/消融显示基准确实能区分单 Agent、无沟通等设置（Table 3、4），这说明评测设计达到了"逼出协作"的目的；CCE 的可复现性主张有人类一致性与三 judge 实验的直接支持，属于**证据支持机制**；而"文档与长视界承重""沟通多不等于好"更接近作者的合理解读，消融与相关性分析支持但不充分证明其因果机制。

**收尾。** 作者发现已有多 Agent 评测普遍视界短、把低层操作与协作混为一谈、且用单一成功率甚至主观打分度量协作，因此提出 AgentWorld：以 MMORPG 沙盒 + 13 个高层 API 抽象操作、以回合制黑盒协议强制自然语言协调、以人工标注的 3–20 Agent 非对称长程任务构成基准，并用因果动作图指标 CCE 量化"多少动作真正有贡献"；实验表明即使最强的 Gemini 3 Flash 也只有 52.0% 成功率、CCE 0.320，沟通数量与成功率不相关，主要失败模式是状态过时与角色混乱，且 oracle 沟通下仍有 40% 失败——说明长程多 Agent 协作在当下仍是基础模型的一个系统性缺口，而该基准对更难 augmented 变体、LLM judge 判定成本与跨模型显著性检验的覆盖仍有边界。
