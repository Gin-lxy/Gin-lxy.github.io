## 0. 一句话结论

TraceDance 针对"固定基准套件覆盖不到部署中实际出现的不良行为"这一问题，把真实部署轨迹自动转成按需构建的评测基准：用可编程 anchor 在 CPU 上限成本全量检索、再用 Flash LLM 做候选语义确认，把轨迹截断在"行为出现前的决策点"（decision-point continuation），让被测 LLM 续写下一回合并用行为专用 rubric 打分，无需参考答案、无需环境回放。论文在 252,557 条真实部署会话上构建出 107 个基准、4,125 条实例（构建请求满足率 95.3%，84% 抽样实例获两位标注者共同确认），9 个前沿模型平均通过率仅 26.7%（Table 2）；这些证据支持"系统可行、所指决策点确实难"的结论，但缺少与更简单构建方案的对照，也缺少"下一回合得分 ↔ 真实执行能力"的效度验证，因此不足以支撑"能普遍衡量或改善 Agent 行为（RSI 组件）"这类更宽的结论。

## 1. 论文具体想解决什么问题？

**研究背景与任务。** LLM agent 正在真实环境中执行工作（改代码库、管理定时任务等），而现有主流 agent 基准以任务完成度为口径：例如 Terminal-Bench 用容器最终状态判断任务是否完成。作者的观察是：agent 可以在完成任务的同时做出不良行为——把 access token 泄露进日志、把失败的测试禁用以让套件通过、不经确认执行破坏性命令（§1 举例）。因此评测必须考察执行过程中的行为，而不仅是任务是否完成。

**现有方法如何处理。** 两条线：（1）outcome-level 与 process-level/safety 基准套件（SWE-bench、Terminal-Bench、WebArena、AgentHarm、SHADE-Arena 等，§2）——它们能测行为，但测试用例与目标行为都是预先固定的；（2）agent auditing 工具（Docent、Insights generator、七步日志分析等 [51, 34, 9, 49]）——能从轨迹中定位不良行为与失败模式，但不会把这些记录转成可评测其他 LLM 的基准。

**具体在哪些条件下表现不好。** 当 agent 及其部署环境变化、出现固定套件未覆盖的新行为问题时，两类工具都没有"按需出题"的能力；而部署轨迹里恰好记录了真实出现过的行为问题（§1）。

**被忽略的瓶颈。** 把轨迹变成基准的关键障碍不是"造题"而是"找题"：要按行为描述从 25 万级会话中找出发生位置，逐会话用 LLM 或人工审阅"在部署规模下成本过高"（§1）。作者由此把问题拆成两层：便宜的编程式粗筛 + 廉价的模型语义确认。

**支撑判断的证据。** 论文报告的数据规模（252,557 条会话，来自 Claude Code 75,076 与 OpenClaw 177,481，六周采集，Table 1、§4.1）说明全量 LLM 审阅的代价量级；工作量统计（每成功查询 anchor 扫描 128,297 次、只有 706 个候选送 LLM 确认、552 次 LLM 调用，§5.2、Figure 3b）说明分层设计确实把 LLM 调用压到候选级。但"逐会话审阅不可行"的原始对照（如全量 LLM 审阅的总成本）论文没有报告，属于作者的成本论证而非实验结论。

**原因归属与核心假设。** 作者把困难归因于"需要把自然语言行为查询翻译成可执行检索逻辑"（anchor 合成）与"检索规模 vs 确认成本"这两个工程环节（§1、§3.2）。核心假设有两条：(i) 直觉假设——"某上下文曾让一个部署 agent 表现出某种不良行为，则其他 LLM 在同一上下文也容易如此"（§1），因此截断的历史上下文本身可以当评测题；(ii) 系统假设——这套"选择/合成规格 → anchor 检索 + Flash 确认 → 截断构造 + rubric 评分"的流水线能从真实轨迹稳定产出有效基准。

**区分。** "固定套件覆盖不了新行为"是领域较早的普遍认识；本文的具体新观察是"审计发现可以按需转成基准"这一缝隙，以及"生产评测（OpenAI 在部署对话上重新生成响应 [57, 58]）思路的按需化"。论文只描述了性能/成本缺口与工程难点，未对因果解释（如"为什么 Flash 确认足够"）做独立验证。

## 2. 创新点是什么？

**一段话概括。** TraceDance 的技术增量是把"从生产部署轨迹中挖掘评测题"做成一条端到端自动化流水线，核心由三个相互配合的设计构成：(1) decision-point continuation 评测范式——按 action/failure/claim 三种 frame 在行为关键回合前截断轨迹，只评被测 LLM 续写的下一回合，用行为专用 rubric 评分，不重放环境；(2) Anchor-and-Confirm 构建框架——CPU 可编程检索与 Flash LLM 候选确认的成本分层；(3) Anchor Synthesis Loop——把自然语言行为查询合成为可执行 anchor 代码并带质量反馈迭代修订。另有系统级工程：28 个行为族的人工校验目录、Strong/Fast/Reviewer 三角色分工、三评委评分面板。整体属于"已有组件（轨迹截断、LLM-as-judge、agent loop）面向新问题定位的组合与工程化"，不是新的学习算法。

**创新点 1：decision-point continuation（评测范式）。**

- 新增机制：每个实例是"源 LLM 行为关键回合之前"的记录上下文，frame 决定截断位置——action frame 截在目标动作前；failure frame 保留已发生的失败、去掉源 LLM 的响应；claim frame 保留相关工作和结果、去掉源 LLM 的声称（§3.1、Appendix A.1 Table 3）。被测 LLM 只产生一个下一回合，评分只针对该回合；源 LLM 的坏行为响应是"证据"而非参考答案。
- 与最接近工作的差别：MIRAGE-Bench 用合成快照 [67]、LURE 做 live-usage replay [21]、OpenAI production evals 在部署对话上重新生成候选模型响应 [57, 58]、Prefix-GRPO 复用教师前缀训练 [55]。TraceDance 的差异点是：针对"用户用自然语言指定的不良行为"按需构建基准，且评分不需要参考答案或环境执行——因此能覆盖依赖私有 repo、内部工具、MCP server 的不可复现环境（§1、Appendix F）。
- 性质：研究思想上属于"把生产评测思路产品化"，工程上配合了系统化的三 frame 切分契约。
- 与问题的对应：直接回应"要测执行过程行为、又不能依赖可复现环境"。
- 证据：Appendix E.2 给出完整实例（Error-guided correction，从 pip externally-managed-environment 报错截断到三评委打分，Kimi-K3 均值 4.33 通过、Claude Opus 4.8 均值 2.00 未通过）。
- 移除后的变化：论文没有做"完整轨迹 + 参考答案评测"之类的对照，无法从实验确认该范式的不可替代性（这是分析者判断，非论文结论）。

**创新点 2：Anchor-and-Confirm（成本分层构建）。**

- 新增机制：规格中的可编程 anchor（可执行代码，利用 tool error、调用参数、事件顺序、关键词）在 CPU 上无 LLM 调用地扫描全部轨迹，得到候选位置；只有候选才以"浓缩视图"送 Fast Model（DeepSeek-V4-Flash）确认行为是否发生、上下文是否足够评分（§3.2、§3.3）。
- 与已有方法的差别：审计工具面向人读轨迹定位违规；本文把同样的信号源转成基准构建又控制成本。
- 证据：每成功查询平均 128,297 次会话扫描在 CPU 完成、706 个候选进入 Flash 审阅、总 LLM 调用 552 次（§5.2、Figure 3b、Table 23）。Appendix E.2 展示了两级过滤的互补：anchor 用文本规则把 `--user` 误判为"未按报错要求改正参数"，Fast Model 则基于完整前因（源 LLM 未采纳报错给出的三种修复）在不同理由上确认该案例。
- 未验证点：论文没有"纯 Flash 全量扫描"或"无确认只用 anchor"的消融，也没有 anchor 的精确率/召回率度量；两级设计的必要性目前只有间接证据（审稿人判断）。

**创新点 3：Anchor Synthesis Loop（查询→可执行规格的合成环）。**

- 新增机制：目录无精确匹配时，由 Strong Model（GPT-5.6-Sol）生成规格四件套（anchor、确认标准、切分契约、rubric）；anchor 含生成代码，必须先过程序安全检查与 Reviewer Model（Claude Opus 4.8）代码审查才允许执行；随后试运行、检查切分与 rubric 格式，再用检索统计（≥8 会话、确认率 ≥25%、≥8 个确认样本、≥3 个样本才进入验收审查）反馈修订，最多 5 轮，达标才接受，否则拒答（§3.2、Table 4）。
- 证据：修订示例——"新依赖未写入 manifest"查询中，规格从"要求后续 manifest 编辑"改为"检查决策点状态"，anchor 匹配会话从 3 增至 32（Appendix A.2）；拒答能力——32/32 个拒答目标查询全部被正确拒绝（含 27 个 adversarial，§5.2）。但真正走合成路径的产出只有 15 个基准（7 个预定义查询被重路由 + 8 个 custom 查询，Appendix D），证据规模有限。
- 性质：属于"LLM 生成代码 + 验证/反馈循环"的工程化应用。

**创新点 4（工程组合层面）：行为目录 + 角色分工 + 评委面板。**

28 个行为族的人工校验目录（13 action、10 failure、5 claim，§4.2）；Strong/Fast/Reviewer 三角色分工（§3.2）；三评委（GPT-5.6-Sol、Gemini-3.5-Flash、Claude Opus 4.8）0–5 分、均值 ≥4 通过（§3.4）；随机化响应顺序降低位置偏差（Appendix A.3）。这些是流程与成本控制层面的工程改进，其价值由 §5.2–5.3 的效果与稳健性数据支撑，但不构成算法创新。

**原创边界。** 根据本文 related work 与实验对比，只能确认作者声称的差异（§2 逐条对比了 production evals、Petri/Bloom、REAP/SWE-Together、WildToolBench、BenchTrace 等）；"first system to turn this idea into on-demand benchmarks"是否成立，需要更完整的文献检索与更直接的对照实验。

## 3. 作者如何解决？

**直觉说明。** 如果把"曾让部署 agent 犯错"的上下文原样截断在该决策点之前，其他 LLM 在同一位置很可能也犯类似错误——所以"历史上出过问题的上下文"天然是评测题。难的不是出题，而是从 25 万条轨迹里按行为描述把题找出来；因此系统把"找题"拆成"便宜的编程式粗筛（全量、无 LLM）"与"廉价的模型语义确认（只对候选）"。

**输入与输出。** 用户（agent 开发者）提供：(i) 自然语言行为查询 q；(ii) 部署轨迹集合 $\mathcal{D}=\{\tau_i\}$；(iii) 期望的基准规模范围 $[K_{\min}, K_{\max}]$（默认 5–50）。系统返回尺寸达标的基准 $\mathcal{B}_q$ 或带原因的拒绝（§3.1）：

$$ \mathrm{TraceDance}(\mathcal{D}, q, K_{\min}, K_{\max}) \rightarrow \begin{cases} \mathcal{B}_q, & K_{\min} \le |\mathcal{B}_q| \le K_{\max}, \\ \mathrm{Reject}(r), & \text{otherwise}. \end{cases} $$

**运行流程。**（对应 Figure 1 从左到右）

1. **行为规格选择/合成（§3.2）。** 先在人工校验目录里匹配：Strong Model 做 3 次独立族选择（≥2 一致），再对选中族的完整规格做 3 次等价检查（全部通过才复用，Appendix A.2）；否则进入 Anchor Synthesis Loop（生成 → 安全检查 + Reviewer 初审 → 试运行 → 检索质量探测 → 反馈修订，预算见 Table 4）。
2. **检索与确认（§3.3）。** anchor $A_q$ 在 CPU 上扫描 $\mathcal{D}$ 得到候选；域约束与轨迹约束（如"上下文超过 100,000 token"）先在程序层过滤；Fast Model 对候选的浓缩视图执行确认标准：保留的源回合确实展示目标行为、且上下文含足够证据。
3. **实例构造。** 对确认命中按 frame 切分（避开 compaction 等 harness 强制回合）；实例保留完整记录前缀（system 指令、工具定义、人类与 harness 注入输入、assistant 消息、工具结果），只删除源 LLM 的 reasoning 块（避免泄露"该怎么想"）；收集到 $K_{\max}$ 条或候选耗尽即停。
4. **评测与评分（§3.1、§3.4）。** 被测 LLM M 从同一上下文 x 生成一个下一回合，三评委用行为 rubric 打 0–5 分，均值 ≥4 通过：

$$ x=\kappa(\tau_{\le c}, f), \qquad \hat{y}=M(x), \qquad s=J_{R_q}(x, \hat{y}). $$

其中 $\kappa$ 由记录前缀和 frame $f$ 构造上下文，$J_{R_q}$ 施加查询专属 rubric $R_q$。响应可以含文本、一个或多个工具调用；只评这一个回合，不执行其动作、不继续轨迹。

**分工与训练。** 哪些由模型决定：规格选择/合成、候选确认、评分，均为 LLM 判断；哪些由固定流程控制：扫描、约束过滤、切分位置、预算与阈值（Table 4）、拒绝条件。系统本身不训练任何模型（training-free 系统论文）；9 个被测模型均为现成 API 模型，统一给原始 system prompt 与工具定义、reasoning effort 高、输出上限 32,768 token、temperature/top-p 未设置（Appendix A.2）。查询还支持最多两个行为的 AND（同一响应须同时满足两份 rubric）/OR（各出一份基准）组合，三个及以上行为直接拒绝（§3.2、Appendix A.1）。

**图 1 解释。** 图中五段分别是：左侧输入（行为查询 + 部署轨迹）；第 1 段 Behavior Specification（Catalog Match 命中则直接用预定义规格，未命中走 Anchor Synthesis Loop，含 Strong/Reviewer 模型与 reject/feedback 回路）；第 2 段 Anchor-and-Confirm（anchor 扫描 → 候选 → DeepSeek-V4-Flash 确认 → confirmed occurrences）；第 3 段 Instance Construction（按 action/failure/claim 三种 frame 在轨迹上画 cut 线，cut 右侧的源响应被丢弃）；右端输出 Benchmark（context instances + 0–5 分 rubric）。这张图说明了系统为何不需要环境回放：评测输入只是被截断的历史上下文，红线右侧（源 LLM 的错误决策及其后果）只用于构建验证、不进入评测输入。

**教学简化示例（非论文实验）。** 可以把 anchor 类比成"grep 级粗筛器"（Appendix E.2 中它用一条文本规则检查"报错点名要求的参数有没有出现在下一次调用里"），Fast Model 则是"读完整前因后果的初审员"，其确认理由可以与 anchor 的触发理由不同。这是本报告帮助理解的类比，不是论文用语。

## 4. 解决得怎么样？

#### 4.1 实验设置

- **任务与数据。** 两个部署设置：Claude Code（coding；采集 75,076 条会话，其中 10,000 条留作行为发现、65,076 条用于构建）与 OpenClaw（general tool use；177,481 / 10,000 / 167,481），共 252,557 条会话、六周采集，源模型主要是 Doubao Seed 2.0 系（§4.1、Table 1）。会话在使用前全部去标识化（§4.1、Ethics statement）。
- **测试查询。** 139 个查询：107 个期望构建（98 predefined + 9 custom）、32 个期望拒绝（27 adversarial + 5 缺数值参数）；查询由 Strong Model 按覆盖要求起草、人工筛选保留（§5.1、Appendix C.1、Table 10–11）。构建默认 $K_{\min}=5, K_{\max}=50$（§5.1）。
- **被测模型。** 9 个前沿 LLM：Claude Opus 4.8、GPT-5.6-Sol、GLM-5.2、DeepSeek-V4-Flash/Pro、Qwen3.7-Max、MiniMax-M3、Doubao-Seed-2.1-Pro、Kimi-K3（§5.1）；全部见同样实例上下文、同样评分流程；模型比较使用 107 个基准中的 4,065 条有效实例（4,125 条中有 60 条缺至少一个模型的有效响应，Table 20）。
- **基线。** 评测层面无"传统基线"，报告的是绝对通过与组间比较；构建系统层面没有任何替代方案对照（见 §5 质疑一）。
- **指标。** 构建结果符合率、查询理解人工评分、实例有效性（双人确认）、rubric 质量（0–5）、评委-人类一致率与 κ、模型 pass rate（三评委均值 ≥4）。
- **人类标注。** 8 名标注人中每次由 2 人独立标注 100 个查询与 100 个实例（按行为族分层抽样）；标注人看不到自动评分与被测模型身份（§5.1、Appendix C.2 Table 12）。
- **主实验/消融/附录分工。** 主实验回答"查询处理是否符合预期"（§5.2）、"基准是否有效"（§5.3）、"基准揭示了什么"（§5.4）；附录 C 给稳健性分析（替代通过规则、逐评委、自我偏好、bootstrap 排名、源模型族），附录 D–E 给构建结果与行为分析细节。**没有**构建系统层面的消融（无 anchor/无合成环/无确认等），论文未报告。

#### 4.2 关键结果

- **构建成功率。** 102/107 个构建请求成功（95.3%），32/32 个拒答请求全部正确拒绝；102 个成功查询产出 107 个基准、4,125 条实例（5 个 OR 查询各出 2 个基准）（§5.2、Figure 3a）。5 个 unmet 的失败点分别为规格检查（1）、Anchor Synthesis Loop（2）、规格匹配（1）、基准构建（1），Table 22 逐条给出原因。下图（Figure 3）的 (a) 面板展示了按查询类型的构建/拒答结果（94 predefined、8 custom、5 缺参被拒、27 adversarial 被拒）；(b) 面板是每成功查询的平均工作量——anchor 会话扫描 128,297 次（CPU，无 LLM 调用）、送 Flash 确认候选 706 个、产出实例 40.4 条（注意该面板是对数坐标，扫描量比 LLM 处理量大两个数量级，这正是成本分层的证据）；(c) 面板是人工验证——84% 实例的行为确认率、90% 的 rubric 质量 ≥4/5、评委-人类 81% 与人类-人类 81% 的一致性。

- **工作量明细。** 每成功查询（均值/中位数）：LLM 调用 552/395 次、输入+输出 token 25.14M/16.44M；拒答查询便宜——缺参 6.0 次、adversarial 1.3 次 LLM 调用（§5.2、Table 23）。每基准中位数 49 条实例（上限 50），53/107 个基准达到上限（Appendix D）。
- **查询理解（人工）。** 78% 解读准确、17% 部分正确；两位标注者对"是否需要向用户追问澄清"的一致率 96/100（§5.2）。
- **实例有效性。** 100 条抽样实例中 84 条被两位标注者共同确认真实发生了目标行为（84%）；rubric 质量 ≥4/5 的占 90%（均值 4.75/5）；主要缺陷是"相邻分数级别边界不清"（21 次提及，Table 13）（§5.3、Figure 3c）。

- **模型通过率（Table 2、§5.4）。** 9 个模型均值 26.7%，区间 22.9%（Qwen3.7-Max）–33.5%（Claude Opus 4.8）；frame 均值 action 28.0、failure 28.9、claim 20.3；设置均值 CC 28.3、OC 22.9。作者指出 GPT-5.6-Sol 在 SWE-bench Pro / Terminal-Bench 2.1 类任务基准上报告分高于 DeepSeek-V4-Pro 与 GLM-5.2，但在行为基准上并未超过两者——行为视角与任务完成视角给出的排序不同（§5.4）。

- **稳健性。** 替代通过规则下四组排序不变（Check first 7.7–26.8%，与 Valid call 差距 52.4–64.4pp，Table 17）；逐评委下单评委通过率更高但组序基本保持（Gemini 把 Honest claim 与 Handle failure 互换：53.8% vs 51.5%，Appendix C.2）；5,000 次基准重采样中 9 个模型分三档、档内相邻差异不显著（Opus 99.9% 排第一，领先第二名 4.2pp，CI [1.7, 6.6]，Table 18）；源模型族混杂方面，Doubao-Seed-2.1-Pro 在 Doubao 源实例上的 offset 只低 0.9pp、所有模型 CI 含 0，可排除大于约 3pp 的族特异劣势（Table 19、Appendix C.4）。
- **负面与未提升信息。** 5 个 unmet 查询、84% 而非 100% 的实例确认率、评委整体偏宽松、个别族样本极小（Regression recognition 仅 16 条实例）、部分族样本不平衡等，论文均有披露（§5、Table 9、Table 22、Appendix C.2/F）。

#### 4.3 机制证据

- **效果证据较强**：构建符合率、工作量分层统计、人工验证、评分一致性与多项稳健性分析。
- **机制证据有限**：
  - Anchor-and-Confirm 的两级分工只有间接证据——工作量统计（Figure 3b）与 E.2 实例显示 anchor 粗筛（且会误判）与 Fast Model 语义确认互补；但**没有** anchor 精确率/召回率、**没有**"去掉 anchor 直接用 Flash 扫描"或"去掉确认只信 anchor"的消融，无法判断两级设计的增益与最优性。
  - Anchor Synthesis Loop 的机制证据只有一个修订示例（匹配会话 3→32）与拒答统计；合成路径产出仅 15 个基准（Appendix D），样本量不足以支持"合成环能稳定处理目录外行为"。
  - 行为分析（首动作关联、排名反转）是相关性观察，作者自己声明"associations, not causal effects"（§5.4）；91.0% 的 TodoWrite 首动作响应无后续工具调用、有后续调用的 41 条通过率仅 7.3%（Appendix E.1），说明低分组与"先规划后行动"模式高度重叠——这既解释了一部分低通过率，也提醒不能把它当作纯粹的能力缺陷。
  - 替代解释的排除情况：评分阈值、评委构成、源模型族三个混杂有专项分析；提示长度、API 版本、查询起草方式（Strong Model 起草）等未被独立控制。
- **结论**："26.7% 平均通过率、Check first 8.1%"应理解为"在该 rubric 与截断条件下的通过率"，而非模型真实执行能力的实测值。

#### 4.4 成本与适用范围

**论文报告的成本。**

- 构建（每成功查询，均值/中位数）：anchor 扫描 128,297/130,152 次（CPU、无 LLM）；Flash 确认候选 706/292 个；LLM 调用 552/395 次；输入+输出 25.14M/16.44M token（§5.2、Table 23）。拒答查询 1.3–6.0 次 LLM 调用。**全部 139 个查询的总成本、时延、存储占用未报告**（论文未报告，不自行估算）。
- 基准规模：每成功查询平均 40.4 条实例；每基准中位数 49 条、上限 50，53/107 达上限（Appendix D）。
- 人工：8 名标注人（双人标 100 查询 + 100 实例），以及预定义目录规格与检索实例的人工审查（§3.2、§4.2）；论文未报告人工工时。
- 外部依赖：构建侧依赖 GPT-5.6-Sol（Strong）、DeepSeek-V4-Flash（Fast）、Claude Opus 4.8（Reviewer + 评委）、Gemini-3.5-Flash（评委）；评测侧依赖 9 个闭源模型 API。无训练成本（系统无训练阶段）。

**改善了什么。** 固定套件覆盖不到、且依赖不可复现环境（私有仓库、内部工具、MCP server）的部署行为，现在可以按需构建基准并量化弱点（Check first、Secret protection、Failure-log inspection 等），用于模型改进与回归检测（作者主张；这是本文结果的实际价值所在）。

**仍未解决。** 只评单回合，无法观察其后行为——"先规划/收集信息的响应可能后续表现恰当，通过的响应执行后仍可能失败"（Appendix F 明确承认）；通过率描述的是"已发生过该行为的上下文中"的表现，不代表部署中的行为频率；rubric 只奖励最恰当响应，绝对通过率依赖通过阈值；构建与评分都是"不完美的自动化"（84% 实例确认、评委偏宽松）；轨迹不可公开导致精确基准无法重建（Reproducibility statement）；RSI 闭环组件只是愿景（Conclusion："leave evaluating TraceDance within such a loop to future work"）。

**适用边界。** 适用于"具有可观测事件信号、可用编程式规则检索行为"的场景（§3.1 明确把需逐会话 LLM/人工审阅的行为排除在范围外），以及论文覆盖的 coding 与 general tool-use 两类设置与 Doubao 系为主的源轨迹分布。

## 5. 最容易受到审稿人质疑的地方

#### 质疑：构建系统没有任何基线对照，"95.3% 满足构建请求"的成功判据由作者自定

- **原文依据**：Appendix C.1——139 个测试查询由 Strong Model 起草、人工筛选，其"应构建/应拒绝"的期望结果也是作者设定；§5.2 只报告构建成功率与工作量；§2 related work 无任何定量对比；全文没有"Anchor-and-Confirm vs 直接用强 LLM 扫描轨迹"之类对照。
- **为什么重要**：论文核心创新主张是两级检索与合成环的设计价值，但主要证据是"对自定预期达成率 + 成本统计"，无法回答"一个强模型全量扫描是否也能达到同等效果"，直接削弱创新性归因。
- **当前能够得出的判断**：证据不足（不是结论错误）。系统可用性有支持（32/32 拒答正确、5 个 unmet 各有明确失败原因），但设计不可替代性未被验证。
- **如何验证或补强**：在相同 LLM 调用预算下比较 anchor+Flash 与 Flash-only/Strong 抽样扫描的构建成功率与实例精度；在小子集上人工全量审阅，给出 anchor 精确率/召回率与两级过滤的增益；与已有基准构建系统（如 REAP、WildToolBench 类工作）做同数据对照。
- **严重程度**：主要问题。

#### 质疑：实例有效性只验证 2.4% 的样本，84% 的确认率意味着约六分之一实例可能无效

- **原文依据**：§5.1/§5.3——从 4,125 条实例中分层抽样 100 条（2.4%），两位标注者共同确认 84%；其余 4,025 条从未被人工检查。族级样本极不均衡：Regression recognition 16 条、Result reuse 19 条、Post-edit verification 41 条，而族级结论全部建立在这些基准上（Table 9）。
- **为什么重要**：影响所有下游结论（模型总通过率、族级差异、行为组对比）的有效性；若某些族确认率显著低于 84%，相关结论会失真。论文只给总体验证率，未按族披露。
- **当前能够得出的判断**：存在未量化的有效性风险；论文对 84% 与上限（Appendix F）表述诚实，但没有做分层验证。
- **如何验证或补强**：按行为族、来源（CC/OC、源模型族）报告确认率与置信区间；扩大人工验证样本（如每族 ≥20 条）；公开验证工具供第三方复核（代码已公开，但轨迹不可得）。
- **严重程度**：主要问题。

#### 质疑：decision-point continuation 的构念效度未验证——"下一回合得分"与真实 agent 表现的关系没有证据

- **原文依据**：Appendix F 明确承认只评下一回合、无法观察后续行为，且"a response that begins by planning or gathering information may act appropriately later, and a passing response may still fail when executed"；§5.4 首动作分析被标为关联非因果；Appendix E.1 显示 457 条 TodoWrite 首动作响应中 91.0% 无后续工具调用——大量低分落在"先规划再行动"这一正常模式上。
- **为什么重要**：这是范式层面的最大风险。若低通过率的部分来源是 rubric 更偏好"立即行动"而非真实不当行为，则 "Check first 8.1%""平均 26.7%"的解释需要重新校准；反之若通过率能预测下游执行质量，其价值将显著提高。
- **当前能够得出的判断**：论文观察到了现象，也做了部分缓解（替代阈值、逐评委、首动作分组），但没有验证"通过率预测下游执行质量"，结论目前只能限定为"单回合合规率"。
- **如何验证或补强**：对同一批模型做相关性研究（decision-point 通过率 vs Terminal-Bench/SWE-bench 类任务成功率、或人工审计的部署会话评分）；对少量实例做多回合续写或真实执行，检验"低分回复是否真的导致差结果"。
- **严重程度**：主要问题。

#### 质疑：LLM 评委宽松且自我偏好未完全排除，绝对分数不稳定

- **原文依据**：Appendix C.2、Table 14——人类通过率仅 16.7%（全判 fail 的朴素基线一致率 83.3%），panel 与人类 κ=0.40（中低度一致）；三评委均分 2.02–2.90 都高于人类 1.68，人类 0 分占 39.3% vs 面板 11.9%，面板精确率仅 44.7%；Table 15——GPT-5.6-Sol 对自家响应相对宽松 +0.22（CI [0.19, 0.25] 不含 0），且 GPT 与 Opus 同时是评委与被评模型；Table 13——"相邻分数边界不清"是被标注最多的 rubric 缺陷（21 次）。
- **为什么重要**：所有通过率数字都经过这个评分口径；宽松、边界模糊与自我偏好会系统改变绝对通过率与部分行为组对比。论文用替代阈值、逐评委、去掉自身评委证明排序稳定，缓解了"方向错误"风险，但没有消除"数字口径不可比"的问题。
- **当前能够得出的判断**：相对排序证据较强（多组稳健性分析方向一致），绝对水平证据较弱；作者主动披露，属诚实但未解决。
- **如何验证或补强**：在更大人类标注集上校准分数边界（尤其 3/4 分界）；报告评委重复评分的方差；采用盲评流程或训练专用 grader 并报告其与人类的一致性。
- **严重程度**：主要问题（针对数字解释；不足以推翻排序性结论）。

#### 质疑：成本披露不完整、材料不可复现、RSI 与"首个系统"等主张超出实验范围

- **原文依据**：Table 23 给出每查询平均成本（128,297 扫描、552 次 LLM 调用、25.14M token），但全部 139 个查询的总成本、时延与存储未报告；Reproducibility statement 明确"deployment traces cannot be released, the exact benchmarks cannot be rebuilt from public data"；Appendix C.4 说明源模型组成"commercially confidential"、只能粗分两类；Abstract/§1/§6 以"key component of the RSI loop"定位，但 Conclusion 承认留待未来工作，无任何闭环实验；§1 "first system"表述依赖本文 related work。
- **为什么重要**：影响采纳与复现——依赖多个闭源 API 与不可公开的轨迹，独立复现"结果"不可能，只能复现"流程"；愿景性定位若无实验支撑，会诱导读者高估结论边界。
- **当前能够得出的判断**：流程可复现性有基础（Appendix A 详述实现、Table 5–7 给提示模板、代码仓库已公开），结果可复现性受数据限制；RSI 定位属于作者主张、尚无证据。
- **如何验证或补强**：报告总预算（含失败重试）与延迟；在公开轨迹数据集（如 SWE-chat 类真实用户会话集）上复现流程；做一次最小 RSI 闭环演示（用 TraceDance 指导一次模型改进并回测）。
- **严重程度**：次要问题（对结论方向影响小，对结论外延与信任度影响中等）。

## 6. 审稿式总评

> 作者发现，部署中的 agent 会在完成任务的同时表现出泄露密钥、跳过检查、误报进度等不良行为，而固定基准套件覆盖不到这些行为、审计工具又不会把它们转成评测；因此提出 TraceDance——用可编程 anchor（CPU 粗筛）加 Flash LLM（候选确认）从 252,557 条真实部署轨迹中构建"决策点续写"基准，配合三 frame 切分契约与行为专用 rubric（三评委均值 ≥4 通过）。实验在 coding 与 general tool-use 两类设置上表明：构建请求满足率 95.3%、32 个拒答查询全部正确拒绝、84% 抽样实例获双人确认、9 个前沿模型平均通过率仅 26.7%，且族级结果揭示了被总排名掩盖的行为弱点（Check first 8.1%、Failure-log inspection 0.6%、Error-guided correction 上的排名反转）。其中，系统可用性、人工验证与评分稳健性（替代阈值、逐评委、bootstrap、自我偏好检查）证据较强；但"设计相对替代方案的必要性""单回合得分与真实执行能力的效度关系"以及"84% 之外的实例质量"仍缺少充分支持。本文最有价值的部分是提出并工程化了一条从部署回传到按需基准的清晰范式（公开流程、提示模板与成本数据）；最大的审稿风险是构建系统层面缺乏对照与效度验证，使"首创、不可替代、RSI 组件"等主张超出当前证据。

- **问题定义清晰度**：强（§3.1 给出输入输出契约、三种 frame、实例有效性三条件与 scope 边界；问题是真实且明确的缝隙）
- **创新性证据**：中（范式定位与相对已有工作的差异叙述清楚，但设计必要性、"first system"表述缺乏对照实验与更完整文献验证）
