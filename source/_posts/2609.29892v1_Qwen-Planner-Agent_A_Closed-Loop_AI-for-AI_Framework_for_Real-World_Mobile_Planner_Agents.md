## 1. 作者发现了什么问题？

**背景。** 语言模型 Agent 正从"生成内容"走向"执行多步工作流"，这让一个老想法变得可操作：让 AI 不仅是被开发的对象，也参与开发下一代 AI 系统本身（§1，引 Turing 1950 与 Good 1965）。作者选择**移动端规划（mobile planning）**作为检验场景：用户一句高层目标，需要跨应用协调动作、在状态变化中维持上下文、从失败中恢复并确认结果真的达成。

**已有方法具体哪里不好。** 作者把瓶颈归为三点。第一，**真实设备交互昂贵且难以并行**，直接限制了数据生产与评估的规模（§1，§2.2.1）。第二，已有移动 Agent 工作（AppAgent、Mobile-Agent-E 等）主要在解决"如何操作界面/如何做屏幕定位"，已有移动 RL 工作（DigiRL、MobileRL、Mobile-R1、PhoneBuddy 等）主要在解决"如何训练策略"，但**数据、训练、运行时支持三者是割裂的**：运行时支撑（记忆、技能、工具暴露方式）变化后，模型的训练分布就过时了；反过来模型变强后，原有的运行时规则又不再适用（§2.5、§4.4）。第三，一个更具体的技术判断：**固定的奖励设计无法匹配能力不同的轨迹组**，而且标准的组内归一化会在成功率饱和后把小到可以忽略的效率差异放大成与"成功与否"同量级的优势信号，诱发过度的轨迹压缩（§2.4.3）。这一条是本文给出的最有技术含量的观察，并在式 (7)–(9) 中有推导。

**核心判断与提问。** 作者的问题是：如何把 AI 的能力组织成一个可扩展、由反馈驱动的开发生命周期（§1）。他们给出的答案是闭环 AI-for-AI 框架——用执行证据同时驱动数据生产、模型训练与运行时（Harness）三者的协同改进，并以一个共享的"动作—反馈—验证契约"（action–feedback–verification contract）把三者串起来。

## 2. 作者如何解决？

![AI-for-AI 生命周期](/images/dailypaper/2026-09-27/2609.29892_fig2.png)

*原文图 2，AI-for-AI 生命周期。三个阶段相互连接：AI for Data 用 AI 辅助出题 + 自动采集与清洗轨迹，并用模型反馈调整下一轮任务与数据配比；AI for Training 在冷启动之后做混合环境在线 RL，CARE 随能力演进调整奖励与优势；AI for Harness 用统一 Harness 管理 Skills、持久 Memory 与执行反馈，AI 辅助诊断又反过来指导模型与 Harness 的修订。虚线橙色箭头表示迭代之间由人工把关的闸门。*

**核心思路。** 系统由**两个可更新的对象**组成：规划模型 $\pi_\theta$（Planner Model）和运行时脚手架 $\mathcal{H}_\eta$（Harness）。形式化上（§2.1.2，式 (1)–(3)），Harness 把请求 $x$、检索到的记忆 $m_t$、加载的技能 $\mathcal{K}_t$、观测与动作历史拼成上下文 $c_t=\mathcal{H}_{\eta}(x,m_t,\mathcal{K}_t,o_{\leq t},a_{<t})$，策略从中选动作 $a_t\sim\pi_{\theta}(\cdot\mid c_t,\mathcal{A}_t)$；环境按转移与观测分布返回下一步；一个**任务专属验证器** $\mathcal{V}$ 依据交互历史与后端状态证据 $\xi_{t+1}$ 判定任务是否完成，证据本身不必暴露给策略。**关键点是验证器提供的是可执行证据，而不是模型自评**——这既是训练奖励的来源，也是后面所有"AI 驱动改进"的判断依据。

三个阶段的具体做法：

**（i）AI for Data：人把门的 agentic 数据飞轮（§2.3）。** 出题 Agent 把目标能力翻译成可执行任务规格，每份规格包含用户目标、可用资源、初始条件、目标能力、完成标准，**只规定要达到什么、不规定唯一参考轨迹**，因此同一个目标允许多种合法解法。构造时同时考虑场景覆盖（应用域、工具、意图、交互模式）与能力覆盖（信息获取、工具路由、参数落地、多步依赖、状态追踪、恢复、可验证完成）。轨迹采集在混合后端进行，**失败与未完成的轨迹同样保留**，因为诊断需要知道执行在哪里偏离、是否尝试恢复。数据清洗把"完成验证"和"适合训练"当作两件事：环境验证器管前者，清洗流程管后者（规范化、去重、schema 与证据一致性检查），低置信、冲突、涉安全或证据不足的样本转人工审核。数据集分移动与非移动两组，移动数据是核心（跨应用规划、工具执行、状态追踪、Memory、Skills、子 Agent 协调、恢复、任务完成），非移动数据（通用 Agent 轨迹走 MCP 服务、编码任务、推理与指令遵循）用于保住通用能力。反馈驱动的精修分两层：任务层把已稳定掌握的任务降采样（保留小规模保存集）、把完成不稳定的任务加权为"稳定化数据"、把特定失败模式归入定向修复集；能力层结合留出开发集的 Tool Use/Memory/Skills/Sub-agent 结果与轨迹失败分布，判断是"池子里有合适样本就调采样比"还是"覆盖不足就让出题 Agent 造新题"。

**（ii）AI for Training：能力自适应的 Agent 优化（§2.4）。** 先做面向规划的监督冷启动：在清洗后的数据上 SFT，学习任务分解、动作排序、工具使用、状态条件下的重规划与恢复；关键是**回合级错误掩码**——对轨迹 $\tau_i$，把清洗阶段判定为错误的回合索引集合记为 $\mathcal{E}_i$，最小化

$$\mathcal{L}_{\mathrm{SFT}}(\theta)=-Z^{-1}\sum_{i,j}\mathbf{1}\{j\notin\mathcal{E}_{i}\}\log\pi_{\theta}(\boldsymbol{y}_{i,j}\mid h_{i,j}),$$

其中 $Z$ 是批内未被掩码的模型生成 token 数（式 (4)）。执行反馈保留在上下文里，而被验证过的恢复回合仍然参与监督——也就是**教模型"看到报错后该怎么救"，但不学错误动作本身**。冷启动之后是混合环境在线 Agent RL（沙箱、LLM 模拟与少量真机），不依赖人工示范覆盖策略演化后才会出现的新状态。

![Planner 模型训练框架与 CARE](/images/dailypaper/2026-09-27/2609.29892_fig3.png)

*原文图 4，训练框架。左侧是 SFT 冷启动（回合级错误检测 + 掩码）与在线 Agent RL 的流水（采样 → 环境执行 → 结果验证 → CARE 更新）；左下是三类混合环境（LLM 模拟、沙箱、真机）；右侧展开 CARE：按组成功率选择三种优化目标，并在最后加一步"保质量的优势校准"。*

**CARE（Competence-Aware Reward-and-Advantage Engineering）** 是这一阶段的核心，只改奖励与优势，不改优化器结构。对每个任务采 $G$ 条轨迹，用规则验证器或评分模型给出二元成功指示 $s_i\in\{0,1\}$，组成功率 $\overline{s}$ 作为"能力信号"（§2.4.3）。它包含三件互相咬合的事：

1. **能力自适应奖励调度。** 同一批训练里允许不同组处在不同"制度"（regime）下：

$$R_{i}=s_{i}+\begin{cases}\lambda_{\mathrm{prog}}R_{\mathrm{prog},i}, & \overline{s}\in[0,p_{\mathrm{low}}) \quad\text{进度塑造}\\ 0, & \overline{s}\in[p_{\mathrm{low}},p_{\mathrm{high}}) \quad\text{结果巩固}\\ -\lambda_{\mathrm{eff}}e_{i}, & \overline{s}\in[p_{\mathrm{high}},1] \quad\text{效率精修}\end{cases}$$

其中 $R_{\mathrm{prog},i}$ 度量被验证的进度，$e_i$ 是归一化执行开销（式 (5)）。直觉是：**还做不成的任务给过程引导，半成不成的任务聚焦把结果做对，已经稳过的任务才开始惩罚啰嗦**。注意成功项 $s_i$ 始终保留，效率项是加性的惩罚而非替代。

2. **AI 辅助的调度配置。** 上述制度只决定辅助项，阈值和权重本身可以随训练演进调整。一个**有界的** LLM 控制器每 $N$ 步策略更新配置一次 $\boldsymbol{\phi}=\{\lambda_{\mathrm{prog}},\lambda_{\mathrm{eff}},p_{\mathrm{low}},p_{\mathrm{high}}\}$，输入是固定提示 $\mathcal{P}$（目标、参数语义、允许范围、输出格式）、近期 on-policy 训练统计 $\mathcal{S}^{\mathrm{train}}_{\leq t}$ 与留出开发集指标 $\mathcal{M}^{\mathrm{val}}_{\leq t}$（式 (6)）。它只在预先定义的参数空间里选值，不生成奖励函数本身。

3. **保质量的优势校准。** 这一步针对的正是 §2.4.3 指出的归一化副作用。在效率精修制度下 $R_i=s_i-\lambda_{\mathrm{eff}}e_i$，记 $\overline{R}$、$\overline{e}$ 为组内均值，标准 GRPO 式优势为

$$\widehat{A}_{i}^{\mathrm{std}}=\frac{R_{i}-\overline{R}}{\sigma_{R}+\epsilon}=\frac{(s_{i}-\overline{s})-\lambda_{\mathrm{eff}}(e_{i}-\overline{e})}{\sigma_{R}+\epsilon},\qquad \sigma_{R}^{2}=\overline{s}(1-\overline{s})+\lambda_{\mathrm{eff}}^{2}\sigma_{e}^{2}-2\lambda_{\mathrm{eff}}\operatorname{Cov}(s,e)$$

（式 (7)）。当一组全部成功（$\overline{s}\to1$，方差与协方差同时归零）时，分子分母里的 $\lambda_{\mathrm{eff}}$ 会**约掉**：

$$\lim_{\overline{s}\to 1}\widehat{A}_{i}^{\mathrm{std}}=-\frac{\lambda_{\mathrm{eff}}(e_{i}-\overline{e})}{\lambda_{\mathrm{eff}}\sigma_{e}+\epsilon}\approx-\frac{e_{i}-\overline{e}}{\sigma_{e}}$$

（式 (8)）。也就是说，即使把效率权重设成 $\lambda_{\mathrm{eff}}=0.1$ 这样的小值，饱和组里的纯效率差异依然会被拉回近似单位尺度，与"成败混杂"的组的优势同量级——作者的意图（先保成功、再谈效率）被归一化抹平了。作者不用"分量分别归一化再合并"（认为那会改变各分量在原始奖励空间中的有效权重、可能改变轨迹排序），而是**给分母加一个由成功率导出的下界**：

$$\sigma_{\mathrm{anchor}}=\sqrt{p_{\mathrm{high}}(1-p_{\mathrm{high}})},\qquad \widehat{A}_{i}=\frac{R_{i}-\overline{R}}{\max(\sigma_{R},\sigma_{\mathrm{anchor}})+\epsilon}\ \ (\text{效率精修制度})$$

其余制度仍用 $\sigma_R+\epsilon$（式 (9)）。这样在饱和组里优势尺度退化为 $\lambda_{\mathrm{eff}}\sigma_{e}/(\sigma_{\mathrm{anchor}}+\epsilon)$，**保留了对 $\lambda_{\mathrm{eff}}$ 的依赖**，效率差异不再被放大到主导梯度。最终用带裁剪的组相对目标（式 (10)）做更新（GRPO 式、无 critic；引用 Shao et al. 2024 与 Yu et al. 2026）。

**（iii）AI for Harness：模型—Harness 共演化（§2.5）。** Harness 里放的是"不该塞进参数、也不该全塞进 prompt"的东西：Scenario Adapter 把**当前实际暴露给模型的工具集**映射到对应的 Skill 指导（删掉依赖不可用工具的规则、加上路由与多轮指令，但它不发现新工具也不执行动作）；Persistent Memory Manager 把跨会话信息分层——紧凑用户模型（稳定偏好）、情节记忆（观察与对话证据）、长期记忆（合并后的事实与经验）、前瞻记忆（带激活条件、范围、过期与完成状态的未来意图），生命周期为捕获→验证→索引→检索→固化→修订，每条记忆链接结构化摘要与原始证据（**摘要质量与源保真度分开观测**，错误的摘要算"入库失败"而非静默替换），新证据推翻旧事实时显式标记 superseded 而不是留下冲突版本；检索融合语义与关键词匹配，并按相关性、时近性、重要性、多样性控制，且**按问题结构装配证据**（时间类问题要事件排序，跨会话聚合要去重，变化中的事实要显式解析替代关系）。检索到的记忆只是"证据"，不是可执行指令，也不获得调用工具的权限。共演化的形式化是

$$J(\theta,\eta)=\mathbb{E}_{x\sim\mathcal{D},\ \tau\sim p_{\theta,\eta}(\cdot\mid x)}\left[R_{x}(\tau)\right]$$

（式 (11)），当前实现用交替更新逼近（式 (12)）：$\theta^{(k+1)}=\mathcal{U}_{M}(\theta^{(k)};\mathcal{B}^{(k)},\eta^{(k)})$（在固定 Harness 指令配置下做 RL），随后在留出开发集上用同一配置评估得到反馈 $\mathcal{F}$，再由 **LLM 编辑器** $\mathcal{U}_{H}$ 修订执行指令得到 $\eta^{(k+1)}$。所有模型与 Harness 更新都是离线、版本化、经审查的，服务期参数固定，候选改动不自动上线。作者自己强调：**这是"开发路径"的论述，不等于已经实现了持续自主的共演化**（§2.5.4）。

**承上启下：这套流程对应了前面的问题。** 真机昂贵 → 用沙箱/模拟/真机三种后端分工，把可并行部分从真机上卸下来；数据、训练、运行时割裂 → 用同一份"动作—反馈—验证"记录贯穿三者，并让 Harness 修订反过来改变后续训练的上下文分布；奖励设计错配 → 用能力自适应调度；归一化抹平权重 → 用成功率锚定的优势校准。

## 3. 解决得怎么样？

**主结果（表 1、图 1）。**

![MobilePA-Bench 上的总体表现、分项能力与成本](/images/dailypaper/2026-09-27/2609.29892_fig1.png)

*原文图 1，(a) MobilePA-Bench Overall（注意纵轴自 60 起）、(b) 四项分项能力对比、(c) Overall 与每千任务输出成本的权衡（成本轴带断裂，刻度分 5–20 与 60–68 两段）。*

在 MobilePA-Bench（1,700+ 可执行任务、200+ 移动工具、13 个查询—任务域）上，Qwen-Planner-Agent 27B 的 Overall 为 **77.05%**，在被评估的模型与系统中排第一，超过 GPT 6 Astra（76.84%）与 Claude Opus 5（75.71%）；分项为 Tool Use 77.79%（该列最高）、Memory 74.76、Skills 86.25、Sub-agent 59.55。两个尺寸都相对各自基线大幅提升：27B 由 67.22% → 77.05%，35B-A3B 由 54.90% → 69.91%。作为参照，开放权重模型中 Overall 最高的是 GLM 5.3（744B-A40B，73.88%），Qwen 3.8 Max 为 71.77%。**注意两点**：其一，主表比较的是"完整系统 vs 其他模型/系统"，其中 Harness 的贡献是系统性的（见下面的配对消融）；其二，图 1 左侧子图的 Overall 柱状图纵轴从 60 起画，视觉上放大了差距，应以上表数值为准（此为该图的读图提醒，非论文结论）。

**成本（§3.1、图 1 右）。** 按每题平均输出 token（含 thinking token）与对应输出单价估算，Qwen-Planner-Agent 为 **$2.41 / 千任务**，对比其他被评估模型的 $3.06–$67.76。作者明确说明该估算**只覆盖输出 token 费用**，不含输入 token、外部工具调用、设备执行与 Harness 自身的处理开销，因此不能当作端到端成本。

**CARE 消融（§3.2.1、图 6）。**

![CARE 与优势校准的训练动态](/images/dailypaper/2026-09-27/2609.29892_fig4.png)

*原文图 6，相同训练配置下三条曲线对比。左：训练准确率；右：平均输出 token 数。蓝实线为 Vanilla RL，红实线为完整 CARE，绿虚线为去掉优势校准的 CARE（原文注：曲线为四个训练环境上的平滑均值，阴影为对应的离散范围）。标注的 32.5% 是最终共同记录步数上的输出长度降幅。*

用 27B 基座、相同训练配置比较三条曲线：完整 CARE 与 Vanilla RL 的**训练准确率相当**，但到最后一个共同记录的步数，**输出 token 少 32.5%**；去掉优势校准后输出更短，但准确率在整段区间明显更低并提前平台化。作者认为这印证了 §2.4.3 的归一化分析——小效率差异获得了不成比例的优势尺度。

**Harness 的配对贡献（§3.2.2）。** 固定 checkpoint 只加 Harness：27B 由 71.90% → 77.05%（Tool Use 72.79→77.79，Memory 70.74→74.76，Skills 79.25→86.25，Sub-agent 55.06→59.55）；35B-A3B 由 64.79% → 69.91%，但 **Sub-agent 保持 52.81% 不变**。这说明主结果里相当一部分提升来自部署期上下文而非参数更新，也说明 Harness 并非对每项能力都有效。

**模型—Harness 共演化（§3.2.3、表 2、图 7）。** 用另一个 27B 基座，在 MobilePA-Internal 与 MCPMark 上做多轮交替：MobilePA-Internal 的 Overall 由 Model Only 82.67% → Model+Harness 84.23% → 共演化四轮后 **88.50%**（Tool Use 89.76、Long Context 88.69、Personalized Planning 82.42）；MCPMark 由 38.00% → 42.26% → 三轮后 **46.98%**。两个任务的最终分数都高于"只加 Harness"的 84.23%/42.26%，即交替迭代带来了超出单次运行时增强的增益。需要留意：这里的评估集是留出的 **evolve/开发集**，作者自己说明它"用于共演化而非独立最终测试集"（§3.2.3），因此不能与表 1 的主结果混为一谈。

**长历史记忆（§3.3、表 3）。** 在 LoCoMo、LongMemEval 与 BEAM 的 100K/500K/1M/10M 四档上，比较四对"同 checkpoint、仅历史访问机制不同"的 Qwen 模型。结论是**增益集中在长档**：BEAM-500K 均值 42.18% → 68.29%，BEAM-1M 40.41% → 70.27%，BEAM-10M 23.42% → 61.66%；而 LoCoMo 93.90% → 94.12%、LongMemEval 91.65% → 92.24%、BEAM-100K 71.12% → 72.05% 基本持平，**个别配对还出现小幅回退**。具体到 Qwen-Planner-Model 27B，加 Harness 后 BEAM-500K 42.01→72.20、BEAM-1M 40.12→73.71、BEAM-10M 21.99→67.24。作为参照，直接上下文（不裁剪）的方案在 BEAM-10M 上没有一个超过 25.64%（Claude Opus 5 在 1M 档为 54.84%），外部报告的 Mem0 在 BEAM-1M/10M 为 64.10%/48.60%。另外**一个诚实的负面观察**：在直接上下文设置下，训练过的 Qwen-Planner-Model 略逊于未训练的 Qwen Baseline（如 27B 的 BEAM-100K 76.26 → 72.32，35B 的 LongMemEval 89.40 → 87.80），说明规划训练本身对"把长历史直接塞进上下文"没有帮助，Harness 才是收益来源。

**非移动泛化（§3.4、表 4）。** 只比较 Planner Model 与各自基座：35B-A3B 在 7 个 Agent 类基准中提升 6 个，均值 57.74 → 62.31（Toolathlon 29.30→37.15、MCP-Atlas 59.40→68.69、SWE-Multilingual 65.67→71.67）；27B 提升 5 个，均值 67.91 → 69.29（Claw-Eval 82.48→79.58、SWE-Multilingual 76.65→74.89 为下降项）。通用能力三项均小幅下降：35B 的 MMLU-Redux 89.67→89.53、C-Eval 90.45→90.39、IFEval 90.94→89.83（均值 90.35→89.92）；27B 为 88.73→88.67、89.74→89.30、91.68→91.13（90.05→89.70）。作者据此称"能力可外溢且通用能力基本保留"，但**下降也是真实的，幅度在 0.06–1.11 点之间（最大为 35B 的 IFEval：90.94 → 89.83），且论文没有报告方差或多种子，无法判断是否显著**（此为本报告的推断）。

**定性证据（§3.5、附录 C）。** 12 条轨迹展示了论文想强调的行为：记忆与实时状态核对（只补建缺失的广州行程监控、不动已有的深圳监控并排除过期的北京价格阈值，图 8）、先停掉活跃投屏再发起新投屏（图 9）、加载 Skill 后先取得便签持久标识再关机（图 10）、按观察到的透传模式选择分支并遵守顺序约束（图 11）、单位换算工具两次失败后改用计算器算出 154.32 磅再发消息（图 12）、等 WhatsApp 三个下载结果返回后才把文件名与目标目录交给文件管理器子会话（图 13）。这些是**说明机制如何落地的案例，不是性能证据**。

**代价与仍未解决的问题。** 论文没有给出任何训练超参、数据规模、GPU 小时或真机使用比例，因此**无法评估这套框架的算力与人力成本**（材料不完整）。每个数据发布点都有"人把门"、Harness 修订要经规则检查与版本控制，所以"闭环"目前仍以人工审核为必要环节，作者也明确表示持续自主的共演化尚未被证实（§2.5.4）。隐私与安全（§2.5.3）通篇是"应当"级别的设计建议（如用户级鉴权、最小权限、加密、可删除），当前实现只有服务级认证令牌，"用户级访问约束依赖上游服务"，**属于规划而非已验证的实现**。此外，共演化实验在开发集上评估、成本对比只算输出 token、通用能力有小幅下降——这些都需要更大范围的独立验证。结论的适用范围是：在移动规划这一任务族与上述评估集上，闭环式的数据/训练/Harness 协同确实带来增益。

作者发现真实设备交互昂贵导致移动 Agent 的开发难以规模化、且固定奖励与标准组内归一化会误配能力不同的轨迹组，因此提出 Qwen-Planner-Agent，通过"动作—反馈—验证契约"下的数据飞轮、混合环境在线 RL 与 CARE、以及模型—Harness 交替共演化把执行证据回灌到全流程，实验表明其在 MobilePA-Bench 上以 77.05% 的 Overall 居首、输出成本估算最低、长历史记忆与通用 Agent 基准均有提升，但仍缺少超参与成本披露、依赖人工审核、共演化仅在开发集上验证。
