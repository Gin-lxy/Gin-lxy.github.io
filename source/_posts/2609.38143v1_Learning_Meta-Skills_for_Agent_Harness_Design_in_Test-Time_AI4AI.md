## 0. 一句话结论

这篇论文把「为 agent 搭建执行环境（harness）」本身当作学习对象：在 Builder 与 Target 两个模型权重都冻结的前提下，让 Builder 从 Target 在开发集上的执行反馈中提炼 when/provide/use 三元组形式的元技能（meta-skill），冻结后为每个未见任务现场构造 harness。在 Harness-Bench 与 NewtonBench、三个 Target 模型的六组设置中，全量技能库相对 no-skill 构造平均提升 8.95 个百分点、相对把同一技能库直接交给 Target 提升 12.02 个百分点（Table 3）（原文事实）；证据支持「让 Builder 把经验翻译成可执行支持」在论文覆盖的两个基准、一个主 Builder、每任务单次执行内有效，但跨 Builder 迁移的全部置信区间包含 0，且论文未报告多次运行方差与 Builder 侧成本（审稿人判断）。

## 1. 论文具体想解决什么问题？

**研究背景与任务.** Agent 的表现不仅取决于推理能力，还取决于它行动所处的环境，作者以 SWE-agent 提出的 agent–computer interface 观点作为出发点（§1，引 [11]）。论文研究的是 test-time AI-for-AI（AI4AI）中的一个特定子问题：给定固定的 Builder 模型 $\mathcal{B}$（负责设计支持）和固定的 Target 模型 $\mathcal{T}$（负责解题），Builder 如何为每个公开任务输入 $x$ 构造一个增强环境 $H_x=\mathcal{H}(x)$，使 Target 在固定执行预算下取得更高的评测分数。形式化目标为最大化 $J(\mathcal{H})=\mathbb{E}_{x\sim\mathcal{D}_{\mathrm{test}},\,\tau\sim\mathcal{T}(\cdot\mid x,H_{x})}[r(x,\tau)]$，约束 $\operatorname{cost}(\tau)\leq C_{x}$；作者明确说明预算 $C_x$ 只覆盖 Target 执行，不含 Builder 构造 harness 的开销（§3，Eq. 1）（原文事实）。

**现有方法通常如何处理.** 相关工作可归为两类（§2）。一类是 test-time agent 系统设计：ADAS、AFlow 搜索 agent 程序与工作流，Darwin Gödel Machine 进化自身 agent 代码，Meta-Harness 用执行反馈搜索 harness 实现，strong-to-weak harness construction 用更强 Builder 为更弱 Target 提供可执行支持（引 [1, 15, 14, 3, 5]）。另一类是技能沉淀：Voyager 存可执行例程，ExpeL 与 Agentic Context Engineering 累积文本经验与 playbook，SkillRL 用 RL 联合进化技能与策略，Evo-Harness 把执行经验编译成可迁移的 solver 技能；元层面的 Meta Context Engineering 学习「如何构造 context 文件与代码」的技能，MetaSkill-Evolve 进化「改进任务技能」的策略（引 [7, 17, 16, 10, 9, 13, 8]）。

**作者指出的空缺.** 作者认为，上述工作要么把经验直接交给解题者（task skill），要么在实现层面搜索 harness，而「支持设计本身」很少被当作学习对象：Builder 需要的是「何时需要支持、提供什么资源」这类原则，而不是解题技巧（§1，§2）。论文的假设是：让 Builder 从自己产出的 harness 的执行结果中提炼这类原则，比直接把同样的知识交给 Target 更有用。

**支撑问题判断的证据.** 论文没有对「问题存在性」做独立的观察性研究，其证据是构造性的：在 Appendix C 给出的对照中，同一 Target（Gemini）在 Harness-Bench 上从 native 环境的 37.35 分升到 no-skill 构造的 53.29 分，再升到使用元技能的 67.81 分（Appendix C）。作者据此把「环境/支持」拆成两个可分离的贡献：构造能力本身（37.35→53.29）与学到的经验（53.29→67.81）（作者主张）。

**作者认为的原因.** 论文把「同一知识给 Builder 优于给 Target」归因于 enactment：Builder 可以把声明式原则落地为持久状态、可执行工具、验证逻辑或控制决策，从而减轻 Target 在推理时自行解释与执行建议的负担（§4.2）（作者主张，未单独隔离验证，见 §5 质疑 1）。

**核心假设.** 可以概括为三条：① 用 when/provide/use 三元组表达的可复用支持原则，能在开发集上从执行反馈中习得并在冻结后泛化到同基准的未见任务；② 把同一知识交给 Builder 编译成 harness，优于直接交给 Target；③ 同一模型兼任 Builder 与 Target 时，也能通过「学习搭更好的环境」提升自身测试时表现。三条假设分别由 Table 3、Table 3 与 Fig. 3(a) 检验。

**须区分.** 领域中早有的一般问题是「环境与工具显著影响 agent 表现」（引 SWE-agent）以及「把经验沉淀下来复用」（Voyager、ExpeL 等）。本文的新观察是：相同知识内容的两种投递方式（给 Builder 编译 vs. 给 Target 直接读）在六个设置上全部出现差距，且反思式更新的收益是延迟且非单调的（§5.1，Fig. 2）。本文实际解决的子问题是：在固定 benchmark、固定 Target 预算、两轮开发集 pass 的限定条件下，验证这条「学习支持设计」的路线是否优于若干对照。至于「为什么 enactment 有效」，论文只给出了机制性解释，没有做因果隔离实验。

## 2. 创新点是什么？

**一句话概括.** 技术上真正的增量是「把支持设计从实现中剥离并进行学习」这一协议：元技能以 when/provide/use 三元组描述「何时需要支持、提供什么、Target 如何使用并保留哪些判断」，Builder 在开发集上通过 construction–execution–reflection 循环迭代外部技能库（权重不变），冻结后为每个测试任务现场生成 harness；并配以一组能分别控制「知识内容」「构造能力」「经验归属」的对照实验。

**创新点 1：元技能表征与「给 Builder 而非给 Target」的定位.** 每条技能是一个三元组 $s=(\mathrm{when},\mathrm{provide},\mathrm{use})$，合计不超过 192 token（§3.1，Appendix B.1）（原文事实）。与最接近的 Evo-Harness（把执行经验编译成 solver 技能）、Meta Context Engineering（学习构造 context 的策略）相比，差异在于学习对象是「支持原则」且接收者是 Builder；作者在 Appendix A.2 把差异表述为「我们关注用于支持设计的可复用知识」（作者主张）。从形式上看，这是已有组件（反思式 prompt 迭代 + 技能库 + harness 构造）的新组合，而非全新机制；论文没有通过穷尽文献对比证明「首次提出」。

**创新点 2：学习–冻结–部署协议.** 开发期每轮为每个开发任务构造独立 harness，Target 执行后产生公开执行记录与开发分数，Builder 每批最多做一次 keep/revise/add 更新、且必须引用该批证据；两轮 pass 后技能库冻结，测试期每个任务从公开输入出发重新构造 harness（§3.1 Eq. 2，§3.2 Eq. 3，Appendix B.1）。该协议的关键约束是：测试期 Builder 看不到测试轨迹、分数、参考答案与评测器内部（Appendix B.1），这使「冻结后泛化」的评测相对干净（原文事实）。

**创新点 3：七类可编辑 harness 组件空间.** 论文定义了 Builder 可改写的七个组件族：instructions、memory、context organization、composed tools、execution control、verification & recovery、workspace preparation，同时固定 benchmark 工具、评测预算与评分规则（Table 1）（原文事实）。这属于工程实现层面的贡献——它把「Builder 能改什么」讲清楚了，但每一族本身都是已知概念（记忆、控制器、工具封装等）。

**创新点 4（方法论）：对照设计.** 论文设置了五类基线，其中两个是互补消融：No-skill Builder 保持相同的构造接口与预算但技能库为空（隔离「构造能力」），Direct Builder skills 把同一技能库直接交给 Target（隔离「enactment」）；另有独立学习的结构化 Target 技能与一次性抽取的自由文本笔记（Appendix C）。**移除该设计的证据**：去掉经验（No-skill）平均损失 8.95 点；去掉 enactment（Direct-all）平均损失 12.02 点；组件消融（Table 4）显示去掉 controller 在 Gemini 上损失 13.36 点（95% CI $[-18.49,-8.22]$，不含 0），是全文唯一脱离 0 的组件效应。

**原创边界说明.** 根据本文的 related work 与实验对比，只能确认作者声称的差异（学习对象与技能接收者不同）；是否构成首次提出，还需要更完整的文献检索。

## 3. 作者如何解决？

**直觉.** 论文用「导师—博士生」类比：能力强的学生反复手工重跑实验，是因为配置与结果散落在脚本和笔记里；有效的导师不会替学生做题，而是建立共享实验日志、可复现工具和清晰的验证流程（§1）。对应到系统里，Builder 学的不是解题，而是「什么样的学生、在什么条件下、需要什么样的支持」，并把这种支持落成具体的环境改造；Target 仍在其中自己做判断。（该类比来自论文原文，非本报告的教学示例。）

![框架总览：开发期学元技能、测试期用元技能](/images/dailypaper/2026-10-01/2609.38143_fig1.png)

图中每个部分的作用：(a) 左上是 Builder 的工作环境（框架提供的接口、设计指引与预算），Builder $\mathcal{B}$ 读取当前完整技能库并为开发任务构造 harness $H_x^j$；右下是 Target $\mathcal{T}$ 在该 harness 中执行，产出公开轨迹与分数组成的反馈 $F(e)$，回送给 Builder 做 keep/add/revise 决策，写入元技能库 $S_j$（初值 $S_0=\varnothing$，图中三条 when/provide/use 字段示例即技能条目结构）。(b) 测试期先把技能库冻结（Freeze $S^*$），对每个测试任务用「全量库或 BM25 检索」挑出技能包，连同同一套框架与 $H_0$ 交给 Builder，Builder 为每个任务现场构造全新 harness，Target 执行后输出 $\hat{y}_x$。这张图之所以是理解全文的钥匙：它把「学习发生在开发期的技能库层面、部署发生在测试期的 harness 层面、而模型权重全程不动」这一核心分工画成了一条闭环与一条单向流水线之间的对照。（另注：Fig. 1 图题自述「Rather than teaching the Target directly...」，即作者把「不直接教 Target」当作卖点。）

**运行流程（按实际执行顺序）.**

1. **输入**：任务公开文本 $x$；中性环境 $H_0$（通用提示、空记忆、默认历史、原生工具、默认循环、原生提交规则、空 scratch，Table 1 第一行）；开发期还额外获得 Target 的公开执行反馈。
2. **开发期技能学习**：从空库 $S_0$ 开始，共两轮开发集 pass。每个开发任务先由 Builder 构造 harness $H_x^j=\mathcal{B}(H_0,x,S_j)$，Target 在其中执行得到 $e_x^j$，再按 $S_{j+1}=\operatorname{Revise}_{\mathcal{B}}\big(S_j,\{(H_x^j,F(e_x^j))\}_{x\in G_j}\big)$ 更新库（Eq. 2）。每个任务至多产生一次 keep/revise/add，且必须引用该批证据；被替换的版本保留归档（§3.1，Appendix B.1）。
3. **测试期构造**：技能库冻结为 $S^*$。技能供给有两种模式——full bank 把全部技能放入 Builder 上下文；retrieval 用固定 BM25（$k_1=1.5$、$b=0.75$）只以公开初始提示为查询、最多取 2 条正分技能，若无正分则技能包为空（§3.2，Appendix C）。随后 $H_x^*=\mathcal{B}(H_0,x,K(x,S^*))$，即每个测试任务都重新构造一份 harness（Eq. 3）。
4. **谁决定什么**：Builder 决定记忆存什么、何时检索、Target 拿到哪些工具与资源、控制器如何切换阶段、提交门槛如何设置；Target 只在 harness 内推理、调用工具、并对最终提交内容负判断责任（§3.2，Table 1）。
5. **是否训练**：不训练任何参数。全程是 training-free 的外部知识学习，Builder 与 Target 权重均固定；所有请求 temperature 0、high reasoning effort（§4.1，Appendix B.2）。
6. **推理阶段的变化**：相比 native 环境，Target 拿到的是一个被 Builder 改造过的环境（额外状态、工具、验证与恢复逻辑），但底层 benchmark 工具、预算与评分规则不变（Table 1 图题）。
7. **最终输出**：每个测试任务一份构造好的 harness 加 Target 的提交结果 $\hat{y}_x$，由 benchmark 原生评测器打分。

**预算与开销（论文报告的）**：Target 侧 Harness-Bench 为 30 轮模型调用、30 次工具调用、96K 累计 token、1200 秒墙钟；NewtonBench 为 12 轮、10 次工具调用、192K token、3600 秒；每次模型调用最多 16384 输出 token，NewtonBench 单次实验调用最多查询 20 个条目（Table 5）。Builder 侧：harness 构造最多 16K 输出 token、允许至多两次接口修复；技能更新调用最多 8K 输出 token（Appendix B.2）。**瓶颈**在于 Budget $C_x$ 的定义排除了 Builder 的学习与构造开销（Eq. 1 明示），因此方法的端到端成本结构在论文中是缺失的。

**教学简化示例（非论文实验）**：可以把元技能理解成给新助教的一张卡片——when：「当学生每次都要手动复现上次的数据清洗」；provide：「挂一个版本化的中间结果目录 + 一条自动校验命令」；use：「提交前先看校验输出，但结论是否成立仍由学生判断」。这张卡片本身不解决任何具体问题，但它让「动手搭架子」这一步有了稳定的触发条件与验收标准——这正是论文希望 Builder 学到的粒度。

## 4. 解决得怎么样？

### 4.1 实验设置

- **基准与划分**：Harness-Bench 覆盖现实 agent 工作流，共 106 个任务，开发 11 / 测试 95，指标为确定性的 completion-oracle 分数（Table 2，§4.1）；NewtonBench 覆盖交互式科学定律发现，共 324 个任务，开发 32 / 测试 292，指标为 symbolic-structure accuracy（Table 2，§4.1）。每个基准约 10% 作开发集，其余全部测试，无验证集（Appendix B.1）。
- **模型**：Builder 固定为 GPT-5.6-Sol；Target 为 Gemini-3.6-Flash、Qwen3.8-Flash、GPT-OSS-120B；自改进实验用 Gemini-3.6-Flash 与 Gemini-3.1-Pro 同模型兼任两个角色；迁移实验用 Gemini-3.1-Pro 作为接收 Builder（§4.1，§5.2，§5.3）。
- **基线（5 类）**：Native environment；No-skill Builder；Direct Builder skills（retrieved / all）；Independent structured Target skills（retrieved / all）；Mined free-form Target skills（retrieved / all）（§4.1，Appendix C）。
- **公平性设置**：所有条件共享开发/测试划分与每任务 Target 执行上限；Builder 条件共享组件接口、构造指引、构造权限（16K token、最多两次修复）与 Target 信息（§3.2，Appendix A.2）。学习与构造不计入 Target 预算。
- **指标口径**：全部声明测试任务都留在分母里；构造或执行失败计 0；配对比较重采样 20K 次任务、保留配对，报 2.5/97.5 分位作为未校正 95% 区间，并明确说明区间描述的是任务间变异而非生成间随机性（Appendix B.3）。
- **实验分工**：Table 3 主结果；Fig. 2 技能精炼动力学；Fig. 3(a) 同模型自改进、Fig. 3(b) 跨 Builder 迁移；Table 4 组件消融（仅 NewtonBench）；Fig. 4 结果转移与分类级效应；Appendix D 两个案例研究。

### 4.2 关键结果

**主结果（Table 3，Builder 均为 GPT-5.6-Sol）.** 全量技能库（Builder meta-skills, all）取得 65.31% 的宏平均分，六个模型–基准列相对 no-skill Builder（56.36）在全部 6 个设置上提升，平均 +8.95 点；相对把同一技能库直接交给 Target（Direct all，53.29）提升 12.02 点，逐设置幅度 3.94–25.43 点；相对独立学习并直接交付给 Target 的结构化技能（54.38）提升 10.93 点；相对 native 环境（51.40）提升 13.91 点。作者同时报告：NewtonBench 上的提升平均 10.96 点（三个 Target 均正），Harness-Bench 为 6.95 点（§4.2）（原文事实，数字由 Table 3 计算核对）。

**哪里提升小、甚至为负（Table 3，§4.2）.** Qwen 在 Harness-Bench 上仅从 71.51 升到 72.64（+1.13）；GPT-OSS 在 Harness-Bench 上总体 +5.20 点，但 vertical workflows 分类下降 2.23 点（§5.5）；full-bank 在 6 个设置中有 5 个优于 BM25 top-2 检索，唯一例外是 Qwen-Harness-Bench：检索版 74.81 反而高于全量版 72.64（-2.17）。作者把「全量通常更好」表述为「在评估规模上的强默认选项」，并承认存在例外（§4.2）。

**技能精炼是延迟且非单调的（Fig. 2，§5.1）.**

### 4.3 机制证据

- 论文区分了两层问题：「方法是否有效」由 Table 3 回答，且六个设置全部改善，这一层证据相对扎实（原文事实）。
- 「为什么有效」的证据是间接的。enactment 差距被解释为 Builder 能把原则落地成状态、工具与控制（§4.2，§6 Message 1），但论文没有测量 harness 中实际生成的组件是否真的对应技能内容，也没有「技能内容被打乱/替换为等价长度但与任务无关」的安慰剂对照；因此无法排除「更具体、更长的 Builder 侧提示 + 额外的构造算力」这一替代解释（审稿人判断，详见 §5 质疑 1、2）。
- 组件层面的因果证据最弱：Table 4 只在 NewtonBench 上、且在冻结 harness 上做移除而不重建，作者自己说明「each paired contrast measures the effect of that intervention on the recorded harness, conditional on a single official execution per task」（Appendix B.3），且 6 个区间中 5 个包含 0（原文事实）。
- 结果转移分析（Fig. 4）提供了与机制相容的证据（无效提交减少、正确发现增多），但仍属相关性描述：论文未做「只提升完成率而不提升正确率」的分解实验（审稿人判断）。

### 4.4 成本与适用范围

**论文报告的代价（原文事实）**：Target 侧执行预算如 Table 5（Harness-Bench 30 轮 / 30 工具调用 / 96K token / 1200 s；NewtonBench 12 / 10 / 192K / 3600 s）；Builder 侧 harness 构造 16K 输出 token、最多两次接口修复，技能更新 8K 输出 token，单条技能 192 token，每开发任务至多一次更新；部署期 BM25 检索成本可忽略。

**论文未报告的代价**：Builder 学习与构造的真实 token 消耗、墙钟时间、金额成本（Eq. 1 明确把这些排除在 $C_x$ 之外）；技能库最终规模（条数）；harness 构造失败率与执行失败率的具体拆分（只规定失败计 0）；多次重复运行的方差与显著性（Appendix B.3 明说区间不是生成级方差，§6 Message 3 自述「one adopted execution per task and condition」）。以上均为「论文未报告」。

**适用范围**：结论限定在同基准内的未见实例（已知任务类别与物理机制），约 10% 开发集学到的库指导其余实例（Appendix A.3）。跨数据集复用、未见任务族、不同工具接口均未验证，作者在 Appendix A.3 明确留作未来工作；同时作者也承认主结论建立在「一个主 Builder、两个基准」之上（§6 Message 3）。

**改善了什么、未改善什么**：改善——无效提交比例下降、完成率上升、六设置全部优于 no-skill（§5.5，Table 3）。未改善——更新非单调（Qwen-Harness-Bench 第二轮退化 4.06，§5.1）；跨 Builder 迁移方向不确定（§5.3）；组件收益依 Target 而异（Table 4）；同模型自改进中 Harness-Bench 的增益（+8.9）明显小于 NewtonBench（+21.9 / +25.3）。

## 5. 最容易受到审稿人质疑的地方

#### 质疑 1：「Direct Builder skills」对照并不对等，enactment 的 12.02 点差距不能完全归因于「把知识落地」

- **原文依据**：Direct 基线的配置是「meta-skills 的 when/provide/use 字段被追加到 Target 的指令中，Target 被明确允许用自己的原生工具与执行预算来实现这些指导，且不安装任何 Builder 生成的 callback 或资源」（Appendix C）。而 Meta-skill 条件额外获得整个 Builder 构造阶段（16K token + 两次修复 + 七个组件族的实现能力），且这部分算力不计入 Target 预算（Eq. 1，Appendix B.2）。
- **为什么重要**：这直接影响核心主张的解释力。论文把差距解释为「operationalizing that knowledge before execution」（§4.2），但比较的其实是「知识 + 一个额外的 Builder 编译阶段及其算力」对「知识 + 无额外编译」；把总量差异全部归因于机制类别，属于因果解释超出实验设计。
- **当前能够得出的判断**：差距本身是真实观察（六个设置全部存在，Table 3）；但「因为 Builder 把它变成了工具/状态/控制所以更有效」这一机制解释未被隔离，存在「额外构造算力」这一替代解释（审稿人判断）。
- **如何验证或补强**：增加安慰剂对照——技能库内容替换为等长但与任务无关/打乱的技能，保持 Builder 构造流程与算力完全一致；或给 Direct 条件的 Target 追加与 Builder 等量的实现预算（允许其自建记忆/工具）；再报告各条件下 Target 是否实际尝试实现建议及其成功率。
- **严重程度**：主要问题（影响核心机制主张，不影响「方法在本文设定下有效」这一经验结论）。

#### 质疑 2：缺少「看到同样执行反馈但不提炼技能」的对照，8.95 点可能混入信息与熟悉度效应

- **原文依据**：No-skill Builder「在相同构造空间与预算下构造 harness，但技能库为空」（§4.1）。开发期的两轮 pass 同时给了 Builder 开发集任务、Target 的执行记录与开发分数（§3.1 Eq. 2，Appendix B.1）。
- **为什么重要**：学习流程与信息暴露是耦合的。No-skill 条件既没有技能，也没有经历过开发集的复盘，因此 8.95 点里可能包含「对 Target 失败模式的熟悉度」「开发分布先验」这类一次性、不可复用的收益，而非「可复用支持原则」的价值。论文用 no-skill 控制构造能力，但没有控制信息暴露量。
- **当前能够得出的判断**：证据不足，混杂因素未被排除。作者在 Appendix A.2 声称各 Builder 条件共享接口与权限，但没有提及信息暴露的对齐。
- **如何验证或补强**：设置「暴露对照组」——Builder 浏览同样规模的开发集执行记录但不允许写技能库（或写入被冻结/丢弃）；对比它与 no-skill 的差距即可分离信息效应与学习效应。也可报告技能库内容与开发集失败模式的对应关系。
- **严重程度**：主要问题。

#### 质疑 3：统计证据薄弱——每任务单次执行、多数关键比较的区间包含 0、存在明确反例

- **原文依据**：Appendix B.3 明确说明报告的区间「describe variation across tasks in the fixed test inventory, rather than variability across repeated stochastic model generations」，且组件消融「conditional on a single official execution per task」；跨 Builder 迁移「all confidence intervals include zero」（§5.3）；Table 4 六个区间中五个含 0；§6 Message 3 自述「one adopted execution per task and condition」。
- **为什么重要**：这决定了结论的可信区间与可复制性。若同一配置重复运行波动接近设置间差距，则 8.95 / 12.02 这类平均差需要重新评估；尤其在 Qwen-Harness-Bench 上差距仅 1.13 点，而 full-bank 又输给检索 2.17 点，方向本身可能是噪声。
- **当前能够得出的判断**：结论方向（六设置全为正）一致性尚可，但幅度与个别设置的方向缺乏稳定性证据；「经验总是有用」的表述超出数据（审稿人判断）。
- **如何验证或补强**：对关键设置重复 3–5 次独立运行并报告均值与标准差；报告技能库层面的多次独立学习运行；对主要对照做任务级配对检验并给校正后的区间；明确披露生成级方差。
- **严重程度**：主要问题。

#### 质疑 4：部件级机制证据不足以支撑「哪个组件有用」，且消融仅在单一基准上进行

- **原文依据**：Table 4 只在 NewtonBench 上做冻结 harness 的组件移除，且不重建其余支持；去掉 memory+context 在 GPT-OSS 上反而 +3.42；作者自述这些对比「measure the effect of that intervention on the recorded harness」（§5.4，Appendix B.3）。
- **为什么重要**：论文的三条 Discussion message 中，「元技能指导资源分配」（§6 Message 1）依赖组件层的解释。若组件效应依 Target 而异且大多不显著，那么「Builder 知道该给什么支持」的说法就只剩间接支持。
- **当前能够得出的判断**：作者对结论的表述已相对克制（多处写明区间含 0、未建立总体效应），但 Harness-Bench 上完全没有组件消融，无法判断结论是否可迁移到工作流类任务（审稿人判断）。
- **如何验证或补强**：在两个基准上都做组件消融；对技能→组件映射做抽样审计（每条技能在生成的 harness 中是否被实现、以何种组件）；用「移除技能但保留组件」的正交消融分离技能内容与组件实现的贡献。
- **严重程度**：主要问题（影响机制成立范围）。

#### 质疑 5：成本结构与可复现性信息不完整，结论的实际可用性难以判断

- **原文依据**：Eq. 1 明确把 Builder 的构造与学习开销排除在 $C_x$ 之外；全文未出现 Builder 侧 token/时间/费用统计；未报告技能库最终条数（Appendix B.1 只给出单条 192 token 的限制与「每任务至多一次更新」）；代码发布口径在正文脚注（「code is released at...」）与 Appendix A.2（「Upon paper acceptance, we will release the full code and all prompts」）之间不完全一致；仓库当前可访问但本报告未审计其与论文描述的一致性；三个 Target 中的两个（GPT-5.6-Sol 作 Builder、Gemini-3.6-Flash）指向外部服务。
- **为什么重要**：若「学习如何搭环境」的收益需要显著超过基线构造算力才能显现，那么它在实际部署中的适用性判定会完全不同；而技能库规模、提示词与除错流程的缺失会直接影响可复现性评级。
- **当前能够得出的判断**：论文未报告，无法核算；这属于披露不足而非结论错误（审稿人判断）。
- **如何验证或补强**：报告 Builder 侧 token/调用/时间/金额的实际消耗与失败重试次数；给出每次运行的技能库快照与条数；给出构造失败率的分解；把代码、提示词与运行配置与论文同时发布。
- **严重程度**：次要问题（不影响主结论方向，但影响推广与复现）。

## 6. 审稿式总评

> 作者发现 agent 的表现同时取决于推理能力与所处的环境，因此提出把「支持设计」本身变成学习对象：让 Builder 从自己产出的 harness 在开发集上的执行记录中提炼 when/provide/use 形式的元技能，通过 construction–execution–reflection 循环迭代两轮后冻结，再为每个测试任务现场构造 harness。实验在 Harness-Bench 与 NewtonBench、三个 Target、共六组设置上表明，全量元技能相对 no-skill 构造平均提升 8.95 点、相对把同一技能库直接交给 Target 提升 12.02 点，六组全为正；其中「同一技能库给谁用」的对照与「失败计 0、分母固定」的口径证据较强，但 enactment 的因果解释、学习效应的信息混杂、以及每任务单次执行的方差问题仍缺少充分支持。本文最有价值的部分是把「知识内容」与「知识落地」两个变量分开的对照设计，以及 Fig. 2 展示的「精炼收益延迟且非单调」这一诚实的负面发现；最大的审稿风险是核心机制主张（builder 编译优于直接交付）混淆了额外构造算力，以及多数关键比较的置信区间包含 0 却仍以正面口径总结。

- **问题定义清晰度**：强（明确固定权重、区分 Builder/Target、给出目标函数与预算定义 Eq. 1，并说明预算边界）
- **创新性证据**：中（表征与协议是已有组件的新组合，原创边界未通过充分文献对比确认；但对照设计具方法论价值）
- **方法可信度**：中（协议与失败记账透明，但 enactment 归因与学习效应未被隔离）
- **实验支持力度**：中（两基准、三 Target、五基线、六设置全为正；但单次执行、无方差报告、多数组件/迁移结论 CI 含 0、单一主 Builder）
- **可复现性**：中（提示 token 上限、BM25 超参、预算、bootstrap 方法等细节齐全，且已有一个可访问的代码仓库；但技能库规模未报告、提示词尚未随论文发布、依赖外部模型服务）
- **综合阅读价值**：中（问题设定与对照设计值得借鉴，「学习支持设计」这一视角对 AI4AI 方向有启发；引用其具体增益数字时需附上限定条件）
