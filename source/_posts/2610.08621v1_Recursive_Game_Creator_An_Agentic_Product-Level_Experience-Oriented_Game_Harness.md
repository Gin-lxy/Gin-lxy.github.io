## 0. 一句话结论

论文针对"编码智能体生成的游戏能运行、但未必好玩"这一落差，提出 Recursive Game Creator：一个不训练任何模型、以 Designer–Builder–Player–Reviewer 四角色组成多轮闭环的体验导向 harness（编排框架），用"写代码策略代替逐帧操作"的 Coding-Native Player 采集游戏轨迹，再由体验导向的 Reviewer 依据共享指标、游戏特定评分细则与用户偏好做出修订反馈与版本取舍。在论文自报的两个基准（GameCraft-Bench 45 个任务三轮迭代总体 72.70→77.89；GameASG-Bench 53.2% 严格任务成功率）上相对同模型基线有提升，但"coding-native 测试优于 GUI 测试"这一核心机制主张没有任何受控对照或消融实验支持，结论目前只适用于这两个基准上的端到端效果，不能推广为"该 harness 的每个组件都被证明必要"。

## 1. 论文具体想解决什么问题？

**研究背景与具体任务。** 编码智能体（coding agent）已能快速产出可运行的游戏，但作者指出"能运行"不等于"好玩"（Abstract、§1）：有吸引力的机制、合适的难度、连贯的表现与及时的反馈才构成玩家体验（player experience）。论文的任务是把智能体游戏开发从"粗糙原型"推进到"产品级可玩、且向目标玩家体验对齐"的游戏，具体形式是让一个 agentic harness（该术语按原文保留，指承载并编排智能体角色的开发框架）在多轮迭代中持续改进同一个游戏工程。

**现有方法通常如何处理。** §2 与 §1 给出两条线：一是角色分工式游戏开发（MetaGPT、ChatDev、GameGPT、OpenGame、AutoUE），负责生成和修复可运行工程；二是迭代式反馈改进（Self-Refine、Reflexion、Harness-of-Harness 的持久开发与独立评估、AVR-Agent 的音视频录制对比，以及并发的 RSIGame 递归自改进）。其中与本文最接近的是 Harness-of-Harness（Yan et al., 2026，简称 HoH）与用 GUI 智能体测试游戏的工作（Huang et al., 2026）：前者提供多轮持久开发与评估的框架，后者让智能体通过图形界面（GUI）截图操作游戏来测试。

**现有方法在哪些条件下表现不好（作者的主张）。** §1 明确列出三条：(1) 截图驱动的测试会丢失程序接口中可直接获得的结构化状态、合法动作、事件与进度信号；(2) 每个动作都需要一次视觉解释加模型决策，延迟高，使得高频、细粒度的 rollout（完整执行采样）难以进行；(3) 编码智能体本身是为代码生成与推理优化的，而不是为细粒度游戏画面理解优化的。

**本文的新观察。** 把"快速游戏控制"与"策略构建、视觉评估"分离开：由智能体一次性写好可执行策略代码并反复执行，即可在不产生逐步模型调用的情况下获得大量轨迹（§1、§3.2）。这本质上是用"代码即策略"把 LLM 的强项（写代码）对齐到 playtest（试玩测试）任务上。

**支撑该问题判断的证据。** 需要区分两类证据：问题存在性的证据是论证性的（程序正确不等于体验良好，这是游戏研究与体验驱动内容生成领域早已存在的共识，§2 亦引 Yannakakis & Togelius 2011、Barthet et al. 2024 等）；coding-native 优于 GUI 的证据只有 Fig. 4 的覆盖度展示（48 条策略 rollout 覆盖 FPS 场景 97.1% 网格、含 11 个室内），且论文自己声明 GUI 路线在图示中是示意性的、该图只表明覆盖度而非实测加速（§4.3）。**审稿人判断：论文观察到了 GUI 测试方式的结构性局限（合理且与已知工程经验一致），但没有用任何测量验证其替代方案在速度或质量上的因果优势。**

**作者认为的原因。** 上述 §1 三条局限（信息丢失、延迟、模型能力错配）被作者视为需要 coding-native Player 的原因；此外作者认为一般评测（游玩时长、成功率）不足以刻画体验，需要游戏特定的评分细则（rubric，评分量表）（§3.3）。

**最终要验证的核心假设。** 以"可执行策略采集的多样轨迹 + 游戏特定与偏好导向的评估 + 多轮闭环修订"为骨架的 harness，能在不更新任何模型参数的前提下（§2、§5），持续提高生成游戏的质量，并向推断或明示的玩家偏好对齐（Abstract、§1、Fig. 2）。

**三类问题的区分。** 领域中早已存在的一般问题：可运行不保证好玩、迭代改进、体验驱动内容生成。本文的新观察（相对具体、有据）：把 playtest 的执行主体改成"智能体写代码策略"，并主张这会一并改善覆盖率与评估的客观性。本文实际解决的具体子问题：搭出一个包含上述 playtest 方式、以体验与偏好为目标的多轮修订 harness，并在 GameCraft-Bench、GameASG-Bench 与一个小型用户研究上给出端到端增益。论文没有证明其因果解释（即增益必须归因于 coding-native 与体验化评估这两个设计）。

## 2. 创新点是什么？

**总括。** 真正的技术增量是系统级组合与流程设计：把游戏开发组织成 Designer、Builder、Player、Reviewer 四角色的多轮闭环（论文 Fig. 2），其中两个最具辨识度的组件是 Coding-Native Player（用可执行策略代码代替 GUI/截图操作，批量采集试玩轨迹）与 Experience-Oriented Reviewer（把共享信号、游戏特定评分细则、视觉证据与"推断/明示"的用户偏好整合为结构化修订记录，并用匿名 A/B 决定版本保留）；配合"固定模型参数、只改游戏制品"的定位构成论文声称的贡献。按规范口径，这属于已有组件的新组合 + 工程/流程改进：角色式多智能体、代码即策略、自反馈迭代、偏好反馈在 §2 中都有出处；更强基座（GPT-6 Astra）与基准选择不算创新，"RSI"（recursive self-improvement，递归自改进）实为游戏制品跨版本改进而非模型更新，术语借用有夸大之嫌；是否"首次提出"需更完整检索（与并发工作 RSIGame、HoH 的逐项对照缺失）。

**创新点 1：Coding-Native Player（代码原生试玩者）。** 新增机制：Player 读取游戏暴露的状态模式（state schema）、可用动作与测试目标，编写可执行策略代码（观测量到动作的规则），经程序接口或命令行反复执行产生轨迹；策略按策略、技巧、探索度、风险偏好变化，并支持并行与重试（§3.2 公式 (3)）。与最接近已有方法的差异：HoH 与 GUI 智能体工作让模型逐步交互，本文把"交互"变成"编译器执行的代码"，模型只在策略构建与修复时介入；该思想可追溯到 Voyager 的技能库、Code as Policies 等（§2 自引）。对应 §1"截图测试丢信息、延迟高、能力错配"；证据见 4.2 的探索分析（论文 Fig. 4），移除/替换后的变化论文未报告（4.3）。

**创新点 2：Experience-Oriented Reviewer（体验导向评审者）。** 新增机制：评审输入为五路——共享信号（成功率与时长，目标是"合适的难度"而非最高成功率）、游戏特定评分细则（评审者自行推断品类标准，并核对规则、视觉线索与实际游玩的一致性）、视觉证据（不知源码与版本顺序的截图与录像）、结构化偏好记录（区分观测事实/推断偏好/用户明说要求，输出期望体验、证据与修订优先级）、匿名 A/B 版本保留（§3.3）。与最接近已有方法的差异：Self-Refine 类改文本输出，experience-driven PCG/RL 改内容或奖励，RLHF/DPO 改模型参数；本文改游戏制品且参数固定（§2）。对应 §1"一般评测不足以刻画体验、需要偏好导向评估"；证据见 4.2 的 Table 1 三轮曲线，移除后变化未报告（4.3）。

**创新点 3：多轮闭环与两条轨道。** 新增流程：闭环顺序为"策略执行产生轨迹 → 轨迹与视觉分析产生体验/偏好反馈 → Designer 转为计划 → Builder 实现新候选"（§1、论文 Fig. 2 中央循环箭头，轮数可配置）；论文 Fig. 2 图注区分"agentic-player（智能体试玩）轮次提升游戏质量"与"human-involved（有人参与）轮次提升游玩体验及其对推断偏好的对齐"两条轨道。与 HoH 的差异主要在 playtest 承担者与评估标准；证据为 4.2 的 Table 1 与 Table 3，论文未做"轮数=1 vs 3"以外的轮数分析。

**创新点 4：Builder 的分阶段实现与验收目标。** Designer 的计划表示为四元组 $P_t=(h_t,\Delta_t,A_t,X_t)$：拟验证的体验假设、具体改动与须保留的强项、以场景/输入/可观察结果为形式的验收目标、资产需求（§3.1 公式 (1)）；Builder 先出可玩草稿，再由框架执行资产生成请求、整合并检查资产在碰撞、动画与交互区域中的表现（公式 (2)）。它把"体验目标"变成可测试的实现目标，使资产生产与游戏内集成验证挂钩，属表示与流程层面的工程改进；对照实验未报告（4.3），实现展开见 §3。

## 3. 作者如何解决？

**直觉。** 游戏的"好玩"难以直接从代码正确性读出，但可以从"玩的过程"里读取：如果有一群风格不同的虚拟试玩者反复玩、留下状态与事件级的记录，再让一个评审者带着"这类游戏该考核什么"的问题去读记录并看截图，就能像工作室一样一轮轮提出修改。关键工程选择是：试玩者不"手操"游戏，而是"写脚本"玩——写好的脚本可零模型调用地跑很多遍，覆盖与复现性都比截图操作好，同时保留结构化状态供分析。整条流水线见图 1。

![图 1：Recursive Game Creator 的多轮修订工作流](/images/dailypaper/2026-10-08/2610.08621v1_fig2_workflow.png)

**图 1**（论文 Fig. 2）：左上 Designer 框把"用户目标 + 评审反馈"编译成修订计划（机制、资产、修复项），它负责把体验语言转成可执行计划，是闭环的入口；右上 Builder 框把计划变成"游戏代码（规则与状态、控制与物理、渲染与 UI）+ 生成资产（图中示例为三个角色形象）"，它决定改动真正落到工程里；右下 Player 框展示核心机制——左侧是一段策略代码（按血量、距离选择 retreat / move_right / attack），右侧是游戏可执行体，下方是"步数-观测-动作"的结构化轨迹表（如 `hp=82, dist=140 → move_right`），并注明"策略跨 rollout 复用"，这正是"写一次、跑多次、零逐步模型调用"的所在；左下 Reviewer 框以 Prior（打叉）与 Candidate（打勾）两段游戏画面对比，配"共享信号（成功率+时长）"与"游戏特定评分细则（玩法、控制、内容、视觉）"两行，输出"偏好 + 修订反馈"，负责判断哪一版留下、下一步改什么；中央环形箭头表示整套流程按可配置轮数循环。没有其中任何一环，闭环都不完整：缺 Player 就没有客观试玩证据，缺 Reviewer 就没有版本取舍标准，缺 Designer/Builder 则反馈无法落地。

**输入。** 用户简述 $U$（user brief）、当前游戏版本 $G_t$、上一轮反馈历史 $\mathcal{H}_{t-1}$（§3.1）；此后每轮以上一轮保留下来的版本作为新的输入。

**关键步骤（按实际运行顺序）。**

1. **Designer 出计划（LLM 角色执行）。** $P_t=\operatorname{Design}(U,G_t,\mathcal{H}_{t-1})=(h_t,\Delta_t,A_t,X_t)$（公式 (1)）：$h_t$ 是拟验证的体验假设及其依据，$\Delta_t$ 是具体改动与须保留的强项，$A_t$ 是以场景/输入/可观察结果为形式的验收目标，$X_t$ 是资产需求。为什么这样设计：它把"体验目标"翻译成可测试的实现目标（§3.1）——只写"让游戏更好玩"无从验收，四元组让每轮改动都带假设与验收标准，评审时才能核对"改动是否解决了上一轮的目标"（§3.3）。这是 §2 创新点 4 的计划表示部分。

2. **Builder 实现候选（LLM 角色 + 固定流水线）。** 先出可玩草稿 $Z_t=\operatorname{Draft}(G_t,\Delta_t)$（允许占位符），再由框架执行资产生成请求 $X_t^{*}=\operatorname{Generate}(X_t;Z_t)$，最后整合为候选版 $C_t=\operatorname{Integrate}(Z_t,X_t^{*})$（公式 (2)）：Builder 检查资产在游戏场景中的呈现，以及与碰撞、动画、交互区域的配合，并做针对性自检与项目检查（§3.1）。为什么分阶段：资产生成与游戏内集成验证被拆开，单独生成一张资产不等于玩法改进（§3.1）；Builder 还会按机制与美术需求选择实现工具。这是 §2 创新点 4 的实现流程部分。

3. **Player 试玩采样（Coding-Native Player，§2 创新点 1）。** 由 LLM 生成策略代码、由运行时执行：Player 读取游戏暴露的状态模式（state schema）、可用动作与测试目标，写出"观测状态 → 选择动作 → 循环到任务结束或达 rollout 预算"的可执行策略；对候选版 $C_t$ 的每条策略 $\pi_{t,k}$ 执行 $\tau_{t,k}=\operatorname{Rollout}(C_t,\pi_{t,k})$，得到含"状态、动作、事件、进度、耗时、终止结果"的轨迹与可选视觉记录 $V_{t,k}$，汇成证据集合 $\mathcal{E}_t=\{(\tau_{t,k},V_{t,k})\}_{k=1}^{K}$（公式 (3)）。工程上，rollout 以执行作业形式派发，可并行、可多开游戏实例；策略若执行失败会被检查并修复；论文强调不能把对话回应当作执行 rollout 的替代（§3.2）。为什么这样设计：把"快速游戏控制"与"策略构建、视觉评估"分离，逐步操作不再需要每步一次模型调用（§1、§3.2），作者列出四条优势——高频控制、高效采集、多样能力模拟、可复现结果（§1、§3.2）；策略在策略、技巧、探索度、风险偏好上变化，用来模拟不同水平的玩家（§3.2）。去掉这一设计就退回 GUI 逐步操作路线，即作者主张的"信息丢失、延迟高、能力错配"（§1）；但论文没有给出实测对照，这一替换会怎样并未被测量（见 4.3）。

4. **Reviewer 评审与取舍（Experience-Oriented Reviewer，§2 创新点 2）。** 由 LLM 角色执行，输入有五路：(a) 共享信号——成功率与游玩时长，关注"合适的难度"而非最高成功率，并区分"多样活动的长局"与"卡在一点的长局"（§3.3）；(b) 游戏特定评分细则——从控制响应、内容丰富度、叙事/进度节奏、视觉一致性、探索与重玩支持等共享维度出发，实例化为品类标准（赛车看转向响应与赛道引导，视觉小说看对话连贯与选择后果），并核对规则、视觉线索与实际游玩是否一致（§3.3）；(c) 视觉证据——采样截图与录像，评审时看不到源码与版本顺序；(d) 结构化偏好记录——区分"观测到的事实/推断的偏好/用户明说的要求"，输出期望体验、证据与修订优先级；(e) 版本保留——对候选版与保留版做匿名 A/B，输出"偏好/平局/无法判断"与证据路径，映射回保留哪个游戏版本（§3.3）。为什么这样设计：一般指标不足以刻画体验，且不同品类该考核的方面不同（§3.3）；视觉评审被刻意与快速控制回路分离，采集轨迹时不需要逐步理解图像（§1、§3.3）。移除该组件会怎样，论文未报告（见 4.3）。

5. **闭环与两条轨道（§2 创新点 3）。** 保留的版本成为下一轮的 $G_{t+1}$，评审反馈进入 $\mathcal{H}_{t-1}$ 供 Designer 使用；循环轮数可配置（论文 Fig. 2 中央循环箭头与图注）。论文 Fig. 2 图注区分两条轨道："agentic-player（智能体试玩）轮次提升游戏质量"与"human-involved（有人参与）轮次提升游玩体验及其对推断偏好的对齐"——4.2 的用户研究对应后者，由明确或推断的偏好驱动定制。

**模型决定 vs 固定流程。** 由 LLM 决定：计划内容、代码实现、策略写法与修复、评估标准的选择与判断、偏好记录文本。由固定流程控制：资产生成请求的执行、rollout 的派发与并行、截图采样、匿名化与版本保留映射、闭环轮数。**论文未报告**每个角色各自使用哪个具体模型、是否共享同一模型、以及提示词设计（这是复现性的直接缺口；只能从 Table 1/2 的配置分组看出 harness 整体在 GPT-6 Astra (high) 上运行）。

**训练与否。** 全程 training-free：不训练、不微调任何部分，模型参数固定，改进只发生在游戏制品上（§2、§5）。推理阶段的行为变化：每轮多出"生成策略代码 + 执行 rollout + 评审"这三段开销，而执行 rollout 本身不产生逐步模型调用（这正是与 GUI 方案的关键差别）。

**输出。** 每轮的候选游戏工程（Godot 项目或浏览器游戏）、保留版本的判定、供下一轮使用的结构化修订反馈，以及可选的面向用户偏好的定制版本。

**关键设计假设与瓶颈。** 假设一：程序接口暴露的状态与事件足以支撑有意义的试玩评估（若游戏为黑盒渲染则退化）。假设二：代理策略（proxy policy）的多样性可以近似"不同水平的玩家"——作者明确承认这不能代表全部人类玩家（§3.2）。瓶颈开销：策略生成与修复、rollout 执行、评审（包括截图理解）都计入测试成本（§3.2 末段），但论文只列出成本构成，未给出任何数字。

## 4. 解决得怎么样？

#### 4.1 实验设置

**任务与基准。** GameCraft-Bench（§4.1.1）：在 Godot 引擎上生成完整游戏，通过"重放游玩 + 游戏特定评分细则"评估机制、内容深度、功能性视觉与美术，覆盖 Action、Timing、Strategy、Simulation、Adventure 五个类别，分数 0–100 越高越好；本文选取 45 个任务（来自 Yan et al., 2026）跑三轮迭代。GameASG-Bench（§4.1.2）：浏览器游戏，L1 检查源码，L2 在浏览器运行，分 P0（启动与测试接口）、P1（必需玩法）、P2（扩展特性）；"任务成功"定义严格——需交付有效、完成评测，并通过全部 L1 检查与全部适用的 L2 P0/P1 检查（47 个任务）。

**基础模型与系统配置。** 本文运行配置为 GPT-6 Astra (high)（Table 1 分组与 Table 2 末行）；对 GameCraft-Bench 的同模型对照是 "GPT-6 Astra (high) Baseline"。其余基线是跨模型的 HoH 变体（Codex + GPT-5.5 (high)、OpenCode + DeepSeek-V4-Pro、Pi + MiniMax-M3，各含 Vanilla 与 HoH@1–3）。GameASG-Bench 的 10 个已报告配置来自 Zhang et al. (2026c) 的 Table 3（含 GPT-6-Astra ultra、Claude-Opus-5、GPT-5.6-Sol、DeepSeek-V4 系列、Kimi-K3、GLM-5.2、Hunyuan-3、MiniMax-M3），Table 2 表注明确写明基线取自该论文表格。

**评价指标与预算公平性。** 指标：GameCraft-Bench 的类别分与总体分；GameASG-Bench 的严格任务成功率、L1 通过率、L2 均值及 P0/P1/P2 通过率（Table 2 表注说明括号内增益是相对 "GPT-6-Astra high with Codex CLI" 的百分点差）；用户研究用 1–10 分制四项评分与平均游玩分钟数（Table 3）。公平性方面：GameASG-Bench 的对照数字不是本文复跑，各配置的提示词、agent harness 与预算是否对齐，论文未报告；"是否使用相同的数据、预算、工具或推理次数"在原文中没有说明。

**主实验/消融/附录各自回答什么。** 主实验（Table 1、Table 2）回答"端到端质量是否提升"；§4.2 的定性对比（Fig. 1、Fig. 3）回答"修订具体改了什么"；§4.3（Fig. 4）回答"策略 rollout 能覆盖多少地图"；§4.4（Table 3）回答"有人参与时体验与偏好对齐是否改善"。**论文没有消融实验**：没有对 Player、Reviewer、闭环轮数、多策略数量等任一组件做移除或替换研究。

#### 4.2 关键结果

- GameCraft-Bench（Table 1，45 任务，三轮）：总体分 Recursive Game Creator@1 = 72.70 → @2 = 75.35 → @3 = 77.89；相对同模型 Baseline 71.26 最终 +6.63，相对表中最高基线 HoH@3（Codex + GPT-5.5）71.52 高 6.37。五个类别三轮全部上升，Action 增幅最大：67.96 → 70.33 → 77.62（+9.66）。**值得注意的负面事实（原文事实）：Action 前两轮（67.96、70.33）都低于同模型 Baseline 的 73.33，只在第三轮反超**；作者给出的解释（动作游戏依赖控制、碰撞、战斗反馈与进度的协同修改）被自己标注为"一种可能解释，类别分数本身不能确定原因"（§4.1.1）。
- 表内增益幅度的对照（原文事实 + 审稿人判断）：HoH 在其自身 Vanilla 上的三轮增益明显更大——Codex+GPT-5.5: 49.58 → 71.52（+21.94），OpenCode+DeepSeek-V4-Pro: 26.90 → 48.98（+22.08），Pi+MiniMax-M3: 42.16 → 58.78（+16.62）；而本文相对同模型基线的增益为 +6.63。两组 "Vanilla/Baseline" 的定义是否等价，论文未说明，因此不能直接得出"本文改进幅度更小"的结论，但"跨模型绝对分数领先"与"相对自身基线的提升幅度"是两个不同的结论，论文摘要只突出了前者。
- GameASG-Bench（Table 2）：GPT-6-Astra high + Recursive Game Creator = 25/47（53.2%），对比同模型 + Codex CLI = 9/47（19.1%），提升 +34.1 个百分点；L1 98.3%（+2.7）、L2 均值 93.4%（+6.8）、P0 99.0%（+1.9）、P1 92.2%（+8.1）、P2 93.9%（+5.3）。作者声称"平均 L2 与扩展特性（P2）分数在所有已报告配置中最高"（§4.1.2）。**边界事实（原文事实）：表中 GPT-6-Astra ultra + Codex CLI 的任务成功率为 26/47（55.3%），高于本文的 25/47（53.2%）；ultra 的 L2 均值 93.2% 与本文 93.4% 只差 0.2 个百分点**。因此摘要的措辞是谨慎的（只声称 "highest mean runtime-check pass rate"，不声称最高任务成功率），但"53.2%"与"55.3%"的并列关系对读者很重要。
- 用户研究（Table 3，三轮）：Expert 评分 Controls 2 → 5 → 8，Playability 1 → 4 → 7，Depth 3 → 4 → 6，Art 2 → 6 → 8；平均游玩时长 1.50 → 4.87 → 12.41 分钟。论文未报告评分者人数、资质、评分协议、盲法或方差。
- 探索分析（Fig. 4，§4.3，见图 2）：48 条 coding-native 策略 rollout 在 FPS 测试场景达到 97.1% 网格覆盖、含 11 个室内、总移动 8.99 km；对照侧是 3 条示意性 GUI 路线。**作者自己限定：GUI 路线是示意性的，图只说明覆盖度，不构成实测加速；受控比较需要对齐预算与观测权限。**

![图 2：FPS 测试场景中的空间探索对比](/images/dailypaper/2026-10-08/2610.08621v1_fig4_exploration.png)

**图 2**（论文 Fig. 4）：左面板 (a) 标记为 "GUI Agent Player"，从共享出生点（星号）画出 3 条示意性路径（Path 1/2/3），代表界面逐步操作方式能走出的轨迹示例；右面板 (b) 标记为 "Coding-Native Player"，把 48 条实际记录的策略 rollout 叠加成访问密度热图（颜色越深访问越频繁），底部标注 97.1% 覆盖、11 个室内、8.99 km。这张图是要证明"写代码的策略能像一批不同风格的玩家一样大面积探索地图（包括建筑内部），且执行这些 rollout 不需要逐步模型调用"；但它的两块面板并非同预算对照——左侧是从未实测的示意路线——因此它只能支持"覆盖度可观"，不能支持"比 GUI 更快"（该局限同时是质疑 1 的直接依据）。

- 统计稳定性：所有主要数字（Table 1、Table 2、Table 3）都没有方差、置信区间或显著性检验；游戏生成任务本身的随机性未知，因此 +5.19 之类的差值无法判断是否超出噪声（审稿人判断）。

#### 4.4 成本与适用范围

- 训练成本：无，方法为 training-free（§2、§5 明确模型参数固定）。
- 推理/测试开销：论文列出了成本构成——策略生成、策略修复、rollout 执行与评审都计入总测试成本（§3.2）；**token 数、模型调用次数、墙钟时间、费用均未报告**。round 数在 GameCraft-Bench 为 3（§4.1.1），GameASG-Bench 的轮数未报告。
- 人工标注/人力：用户研究涉及人为评分与游玩，但评分者数量、资质、报酬与协议未报告；其余环节宣称自动化。
- 外部依赖：依赖闭源模型（GPT-6 Astra 系列为本文运行配置）、资产生成框架、Godot 与浏览器两类运行时；`Code is coming soon`，无官方代码或项目页（无法确认可复现性）。
- 系统复杂度：四角色、资产管线、作业派发、截图采样、匿名 A/B 与版本映射等多个子系统，工程复杂度高，但论文未给出系统开销分解。
- 得到改善的问题：在报告的两个基准上，端到端分数与严格任务成功率提升；体验层面的修订有定性示例与人评支持。仍未解决的问题：coding-native 与体验化评估的因果贡献未知；"产品级"与"个人偏好对齐"只在单一用户研究与示例上演示，代理玩家与真实玩家的差距未被量化；跨模型、同预算的对照缺失。

## 5. 最容易受到审稿人质疑的地方

#### 质疑：旗舰机制"coding-native Player 优于 GUI 玩家"没有任何受控对照或消融实验支持

- **原文依据**：§1 与 §3.2 主张 GUI 测试慢、丢信息、错配模型能力；但证据只有 Fig. 4，且 §4.3 明说 "The GUI routes are illustrative, so the figure shows coverage rather than a measured speedup"，并指出受控比较需对齐预算与观测权限。全文无消融实验。
- **为什么重要**：这是论文两个核心创新之一。若该组件并非关键（例如"多轮 + 更强基座"就能取得同样增益），则 harness 的核心叙事需要重写；它直接影响创新性与方法有效性的判断。
- **当前能够得出的判断**：证据不足。论文给出了合理的工程论证与覆盖度演示，但没有测量，也没有移除/替换实验；作者对此是自知的。
- **如何验证或补强**：在同一基座、同一游戏、同一预算（计入策略构建、修复、执行与评审的总成本）下比较三条管线：GUI 逐步操作、单条 coding-native 策略、多条多样策略；报告成功率、轨迹覆盖、收集时长与下游游戏分数，并做编码策略数 $K$ 与策略多样性的消融。
- **严重程度**：主要问题

#### 质疑：跨模型比较主导主表、基线异源，"state-of-the-art" 的边界容易被误读

- **原文依据**：Table 1 中三组 HoH 基线使用 Codex+GPT-5.5、OpenCode+DeepSeek-V4-Pro、Pi+MiniMax-M3，本文使用 GPT-6 Astra (high)；Table 2 表注写明基线数字取自 Zhang et al. (2026c) Table 3，而非本文复跑；表中 GPT-6-Astra ultra 的 26/47（55.3%）高于本文 25/47（53.2%），L2 均值 93.2% 与 93.4% 仅差 0.2pp。
- **为什么重要**：绝对分数领先可能主要来自更强的基座或不同的 harness 默认配置；提示词、工具、预算是否对齐未披露，"最高分"的可比性无法确认，直接关系到结论范围与公平性。
- **当前能够得出的判断**：同模型对照（GameCraft 的 Baseline 71.26、GameASG 的 Codex CLI 9/47）是更可信的比较，且方向为正；但跨模型行与"state-of-the-art"表述的证据强度中等偏弱。
- **如何验证或补强**：复跑 GameASG-Bench 上与 ultra 档位的对照（或直接以 ultra 运行本文 harness），披露各配置的提示与预算，并把"比同模型基线提升多少 vs 比他人表格高多少"分开陈述。
- **严重程度**：主要问题

#### 质疑：用户研究无法复核——评分者、协议、样本量全部缺失

- **原文依据**：Table 3 报告三轮的 Controls 2→8、Playability 1→7、Art 2→8、时长 1.50→12.41 分钟；§4.4 未说明评分者人数、是否作者本人、是否盲评、评了几款游戏、每款多少人游玩、方差或区间。
- **为什么重要**：这是论文"体验导向、偏好人机协同"主张的主要人类证据，也是与纯自动评测区别开的唯一人类环节；不可复核的大跨度分数难以支撑"对齐玩家偏好"的强结论。
- **当前能够得出的判断**：数据方向一致且幅度大，但缺少方法细节与统计，存在评分者偏差与选择偏差的可能，当前材料无法确认。
- **如何验证或补强**：公布评分者数量与资质、盲评协议、随机化与重复次数，报告均值与置信区间，并加入"无偏好反馈的对照轮次"以分离"迭代本身"与"偏好引导"的作用。
- **严重程度**：主要问题

#### 质疑：可复现性不足——无代码、无提示词、无关键超参

- **原文依据**：正文写 "Code is coming soon."；论文未报告各角色使用的模型、提示词、rollout 预算 $K$、策略数量与选择方式、GameASG-Bench 的迭代轮数、资产生成所用工具、温度等采样参数；无项目页链接（PDF 链接注解仅含参考文献）。
- **为什么重要**：方法的关键行为（评审细则如何实例化、策略如何修复、版本如何保留）都实现依赖，缺少这些内容即使有代码也难以复现分数；影响方法可信度与实际可用性。
- **当前能够得出的判断**：无法确认可复现性；在代码与配置发布前，只能作为方法叙事阅读，无法在第三方环境中验证。
- **如何验证或补强**：开源 harness 与提示词、给出每轮的轨迹样例与评审记录、披露 $K$、轮数与模型角色分配、提供基准运行的日志与随机种子处理方式。
- **严重程度**：主要问题

#### 质疑："product-level" 与 "experience" 缺少可操作定义，RSI 术语借用

- **原文依据**：标题与贡献声称 "product-level games" 与 "experience-oriented"，但论文对 "product-level" 没有任何量化标准；体验主要通过代理策略的成功率、时长与 rubric 间接度量，作者自己在 §3.3 承认 "Proxy playtime alone does not show human interest or enjoyment"；Fig. 3 图注用 "multi-round RSI"，而模型参数固定，改进对象是游戏制品而非模型（§2、§5）。
- **为什么重要**：概念边界决定结论范围。若"产品级"不可操作化，"推进到产品级"的结论就只能读作方向性描述；"RSI" 的借用可能高估方法含义。
- **当前能够得出的判断**：属于表述过宽而非数据错误；论文内部有自我澄清（§2 区分参数更新类工作、§3.2/§3.3 声明代理局限），但摘要与引言未充分回收这些限制。
- **如何验证或补强**：给出"产品级"的最低可验收清单（如无阻塞 bug 率、内容时长、控制延迟阈值），在摘要中明确"proxy 玩家、非人类体验"的限定，或改用 "artifact-level recursive refinement" 类表述。
- **严重程度**：次要问题

## 6. 审稿式总评

作者发现编码智能体可以产出可运行的游戏原型，但"能运行"并不等于"好玩"，而现有工作（GUI 智能体测试、HoH 式多轮开发）在测试环节受限于截图交互的延迟与信息损失；因此提出 Recursive Game Creator——把 Designer、Builder、Player、Reviewer 组织成多轮闭环，用"写可执行策略代替逐步操作"的 Coding-Native Player 批量采集结构化试玩轨迹，用集合共享信号、游戏特定评分细则、视觉证据与用户偏好的 Experience-Oriented Reviewer 决定版本保留与修订方向，全程不更新模型参数。实验在 GameCraft-Bench（45 任务三轮，总体 72.70 → 77.89）、GameASG-Bench（同模型 9/47 → 25/47，L2 均值 93.4%）与一个人评研究（四项 1–10 分、平均时长 1.50 → 12.41 分钟）上表明端到端质量与体验评分上升；其中较强的证据是同模型对照的稳定提升、多轮单调曲线与特征级的定性对照（Fig. 1/3），而"为什么有效"的机制证据薄弱：没有任何消融或受控比较能隔离 coding-native Player 与体验化 Reviewer 的贡献，Fig. 4 被作者自己限定为非速度测量，跨模型基线与异源表格削弱了 state-of-the-art 表述，用户研究与关键配置（模型角色、提示词、$K$、成本）均未披露。本文最有价值的部分是对"agentic 游戏开发闭环"的完整系统化与一批可借鉴的工程决策（代码原生 playtest、体验化 rubric、匿名 A/B 版本保留、代理证据的自我设限）；最大的审稿风险是核心组件缺乏隔离验证且无代码，导致创新性目前只能被"声称"而不能被"检验"。综合判断：

- **问题定义清晰度**：中。问题真实、动机清楚，属于领域公认的"可运行≠好玩"落差；但 "product-level" 与 "experience" 缺少可操作定义（4.1、5-质疑5）。
- **创新性证据**：中。组合与定位有新意（coding-native playtest、偏好导向评审、无训练闭环），但无消融、无受控对照，只能确认作者声称的差异（§2 分析、5-质疑1）。
- **方法可信度**：中。流程、公式与角色分工描述完整，作者对代理证据的边界诚实；但关键配置缺失、机制未被隔离验证（4.3、4.4）。
- **实验支持力度**：中。两个基准 + 用户研究 + 定性对照 + 覆盖度分析，同模型对照方向一致；但无方差/显著性、基线异源、存在笔误（"9.47"）与 ultra 档反例（4.2）。
- **可复现性**：弱。无代码（Code is coming soon）、无提示词与超参、无成本数据（4.4、5-质疑4）。
- **综合阅读价值**：中。对构建 agentic 游戏开发与评估闭环的读者，其角色分解、轨迹证据表示与版本保留协议有直接参考价值；对想验证"代码原生测试是否真优于 GUI 测试"的读者，本文不提供答案，需要自己补对照实验。
