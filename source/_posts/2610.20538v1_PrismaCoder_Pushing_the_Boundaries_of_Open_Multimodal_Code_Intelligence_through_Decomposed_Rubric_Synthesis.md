## 0. 一句话结论

这篇论文要解决的是多模态代码智能（multimodal code intelligence）中“训练数据质量难以度量”的问题：代码能执行不等于渲染正确，而整体打分又说不清错在哪里。作者提出 PrismaForge，为每条指令合成同时包含代码级与视觉级标准的评分量表（rubric），并把它同时用作数据过滤器和强化学习（RL）奖励；在论文报告的 13 个评测镜头上，视觉中心基准的提升较强，但文本中心基准仍明显落后于最强闭源（proprietary）模型，且 RL 的全基准贡献、数据去污染与评测独立性仍缺少充分隔离。

## 1. 论文具体想解决什么问题？

**任务背景。** 多模态代码智能指的是让模型根据文本描述或参考图像生成程序，并以程序执行后渲染出的图表、网页、SVG、LaTeX 文档、动画等视觉产物作为最终交付物。这里的“正确”至少有三个层次：程序本身可执行、实现结构合理、渲染结果在视觉与语义上符合意图（§1）。这类任务已经从单一绘图扩展到截图转网页、图表复现、科学示意图、交互式演示和符号记谱，形成了作者所说的视觉-程序接口（visual-programmatic interface）。

**现有做法。** 早期工作通常一个任务配一套数据和一套验证器：图表任务用元素级或渲染相似度检查，网页任务用视觉相似度或 DOM 结构匹配，交互式产物用任务专用裁判模型（judge）。JanusCoder、VisCodex、VisCoder2、VinciCoder 等近期工作开始把这些任务统一到共享的视觉-程序接口下，但数据仍然稀缺且质量参差，数据构建管线也很少公开（§1、§2）。在训练信号上，常见的做法要么是执行测试给出通过/失败，要么是一个整体分数（holistic score），要么是任务专用验证器（verifier）。

**现有方法具体差在哪里。** 论文给出的诊断是：执行只确认“能跑”，代码相似度不等价于视觉正确，任务专用 verifier 不能跨产物类型组合，而单一整体分数既难验证又缺少诊断信息（§1、§3.1）。作者用论文 Fig. 3 的一个网页重建案例把这一点具体化：生成页面的代码包含了参考页面的内容、颜色和布局，所以代码级检查 5/5 全部通过、代码 rubric 得分 1.00；但渲染后 footer 被画到了 Services 区域中间，遮住并裁掉了第三个按钮。此时整体 judge 仍给出 78/100，高于约五分之四的样本池，而视觉 rubric 只给 0.18（§3.1、Appendix C、论文 Table 6）。这个案例说明：不是模型完全不会写代码，而是“代码正确”和“视觉正确”发生了分离，单一信号把局部但显眼的布局错误压成了一个看起来还不错的分数。

**作者认为问题产生的原因。** 作者把瓶颈归因于评价信号，而不是单纯的数据量或模型容量：一个样本必须同时是“正确的程序、构建良好的实现、渲染正确的产物”，但现有公开信号没有一种同时覆盖这三者（摘要、§1）。进一步地，固定 rubric 对不同指令太粗，而为每条指令手工设计 rubric 又无法扩展；因此需要一个既能复用领域知识、又能按指令定制、还能控制评分成本的可扩展评价程序（§3.1）。这里要区分三个层次：领域早已知道“视觉代码难评”是一般问题；本文的新观察是“代码检查与整体 judge 会同时漏掉局部渲染错误”，并用一个具体案例展示；本文实际要解决的子问题是“如何合成可规模化的逐指令 rubric，并把它同时用于数据筛选和 RL”。

**核心假设与证据边界。** 论文最终要验证的假设是：如果把代码级和视觉级标准拆开、按指令合成 rubric，并用同一套 rubric 既过滤 SFT 数据又作为 RL 奖励，那么得到的开放数据与模型会在多个视觉代码基准上超过现有开放基线，并能迁移到不同骨干。支持这一假设的证据主要是后续的过滤消融（ablation，论文 Fig. 5）和跨骨干实验（论文 Fig. 6）；但“信号是唯一瓶颈”并没有被单独证明，数据规模、模型规模和训练预算仍是混杂因素。论文观察到的是现象与相关性，因果解释需要用更严格的对照来补强。

## 2. 创新点是什么？

真正的技术增量不是“发明 rubric”或“使用组相对策略优化（Group Relative Policy Optimization, GRPO）”，而是把逐指令、分解到代码/视觉两个模态的 rubric 做成一条可复用的数据与训练基础设施：同一套标准先在数据侧做筛选，再在策略优化侧做奖励，并用难度带（difficulty band）控制评分粒度。下面逐项拆开。

1. **分解式逐指令 rubric（decomposed per-instruction rubric）。** 每条指令的 rubric 由领域共享标准与样本特有标准组成，且代码级与视觉级分开评分；难度等级决定 rubric 条目数的预算，使复杂样本得到更细的检查、简单样本控制 judge 成本（§3.1，Eq. 1–3）。与 JanusCoder 的固定维度单次 rubric 相比，它多了“按指令定制”和“按难度控制条目数”；与 VinciCoder 的粗到细奖励相比，它把评价对象明确拆成程序与渲染产物。这个想法本身是已有组件的新组合，不是全新的评价理论；其价值取决于分解是否真的带来可测的增益，证据见 §4.3 的过滤消融与案例，但论文没有对“分解”本身做受控消融。

2. **同一 rubric 同时作为数据过滤器与 RL 奖励。** 数据侧用 rubric 分数做三档路由（丢弃、带失败条目反馈重合成、保留），训练侧用同一套 rubric 计算 rollout 分数并做组内归一化优势（advantage）（§3.2、§4.2）。与“过滤器用一套信号、奖励用另一套信号”的常见管线相比，这减少了信号不一致；与任务专用验证器相比，它试图跨格式复用。证据上，过滤侧有论文 Fig. 5 的等规模子集对照，奖励侧只有 Appendix D 的一个聚焦实验，二者的证据强度不同，详见 §4.3。

3. **PrismaCoder-2M 数据资源与配套数据工具。** 论文从四类种子（公共可视化语料、GitHub/arXiv 科学图、网页与交互 demo、符号记谱与化学结构）构建了 2M 样本、18 个任务族、覆盖 13/15 种视觉数据类型的语料，并用抽象语法树（abstract syntax tree, AST）分解、按格式执行门控和 rubric 门控统一处理（§4.1、Appendix A、论文 Table 1/4/5）。与 JanusCoder-800K、VinciCoder-1.6M 等公开语料相比，它的增量主要在覆盖面和统一的质量控制流程，而不是单个新任务。这是资源贡献，不宜直接当作方法创新。

4. **开放模型与跨骨干经验结论。** 作者训练 PrismaCoder-9B 与 PrismaCoder-35B-A3B，并声称发布两者（截至 2026-10-22，仓库只提供 9B 与两个 SFT checkpoint，35B 最终权重尚未上传）；同时在 Gemma-4-31B-it、Qwen3-VL-30B-A3B-Instruct 上复现同一数据与训练配方，报告 12 个指标全部高于各自 base（§5.1、§6.2、论文 Fig. 6）。开放模型本身是资源贡献；“配方可迁移”才是经验贡献。根据本文的 related work 与实验对比，只能确认作者声称的差异；这些设计是否“首次提出”，还需要更完整的文献检索，尤其是 rubric-based reward 与 visual code 数据筛选的交叉领域。

## 3. 作者如何解决？

**输入与任务表示。** 一条训练样本写成 $(x_i,c_i,v_i)$：$x_i$ 是指令，可以是纯文本，也可以带参考图像或待编辑代码；$c_i$ 是对应程序；$v_i=\operatorname{Exec}(c_i)$ 是执行后得到的视觉产物（§3.1）。任务覆盖 18 个族，包括文本到图表、图到代码、文本/截图到网页、网页编辑、SVG、LaTeX、Mermaid、Vega-Lite、LilyPond、Asymptote、Manim 动画、化学结构等（论文 Table 1）。不同族的“正确”定义不同，但都被映射成“代码分数 + 视觉分数”的统一接口。

**总览：一条 rubric，两条回路。** 图 1 把 PrismaForge 的整体结构画在一起：一条是数据筛选回路，另一条是策略优化（policy optimization）回路，两条回路共享同一套逐指令 rubric。数据筛选回路上，种子先经过数据整理模型（curation model）补全代码，再经过与语言匹配的执行/渲染门控，随后由 judge 按代码与视觉 rubric 分别打分，最后按总分路由到丢弃、重合成或保留；策略优化回路上，当前策略对同一指令采样多条轨迹（rollout），执行成功的轨迹进入 judge 得到 rubric 分数，再转成组内优势去更新策略。这个结构的关键不是某个单点模型，而是“评分标准只生成一次，却在两个阶段复用”，从而让数据筛选与奖励信号保持一致。

![图 1：PrismaForge 的双回路总览](/images/dailypaper/2026-10-22/prismacoder_fig1.png)

**图 1**（论文 Fig. 2）：图中把 PrismaForge 分成数据筛选与策略优化两条通路，二者通过中间由指令触发的 rubric 合成相连。数据筛选通路从种子代码出发，先做执行/渲染检查，失败样本进入修复池；通过的样本由 judge 按代码与视觉两组标准打分，再按总分路由为丢弃、带失败条目反馈重合成或保留，保留者构成 PrismaCoder-2M。策略优化通路从当前策略采样多条 rollout，执行失败的 rollout 直接得 0，成功的 rollout 用同一套 rubric 评分，经过组内归一化得到优势，再更新策略。读者应从中理解两点：第一，rubric 是“逐指令生成”的，不是全局固定清单；第二，过滤与奖励不是两套独立评价，而是同一标准的两次使用。

**第一步：合成代码级与视觉级 rubric。** 对每个模态 $m\in\{c,v\}$，rubric 由领域共享项与样本特有项求并集；每个条目有非负权重，judge 对条目给出 $[0,1]$ 的满足度，模态分数是加权平均，最终分数再按 $\lambda_c,\lambda_v$ 组合（§3.1，Eq. 1–3）：

$$\mathcal{R}_i^{(m)}=\mathcal{R}_{\mathrm{shared}}^{(m)}(d_i)\cup\mathcal{R}_{\mathrm{spec}}^{(m)}(x_i),\qquad S_i^{(m)}=\frac{\sum_{r\in\mathcal{R}_i^{(m)}}w_{i,r}^{(m)}f^{(m)}(r,y_i^{(m)})}{\sum_{r\in\mathcal{R}_i^{(m)}}w_{i,r}^{(m)}},\qquad S_i=\lambda_cS_i^{(c)}+\lambda_vS_i^{(v)}.$$

这里 $d_i$ 是样本所属的可视化领域，$\mathcal{R}_{\mathrm{shared}}^{(m)}(d_i)$ 负责该领域反复出现的检查（例如坐标轴、图例、页面结构），$\mathcal{R}_{\mathrm{spec}}^{(m)}(x_i)$ 负责这条指令独有的要求（例如“三条 teal 色 Product 按钮、圆角、footer 在底部”）。难度等级 $q_i$ 不是装饰：每个难度带对应一个 rubric 条目数区间，复杂样本获得更细的检查，简单样本则控制 judge 调用成本（§3.1）。生成 rubric 的模型与打分的 judge 是分开的：论文用 Gemini-3-Pro 生成 rubric，用 Gemini 3 Flash 打分（§5.1），理由是避免 rubric 构造中的偏差在评分时被原样复制（§4.2）。图 2 用一个具体案例说明，代码 rubric 与视觉 rubric 会在同一份输出上给出截然不同的判断。

![图 2：代码与视觉 rubric 的分歧案例](/images/dailypaper/2026-10-22/prismacoder_fig2.png)

**图 2**（论文 Fig. 3）：这是一张按参考页面合成的网页截图，内容、配色和整体分区都被保留下来，但 footer 被放到了 Services 区域中间，遮住并裁掉了第三个 Service 按钮，按钮也变成了直角而不是参考中的圆角。论文 Table 6 给出的逐条判断是：代码 rubric 的 5 项全部通过（背景色、纵向堆叠、居中、footer 颜色、版权文本都能在源码中找到），代码分数 1.00；视觉 rubric 的 5 项只有水平居中通过，视觉分数 0.182；整体 judge 给 78/100。这个例子说明“代码存在”与“视觉关系正确”是两种不同的可验证性，分开评分才能把 footer 遮挡、圆角错误这类局部失败暴露出来。

**第二步：用 rubric 做数据门控。** 种子来自四类互补来源：公共绘图数据集提供基础绘图技能；GitHub 仓库与 arXiv 论文提供长尾科学图；WebCode2M、MCD 等提供网页布局，交互 demo 提供行为；PubChem、LaTeX、Asymptote、LilyPond、Manim 等提供符号记谱与化学结构（§4.1、Appendix B）。如果种子没有可用代码，数据整理模型（curation model，论文用 Claude-Opus-4.6）先生成代码；随后每个候选必须通过与语言匹配的执行/渲染门控：Python 绘图要无头执行并保存图片，HTML 要在无头浏览器里渲染成截图，SVG/LaTeX/Mermaid/Asymptote/LilyPond/Vega-Lite 走各自的标准渲染器，Manim 渲染成帧，化学结构必须解析成合法分子（Appendix A.2）。执行失败或超时的候选进入修复池，而不是直接进入评分。通过执行门控的样本再由 rubric generator 分配难度与两组 rubric，由独立 judge 打分；总分低于 $\tau_1$ 的丢弃，位于 $[\tau_1,\tau_2)$ 的带着失败条目反馈重合成，高于 $\tau_2$ 的保留；最终 SFT 语料还要求总分不低于该领域的 $\tau_{d_i}$（§4.2）。重合成和“以保留样本为种子合成新样本”都会重新进入执行门控，形成一个迭代回路。表 4 给出了各来源的种子数、重生成数和合成数；按表中数字相加，重生成与合成候选约 2.39M，经门控后得到 2M，但论文没有给出逐源最终保留量，因此无法精确核对 2M 的构成。

**第三步：为 RL 挑选“能力边界”上的指令。** RL 数据不是从 SFT 语料随机抽，而是在 SFT 之前就留出一部分指令，SFT 完全看不到它们（§4.3）。作者只保留中等或困难、且 SFT 策略有时成功有时失败的指令：全部成功或全部失败的指令在组相对优化中优势为 0，提供不了学习信号。形式化地，对每个候选指令从 SFT 策略采样 $K$ 条 rollout，用 rubric 打分，计算分数的经验离散度 $U_i$；$U_i$ 越大说明策略在这条指令上越不稳定。实践中，每个领域先留出 20K 条中等/困难候选，采 $K=5$ 条 rollout，保留 $U_i$ 最大的 5K 条；RL 覆盖 Python、HTML、SVG 三个领域（§4.3）。这一步是固定的算法流程，只有 rubric 分数由 judge 决定。

**第四步：SFT 与 rubric-based RL。** SFT 从 Qwen3.5-9B / Qwen3.5-35B-A3B 初始化，做全参数微调 5 个 epoch，最大序列长度 32,768，全局 batch 128，学习率峰值 $1\times10^{-5}$，5% warm-up，最低 $5\times10^{-7}$（Appendix F）。RL 从 SFT checkpoint 初始化，做 1 个 epoch 的 GRPO/GSPO；全局 batch 按 rollout 计为 512（等价于 64 条 prompt × 8 条响应），学习率 $3\times10^{-6}$，KL 系数 0.04，非对称裁剪 0.20/0.28，rollout 用共置 vLLM、张量并行 8、最大长度 36,000、温度 1.0、top-p 0.95（Appendix F）。奖励就是 rubric 分数：执行或渲染失败的 rollout 得 0；对 interface reproduction/editing 这类“允许多种合法实现”的任务，再混入一个整体分数，权重记为 $\lambda_h$（Appendix D、论文 Table 7）。GRPO 的组内优势为

$$\hat{A}_i^{(k)}=\frac{S_i^{(k)}-\mu_i}{\sigma_i+\epsilon},$$

其中 $\mu_i,\sigma_i$ 是同一 prompt 的 $K$ 条 rollout 分数的均值和标准差（§3.2，Eq. 5）。对混合专家（Mixture-of-Experts, MoE）模型，作者还用 GSPO 目标与 Rollout Routing Replay 来稳定专家训练（§3.2）。这样设计的原因是：rubric 分数是 $[0,1]$ 的绝对分，但不同指令的难度不同，直接拿绝对分做策略梯度会让简单样本主导；组内归一化只比较同一指令的 rollout，能把“这条指令上哪种写法更好”变成相对信号。

**第五步：推理与输出。** 训练完成后，模型接收文本指令或参考图像，直接生成对应程序；论文没有描述推理阶段的 rubric 重排、best-of-N 或工具调用，按方法描述，部署时是单次策略生成，rubric 只服务于数据与训练（§3.2、§5.1）。输出是代码及其渲染产物；评测时再按各基准的官方协议执行、渲染、打分（§5.2、Appendix E）。这一点很重要：PrismaCoder 不是“推理时自带评分器的 agent”，而是一个把评价信号内化到数据和参数里的后训练模型。

**哪些由模型决定，哪些由固定流程控制。** 策略决定代码内容；rubric generator 决定难度、条目和权重；judge 决定每条标准的通过与否；执行门控、三档路由规则、$U_i$ 公式、GRPO 目标、阈值和权重组合都是固定流程。论文没有报告 $\tau_1,\tau_2,\tau_{d_i}$ 的具体数值，也没有给出每个难度带的条目数区间，这意味着“哪些样本被保留”这一关键行为无法从论文复现（详见 §5）。从设计理由看，分开代码/视觉是为了捕捉论文 Fig. 3 这类“代码全过、渲染失败”的样本；共享+特有条件是为了避免固定 rubric 太粗、手工 rubric 不可扩展；难度带是为了在评分粒度与 API 成本之间折中；生成器与 judge 分离是为了降低自我偏好；RL 只看离散度高的指令是为了让组内对比有信号。这些理由在论文中都有对应段落，但除了过滤消融外，多数没有“移除该设计会怎样”的对照实验。

## 4. 解决得怎么样？

### 4.1 实验设置

**任务与基准。** 论文在 10 个基准、13 个评测镜头上报告结果。视觉中心套件包括 ChartMimic（图到图表复现，低层元素分与高层 judge 分）、WebCode2M（截图到网页，LLM 分、视觉相似度、CLIP、TreeBLEU）、DesignBench（网页生成与编辑，judge、CLIP、MAE、SSIM、CMS）、Design2Code（截图到网页，block/text/position/color、CLIP、LLM 分）、ChemDraw（图到化学结构，validity、exact match、Tanimoto）、InteractScience 的 VQT 镜头、UniSVG 的 ISVGen 镜头。文本中心套件包括 ArtifactsBench（五类产物总体分）、PandasPlotBench（错误代码率、visual/task 均值、Good≥75）、VisPlotBench（八种可视化语言）、InteractScience 的 PFT 镜头、UniSVG 的 TSVGen 镜头（§5.2、Appendix E）。

**模型与基线。** PrismaCoder-9B 从 Qwen3.5-9B 后训练，PrismaCoder-35B-A3B 从 Qwen3.5-35B-A3B 后训练；后者虽然名字里有 35B，但激活参数只有 3B，和 9B dense 模型不是同一算力档位（§5.1）。基线包括 Qwen3.5 两个 base、JanusCoderV-7B/8B、VinciCoder-7B/8B、VisCoder2-7B，以及 GPT-4o、Gemini 3 Flash、Gemini 3.1 Pro、Claude Sonnet 4.6、Claude Opus 4.6 等 proprietary 模型（论文 Table 2/3）。跨骨干实验另外训练 Gemma-4-31B-it 与 Qwen3-VL-30B-A3B-Instruct，但只覆盖 Python plotting 与 HTML 两个域（§6.2）。

**指标与公平性。** 评测遵循各基准的官方协议，并尽量使用其指定 judge；ChartMimic 的高层分因为原 judge 不可用，改用 GPT-5.5（Appendix E）。这意味着主表混合了确定性指标（执行率、exact match、Tanimoto、block/text 匹配）与 LLM judge 分数，后者对提示和 judge 版本敏感。基线不是在同一数据与算力预算下重训的，PrismaCoder 使用了 2M 数据和 32 张 H200，因此“超过开放基线”不能直接解释为“方法更优”，其中包含数据规模与训练预算的差异。主实验回答“最终模型是否领先”，论文 Fig. 5 回答“rubric 过滤是否比整体打分过滤更好”，论文 Fig. 6 回答“配方能否迁移到别的骨干”，论文 Fig. 7 与 Appendix H.2 回答“rubric 是否更贴近人类”，Appendix G 给出每个基准的完整指标。

**视觉中心：提升最大，但不是全面领先。** 在 ChartMimic 上，PrismaCoder-9B 的低层分从 Qwen3.5-9B 的 58.35 提到 81.57，高层分从 55.55 提到 73.82；35B 从 70.22/63.90 提到 83.42/80.69（论文 Table 2）。Design2Code 的视觉分 91.54 比任务专用开放基线 VinciCoder-8B 的 81.89 高 9.65，LLM 分 70.51 比其 45.72 高 24.79；相对其 Qwen3.5-9B base 的 85.60/53.12，则分别提升 5.94/17.39。DesignBench 生成 judge 69.95 比 VinciCoder-8B 的 48.09 高 21.86，基本追平 Gemini 3.1 Pro 的 69.47；但编辑 judge 只有 8.93/8.89，低于 Gemini 3.1 Pro 的 9.57，是作者承认的弱项（论文 Table 2/15/16）。ChemDraw 上 35B 的 128 个输出全部可解析，exact match 92.19%、Tanimoto 97.56，远高于其 base 的 53.12%/79.86，也高于 Claude Opus 4.6 的 52.34%/77.71（论文 Table 13）。这些是论文最强的证据，尤其是 ChemDraw 的确定性指标和 Design2Code 的多维视觉指标，不容易仅由 judge 偏好解释。

**文本中心：仍是明显短板。** ArtifactsBench 上 35B 的 46.01 高于任务专用开放基线（最好 31.16）和 GPT-4o（33.54），但相对 Qwen3.5-35B base 的 44.98 只领先 1.03，且低于 Gemini 3 Flash 的 51.42、Gemini 3.1 Pro 的 53.04、Claude Sonnet 4.6 的 64.65（论文 Table 3/17）。PandasPlotBench 上 35B 的 visual/task 均值为 62.38/79.85，错误率 9.29%，而 GPT-4o 是 67.63/82.46、8.00%，Claude Opus 4.6 是 76.03/94.97、1.71%（论文 Table 9）。VisPlotBench 上 35B 的均值 62.47 高于所有开放模型（Qwen3.5-35B 为 51.45），但低于 Claude Opus 4.6 的 65.94 与 Gemini 3.1 Pro 的 69.47；Good≥75 的 61.49 也低于 Claude Opus 的 66.03 与 Gemini 的 69.15。错误率 28.86% 虽低于任务专用基线 VinciCoder-7B 的 35.90%，却远高于 Qwen3.5-35B base 的 15.43%、VinciCoder-7B 的 9.14% 与 Claude Opus 的 1.71%（论文 Table 3/10）。InteractScience PFT 的 28.00 低于 GPT-4o 的 31.07 和 Gemini 3.1 Pro 的 44.13（论文 Table 3/18）。这些结果说明“rival proprietary”只在部分视觉中心任务上成立，文本中心与长尾语言仍有明显差距。

**规模与覆盖的细节。** 一个反直觉现象是 9B 在不少视觉列上优于 35B-A3B：WebCode2M 的 LLM/visual/CLIP（69.72/90.41/88.46 对 67.78/89.66/87.78）、DesignBench 的生成/编辑（69.95/8.93 对 68.98/8.89）、Design2Code 的 LLM/视觉（70.51/91.54 对 67.55/91.22），9B 都更高（论文 Table 2）。但 UniSVG 的 ISVGen 相反，35B 为 84.14、9B 为 69.64。这不一定是“大模型更差”，因为 35B-A3B 只有 3B 激活参数；但它提醒读者不要把“35B”当成 9B 的等算力放大版。另一个细节是 UniSVG 的 ISVGen：VinciCoder-8B 的 87.18 高于 PrismaCoder-35B 的 84.14，作者也承认这是唯一一个由开放基线领先的视觉中心列（§5.3）。平均分确实掩盖了任务间差异：PrismaCoder 在 ChartMimic、Design2Code、ChemDraw 上很强，在 PandasPlotBench、ArtifactsBench、VisPlotBench 的某些指标上仍落后于较老的 proprietary 模型。

**统计稳定性。** 论文没有报告重复运行、方差、置信区间（confidence interval）或显著性检验；ChemDraw 只有 128 个测试样本，1 个样本就是 0.78 个百分点，9B 与 35B 在该表上的差距可能落在噪声范围内（论文 Table 13）。主表的多数比较是单次评测，LLM judge 的温度和重复次数也没有说明。这不是说结果不可信，而是说“领先 0.2 分”这类差距不应被过度解读。

### 4.3 机制证据

**过滤环节的证据相对最干净。** 图 3 的消融把同一数据池分成两个等规模子集，一个用整体 judge 分数过滤，一个用 PrismaForge rubric 过滤，再在同一个 Qwen3.5-9B 上做 SFT；8 个基准全部是 rubric 过滤更高，Vega-Lite 从 48.5 提到 72.6（+24.1），Design2Code 只从 68.0 提到 68.2（+0.2）（§6.1、论文 Fig. 5）。因为两个子集大小相同，这个对比至少排除了“rubric 子集更大”的解释，把差异收窄到“两个 judge 保留了哪些样本”。但它仍只有一个骨干、一次运行，且没有拆开 rubric 的各个组成部分（共享项、样本特有项、代码/视觉分解、难度带）分别做消融。

![图 3：rubric 过滤与直接打分过滤的对比](/images/dailypaper/2026-10-22/prismacoder_fig3.png)

**图 3**（论文 Fig. 5）：横轴是 8 个评测，纵轴是 LLM 分数；每组两根柱子分别代表“整体 judge 过滤”和“PrismaForge rubric 过滤”，颜色区分视觉中心与文本中心任务。图上每个基准的 rubric 柱子都更高，Vega-Lite 的差距最大，Design2Code 几乎持平。这个图支持“在固定数据规模下，rubric 过滤选出的样本更适合训练”，但它比较的是过滤信号，不是完整模型；读者不能从这张图直接推断 RL 奖励也一定更好。

**跨骨干证据支持“配方可迁移”，但覆盖有限。** 图 4 在 Gemma-4-31B-it 与 Qwen3-VL-30B-A3B-Instruct 上，对 ChartMimic、WebCode2M、DesignBench、Design2Code、VisPlotBench 的 Python/HTML 等 12 个指标画出 base、+SFT、+SFT+RL 三档；作者报告所有 12 个指标最终都高于 base，且 RL 在每一个指标上都比 SFT 更高（§6.2、论文 Fig. 6）。这比“只在一个骨干上有效”强，但仍只覆盖两个域，且没有报告每个点的方差；此外 SFT 单独在部分指标上会低于 base（图中有负增益点），说明 SFT 数据并非对所有指标都单调有益，RL 的作用之一是“把 SFT 拉下来的指标补回来”。

![图 4：两个骨干上的 SFT/RL 分阶段增益](/images/dailypaper/2026-10-22/prismacoder_fig4.png)

**图 4**（论文 Fig. 6）：每个指标是一根从 base 到最终模型的哑铃，圆点标出 base、+SFT、+SFT+RL 三档；横轴按 ChartMimic、WebCode2M、DesignBench、Design2Code、VisPlotBench 的 Python/HTML 等指标排列，纵轴是相对 base 的增益。可以看到有些指标的 SFT 点落在 0 以下，最终 RL 点又回到 0 以上；ChartMimic 的增益主要来自 SFT，HTML 的增益更多来自 RL。这张图说明“同一数据与训练配方可以迁移到不同骨干”，但它不是全基准消融，不能回答 9B/35B 在 13 个评测镜头上的平均 RL 贡献。

**人类一致性证据很强，但设计有混杂。** 图 5 报告 100 个训练样本上，三个 proprietary judge（Claude Sonnet 5、Gemini 3.5 Flash、GPT-5.5）与人类评分的绝对一致性（Krippendorff's α）和排序一致性（Kendall's τb）。直接整体打分时 α 为 0.30–0.51、τb 为 0.28–0.44；改用 PrismaForge rubric 后 α 升到 0.86–0.92、τb 升到 0.64–0.67（§6.3、Appendix H.2、论文 Table 20）。这说明 rubric 不仅让分数更接近人类，也让不同 judge 诱导出的排序更稳定；对 RL 来说，排序稳定性比绝对分数更重要。不过，人类标注者在 rubric 模式下也使用同一套 rubric，direct 模式下则看整体分，两种模式的任务结构不同；每个样本每种模式只有 2 个人类评分，论文没有报告人类-人类一致性、标注者资质或置信区间。因此这组证据更适合支持“rubric 评分与人类在同一语义下更一致”，不足以单独支持“PrismaCoder 的输出在开放人类偏好上更好”。

![图 5：三种 judge 与人类评分的一致性](/images/dailypaper/2026-10-22/prismacoder_fig5.png)

**图 5**（论文 Fig. 7）：两段分别是 Krippendorff's α 与 Kendall's τb，每段有三行，对应三个 judge；空心点代表 direct 整体打分，实心点代表 PrismaForge rubric 打分。所有 judge 的实心点都明显向高一致性方向移动，α 的提升尤其大，τb 的提升较小但仍一致。这张图回答的是“评分方式是否更贴近人类”，不是“模型输出是否更受人类欢迎”；后者需要独立的人类盲评，论文没有做。

**把三类证据放在一起看。** 过滤消融（论文 Fig. 5）最直接地支持“rubric 数据筛选有效”；跨骨干实验（论文 Fig. 6）支持“配方不是只对一个模型有效”；人类研究（论文 Fig. 7）支持“rubric 评分比整体分更稳定、更接近人类”。但论文对“代码/视觉分解本身是否必要”“共享项与样本特有项各贡献多少”“难度带是否真的优于固定条目数”“rubric 奖励是否优于直接分数奖励”都没有做完整消融。尤其是奖励侧：Appendix D 明确说资源限制阻止了完整的 GRPO 对比，只在一个 Python plotting 的聚焦实验里报告 rubric scoring 比 direct scoring 在 ChartMimic overall 上高 6.91 分。这个数字有价值，但它是一个域、一个设置、一个基线的结果，不能支撑“同一 rubric 作为奖励在所有格式上都更好”的强结论。因此，论文的机制证据是“部分成立”：数据过滤的因果链较清楚，奖励与分解的因果链仍主要靠设计理由和下游结果间接支持。

### 4.4 成本与适用范围

**实际付出的成本。** 数据侧的核心开销是 rubric 生成与 judge 调用。Appendix C 报告：常见可视化任务（如 Python plotting）单样本 rubric 生成约 $0.006、代码与视觉评估约 $0.01；HTML 任务因为代码更长，rubric 生成约 $0.01、评估约 $0.04。RL 侧，一次完整 GRPO 训练约 808K 次 judge 请求；由于代码与视觉分开评分，rubric 方法的 API 成本约为“只评视觉输出”的 2 倍（Appendix D）。训练侧使用 4 个节点 × 8 张 H200，共 32 张 GPU；SFT 5 个 epoch、RL 1 个 epoch，全参数训练，序列长度 32K/36K（Appendix F）。论文没有报告总 GPU 小时、总 API 费用、数据构建的总人工成本，也没有报告推理时延或吞吐。按 2M 样本粗算，即使按最低的 plotting 单价，数据侧也是数万美元量级；这只是分析者根据单价做的量级估算，不是论文给出的数字。

**人工与外部依赖。** 人类研究用了 20 名标注者、100 个样本、每人 10 个 direct + 10 个 rubric，共 400 条评分；论文没有报告标注者背景、培训、报酬或人类-人类一致性（Appendix H.2）。数据构建依赖 Claude-Opus-4.6、Gemini-3-Pro、Gemini 3 Flash 三个 proprietary API；Appendix C 又写“use Gemini-3-Flash for rubrics”，与 §5.1 的 Gemini-3-Pro rubric generator 不一致，读者无法确认实际配置。虽然论文说 PrismaForge 的模型是可插拔的，但换模型后 rubric 质量、成本和结果都可能变化，论文没有给出跨生成器/跨 judge 的鲁棒性实验（§5.1、Appendix C）。数据来源包括 GitHub、arXiv、3Blue1Brown 视频代码和 PubChem，论文没有讨论代码/图像的许可证、署名或再分发限制，这对“开放数据集”的实际可用性是一个未决问题。

**适用范围与仍未解决的问题。** 方法适用于“有可执行程序、能渲染成视觉产物、正确性可被分解成检查项”的任务；论文覆盖 18 个任务族，但评测只覆盖 13 个镜头，Manim 动画与定理/符号可视化明确只作为训练数据、不参与评测（Appendix E）。在视觉中心任务上，PrismaCoder 已经能超过开放基线并与部分 proprietary 模型接近；在文本中心、长尾语言和交互式科学演示上，它仍落后于最强 proprietary 模型。方法没有解决 reward hacking、judge 自偏好、训练/测试同源和推理阶段无法自我检查的问题；它把“评价”前移到了数据和训练，而不是让模型在部署时调用 rubric。结论的合理边界是：在论文覆盖的视觉代码任务和 9B/35B-A3B 规模上，rubric 过滤的数据与 rubric 奖励的 RL 能带来可测提升；不能外推为“通用代码能力”或“所有多模态产物”的普遍提升。

#### 质疑：训练数据与评测基准高度同源，去污染只检查指令 n-gram，无法排除测试集泄漏

- **原文依据**：论文 Table 4 把 WebCode2M、UniSVG、PubChem、arXiv/GitHub 作为训练数据源；§5.2 又在 WebCode2M、UniSVG、ChemDraw、ChartMimic 上评测；Appendix A.3 只按“instruction shares a long n-gram with a test instruction”删除样本，没有报告图像、代码或分子结构的去重。
- **为什么重要**：如果测试样本或近邻进入训练，ChartMimic、ChemDraw、WebCode2M 的高分可能部分来自记忆而非能力；这直接影响“开放 SOTA”的结论，也会让跨模型比较失真。
- **当前能够得出的判断**：无法确认存在泄漏；论文没有给出训练/测试 split 的交集统计，也没有说明 WebCode2M 使用的是哪个 split。仅按指令 n-gram 去污染，无法排除“同一张参考图换了描述”“同一段代码改了变量名”“同一分子换了表示”的近重复；若确认重叠，则升级为致命问题。
- **如何验证或补强**：报告每个基准与训练集的 ID 交集；对图像做感知哈希、对代码做 AST/规范化相似度、对分子做 canonical SMILES 最近邻检索，并给出阈值与命中数；在完全去重后的训练集上重训并复测；对 ChemDraw 的 128 个测试分子做 PubChem 最近邻审计。
- **严重程度**：主要问题。

#### 质疑：核心的“rubric 作为 RL 奖励”没有被完整隔离，RL 贡献与数据规模、SFT 数据质量混在一起

- **原文依据**：§5 主表只报告最终模型；Appendix D 明确“Resource constraints prevented a full GRPO comparison between PrismaForge and direct scoring”，只给了一个 Python plotting 的聚焦实验，rubric scoring 比 direct scoring 在 ChartMimic overall 上高 6.91；论文 Fig. 6 只覆盖 Gemma-4-31B 与 Qwen3-VL-30B 的两个域、12 个指标。
- **为什么重要**：论文标题与贡献把“同一 rubric 既做过滤又做奖励”作为核心；如果 RL 的增益主要来自 SFT 数据或模型规模，核心主张就被削弱。主表也没有给出 9B/35B 的 SFT-only 与 SFT+RL 全基准对照，读者无法量化 RL 的平均贡献。
- **当前能够得出的判断**：SFT 阶段的收益有论文 Fig. 5 的等规模过滤消融支持；RL 阶段的全基准收益只有论文 Fig. 6 和附录案例，证据强度明显低一档。RL 奖励优于直接分数奖励的结论，目前只能在一个域的一个实验上成立。
- **如何验证或补强**：在同一 SFT checkpoint 上报告 9B/35B 的 SFT-only 与 +RL 全基准表；做 direct-score reward、rubric reward、rubric+holistic reward 三组同预算 GRPO；报告每组在 ChartMimic、Design2Code、VisPlotBench 上的均值与方差；对 λ 权重和 holistic 权重做敏感性分析。
- **严重程度**：主要问题。

#### 质疑：训练 judge 与评测 judge 同族，主结果又高度依赖 LLM judge，存在自偏好与“裁判即训练信号”风险

- **原文依据**：§5.1 数据门控和 RL 都用 Gemini 3 Flash 作 judge；§5.2/Appendix E 的多个基准使用 LLM judge 分数；§6.3 声称“gains hold across judge models”，但 Appendix H.1 的论文 Table 19 只在 Gemma 的 VisPlotBench 上换 GPT-4.1/GPT-5.5 复评，没有对 PrismaCoder-9B/35B 的主表做跨 judge 复评。
- **为什么重要**：如果 Gemini 3 Flash 在训练中被优化，它给出的分数可能系统性偏高；主表的 DesignBench、Design2Code、ArtifactsBench、PandasPlotBench 等列又依赖 judge，结论可能是“迎合 judge”而不是“视觉正确”。Gemini 3 Flash 本身还作为 proprietary 基线出现在主表中，训练 judge 与被比较模型同体，比较的解释会更复杂。
- **当前能够得出的判断**：无法确认自偏好的大小；论文只证明了 rubric 评分与人类评分更一致（论文 Fig. 7），没有证明最终模型在独立 judge 或人类评估下仍保持同样的领先幅度。
- **如何验证或补强**：用 GPT-5.5、Claude Sonnet 5 等独立 judge 盲评主表全部模型；报告 judge 间排序一致性（Kendall τ）和分数差；对同一批输出做 100–200 例人类盲评，比较 PrismaCoder 与最强 proprietary；把训练 judge 换成另一家族，重跑小规模 RL，观察增益是否保留。
- **严重程度**：主要问题。

#### 质疑：关键超参数、阈值与推理协议缺失，开源发布也不完整，当前难以复现

- **原文依据**：§3.1 只说难度带对应“bounded range”的条目数，没有给出每个难度带的 min/max；§4.2 的 $\tau_1$、$\tau_2$、$\tau_{d_i}$ 没有数值；Eq. 3 的 $\lambda_c,\lambda_v$ 在数据门控中未给出；Appendix F 给了训练超参，但没有推理时的 prompt、解码参数、尝试次数；README（2026-10-22）的 roadmap 显示 PrismaForge rubric 合成/评分/数据门控、SFT/RL 训练脚本、35B 最终权重和完整 2M 数据集仍未发布。
- **为什么重要**：这些不是实现细节，而是决定“多少样本被保留、rubric 多细、RL 奖励如何组合”的核心变量；没有它们，外部无法复现 2M 的构成和训练结果。论文声称“release our code, model, and data”，但当前仓库只覆盖部分渲染检查、部分 RL verifier 和两个评测脚本，与“全开放”不一致。
- **当前能够得出的判断**：即使拿到 9B 权重，也无法从零重建数据与 RL；论文的可复现性目前是“部分可复现”。35B 最终权重只有 README、没有 safetensors，2M 数据集仍在分批上传，这两点会直接影响对“开放 SOTA”的独立验证。
- **如何验证或补强**：补齐阈值表、难度带条目预算、λ 权重、每任务样本数、推理 prompt/解码设置；发布 PrismaForge 代码与完整数据卡；给出从 seed 到 2M 的可执行脚本和版本锁定；在 README 中明确哪些结果是可复现的、哪些依赖未发布组件。
- **严重程度**：主要问题。

#### 质疑：人类研究的设计不足以支撑“更符合人类偏好”的强结论

- **原文依据**：§6.3/Appendix H.2 只用了 100 个训练样本、20 名标注者、每个样本每种模式 2 个人类评分；没有报告标注者资质、培训、报酬、人类-人类一致性；rubric 模式下人类也按 rubric 打分，direct 模式下按整体分打分，两种模式的任务结构不同。
- **为什么重要**：α 从 0.30–0.51 升到 0.86–0.92 很醒目，但如果人类和 judge 共享同一套 rubric 结构，这种一致性可能部分来自评分界面，而不是“模型 judge 更像人”；而且研究评的是训练样本，不是模型输出。
- **当前能够得出的判断**：可以支持“在同一 rubric 语义下，judge 与人类的绝对一致性和排序一致性更高”；不能支持“PrismaCoder 的输出在开放人类偏好上更好”。论文的贡献段把后者写成结论，属于表述过度。
- **如何验证或补强**：报告人类-人类 α/τ 作为上限；让独立标注者在不知道模式的情况下盲评模型输出；把样本扩大到每个基准 100–200 例并报告置信区间；比较 rubric 与 direct 在同一批样本上的排序差异，而不是让两种模式对应不同样本。
- **严重程度**：次要问题。

## 6. 审稿式总评

作者发现多模态代码数据的质量信号存在结构性缺口：代码可执行、实现合理、渲染正确是三种不同的正确性，单一的通过/失败、代码相似度或整体 judge 分数都无法同时覆盖，也无法定位错误。因此他们提出 PrismaForge，用按指令合成的、分解为代码级与视觉级的 rubric 同时做数据过滤和 RL 奖励，并据此构建 PrismaCoder-2M、训练 PrismaCoder-9B/35B-A3B。实验在 13 个评测镜头上表明：视觉中心的 ChartMimic、Design2Code、DesignBench 生成、ChemDraw 等结果较强，部分指标接近或超过 proprietary 模型；但文本中心的 ArtifactsBench、PandasPlotBench、VisPlotBench、InteractScience PFT 仍明显落后，RL 的全基准贡献、训练/测试同源、judge 独立性与关键阈值披露仍缺少充分支持。本文最有价值的部分是把“评价标准”做成可复用的数据与训练基础设施，并用等规模过滤消融和跨骨干实验展示了它的可迁移性；最大的审稿风险是数据与评测同源、奖励消融不完整，以及“开放”发布目前只完成了一部分。

- **问题定义清晰度**：强。§1 与 §3.1 把“代码正确/实现合理/渲染正确”三种正确性拆得很清楚，论文 Fig. 3 的案例也把失效模式具体化；任务族、基准和指标的定义基本完整。

- **创新性证据**：中。逐指令 rubric、代码/视觉分解、同一 rubric 双用是有意义的组合，但各组件在 prior work 中都有影子；论文没有对“分解”本身做受控消融，也没有充分比较其他 rubric 生成策略，因此“首次提出”的边界只能确认作者声称的差异。

- **方法可信度**：中。执行门控、独立 generator/judge、组内归一化奖励等设计是合理的，管线从输入到输出能走通；但阈值、难度带、λ 权重未披露，reward hacking 与 judge 自偏好没有系统评估，方法可信度受可复现性拖累。

- **实验支持力度**：中。基准覆盖广，视觉中心结果有确定性指标支撑，过滤消融和跨骨干实验是加分项；但缺少重复运行/方差/置信区间，文本中心仍有明显落后，RL 奖励只有单域聚焦实验，人类研究的设计也有混杂。

- **可复现性**：弱。核心 rubric 管线、SFT/RL 脚本、35B 最终权重与完整 2M 数据集截至 2026-10-22 仍未发布，关键超参数与推理协议缺失；已发布的 9B 权重和部分数据/工具只能支持部分复现，无法支持从零重建。

- **综合阅读价值**：高。对做多模态代码、可视化数据合成、rubric-based reward 或后训练数据筛选的读者，这篇论文提供了完整的管线视角、可借鉴的失败案例和一组值得复核的实验；阅读时应把“视觉中心的强结果”和“文本中心的弱结果、开放承诺的缺口”分开看。
