Coding Agents for Generalized Task and Motion Planning Problems

GIn Lv3

1. 作者发现了什么问题？

任务与运动规划（TAMP）即使在完全可观测、状态以物体为中心（object-centric）的设定下依然很难：horizon 长、奖励稀疏，离散决策（操作哪个物体、用哪个工具、先做哪个子目标）与连续的几何/运动学/动力学约束死死耦合——换一个离散选择，剩下的可行运动空间就完全变了（§I、§II-B）。通用化 TAMP（generalized TAMP） 的思路是：同一环境里不同实例之间有规律可循，把规律固化下来就能在新实例上少花力气。此前做法是学习可复用的 sampler、可行性预测器、搜索启发式或状态/动作抽象，但每一种都需要大量 TAMP 专用工程（§V-A）。

作者的问题很直接：既然编码 Agent 在软件工程任务上越来越强，它们能不能把这份「领域工程」自动化——只给任务描述和模拟器访问，让 Agent 自己写一个跨实例通用的程序？这个问题在文献里证据是矛盾的：LLM 在经典规划上的表现持续变好（如用 LLM 生成 Python 启发式），但当 LLM 被要求承担 TAMP 里的几何与物理决策时表现很差，即使把相关几何放进提示词也一样（§I，引 Mendez-Mendez 2026 对 PDDLStream 的系统研究）。所以「写代码的能力」能否迁移到「物理推理」并不显然，两种结果对该领域都有价值（成功意味着可以大幅减少领域工程，失败则给出当前 Agent 的具体能力边界）。

这里要分清：本文不是提出一个新的规划算法，而是一项系统性实证研究（作者称方法为 AgenticGenPlan）：在 28 个环境上，把「通用化 TAMP」直接当成程序合成问题，检验现成编码 Agent 能走多远，并把交互日志、程序演化过程一起分析清楚。

2. 作者如何解决？

核心思路。 学习方法在合成期拥有任务描述 ddd 与模拟器访问权（可反复 reset/step），在固定预算内自由探索环境、写代码、做实验，最终交付一个程序；评测期程序被冻结，LLM 完全不在场，只在未见过的初始状态分布 s0∼ρs_0\sim\rhos0​∼ρ 上跑。程序即策略：在每个时间步接收物体中心状态 sts_tst​，返回动作 ata_tat​；由于程序可有内部状态，等价于以交互历史为输入的策略 at=π(ht)a_t=\pi(h_t)at​=π(ht​)（§II-A、§II-C）。这样「通用化」的收益不来自测试时的模型调用，而来自程序里固化的、跨实例复用的规律。

原文图 1：上排为研究覆盖的 28 个 KinDER/PDDLStream 环境；中排对比传统路线（人工编写谓词/算子/sampler 再交给 planner）与本文路线（Agent 在沙箱里调试出程序，冻结后跨实例复用）；下排为平均性能、成功率随物体数变化、单实例计算时间随物体数变化，橙色为 AgenticGenPlan。

具体流程（§III-A）。 作者用两个厂商的现成编码 Agent：Claude Code + Opus 5（high），以及 Codex + GPT-5.6 Sol（medium）与 GPT-6 Astra（high）。所有基线也用 Opus 5，保证模型一致。Agent 跑在隔离的 Docker 沙箱里（独立文件系统、无网络），只给 Python + NumPy + SciPy，连环境源码都不给——迫使它生成端到端程序而不是调用现成库。初始提示包含：环境名，任务、观测空间、动作空间、目标的文字描述，以及「物体数量会变化、程序必须支持任意合法数量」和评测时限 τ\tauτ 的说明；不提供任何手写谓词、算子、sampler 或技能。为支持交互学习，Agent 拿到一个实现了 reset、step 与渲染辅助函数的客户端，真正的环境服务器在容器外不可见。程序接口固定为一个类：reset 做回合初始化，get_action 计算动作。每次测试前要求 Agent 把程序提交到 git，于是能看到程序的修订历史并回放每次提交的表现。

另有 + source 设置：把环境源码放进容器（Opus + source、Astra + source 两组）。这一设置给 Agent 的是「完整信息」参照——它可以直接读目标判定、导入逆运动学等辅助实现，也能在合成期直接设置任意状态、在私有模拟器里试动作。注意这只是参照条件，主设置才是论文主张的「除任务描述与模拟器外零工程」场景。

与什么比较（§III-B）。 三类基线：① TAMP planner：符号搜索 + 采样满足连续约束，谓词、算子、sampler、运动规划技能都用官方实现，每个评测实例重新规划；28 个环境中有 16 个提供 planner（KinDER 13 个 + PDDLStream 3 个，PDDLStream 环境的 planner 就是 PDDLStream 本身）。② LLMGenPlan：用 Opus 5、关闭思考、无工具、无文件系统，但给全环境源码；它不能自己跑实验，只能收到固定管线返回的三类预定义反馈（异常栈、非法动作、某 seed 实例未解出），预算与编码 Agent 相同。③ One-shot：LLMGenPlan 生成的第一个程序，代表没有任何迭代反馈的一次性生成。

评测协议（§IV-A）。 28 个环境 = KinDER 25 个（Kinematic2D、Dynamic2D、Kinematic3D、Dynamic3D 四族，其中 19 个环境有不同物体数的变体，且物体数超出原基准评测范围）+ PDDLStream 3 个域（Packing、Blocked、Rovers）。每个方法每环境跑 5 次独立合成；每次合成预算 $20（模型费用）；每次合成出的程序都在同一批 100 个隐藏实例上评测（评测 seed 随机生成并核验过未在合成期出现过）；单实例超时 60 秒，与 KinDER 原协议一致。7 种合成方法（LLMGenPlan、One-shot、Opus、Sol、Astra、Opus + source、Astra + source）× 28 环境 × 5 次 = 980 个程序，共 98,000 个评测回合。

3. 解决得怎么样？

Q1：Agent 能写出通用程序吗？能，而且超过手工 planner（表 I、表 II）。 在有 planner 的 16 个环境上，三种 Agent 配置的平均成功率均高于 planner 的 47%：Astra 95%、Opus 82%（约 1.7 倍于 planner）、Sol 56%；逐环境看，Astra 在 15/16 个环境超过 planner，Opus 12 个，Sol 9 个——而 planner 用的是人工写好的谓词、算子、sampler 和技能，Agent 什么都没拿到。按环境族看，Astra 平均为 Kinematic2D 99%、Dynamic2D 97%、Kinematic3D 93%、较难的 Dynamic3D 65%、PDDLStream 近 100%；Opus 依次是 96%、92%、90%、45%、78%。Astra 在 28 个环境里 20 个高于 Opus，其中 11 个环境里「最好的 Opus 程序」其实不差于「最好的 Astra 程序」，差距主要来自稳定性（例：Shelf 上 Opus 的 5 次程序成功率从 0% 到 100%，而 Astra 每次都先测到 8 个方块再改，全部 ≥98%）。Opus 在 22/28 个环境高于 Sol（4 个持平），只有 Dynamo 和 Blocked 例外——Blocked 上 Sol 75%、Opus 38%、planner 74%。

Q2：Agent 发现了什么策略？ 论文展示了一批「未见诸公开解」的策略（图 2），作者认为这是最有说服力的定性证据之一——因为公开文献里没有的解，很难归因于记住了预训练数据。例子：Dynamic2D ScoopPour 中 Opus 程序把工具旋转后从左侧重新抓取，一次能舀起更多球；SweepIntoDrawer 中 Opus + source 程序干脆不用扫帚工具，用夹爪把方块一个个扫进抽屉；其余还有用工具长边推物、只移动两个障碍物、放弃工具用夹爪抓取并倾倒托盘等。

原文图 2：Agent 发现的意外成功策略，每行一次执行（左到右），标注为该行的非预期行为。这些策略来自主设置与 + source 设置。

Q3：「agentic」优势在哪里？ 三个可观察的机制：① 自写测试：StickButton 中 Opus 写脚本用不同随机种子反复 reset，专门搜集「棍子贴墙」「按钮很高」的边界实例，和普通实例构成测试集来挑战自己的程序（图 3 左）。② 自建并校准内部模型：Shelf 里一次 Opus 运行凭先验知识写出 Kinova Gen3 的运动学模型，再用夹持的方块当标记物（状态只暴露物体位置、不暴露手的位置），通过多组关节角—方块位置观测拟合出 6 个装配/抓取偏移参数，把校准观测上的 RMSE 从 38.9 mm 降到 1.8 mm，然后用这个模型做逆运动学（图 3 右）。③ 持续精化策略：BalanceBeam 里 Sol 把放小方块的目标点向横梁中心收拢，成功率从 6% 升到 64%；Blocked 里 Sol 增加「近处方块抓不动就改用远处无障碍方块」的回退分支，成功率从 15% 升到 56%（新解 41 个实例、没有损失任何原有成功），后续提交到 83%（图 4）。

原文图 4：合成期间的策略精化。Sol 在 Blocked 的一次运行中，加入「备用方块」回退后成功率从 15%（A）提升到 56%（B）；曲线是各次 git 提交版本在隐藏实例上的成功率（按提交顺序）。

Q4：程序算得快吗？ 在四种配置都至少有一次满分运行的 15 个环境上（表 III，按各自满分运行平均）：主设置 Opus 平均 11.7 ms/动作，Astra 平均 1.3 ms/动作（约快 9 倍）；+ source 版反而慢得多（Opus 42.5 ms、Astra 50.4 ms），因为很多程序在决策时直接调用环境源码里的 IK/碰撞检查/运动规划。风格上 Astra 偏向紧凑的闭式控制（少量硬编码关节位姿或解析 IK），Opus 偏在决策时搜索大量预计算候选并带重试/回退逻辑。与 planner 比：在有 planner 且有多种物体数的 14 个环境上，Opus 与 Astra 程序平均每实例 2.1 s 与 0.5 s，而 planner 要 29 s；随着物体数增加，planner 越来越慢、成功率下降，Agent 程序则保持较高成功率（图 1 下排）。

Q5：给源码有帮助吗？ 有——Opus 平均 74%→84%，Astra 86%→95%——但源码本身不够：同样拿到源码、同样 $20 预算的 LLMGenPlan 只有 28%，Opus + source 在 28 个环境中的 27 个更高。源码的价值一半在信息（例如 SortClutteredBlocks 里主设置的 Astra 程序只能靠状态顺序猜方块该进哪个箱，四块能过、二十块全挂；读源码后直接读到目标箱，43%→95%），一半在实现复用（导入 IK、调运动规划与碰撞检查、在私有模拟器里试动作；Packing 中一次 Opus + source 运行发现是夹爪（而非被夹的零件）与架子碰撞，于是改了抓取姿态）。

代价与未解决的问题（§VI）。 所有结论都建立在完全可观测、物体中心状态、可访问模拟器的假设上，不涉及感知不确定性；评测全部在仿真里，没有真机。模型训练数据未公开，无法完全排除预训练见过基准代码，作者的反驳证据是合成日志显示程序是经过探测、测试与多次修订逐步演化的，且包含公开解里没有的策略。失败仍集中在 Dynamic3D 的「扫/倒大量小物体」类任务：Astra 在该族平均只有 65%，比如 Dynamic3D 的 ScoopPour 上各 Agent 都放弃「舀」、改为整体搬托盘，Astra 主设置只有 0.14（+ source 0.42，主设置 Opus 0.09）；ConstrainedCupboard 上 Astra 只有 0.29（Opus + source 0.47）；Sol 整体明显弱于 Opus 与 Astra。

作者发现通用化 TAMP 的既有方法需要大量 TAMP 专用工程，而 LLM 直接做几何物理决策表现很差，因此提出把「通用化 TAMP」交给现成编码 Agent：只给任务描述、模拟器客户端与固定预算，让 Agent 自己在沙箱里探测环境、写测试、校准物理模型并迭代程序，冻结后在隐藏实例上评测，实验覆盖 28 个环境、980 个程序、98,000 个回合，表明三种 Agent 配置的成功率（56%–95%）全面高于手工 planner（47%，16 个可比环境），单实例计算量比 planner 低约一个数量级，并发现了一批未见诸公开解的操作策略，但仍存在 Dynamic3D 中扫/倒类任务大面积失败、依赖完全可观测与仿真、以及无法完全排除预训练数据泄漏等边界。
