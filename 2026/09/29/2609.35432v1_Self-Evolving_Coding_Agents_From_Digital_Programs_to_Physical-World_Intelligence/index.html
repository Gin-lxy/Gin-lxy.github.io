0. 一句话结论

这篇论文把”数字世界 coding agent 之所以能靠迭代自我改进”归因于三件事——显式的可执行状态、独立于模型的验证、可版本化修订的工件——并主张把同一套表示搬到物理世界：用代码同时写出世界状态（Code as World）与执行过程（Code as Policy），由独立 verifier 判定谓词,让通过验证的执行轨迹反过来成为数据与记忆,驱动机器人系统的持续演化。系统 HexaAnything 在 RoboCasa365 长程操作、RoboDojo 工具修订、自建 PhyBench 模拟物理实验和 AgileX 真机上报告了初步改进;但增益量级普遍较小（多为 1–4 个百分点）、论文未报告方差与显著性检验,且作者自己声明证据是 “preliminary”、完整的四目标协同自演化尚未实现。结论只能限于其覆盖的基准与任务,不能扩展为”通用具身自演化已被验证”。

1. 论文具体想解决什么问题？

研究背景与任务

VLA（vision-language-action）与 WAM（world-action）模型把观测和指令直接映射为一段动作（observation, instruction → action chunk → stop,Eq. 1,§3.1）。论文要解决的不是”如何预测更好的动作”,而是”系统是否维护了一个在执行全过程中可检查、可修订的任务状态表示”（§1）。作者把长程物理任务所需的能力逐项列出:跟踪对象、约束、未完成子目标、状态变化、完成条件与恢复决策——这些都不在 action chunk 与 stop signal 里（§1）。

支撑问题判断的证据

  • 论文自己训练并报告的一个观察:一个 QwenGR00T policy（Qwen3-VL-4B backbone + GR00T-style action head,在 StarVLA 中训练于 LIBERO）把指令掩蔽后仍取得 92.3% 成功率,而指令条件版本为 96.2%,任一 suite 上差距至多 6.0 个百分点（§2.1,Figure 2）。作者引用 LangForce 报告了相差 1.1 点以内的类似结果 [46]。
  • 文献层面的现象（转述,非本文实验）:已发布 VLA 在视角或初始位姿小扰动下掉一半以上成功率 [20],对象布局扰动时接近零 [104];增大数据或模型容量不能可靠消除该失效模式 [43]（§2.1）。
  • 数字侧的先例:LLM 编程代理通过代码表示过程、调用工具、检查中间结果并按反馈修订（§1,§2.4）。软件 agent 的测试是”独立于模型的 verifier”,这是它可以被信任去迭代的原因（§2.4）。

作者认为的原因与核心假设

作者把根因判为表示问题（representational）:任务要求、条件、进度、失败恢复被隐式编码在动作序列中,难以检查与修改（Abstract,§1）。由此提出核心假设:如果把物理任务的状态与执行写成可执行、可验证、可版本化的程序,并将验证置于独立于 proposing model 的 verifier 上,那么（a）失败可被局部化到谓词/工具/工作流并修复;（b）通过验证的执行轨迹可以沉淀为数据、记忆与学习信号,支撑 Harness→数据→模型→硬件四类目标的分阶段自演化（§3,§4）。

需要区分的三层问题

  1. 领域中早已存在的问题:VLA 泛化差、长程任务难（论文引用多项工作）。
  2. 本文的新观察:指令掩蔽实验（92.3% vs 96.2%）作为”策略更多在拟合场景到轨迹”的证据之一（§2.1,Figure 2）。
  3. 本文实际解决的子问题:在固定动作模型的前提下,用 Harness（工作流+谓词+验证+恢复）改善长程成功率;并给出初步的”轨迹→数据→模型”与”固定 evaluator 下工具修订”的实验。论文并未解决”物理世界因果理解的表示学习”这一类更大问题,§8.3 明确说证据是 preliminary。

需要说明的是:论文对”表示是根因”的论证以归纳和类比为主（软件 agent 的成功先例 + VLM 空间能力不足的文献）,没有设计实验来排他性地证明”表示而非容量/数据”是瓶颈;作者自己也承认增大容量能否消除失效仍未定（§2.1 引 [43]）。

2. 创新点是什么？

一段话概括:论文的技术增量可以概括为”把 coding agent 的三要素（显式可执行状态、独立测试、版本化修订）从软件仓库搬到物理执行”——用一对可执行工件 Code as World（对象、关系、观测、约束、进度谓词）与 Code as Policy（规划、工具调用、验证、恢复、执行）描述任务;用带类型（Pass/Fail/InsufficientEvidence/Blocked/SafetyStop）的独立 verifier 对谓词做证据判定;把 typed execution trace 作为归因与演化的单位,并给出四目标（Harness、数据/环境、模型/算法、实体/硬件）加 7 步准入循环（Specify→Execute→Verify→Diagnose→Propose→Evaluate→Select/Commit）的自演化框架（§3,§4,Figure 1/4/5）。

创新点 1:Code as World + Code as Policy 的成对可执行表示

  • 新增了什么:世界状态与执行过程都以程序表达,彼此通过谓词耦合;验证针对世界程序的谓词而不是感知原语输出或模型自述（§2.2,§3.2）。
  • 与最接近工作的差异:Code as Policies / CaP-X 一系把程序当策略,但”感知被信任而非验证”、误差沿原语链复合、改进只能作用于组合方式、测试时收益不持久（§2.2 对 [21,47] 的分析）;结构化状态表示（VisProg、ConceptGraphs、Statler、VoxPoser、ReKep 等）多为一 query 或一 episode 设计,世界程序 WWW 本文强调”跨 episode 持久 + 带 provenance + 由独立 verifier 检查”（§2.3）。
  • 性质:属于”已有组件的新组合 + 新形式化”。论文没有声称某个单独模块全新,而是主张这个接口组合使”表示本身成为可修订对象”。
  • 对应问题:直接回应 §1 的”任务状态不可检查修正”。
  • 原文提供的证据:概念层（Figure 1/3）;实验层没有针对”表示 vs 其他”的消融实验（论文未报告）。间接证据是 RoboDojo 的工具/工作流替换实验（Table 5）与 LoadKebabSandwich 的谓词门控案例（Figure 6）。

创新点 2:HexaAnything Harness 与执行契约

  • 新增了什么:五接口拆分（Tools / Workflow / Verifier / Recovery / Memory,§5.4）+ 具体契约:GoalContract（原始任务文本不可变）、typed policy node kinds（observation/action/VLA invocation/judging/verification/recovery/branching/sequencing/looping）可静态检查、ObservationEnvelope（观测 provenance）、五种 typed verdict、TrialOutcome、ExperimentSpec;恢复 fail-closed,即”未完成或歧义状态不会被静默升级成成功”（§5.5）。
  • 差异:把 VLA/WAM 降格为”action tools 之一”而非任务智能的全部所在（§4.8,§5.4）。
  • 证据:这套契约是后续所有实验的公共运行时;论文强调它使增益可归因（§5.5）。可替代性未单独消融。

创新点 3:以”验证通过的轨迹”为单位的自演化准入机制

  • 新增了什么:演化单位是版本化工件束 av=(Wv,Pv,Hv,Dv,Mv,Ev)a_v=(W_v,P_v,H_v,D_v,M_v,E_v)av​=(Wv​,Pv​,Hv​,Dv​,Mv​,Ev​),每轮 7 步操作,候选修订必须通过静态检查、回归测试、canary rollout、held-out 评估与 rollback,才被准入并回到语料/记忆/模型（§4.2,Eq. 2,Figure 4）。
  • 与已有自演化系统的差异:现存系统多数”只演化一个组件、其余固定”;本文强调”谁学习”——被学习的不仅存入 Memory/技能库,而是变成训练数据训练新 checkpoint（HexaModel）,并可扩展到表示标准与硬件（§2.4,§2.5,§4.5–4.7）。论文提出 E0–E4 证据阶梯（能跑→oracle 能完成→能区分策略→训练新 checkpoint 有效→迁移到真机/分布偏移）以避免”更好的 Harness 被误认为更好的模型”（§4.7）。
  • 证据:该框架大部分是路线图;实验中实际验证的是 Harness/工具层与一次数据→模型更新（§6.2）。四目标协同演化明确是 future work（§1,§4 首段）。

创新点 4:PhyBench——把同一接口扩展到科学实验

  • 新增了什么:一个 Isaac Sim 模拟实验室基准,三个任务（弹簧劲度系数 kkk、重力加速度 ggg、耦合振子简正频率 ω1,2\omega_{1,2}ω1,2​）,任务只给目标与器材、不给流程;成功条件是定量结论的误差（kkk:≤15%;ggg:≤3%;ω\omegaω:每模 ≤10% 相对误差,§7.2）,并以 MRE（Eq. 10）与 valid-run 计数 n/Nn/Nn/N 报告（§7.3）。
  • 差异:操作类基准以”物体到达目标位置”为成功,PhyBench 要求 agent 自行设计实验、操作仪器、带条件记录测量、拟合模型并用残差决定是否再测（§7 首段）。
  • 证据:Table 6 与附录 C 的案例。注意:PhyBench 是作者自建基准,论文未报告任何外部系统在该基准上的对照分数（论文未报告）。

创新性的边界:根据本文 related work 与实验、只能确认作者声称的差异;是否”首次提出”需更完整文献检索。论文中的表述也较克制,把 Physical Coding 定位为”formulation”而非新模型。

3. 作者如何解决？

直觉:让物理执行获得软件工程式的”介质”——状态是一份可读的程序、动作是工具调用且返回结果、完成由不写给自己用的测试判定;失败变成对谓词/工具/工作流的局部化编辑,通过验证的经历变成可复用的程序、记忆或证据（§3.1,§3.3）。

Figure 1（Physical Coding 界面总览,§1）的组织方式:左侧 Inputs 把任务目标、图像/深度、本体感觉、工具结果送进中间层;中间 Physical Coding Interface 分成两个可执行工件——Code as World 记录 objects / relations / observations / constraints / predicates,Code as Policy 组织 plan / tool calls / execute / verify / recover,两者之间的 Improvement 双向箭头表示世界模型与策略可以互相修订;右侧 Physical World 接收 Actions 并回传 Obs / State;下方 HexaAnything Harness 是运行两者的运行时（Observe–Plan–Act–Verify–Recover 循环,附可调用工具:感知工具、规划器、控制器、VLA/WAM 策略）,并有 Improve World Model / Improve Policy 两条上行箭头;最底部 Persistent Artifacts 说明验证过的轨迹如何沉淀为 Memory Entries 与 Learning Signals。这张图解释了论文的核心主张:表示层与执行层共用同一个可执行介质,Learn 的产物以 artifact 形式持久化,而不是消失在 episode 结束时。

输入与两个程序

  • 输入:任务规范 zzz、图像/深度等观测、本体感觉（proprioception）、工具返回;论文特别声明 agent 不读模拟器内部状态,场景结构以 VCode 式（模型写代码、渲染需保真）从图像写出（§2.3,§3.3）。
  • Code as World 的三类来源:场景结构（从图像写 objects/regions/relations）、测量（感知工具返回检测/深度/位姿;仪器返回读数,可按需裁剪放大图像）、执行状态（机器人本体感觉、夹爪状态、每次工具调用的返回值）。每条 entry 带 provenance（哪个调用、何时观测、测量时的实验条件）;由于机器人反复观察同一场景,entry 逐条更新而非整体重生成,新旧矛盾可见而非被静默覆盖（§3.3）。
  • 任务要求写成谓词:例如”两个食材都在烤箱内””每个盘子恰有一面包一香肠””摆幅低于 5∘5^{\circ}5∘ 的完整周期计时”。当现有 entry 无法判定谓词时,结果是 InsufficientEvidence 而不是猜测,策略必须重新观测（§3.3,§5.5）。
  • Code as Policy:对 typed tools 的程序（感知、运动规划、抓取、放置、接触控制 + terminal/file/Python 计算工具 + 以局部指令调用的学习型动作模型;真机上经 URAI 暴露同一套工具）。节点类型化,因此工作流可在执行前静态检查;程序里还保存动作序列装不下的东西:固定实验条件的计划、把读数变成估计值的分析代码、掉落/卡死的恢复分支（§3.3）。

自演化循环与训练

Figure 4（物理自演化,§4 章首图,正文于 §4.2 引用）左上是版本化工件束 av=(Wv,Pv,Hv,Dv,Mv,Ev)a_v=(W_v,P_v,H_v,D_v,M_v,E_v)av​=(Wv​,Pv​,Hv​,Dv​,Mv​,Ev​);中央是七步循环 Specify→Execute→Verify→Diagnose→Propose→Evaluate→Select & Commit,Commit 附带 reject/rollback 到 parent 的回路与 Independent acceptance protocol 标注;右侧 Evolution Targets 四象限是 Harness、Data & Environments、Model & Algorithms、Embodiment,底部横条注明 Representation & Interface Evolution（Code as World ↔ Code as Policy）贯穿四者;下方 Validated Execution Products 展示 accepted 记录如何变成 typed traces→counterexamples→memory→training data→tool/harness revisions→next model checkpoint。这张图解释了本文与”只改 memory/技能库”的系统在机制上的差别:准入必须经过独立评估与回滚保护,产物要能回流成训练数据与下一版模型。

  • 训练实例:HexaModel v0.1 = Qwen3.8-27B 在”Harness 返回数据 + 通用数据”上微调一个 epoch。Harness 提供两路数据:9.3K 条 RoboCasa365 VQA（含 chain-of-thought,覆盖状态与任务完成判定）与 1.0K 条 agent traces（子目标、工具调用、verifier 结果、恢复决策;分别来自 base Qwen3.8-27B 的 703 条成功轨迹、GPT-5.6-Sol 的 204 条恢复轨迹、以及上一轮 fine-tuned checkpoint 的 103 条恢复轨迹——即部分训练数据由上一轮模型产生）。合计 Harness 数据占 178.6M 训练 token 的 38.8%（§6.2,Table 3）。
  • 真机流程（Vibe as Policy）:编程 agent 在 episode 之间写、验证、冻结工具;执行 agent 在运行时组合这些工具;每个工具以机器人自身控制频率执行,基础模型只在工具调用之间介入（§8.1）。

Figure 10（§7.4 案例,Opus 5.5）把一次 Hooke 定律实验从头到尾摊开:顶部 Plan 在执行前写好（荷载 0→0.20 kg 共 5 档;读数规则为”移开手臂、相隔 2 s 的两帧图像一致才读”;分析用带自由截距的加权线性拟合）;a 行是每个砝码重复的五步装载循环（依次 Segment 选择抓取点并生成 mask、Grasp、Place 到托盘槽位、Retract 移出标尺视野、Read 在 2 cm 刻度间插值,单像素约 0.11 cm）;b 行是 5 个载荷下的读数（各自标注来源观测 obs 3/6/9/12/15）与加权拟合 k=24.82±0.40k=24.82\pm 0.40k=24.82±0.40 N/m 对 25.16 N/m 参考值（误差 1.4%）,蓝带是 ±0.10 cm 读数不确定度。这篇图的机制意义是:每条测量都绑定”产生它的条件与观测编号”,最终估计可回溯到 5 帧相机图像——即论文所称”验证与 provenance 让结论可检查”的具体形态。

4. 解决得怎么样？

4.1 实验设置

  • RoboCasa365（操作主实验）:三个 split——Atomic-Seen（18 任务）、Composite-Seen（16）、Composite-Unseen（16）,每任务 50 seeds;action model 固定为 XR-1 VLA（论文称其为该基准上的 state-of-the-art VLA）,原生 VLA 与 coding agent 共享同一”最大环境步数”。planner 分别用 GPT-5.6-Sol、Qwen3.8-27B、HexaModel v0.1;对照 Codex 由同一 GPT-5.6-Sol 驱动（§6.1,Table 1/4）。
  • RoboDojo（工具演化）:三个模拟任务（Fold cloth、Pour vase、Press by number）,任务定义与 evaluator 全程固定,只允许改工具与调用工作流;每轮由编程 agent 读失败轨迹、诊断、编辑工具代码,再用同一 evaluator 计分（§6.3,Table 5）。
  • PhyBench（自建,科学实验）:Isaac Sim 实验室;每模型每任务 10 次自主运行,7,200 s wall-clock 与 18,000 仿真帧预算;运行前 agent 收到公开任务 + 一份”实验指南”participant prompt（建议及时记录读数、在可见刻度间插值、用代码拟合等,§7.3);参考值提交后由 evaluator 揭示（§7.1）。
  • 真机:AgileX PiPER-X 双臂 + 4 台 RealSense D435;7 个桌面任务各跑 3 次,执行 agent 为 GPT-6-Astra,经 URAI 工具集调用（§8.1,Table 7）。
  • 指标:任务成功率;PhyBench 用 MRE（Eq. 10）并附 valid-run 计数 n/Nn/Nn/N;真机另报完成进度、输出 token 数与 wall-clock 时间。
  • 公平性控制:RoboCasa 上固定 XR-1、固定 seeds、同等步数预算;RoboDojo 固定任务/evaluator/权重;并做了”加倍 VLA 动作预算”的排他性检验（§6.1.1）。真机对比对象为其他硬件上的已发布数字,论文在 Table 7 图注中明示”不同机器人测得的,不可直接比较”。
  • 主实验/消融/附录分工:§6.1 固定动作模型下的 Harness 效应;§6.2 数据→模型更新;§6.3 固定 evaluator 的工具修订;§7 PhyBench 扩展;§8.1 真机;§8.2 设计了更长程任务但未评估;附录 B/C 为案例。

4.3 机制证据

  • Harness 实验:接近”隔离变量”设计——同一 XR-1、同一 seeds、同等预算,另有动作预算加倍检验与逐任务案例（Figure 6,12–14）显示机制（”两食材都在烤箱内”作为关门前置谓词;检测 dropped bread 后重新抓取）。该证据支持”在 RoboCasa365 复合任务上,Harness 层面确实贡献了成功率”,但只覆盖单一 benchmark、单一动作模型、无统计检验,且有 Codex 对照组说明”通用 coding agent 也能拿到大部分增益”（Overall 59.5 vs 61.1）,因此增益中有多少来自本文特有的契约设计（§5.5）而非”把 VLA 包进任意编程循环”无法区分。
  • 模型演化:只有 base→fine-tuned 的单点对比,没有做训练数据流消融（38.8% Harness 数据 vs 61.2% 通用数据谁贡献了 0.2–2.2 点本质未隔离）;训练数据含 GPT-5.6-Sol 与上一轮 checkpoint 的输出,存在自我蒸馏/循环放大风险。因此”code traces internalize physical execution”（Abstract 的表述）属于作者解释,机制的因果证据不足。
  • 工具演化:evaluator 固定 + 权重不变,把增益干净地隔离到”工具代码+接口”上,这是全篇最强的机制证据;”非单调曲线”与”两版本因物理条件被回滚”（§8.1）恰好展示了搜索过程是真实的。但像素由人类 operator 选择（论文自述”these numbers measure the tool and the interface rather than autonomous perception”）,所以它证明的是”在人类给定感知输入下,编程 agent 能否改好工具”,不是端到端自主闭环。
  • PhyBench:是能力证据（agent 能否设计并完成可验证的定量实验）而非对照机制证据;论文未报告任何 baseline 系统在 PhyBench 上的分数,无法判断”HexaAnything 的接口”相对于”任意强 agent + 通用工具”的增量。

4.4 成本与适用范围

  • 训练成本:HexaModel v0.1 训 1 个 epoch,总量 178.6M tokens;按 §6.2 原文,Harness 返回的数据占 38.8%（其中 agent traces 1,010 条/42.4M tokens 为独立数据流;RoboCasa365 VQA 9.3K 条属于 12,075 条的 VQA 流,Table 3）。GPU 成本与时长论文未报告。
  • 推理与上下文:论文报告了一个工程优化——把冗长的 action dumps 换成按需执行摘要,使代表性轨迹的 active context 从约 190K 降到估计 30–35K tokens,完整轨迹留在磁盘上（§6.1.1,该数为估计值,论文标注 “estimated”）。真机每 episode 的输出 token 为 443–4.69K,时间 1.0–8.1 min（Table 7,含模型延迟与机器人运动）。
  • 人工与外部依赖:RoboDojo 中 operator 逐 call 选像素;真机工具演化中 operator 录制人类投掷视频并做版本取舍;主要 planner 是闭源 API 模型（GPT-5.6-Sol、GPT-6-Astra、Opus 5.5、Claude Fable 5.1）;URAI 接口为自研（论文未报告公开代码或数据,亦未见项目仓库链接）。
  • 未解决/未覆盖:模型权重内部化（”reduced Harness assistance”的验证）尚未做;架构与硬件演化是路线图;长程任务集（§8.2）”已设计但未评估任何系统”;物理部署限制在受控桌面任务;作者列出的开放问题还包括 model–verifier 共同适应、lifelong memory 隐私、真实安全测试等（§8.3）。结论适用范围即上述四个实验场景;不能外推到非受约束环境或”通用具身智能”。

5. 最容易受到审稿人质疑的地方

质疑:核心增益小且无不确定性度量,”优于 Codex”等对比缺少统计支撑

  • 原文依据:Table 1（Composite-Unseen 34.3→38.3,Overall 56.6→61.1;HexaAnything 61.1 vs Codex 59.5,差 1.6 点;Atomic-Seen 反而落后 Codex 0.8 点）;§8.3 作者自述 “overall margin over Codex … is 1.6 points”。全篇未报告方差、置信区间或显著性检验（论文未报告）。
  • 为什么重要:1.6 点的总体差异、0.2 点的 HexaModel 提升（Atomic-Seen）完全可能落在种子噪声内;若如此,”Harness 优于通用 coding agent””模型内部化有效”的核心结论就不成立。
  • 当前能够得出的判断:效果证据存在（且动作预算加倍检验排除了一个替代解释）,但差异的稳定性无法评估;单项任务的 31.0/15.0/17.0 点提升（Table 2,100 seeds）比总体提升更有说服力,说明增益高度集中在少数困难任务上。
  • 如何验证或补强:报告多 seed 重复的均值±标准差、对关键对比做配对显著性检验;扩大 Overall 的试验量。
  • 严重程度:主要问题。

质疑:”模型演化”证据不足以支持”轨迹内化了物理执行”的主张

  • 原文依据:§6.2 Table 3/4——HexaModel v0.1 每 split 提升 0.2–2.2 点;训练混合了 38.8% Harness 数据与 61.2% 通用数据,数据含 GPT-5.6-Sol 与上一轮 checkpoint 的轨迹（”part of the training data is produced by a model trained in a previous round”）;没有数据流消融、没有多个 checkpoint、没有”减少 Harness 协助后仍成功”的验证（§4.5 承认模型更新是 staged claim）。
  • 为什么重要:这关系到论文最有卖点的论断——执行经验回流为可复用学习信号。混合数据 + 自我蒸馏会让”提升”既可来自数据蒸馏也可来自真正内化,因果归属不清。
  • 当前能够得出的判断:在论文报告条件下,新 checkpoint 确实略优于 base;但”内化”是作者解释而非已证机制。且总体 61.7 vs GPT-5.6-Sol 61.1 的差距同样可能来自噪声。
  • 如何验证或补强:分别用”仅 Harness traces””仅通用数据””两者”训练并比较;检验 fine-tuned 模型在移除部分 Harness 组件（如谓词门控）后的表现;发布复现细节。
  • 严重程度:主要问题。

质疑:工具自演化的”自主性”被高估——关键环节依赖人类提供感知输入

  • 原文依据:§6.3 Figure 8 段落自述 “the operator chose the pixels for each call, so these numbers measure the tool and the interface rather than autonomous perception”;工具开发最初还受益于与官方 check 同源的 garment keypoints,需事后重评（3/5 dev,4/5 held-out）;Fold cloth 仅 5 seeds;Table 5 未标注各轮试验数;Pour vase 第一轮从 40% 掉到 0%。
  • 为什么重要:Abstract 与 §6.3 的表述是”agent 读失败轨迹、诊断、编辑工具代码”从而自演化;若每次调用的关键感知参数由人类给出,那么”从失败中自主改进工具”的闭环并不完整。
  • 当前能够得出的判断:工具代码的修订确实是机器完成的（含被回滚的两个真机版本）,搜索过程真实且非平凡;但”自主”要从”人类选像素”这一步开始打折。论文对此披露诚实,却仍在标题/摘要层面使用较强的自演化叙述。
  • 如何验证或补强:让 agent 自行完成分割与像素选择（即便退化到可用的精度）后重报成功率;增加 seeds 至统计可分辨水平;报告每次调用的失败归因分布。
  • 严重程度:主要问题。

质疑:真机速度对比与”verified”性质都有混杂因素

  • 原文依据:Table 7 图注自述 published references 是 “other hardware … not same-robot measurements”（GPT-Policy 在自己机器人上;Robocurve 在 YAM 臂上且限速 25%、至多 20 次模型调用）;每任务仅 3 次试验;时间包含模型延迟、机器人运动、井字棋还包含人类走子;真机验证依赖 operator 判断与机器人自身 traces（§8.1）,而非 §5.2 要求的独立 verifier;两项任务未稳定完成。

  • 当前能够得出的判断:这些数字只能作为可行性信号,不能作为性能结论;作者在细节处如实标注了,风险在于摘要与二手传播会丢掉这些限定。
  • 如何验证或补强:在同一台 AgileX 上复现对照方法的完整流程;报告 trial 级原始数据与失败模式。
  • 严重程度:次要问题（已被作者部分披露,但摘要层面仍有夸大空间）。

质疑:标题与框架的”自演化”承诺远超实验兑现的程度

  • 原文依据:§1 结尾与 §4 首段明确”experiments cover Harness and tool evolution and a first data-to-model update, while coordinated evolution of all four targets remains a longer-term program”;§4.7 说硬件/算力演化是 longer-term targets;§8.2 长程任务”designed but not yet evaluated”;PhyBench 为自建基准且无外部系统对照（论文未报告）;§8.3 自述 “The evidence in this report is preliminary”。
  • 为什么重要:论文题目与 Abstract 覆盖”从数字程序到物理世界智能””weight internalization、autonomous redesign of architectures…”等宏大路线;若以实验章节为评估对象,论文实际交付的是”表示接口 + 三个受控实验”。审稿人需要区分”框架论文的愿景”与”已验证的结论”。

  • 严重程度:主要问题。

6. 审稿式总评

作者发现 VLA/WAM 把任务要求、进度与恢复逻辑隐含在动作序列中,导致状态不可检查、失败不可局部化,因此提出 Physical Coding——用 Code as World 与 Code as Policy 两个可执行工件把物理任务写成程序,由独立 verifier 对谓词做证据判定,并让验证通过的轨迹回流为数据、记忆与工具修订,经 HexaAnything Harness 在 RoboCasa365（固定 XR-1 时 Composite-Unseen +4.0 点、Overall +4.5 点）、RoboDojo（三任务经两轮工具修订从 0/40/0 到 80/100/100）、自建 PhyBench（多模型 MRE<5%）与 AgileX 真机（7 任务中 5 个全成）上实现。实验在”隔离变量”的意义上有可取之处（固定动作模型、固定 evaluator、动作预算排他检验、工具版本回滚记录）;但主要对比缺少方差与显著性,模型演化证据依赖混合数据无法归因,工具”自主”修订依赖人类选像素,真机对比跨硬件不可比。本文最有价值的部分是把”表示可检查、验证独立、修订可回滚”组织成一个贯穿数字与物理的可执行接口,并给出诚实标注边界的初步证据;最大的审稿风险是标题级主张远大于实验覆盖——四目标协同自演化、权重内部化、架构与硬件演化均未验证,而现有增益又普遍处于噪声敏感的量级。

  • 问题定义清晰度:强（问题、根因假设、与相关工作的边界都写得明确,§1–§2;且自陈”preliminary”）。
  • 创新性证据:中（表示与接口组合的定位清晰,但与 Code as Policies 一系及 embodied harness 的增量主要是”验证独立 + 持久化 + 可训练”,其中的独立证据未做消融）。
