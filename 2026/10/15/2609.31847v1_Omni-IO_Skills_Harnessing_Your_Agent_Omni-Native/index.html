0. 一句话结论

论文解决的是”通用智能体不会接收和产出多模态内容”的问题：不让宿主模型学新模态，而是在宿主与外部工具之间加一层可插拔的智能体执行框架（Agent Harness，下称 harness），把 27 个分层技能、依赖图编排和常驻资产账本组织成统一的执行接口。在自建基准 UniM-90 上，两个宿主智能体的输入支持率（input-support rate，τ）从约四成升到 100%，相对语义–质量耦合分数（Semantic–Quality Coupled Score，SQCS）提升约 48–50 点；但由于缺少消融实验和”只接工具”的对照，”这套设计本身是否必要、哪一部分在起作用”没有得到验证。

1. 论文具体想解决什么问题？

一般问题。 通用智能体（Codex、Claude Code 一类）已有较强的指令遵循、长程规划与代码执行能力，但其生产面集中在软件与知识工作；真实任务（论文以制作线上课程为例：讲座录像与参考资料 → 内容分析、视觉设计 → 幻灯片、插图、旁白、讲解视频）天然跨文本、图像、音频、视频、文档、3D、代码七种工件（artifact）模态，且各产物共享事实、风格、时序等约束（§1）。这是领域早已存在的一般矛盾：生产能力按模态碎片化，而需求是交错式的。

现有做法与它们何时不好用。 论文归纳两条路线。一是把模态做进基础模型（统一自回归建模或混合离散–连续设计，如 Unified-IO 2、AnyGPT、Chameleon、NExT-GPT），代价是新增模态需模型更新，且要调和表示、目标与保真度要求（§1、§2.1）。二是拼装专用模型与工具，但”程序、依赖、中间资产与跨轮修订如何协调”没有答案（§1，作者主张）。模型协作系统（如 Agent-Omni）证明可以让 agent 委派模态专家而不动底层模型，Agent Skills 类工作（SkillsBench、CUA-Skill、MMSkills）把过程知识做成推理期可复用的技能；作者认为两者的交集——any-to-any 理解与生成 + 多资产执行 + 持久资产状态——仍未被覆盖（§2.2，作者主张，未给出与这些系统的实验对比）。

本文指认的缺口。 作者把缺失组件命名为”Omni agent harness”：位于 agent 推理与异构执行后端之间的一层，让分散的模型、工具、程序变成”可挑选、可组合、可执行、可追溯”的能力（§1）。支撑这一判断的现象是：默认环境下的两个宿主输入支持率只有 40.00% 与 38.89%。需要指出：论文只观察到了这一总体差距，没有分解实验说明差距里有多少来自”缺少模态输入通道”、多少来自”不会编排多步多资产任务”——缺口成因属于作者的因果解释，并未被单独验证（审稿人判断）。

核心假设。 在宿主默认环境上加载同一套 harness（技能 + MCP 工具服务 + 编排 + 资产层），即可把输入支持率抬到 100% 并在质量与结构指标上取得一致提升，同时不改变宿主的推理核心（§1 的 central question；§7）。

2. 创新点是什么？

概括：技术增量是把”Omni 能力”从模型层搬到系统层的一套可运行工程配方——多粒度声明式技能、依赖感知编排、常驻资产账本与可替换后端绑定，在同一个可插拔框架内闭环（整体组成见图 1，论文 Fig. 1）。

图 1（论文 Fig. 1）：该图传达 harness 的整体闭环。宿主智能体面对任意模态的输入，由三级技能把散落的能力组织成可挑选的工序，请求被翻译成一张声明式执行图（Declare Execution Graph，DEG）来调度执行，产物最后进入资产注册表（Asset Registry）保存并供后续复用；图中四个能力族（理解、生成、推理、检索）与七种工件模态刻画的是系统对外的能力面，而不是某个模型内部的新能力。读者应抓住的核心是：新增的是”组织与执行”这一层，宿主模型本身没有被改动。

  • 三级声明式技能体系。 新增了统一技能表示（适用条件、输入、执行过程、输出、与其他技能的关系），三种粒度分别承担单步操作（Atomic Skill，原子技能）、单品生产过程（Expert Skill，专家技能）与应用场景下的交付物协调（Scenario Skill，场景技能）。与 SkillsBench、CUA-Skill、MMSkills 等技能工作相比，差异在于面向 any-to-any 多模态生产而非计算机使用或视觉决策，并与执行图、资产层协同；属于已有组件面向新场景的组合与扩展。证据一句话：效果见 §4.2 主表，但无消融（§4.3）。
  • 依赖感知编排（DEG）。 把技能展开后的终端任务实例化成显式依赖图：执行前做结构校验，按”波次”（Wave）并发调度互相独立的节点，失败只取消下游、独立分支继续，不回滚已完成产物（§5.2–5.3）。相对 ReAct 式循环与 MCP 单纯暴露工具的做法，差异是把并发机会与失败边界固化成图性质，而不是每次靠模型即兴决定。证据：Table 2、论文 Fig. 10/Table 17 的示例（定性，无对照）。
  • 常驻资产注册表。 所有产物归一化为含全局 asset_id、类型、物理路径、描述、生效参数、轮次与来源指针的记录，以只追加（append-only）方式持久化，支持跨轮按语义匹配复用与版本溯源（§4.5、§5.5）。相比”靠工作区文件路径约定”的做法，资产与路径解耦、可检索、可回溯。证据：论文 Fig. 11 的两轮复用示例（定性）。
  • Provider 与配置分层。 技能只引用语义能力（如”图像生成”），具体提供方、模型、密钥、默认参数与回退策略绑定在配置层，一处改动即可替换后端，并支持缺凭证时的能力降级（§4.4、Table 7、Appendix C.4）。这是工程解耦改进，直接服务”可演化”主张。证据：Table 7/Table 8 的绑定与默认参数表（无对比实验）。

边界说明：根据本文 related work 与实验对比，只能确认作者声称的差异；是否构成”首次提出”，还需要更完整的文献检索。

3. 作者如何解决？

直觉。 如果”不会做多模态生产”不是推理能力不足，而是外部能力没有被组织成可执行的工序，那么就不必重训模型：把工序知识、调用接口、依赖关系与产物状态结构化，让宿主像调用一套工具箱那样调用整套生产能力。harness 因此位于宿主 agent 与外部多模态工具之间——上面是不变的推理核心，下面是可替换的生成与理解服务，中间负责把一句自然语言请求翻译成可校验、可并发的执行计划，并跟踪、保存每一步的产物（§4.1）。

输入与能力面。 输入是带多模态素材与交付要求的用户请求（录音、文档、产品图、既有 3D 模型等），宿主 agent 保持默认环境。系统的对外能力面由 27 个技能构成（19 个原子、2 个专家、6 个场景，§1），覆盖文本、图像、视频、音频、文档、3D、代码七种工件模态与 38 个代表性任务，分布在理解、生成、推理、检索四个能力族；图 2（论文 Fig. 2）按应用域给出了这张覆盖表。

图 2（论文 Fig. 2）：这张图回答”能力面多大、怎么组织”：四个能力族下按应用域（教育科研、商业营销、职场、创意等）列出代表性任务，任务旁的括号图标表示输入到输出的模态流，多个图标意味着多模态输入或输出。读者应从中理解覆盖广度的组织方式——按”能力族 × 应用域”而非按模型划分——以及任务与技能的多对多映射；完整映射在附录 B（Table 5），其中理解类 16 个、生成类 14 个、推理与检索各 4 个，合计 38 个任务。

四层架构。 图 3（论文 Fig. 3）给出 harness 的四层分工与数据流：技能入口层（Skill Entry）存放技能规格，并把选中的技能展开成 DEG；MCP 工具服务层（MCP Tool Service，MCP 即 Model Context Protocol）把每个可执行节点映射为标准工具调用契约；提供方与配置层（Provider and Configuration）把能力绑定到具体服务、模型、凭证与默认参数；资产注册表层（Asset Registry）统一登记产物。

图 3（论文 Fig. 3）：该图展示请求自上而下的”翻译链”——用户请求 → 所选技能 → 执行图 → 工具契约 → 具体服务 → 资产登记。每一层只依赖上一层的语义：技能不写死服务端点，工具不向技能暴露提供方 API 细节，因此任何一层的实现可以整体替换而不牵连其他层；产物从最底层登记后又能回流，供下游节点与后续轮次引用。读者应理解这是”能力解耦”的落地方式，也是后文”可演化”说法的架构基础。

技能的选择与展开（创新一展开）。 技能入口层按任务粒度组织三级技能，调用方向严格向下：请求命中某个应用情境就激活场景技能（如 S5 Event Material），要求单一专业成品可直达专家技能（E1 Poster Design、E2 Complex Video Production），一步能完成的直接调用原子技能。选定后递归展开——场景技能被其交付物所需的专家或原子技能替换，专家技能被其生产步骤替换——直到终端任务全部可执行；共享输入与中间结果只表示一次；由宿主原生执行的任务（代码、Markdown、图像理解）同样作为终端任务进入执行图（§4.2，图 4 论文 Fig. 4）。

图 4（论文 Fig. 4）：该图说明三级技能的调用方向与展开关系。高层技能只声明”交付什么”——场景技能覆盖社交发布、办公文档、求职、教育、活动、游戏资产六个应用情境，专家技能封装海报与复杂视频两种成品工序——而执行永远向下展开到原子技能这一层：场景由成品所需的专家或原子技能兑现，专家由工序中的原子步骤兑现，高层不复制底层实现。由此也解释了为什么 DEG 的节点最终都是原子级任务，以及技能扩展为什么只需在对应层级登记规格（§4.2.2、Appendix D）。

DEG 构造与校验（创新二展开）。 展开后的终端任务被宿主实例化为 DEG：图记为 G=(V,E)G=(V,E)G=(V,E)，节点形如 v = ⟨id, type, prompt, params, depends_on⟩，边既表达控制依赖（前驱完成后继才可开始）也表达数据依赖（消费前驱输出）；历史资产以带 asset_ref 的资产源节点表示，解析成功即视为”已完成”，不发起任何生成调用（§5.2）。执行前有 8 条结构规则把关——节点 id 唯一、类型在可执行类型表内、prompt 与 asset_ref 恰好出现其一且 prompt 自包含、依赖与资产引用都能解析、依赖图无环、数组式多依赖仅允许 code/markdown 节点、凡消费上游输出就保守声明依赖；任一不满足按规划错误退回重建，不带错误执行（§5.3、Table 15）。随后按波次调度：所有前驱已完成的就绪节点进入同一波并发派发，波次由声明的依赖而非模态决定——图像与音频若无相互依赖可并发，图像条件的视频节点则必须等待其参考图（§5.3，图 5 论文 Fig. 5）。

图 5（论文 Fig. 5）：该图用一个产品推广请求把控制流与资产流画在一起。控制流从请求出发：选定 S5 Event Material 场景技能，经层级展开变成原子任务，再构造并校验 DEG；右侧按依赖划分出四个执行波——先分析产品参考图，然后海报素材与”视频+音效”两条支路并发，接着合成宣传视频与海报，最后生成落地页（逐波内容见 Table 2）。资产流从用户素材与历史资产开始，每个节点成功后登记进 Register，供下游注入与跨轮复用；底部是每个就绪节点共用的执行循环：工具路由、提供方解析、上游资产注入、执行。读者应理解：执行顺序与并发机会完全由图中依赖决定，这正是”依赖感知”的含义。

逐节点执行（创新四展开）。 对每个可执行节点，MCP 工具服务按任务类型选工具，配置层解析提供方、模型、凭证、默认参数与回退策略；实际生效参数由”配置默认值 ⊕ 节点级覆盖 ⊕ 上游注入”合并而成，上游产物按任务关系注入（图像 → 视频作为首帧条件，图像 → 3D 作为参考图），因此 prompt 不需要写文件路径（§5.4）。代码、Markdown 等原生任务跳过 MCP 生成服务，但保留相同的输入解析、状态与注册契约（§4.3）。论文列出的绑定全部可替换：图像生成默认 OpenAI gpt-image-2，视频生成 Alibaba wan2.7，音乐与音效用 ElevenLabs，语音用 OpenAI tts-1，3D 用 Tripo v2.5，视频与音频理解用 Google gemini-2.5-flash，文档理解用 Mistral OCR，检索用 Brave Search API（Table 7；默认参数见 Table 8）。

资产与跨轮复用（创新三展开）。 节点成功后，产物写入工作区并按统一记录登记：asset_id、类型、子类、路径、生成时写下的自然语言描述、实际生效参数、轮次号、来源资产指针；MCP 生成工具在返回前自动注册，宿主原生写出的文件需显式注册；注册表是只追加的 JSON 文件，写入原子化并以文件锁串行化，失败或取消的节点不登记（§4.5、§5.5、Appendix H）。跨轮时用户引用历史资产，宿主按描述做语义匹配找到记录，并把它物化为新图中已完成的资产源节点——论文的两轮示例中第二轮没有重新生成任何东西（论文 Fig. 11）；修订产生带来源指针的新记录，旧版本仍可检索（§5.5）。

谁决定、谁固定。 由模型决定的包括：技能选择，展开时各步骤 prompt 的撰写，专家技能装配代码的编写，成品检验结论与返工范围的判断，以及用户中途改需求时哪些在途节点受影响。由固定流程控制的是：图校验、波次划分、参数合并与注入、注册、失败传播与取消（Algorithm 1）。专家技能的自动返工默认最多两轮，仍未解决则交付最佳版本并把问题交回用户（Appendix E.3）。

训练与推理变化。 全程不需要训练：不更新宿主模型、不训练新模型，能力来自推理期的技能加载、工具接入与状态管理（training-free，免训练）；这正是标题中”不改动宿主推理核心”的含义（§1、§7）。宿主推理侧的变化，是把过去零散的工具调用换成”写规格、构造图、交由图机制执行”。

输出。 最终输出是请求交付的多模态工件集合（逐个登记为资产）、每个节点的最终状态（完成/失败/取消）与完整溯源链；失败只影响下游分支，已完成资产保留（§5.3、§5.5）。

4. 解决得怎么样？

4.1 实验设置

  • 任务与数据：UniM-90，从 UniM 基准（CVPR 2026，与本文同一研究组的先行工作）抽取的固定 90 例子集，覆盖文本、图像、音频、视频、文档、代码、3D 及其交错组合；选取方式为 30 个应用域各取 easy、medium、hard 一例，某难度不可用时以同域其他案例补足，且论文声明选取独立于任何被测 agent 的原生模态能力（§6.1、Appendix I.1）。
  • 宿主与配置：GPT-5.6 Sol（OpenAI，运行于 Codex 环境）与 Claude Sonnet 5（Anthropic，运行于 Claude Code 环境）各两种配置——Base Agent（仅保留宿主内置技能与工具，不装第三方扩展）与 Agent + Omni-IO Skills（再加装 harness 及其 MCP 工具服务），其余设置（工具配置、系统提示、执行预算）声明保持不变（§6.1、Appendix I.2）。
  • 对比对象：只有”同一宿主的默认配置”这一种基线；没有与其它 Omni agent 系统（如 MM-ReAct、Agent-Omni、CUA-Skill、MMSkills）的直接对比，也没有”接同样工具但不加编排”的中间配置（全文未出现消融，见 §4.3）。
  • 指标：采用 UniM Evaluation Suite：输入支持率 τ，以及 SQCS（语义–质量耦合分数）、ICS（交错连贯性分数，Interleaved Coherence Score）、StS/LeS（严格/宽松结构分数，Strict/Lenient Structure Score）的绝对与相对版本。相对分定义为 Xrel=τ⋅XabsX^{\mathrm{rel}} = \tau \cdot X^{\mathrm{abs}}Xrel=τ⋅Xabs，即绝对分只在 agent 支持的实例子集上测量、相对分再折算回全测试集；输入可处理但输出无法生成或无法完成的失败仍计入指标（§6.1）。
  • 分工：主结果只有 Table 3（§6.2）与两个定性案例（§6.3）；附录 A–H 是技能目录、工具/绑定/规格/流程等技术文档，Appendix I 是实验细节（子集构造与配置）。论文没有设置消融实验组，也没有分模态、分能力族的细分结果。

4.2 关键结果

  • 输入支持率（Table 3，§6.2）：GPT-5.6 Sol 的 τ 从 40.00% 升到 100%，Claude Sonnet 5 从 38.89% 升到 100%。
  • 相对 SQCS（Table 3、§6.2、§7；全 90 例）：GPT-5.6 Sol 26.99 → 74.94（+47.95），Claude Sonnet 5 27.82 → 77.78（+49.96）。注意相对分是 τ 与绝对分的乘积，τ 从约 0.4 涨到 1.0 本身就带来约 2.5 倍放大，这一”提升”的大部分来自覆盖率折算而非生成质量本身（审稿人判断，见 §4.3 与 §5）。
  • 绝对 SQCS（只在各 agent 支持子集上测量）：GPT-5.6 Sol 67.49 → 74.94（+7.45）；Claude Sonnet 5 71.53 → 77.78（+6.25）。提升真实存在，但两端不是同一实例子集（基线只支持约四成实例，加壳后在全部 90 例上测量），不能读成同一批样本上的质量跃升；论文在 §1 与 §6.2 均以该跨子集对比作卖点（审稿人判断）。Claude 的提升明显小于 GPT。
  • ICS（Table 3）：GPT-5.6 Sol 绝对分 86.53 → 93.98（+7.45）；Claude Sonnet 5 绝对分 82.29 → 83.28，仅 +0.99，几乎不动——这是全文提升最小的指标，说明并非所有子指标都大幅受益。
  • 结构指标（Table 3）：StS 绝对分 47.84 → 100.00（GPT）与 52.21 → 99.78（Claude）；LeS 绝对分 72.22 → 100.00 与 68.57 → 100.00；相对 StS 19.14 → 100.00 与 20.30 → 99.78。结构完备性提升幅度最大，作者主张这验证了多模态工具调用、资产组织与输出结构控制有效（§6.2，作者主张）。
  • 定性案例（§6.3、论文 Fig. 6）：艺术教程案例通过视频与音频理解提取绘画步骤与讲解、生成 11 张教程图；产品推广案例先做图像理解抽取产品属性，再由海报设计、复杂视频生产与代码生成产出海报、10 秒竖版推广视频与落地页三个交付物，且保持产品身份一致（图 6，论文 Fig. 6）。

图 6（论文 Fig. 6）：该图展示两个多资产交付任务在两家宿主上的端到端过程记录（艺术教程与产品推广两个案例，每个案例给出对应宿主下的对话与产出）。教程案例中，系统把视频与音频里的步骤、讲解按顺序恢复，再逐图生成完整教程；推广案例中，三个交付物共享同一份产品分析，海报、视频、网页在内容与身份上互相一致。读者应把它理解为”编排在工作流层面确实闭合”的定性证据——多步依赖、跨能力族协作与多产物一致性都被走通——而不是质量分数的替代物，因为它没有对照，也没有评分。

  • 缺失项：论文未报告方差、置信区间、重复运行或显著性检验；未报告失败样本统计与生成工具失败率；没有分模态或分能力族的细分结果，也未报告任何”无提升”数据集（唯一近似”无明显提升”的是 Claude 的绝对 ICS +0.99）。单次运行的偶然因素无法排除（审稿人判断）。

4.3 机制证据

  • 实验只说明”加载 harness 后两家宿主的聚合指标都变好”，没有回答”为什么变好”。全文（含附录）未出现 ablation 字样：层级技能、DEG 并发调度与失败隔离、资产跨轮复用、Provider 解耦均没有”移除或替换该设计后重跑”的对照。
  • 逐一核对 §2 创新点：三级技能体系——只有论文 Fig. 8（海报的专家展开片段）与论文 Fig. 9（游戏资产的场景计划）演示”展开按设计发生”，无对照说明层级组织优于扁平工具列表；DEG 调度——Table 2、论文 Fig. 10、Table 17 是单个示例的手工走查，未比较顺序执行与波次并发的时延或成功率，失败隔离的收益（Table 16 的中断语义）也未被度量；资产注册表——论文 Fig. 11 演示了第二轮”零重新生成”，这是结构性的机制演示，不是被度量的收益（例如可对照禁用注册表时的重复调用次数，论文未做）；Provider 解耦——Table 7 列出可替换绑定，但实验声明绑定固定，未做后端替换对比。
  • 论文声明两配置除 harness 外其余不变（Appendix I.2），这排除了提示与预算差异的朴素解释，但该声明不可外部核查（宿主为闭源服务，默认环境与执行预算细节未披露）；更关键的替代解释没有被排除：τ 从约 40% 到 100%，在结构上等价于”agent 现在能读所有模态的文件并调用生成服务”，这与 harness 是否使用层级技能、DEG、注册表无关（审稿人判断）。
  • 结论：本文当前提供的是”整体有效”的证据（弱受控、无方差），没有”机制有效”的拆分证据；§2 的四个创新在实验层面均未被单独支持。

4.4 成本与适用范围

  • 训练成本：无（training-free，不更新任何模型；§1、§7）。
  • 推理时延、token 与工具调用次数：论文未报告；只有 Table 17 给出单个示例图的调用数（三次外部生成——图像、视频、3D；音乐资产从注册表直接解析不发起调用，另有一次原生写文件），不足以估计一般任务开销。
  • 外部依赖：生成与理解能力绑定多家第三方服务（OpenAI、Google、Alibaba、ElevenLabs、Tripo、Mistral、Brave，fal.ai 等备选；Table 7），多数闭源且需要 API key；图像理解、代码/Markdown 写作、文档渲染、Edge TTS 与浏览器等可本地或由宿主原生执行，缺部分凭证时仍有子集可用（Appendix C.4），但论文没有在”部分配置”下做实验。
  • 人工标注与评测成本：论文未报告（评测由谁执行、是否为人工或 LLM 评审均未说明）。
  • 存储与系统复杂度：注册表为单个只追加 JSON 文件加文件锁（Appendix H.3）；规模上限、并发会话压力等未报告。
  • 适用范围：结论只覆盖 UniM-90 的 90 个实例、七种模态与两个特定宿主，作者未声称可推广到所有 agent 或生产环境。τ = 100% 表示”输入都能被接收处理”，结构分接近满分表示输出结构与模态覆盖达标，均不保证内容语义正确——这正是 SQCS 只到 74.94/77.78 的原因。
  • 未解决：生成后端的实际失败率与重试行为（规格层面仅”网络超时重试一次”，论文 Fig. 7）、成本、时延与长任务稳定性都缺少数据。

5. 最容易受到审稿人质疑的地方

质疑：没有消融、没有”只接工具”基线，无法证明提升来自论文的编排设计，而不是”给闭源 agent 接上了多模态 API”

  • 原文依据：全文（正文与附录）搜索无消融内容；实验只有 Base Agent 与 +Omni-IO Skills 两档配置（§6.1、Appendix I.2），基线仅为宿主默认环境；对比对象不含任何其它系统或简化变体。
  • 为什么重要：论文贡献清单中三项属于设计机制（层级技能、DEG 编排、资产注册表，§1 贡献 2–3），但 Base 基线在结构上缺少全部外部模态通道（τ ≈ 40%），任何补上外部能力的系统都会显著抬高 τ 与相对分；”harness 的架构设计带来了什么”这一核心机制主张没有被隔离验证。
  • 当前能够得出的判断：能确认”整体改装有效”，不能确认”这套设计优于更简单的工具接入”；机制必要性证据不足（审稿人判断）。
  • 如何验证或补强：加入”同组 MCP 工具、无技能分层/无 DEG/无注册表、由宿主自由编排”的工具版基线，并对 Expert 层、波次并发、跨轮注册表分别做组件消融，在相同 90 例上重跑。
  • 严重程度：主要问题

质疑：头条数字（相对 SQCS +47.95/+49.96）被指标构造放大，且绝对分做了跨子集比较

  • 原文依据：相对分定义为 τ 与绝对分的乘积（§6.1）；τ 从 40.00%/38.89% 到 100% 使任何绝对分被乘以约 2.5 倍；摘要、§1 与 §7 把相对分大幅提升与”超过基线绝对分 67.49/71.53”并列宣传，而后者只在基线支持的约四成实例子集上测得（§1、§6.2、Table 3）。
  • 为什么重要：读者容易把相对分跃升误读为生成质量跃升；”加壳后在全部 90 例上的绝对分”与”基线的子集绝对分”不是同一评测集合，正常做法应先在基线支持子集上对齐比较，再单独报告覆盖扩展的增量。
  • 当前能够得出的判断：覆盖率结论成立；质量提升的幅度被跨子集比较与相对分放大效应显著高估（审稿人判断；所引数字均为 Table 3 原文事实）。
  • 如何验证或补强：报告 harness 在基线支持子集上的同子集绝对分；把相对分变化分解为”覆盖扩展”与”支持子集内质量变化”两部分；给出分能力族的细分表。
  • 严重程度：主要问题

质疑：用同一研究组自建的基准与未披露细节的指标，评价自家系统

  • 原文依据：UniM-90 全部取自 UniM（CVPR 2026），而 UniM 的作者列表（Yanlin Li、Shengqiong Wu、Hao Fei、Mong-Li Lee、Wynne Hsu 等）与本文高度重叠（HTML 参考文献 [12]）；指标”adopt the UniM Evaluation Suite”（§6.1），本文未给出 SQCS/ICS/StS/LeS 的计算方式、评分主体（模型或人工）与任何可靠性数据；Appendix I 也只含子集构造与配置。
  • 为什么重要：自建基准加自家指标评价自家系统存在循环风险；指标定义不可核查，使独立复现无法对齐目标。
  • 当前能够得出的判断：报告的数字忠实于原文，但评测独立性与可核对性无法确认（审稿人判断；同一研究组关系为原文事实）。
  • 如何验证或补强：补充第三方 any-to-any 基准上的结果；公开指标实现与评分协议；报告与人工评分的一致性研究。
  • 严重程度：主要问题

质疑：无方差、无失败率、单次运行，小差异（如 Claude 绝对 ICS +0.99）无法判断显著性

  • 原文依据：全文无方差、标准差、重复次数或显著性报告；UniM-90 每个配置只给一个数值（Table 3）；图像/视频/音频生成输出天然带随机性；失败处理只有规格层面的描述（论文 Fig. 7 中”网络超时重试一次”），未报告工具失败率与失败样本量。
  • 为什么重要：无法区分稳定改进与运行噪声；”99.78 对 100.00”这类小数差异以及几乎不动的 ICS 难以解读；审稿人也无法评估 90 例是否足以支撑结论。
  • 当前能够得出的判断：结论方向可信，幅度不可靠（审稿人判断）。
  • 如何验证或补强：每个配置至少重复 3 次并报告均值与方差或置信区间；报告按任务族的失败率与重试统计。
  • 严重程度：次要问题

质疑：成本、时延与调用数全部未报告，可复现性受限（闭源宿主 + 仓库无许可证）

  • 原文依据：论文未报告任何成本、时延或 token 统计（正文与附录均无）；系统依赖多家闭源 API（Table 7）；两个宿主为闭源商业模型，其”默认环境”、系统提示与执行预算只有定性声明（§6.1、Appendix I.2）；官方仓库（补充材料核查结果）无 License 声明。
  • 为什么重要：影响实用性评估与独立复现；读者无法判断这套方案在生产中的代价与上限。
  • 当前能够得出的判断：论文未报告成本；可复现性当前无法确认（材料核查：仓库存在但无许可证，论文未披露环境细节）。
  • 如何验证或补强：补充每次任务的平均调用数、费用与时延；公开宿主环境配置与提示；为仓库补充许可证与可运行的评测脚本。
  • 严重程度：次要问题

6. 审稿式总评

作者发现通用智能体的多模态生产面存在系统性缺口——缺的是推理与执行后端之间的一层，因此提出 Omni-IO Skills：以三级声明式技能、DEG 依赖编排与常驻资产注册表，把外部能力组织成可执行、可并发、可复用、可替换的工序，通过 MCP 工具与配置绑定接入生成/理解服务。实验在 UniM-90 上、两个闭源宿主、各自默认环境条件下表明：输入支持率 40.00%/38.89% → 100%，相对 SQCS 提升约 48–50 点，结构分接近满分。其中”整体改装带来覆盖与结构完备性提升”证据较强（两个宿主方向一致、配置同源），但机制归因、质量提升的真实幅度与评测独立性仍缺少充分支持。本文最有价值的部分是一套完整、可读、可直接借鉴的 harness 工程设计（附录细到 JSON schema 与执行算法），最大的审稿风险是没有任何消融与工具级基线，使核心设计主张停留在架构叙述层面。

  • 问题定义清晰度：强——“缺一层 Omni harness”的问题边界与”不改宿主推理核心”的约束在 §1 定义明确，§3 的覆盖与 §4 的架构与之对应。
  • 创新性证据：弱——增量主要是已有组件（Skill、MCP、DAG 调度、资产表）在 any-to-any 生产场景的整合；与最接近系统（Agent-Omni、CUA-Skill、MMSkills、SkillsBench）没有直接实验对比，首次性只有作者主张（§2.2）。
  • 方法可信度：中——架构、规格与失败/中断语义描述详尽且自洽（§4–§5、附录 C–H），但设计有效性无实验隔离（§4.3）。
  • 实验支持力度：弱——单一自建基准、弱基线、无消融、无方差、无成本；头条数字存在放大与跨子集比较问题（§4.1–4.2）。
  • 可复现性：无法确认——依赖闭源宿主与多家闭源 API，环境与评测细节未披露，官方仓库无 License（§4.4 与 §5 的材料核查）。
  • 综合阅读价值：中——对做多模态 agent 与 harness 工程的读者有较高借鉴价值，但作为科学证据支撑有限（全文证据分布见 §4.3）。
