0. 一句话结论

IQuest-Q1 想解决的是通用大模型在长程、跨 scaffold 的真实命令行任务中不够专、不够稳的问题；作者用 320B 总参数、15B 激活的稀疏 MoE，配合两段预训练课程、中期训练、两阶段 SFT、领域 RL、四教师 on-policy 蒸馏与模型合并，构建一个面向 CLI 的开源智能体基座。论文在自报的 20 余个基准上给出了有竞争力的数字（如 DeepSWE v1.1 64.6、CyberGym 84.5、Toolathlon-Verified 75.0），但缺少组件消融、评测协议与基线并不完全对齐，human-on-the-loop RSI 也只有一次内部案例，因此「能力从何而来」和「相对闭源前沿的全面性」都还不能算被证明。

1. 论文具体想解决什么问题？

论文没有单列「问题定义」节，以下根据 §1、§5、§6.2 与 Limitations 归纳。背景是：基于大语言模型的 agent 不再只生成回答，而是通过多轮推理、行动与环境交互完成任务；在各类环境里，命令行接口（command-line interface，CLI）又是模型访问文件、执行代码、调用工具和操作外部系统最通用的接口之一（§1）。因此，作者把「更强的 CLI 能力」当作构建更强 agentic model 的前提，并希望做一个在软件工程、通用任务执行、长程推理和安全场景上都能用的开源基座（§1）。

现有做法大致是两条路。第一条是用通用大模型加一个 agent scaffold（运行框架/脚手架，例如 Claude Code、Codex、OpenCode），由 scaffold 负责工具定义、上下文管理、命令执行与结果回传；第二条是在通用模型上做 SFT、RL 或蒸馏，把某个 scaffold 上的任务轨迹压进模型。作者认为这些做法在真实 CLI 场景下仍有明显缺口：长程任务需要多轮调试和验证，模型容易漏掉约束、重复失败尝试或留下未解决的问题；换一个 scaffold 或工具 schema，模型的表现会明显波动；真实工程环境还有仓库、依赖、权限和沙箱等系统复杂度（§6.2、Limitations）。论文用 Terminal-Bench 3.0/4.0 的低分、以及一次内部任务中因工具名和参数不匹配产生的 35 次 tool-call 错误来支撑这一判断（§5.4、§6.2）。

需要区分三层。领域一般问题是「如何让语言模型在长程、可执行的 CLI 环境里稳定完成工程任务」；本文实际解决的具体子问题是「如何从零训练一个 320B/15B 的稀疏 MoE，并让预训练、中期训练与后训练的数据分布逐步对齐 CLI 交互，同时覆盖多个 scaffold 和版本」；它顺带提出一个内部 CLI 体验基准和一次人机协作的模型迭代案例，但这两件事并不是同一个问题。论文没有提出新的失败模式理论，也没有用受控实验证明「通用模型失败的原因就是 CLI 数据不足」；它观察到现象，给出的原因解释主要是作者主张。

作者给出的原因可以概括为四点：CLI 相关的数据与工具调用格式在通用预训练中占比不足；训练数据偏向单一 tool-call schema，导致跨 scaffold 时 schema 不匹配；大模型在长上下文和高稀疏 MoE 下的训练稳定性限制了 scaling；不同能力分散在多个专家模型里，需要一次合并或蒸馏才能得到一个统一模型（§1、§2.2、§6.2）。这些解释与后文的设计一一对应，但论文没有逐条做因果验证。最终要验证的核心假设是：以 CLI 为中心的多阶段课程、稳定的架构与优化器、多 scaffold 的 RL 与多教师蒸馏，能让一个开源 MoE 在 coding、通用 agentic 与 CLI 交互三类任务上达到有竞争力的水平；此外，human-on-the-loop 的模型开发流程可以缩短后续迭代周期。前一个假设有大量自报基准数字，后一个假设只有一个案例。

2. 创新点是什么？

如果把「创新」定义为新算法，本文的增量有限；如果把它定义为「把已有组件组织成可训练、可评测的 320B CLI 基座」，增量是实质的。论文明确借用了 SplitNorm、Muon、μP、MTP、GRPO、MOPD、EAGLE-3 等已有工作，真正的差异主要在数据课程、跨 scaffold 的后训练组织方式，以及把这些东西跑在一个 320B/15B 模型上的系统实现。以下四点分别对应数据、模型、后训练和开发流程；证据统一放在 §4。

第一，CLI 中心的多阶段训练课程。预训练先用多样语料建立语言与知识，再在第二阶段把代码比例从 40% 提高到 70%；中期训练加入 agentic 轨迹、QA 与长上下文（32K→128K→512K）；后训练再用任务合成、真实环境和验证式 agentic 微调把分布推向 CLI。与「在通用基座上直接做 SFT」相比，这套课程让工具调用格式和长程交互更早进入训练；与 Kimi K3、DeepSeek-V4 等同样强调 agentic 后训练的路线相比，本文的差异主要是 CLI 聚焦和跨 scaffold 覆盖，而不是新的训练目标（§1、§3、§4.2）。

第二，面向稳定 scaling 的架构与优化器组合。模型使用混合 GQA/SWA 注意力、query-aware sink、QKNorm/QKNorm Clip、Partial RoPE、首层 dense MLP 与 Stable SplitNorm，并用 Muon + μP 做优化和超参迁移。作者报告在与 Qwen3-MoE 风格、相同数据的受控对比中取得 1.93× 的 scaling efficiency，并给出 572B 激活参数 / 12T 总参数的 Critical Model Size 外推。这里多数组件是已有的，新的部分是组合方式、规模与稳定性分析；论文没有把收益拆到单个组件（§2.1、§2.2、§4.3）。

第三，多 scaffold、多版本的后训练与能力合并。SFT 之后，作者在 Claude Code、Codex 等不同 scaffold 及其版本上做领域 RL，再用四个冻结专家（agentic UX、multi-harness、long-horizon、general）做 multi-teacher on-policy distillation（MOPD，多教师同策略蒸馏），最后用 residual model merging 把不同阶段和专家分支的 checkpoint 合入一个模型。MOPD 本身来自已有工作，本文的增量是把它放到跨 scaffold/version 的设置里，并配套异步教师执行与按需权重加载（§4.4–§4.7、§4.3）。

第四，human-on-the-loop 的模型开发流程。作者让一个基于 IQuest-Q1 的 agent 追踪工具调用失败、诊断训练数据中的 schema 偏置、提出清洗与增强方案，再由人类专家审批训练实验。这个流程被描述为通向 recursive self-improvement（RSI，递归自我改进）的路径；但论文只报告了一次内部迭代，没有与人类工程师单独工作的对照，也没有跨迭代的量化闭环（§6.2、§4.3）。

3. 作者如何解决？

整体直觉是：与其在推理时不断给通用模型加 scaffold，不如把 scaffold 里的交互模式提前写进训练分布。模型看到的输入是「用户指令 + 工具定义 + 环境观察」，输出是「工具调用/命令 + 自然语言」，环境执行后再把结果作为下一轮观察；预训练负责语言与世界知识，中期训练负责把 agentic 轨迹、长上下文和工具格式灌进去，后训练负责在可验证的任务上把行为校正到「能完成任务」而不是「像在完成任务」。图 1 给出了这条主线的三段式结构。

图 1（论文 Fig. 2）：这张图把训练主线画成三段：预训练使用 web、code、STEM 等多样数据，并在架构侧强调稳定高效扩展；中期训练加入 agentic/reasoning 数据（QA、知识、agent 轨迹）并扩展上下文；SFT 阶段把任务合成、真实环境和验证式 agentic 微调接上。箭头表示 checkpoint 逐段传递；后训练的 RL、四教师 MOPD 与模型合并细节在论文 Fig. 6（本报告图 3）展开。读者应把它理解为一条数据分布逐步向 CLI 交互靠拢的课程，而不是端到端一次训练。

3.1 输入、输出与训练阶段

训练样本的基本单位是一条多轮轨迹：系统提示与工具 schema、用户任务、模型发出的 tool call 或 shell 命令、环境返回的观察，循环直到模型给出最终答案。模型只负责生成文本与工具调用；命令的实际执行、沙箱隔离、网络限制、文件系统状态和 verifier 判定都由外部 harness 控制。训练时只对模型生成的 assistant token（包括 tool-call token）计算损失，用户指令和工具观察被 mask 掉（§4.3）。推理时模型仍然输出同一种格式，因此需要一个能解析 IQuest 专用 tool-call 格式的 serving parser 和兼容的 agent harness；这也是作者在 Limitations 中明确承认的部署约束。

论文把第一阶段称为预训练，但没有说明模型是否从某个公开基座初始化；按全文叙述，这里理解为从零预训练（这是分析者推断，论文未明确写出初始化方式）。预训练和中期训练合计 29T tokens（§3.1）；后训练包括两阶段 SFT（240B+ 与 50B+ tokens）、领域 RL、MOPD 和模型合并（§4.3–§4.6）。三个阶段解决的不是同一个问题：预训练决定知识上限，中期训练决定长上下文与 agentic 格式的覆盖，后训练决定任务成功率与跨 scaffold 的鲁棒性。论文没有给出三个阶段各自的 token 配比和算力，因此无法判断哪一段对最终榜单贡献最大。

3.2 模型架构：混合注意力 + 稀疏 MoE + 稳定化设计

模型是 88 层、隐藏维度 3,072 的稀疏 MoE：每个 MoE 层 256 个 routed experts，每 token 激活 8 个，专家中间维度 1,536；注意力有 48 个 query head 和 8 个 KV head，每个 head 维度 128；词表 160,000，输入 embedding 与输出权重不共享（Table 1）。第一层用 dense FFN（中间维度 12,288）替代 MoE 路由，作者给出的理由是缓解最早层的专家负载不均；其余层才是稀疏 MoE。这个细节很重要：它说明「320B 总参数、15B 激活」是一个平均意义上的稀疏度，首层 FFN 和注意力部分不参与 MoE 稀疏化。

注意力采用混合设计：最前两层和最后两层用 full attention（FA，全注意力），中间按 3 层 sliding window attention（SWA，滑动窗口注意力）+ 1 层 FA 重复，窗口大小 4,096；Partial RoPE 只作用于每个 head 的 32 个维度，SWA 与 FA 的 RoPE base 分别为 10,000 和 1,000,000（Table 1、§3.2）。这样做的直觉是：局部窗口承担大多数 token 的廉价交互，少量全局层负责跨段信息；Partial RoPE 则把位置信息限制在一部分维度，减少长上下文外推时的扰动。每个注意力模块还带一个 query-aware sink token，为多余的注意力权重提供不影响输出的去处；QKNorm 控制 query/key 的尺度，QKNorm Clip 把仿射参数上限压到 10，防止训练中出现过大的缩放（§2.1、§3.2）。图 2 把这些组件放在一张架构图里。

图 2（论文 Fig. 3）：从左下输入 embedding 进入首个 Transformer block（dense FFN + full attention），随后是 N× 重复块（3 层 SWA + sparse MoE 与 1 层 full attention + sparse MoE 交替），再经顶部一个 full attention + sparse MoE 块接 LM head。右侧放大 attention：Q/K 投影后分别做 QNorm/KNorm、Partial RoPE，再进入 scaled dot-product attention；额外的 sink K 与 zero V 给多余注意力一个不影响输出的去处，最后 O projection。左侧的 RMSNorm 位置体现 Stable SplitNorm：attention 前归一化、FFN 的残差路径保持未归一化，attention 输出再加 RMSNorm。读者应理解这是「局部窗口为主、全局层兜底」的混合注意力，加上 MoE 的稀疏激活，共同决定 15B/token 的计算路径。

稳定化设计的核心是 Stable SplitNorm。传统 Pre-Norm 在残差流上逐层累积未归一化的方差，深层残差更新的相对贡献会变小；SplitNorm 把注意力子层前的残差流归一化、FFN 的残差路径保持未归一化，试图同时拿到 Pre-Norm 的稳定性和 Post-Norm 的深度利用。作者在此基础上加了两处修改：attention 输出先做 RMSNorm 再回加，首层再用 SandwichNorm 稳定残差流入口，合起来称为 Stable SplitNorm（§2.1）。需要说明的是，SplitNorm 本身来自先前工作，本文的增量是这两处稳定化修改；论文没有单独报告「去掉 attention 输出 RMSNorm」或「去掉首层 SandwichNorm」的对照。

优化器方面，Muon 用于除 token embedding、LM head、归一化参数和 MoE router 之外的所有参数，其余用 Adam；Muon momentum 为 0.95，正交化更新按 0.2max⁡(m,n)0.2\sqrt{\max(m,n)}0.2max(m,n)​ 缩放，weight decay 为 0.1（§3.2）。μP 参数化用于宽度方向的 learning-rate transfer；作者在一个隐藏宽度 896、18 层的 proxy 上搜学习率，再零样本迁移到目标模型，并报告在 4× 宽度和 4× 深度范围内可迁移（§2.1、Table 3、论文 Fig. 9）。学习率采用 warmup-stable-decay：升到 6×10−46\times10^{-4}6×10−4 后在 Stage 1 保持，Stage 2 末降到 2×10−42\times10^{-4}2×10−4，中期训练末降到 6×10−56\times10^{-5}6×10−5（§3.2）。这些数字说明作者确实在做大模型训练，但「μP 迁移在 4× 范围内成立」是优化器层面的证据，不等于下游 agent 能力也按同样比例扩展。

多 token 预测（multi-token prediction，MTP）方面，预训练时加两个 MTP 层，损失权重 0.3；训练结束后把第一层改造成递归 drafter，用于 speculative decoding（投机解码），第二层在专门阶段丢弃。推理时复用同一个 MTP 层做多步递归起草，并把它的注意力换成更小窗口的 SWA，以固定参数预算延长预测跨度（§2.1、Table 1、论文 Fig. 11）。这是一个推理加速设计，不改变主模型的输出分布；论文没有报告 draft 接受率或端到端加速比。

3.3 预训练与中期训练：把数据分布推向 CLI

预训练数据来自网页、公开 GitHub 代码、书籍、论文、新闻和领域材料，代码部分强调编程语言、模态和任务粒度的多样性；统一处理管线包括清洗、质量过滤、精确去重和模糊去重（§3.1）。Stage 1 用多样语料建立基础语言能力，Stage 2 逐步提高代码和 STEM 比例，作者设计了一个四阶段管线，把代码数据占比从 40% 提高到 70%（§3.1）。这一步的动机很直接：CLI 任务既需要自然语言理解，也需要代码、仓库和科学知识；但论文没有给出各来源的 token 数、采样权重、去重阈值，也没有说明是否对评测集做了污染检查。

中期训练把三类数据混在一起：高质量自然语料、QA 对和 agentic 轨迹；数据用适配中期训练的 chat template 组织，保留推理与工具调用相关的特殊 token（§3.3.1）。与常见后训练不同，这里的 loss mask 是 token 级的：作者直接指定哪些 token 参与损失，而不是按角色（user/assistant/tool）整段 mask，从而可以在一条样本里只监督选定的片段（§3.3.1）。上下文长度按 32K、128K、512K 三阶段扩展，使用变长序列打包；全局注意力的 RoPE base 从 500,000 提到 1,000,000，SWA 的 4,096 窗口和 10,000 base 保持不变（§3.3.1）。学习率在三阶段共用一条 cosine decay，阶段切换时只重置优化器状态，不重新 warmup（§3.3.1）。

agentic 数据的构造是中期训练的关键。作者以选定的轨迹作为行为锚点，同时用预训练文档扩展技术与任务覆盖；从兼容的代码仓库构造可执行、容器化的实例，再用 agent 在每个实例上 rollout，保留有效且完整的轨迹（§3.3.2）。论文称这个过程产出超过一百万个实例，但没有给出任务类型分布、成功率、平均轮数、容器启动成本，也没有说明这些实例与评测基准的重叠程度。预训练和中期训练的评价使用 held-out agent 轨迹上的 bits-per-byte（BPB）以及「原子能力」分解评估，前者衡量模型对专家轨迹的似然，后者把长程行为拆成可单独测的能力；论文没有报告这两项的具体数值（§3.4）。

3.4 后训练：SFT、领域 RL、MOPD 与模型合并

后训练的第一步是任务合成。作者把任务分成 general、reasoning、coding 三类：general 从 RapidAPI、Smithery 的 API/MCP server、公开技能和 workspace 文件出发，按 Standard Occupational Classification 覆盖职业并做 solve-then-refine；reasoning 用文档驱动的管线，从概念清单扩展到科学主题、检索与筛选文档、再生成带参考答案的任务；coding 从 GitHub 仓库和工业数据构造可执行环境，使用 Claude Code、Codex 等多个版本的 harness，任务查询来自 PR、issue、仓库知识图谱、文档和清洗后的使用日志（§4.1）。coding 任务的 verifier 由 agent 写的测试、适配后的仓库测试和文档行为检查组成；一个 agent-judge 循环检查可执行性、泄漏、指令/参考解/环境/verifier 的一致性，要求参考解通过、no-op 解失败，并用 rubric 审查轨迹是否作弊（§4.1）。

第二步是防 reward hacking（奖励黑客）。作者从三个层面保护环境：准备阶段清理 Git 历史、移除可能泄漏解的文件、隔离任务环境；执行阶段限制网络与敏感文件访问、在执行前拦截工具调用、用观察到的 hacking 行为更新阻断规则；轨迹审计阶段用规则和 LLM judge 检查命令、工具输出与提交解，确认作弊的轨迹从训练中剔除（§4.2）。对 SWE 类任务只保留 base commit 之前的 Git 历史，并在 Claude Code、Codex、OpenCode 中用 hook 阻断取回已有解；Terminal-Bench 在不需要时删除 Git 历史；ProgramBench 则用只含编译好的 oracle 和任务文档的新容器（§4.2）。这些措施说明作者意识到 agentic 训练中「环境泄漏」会直接污染 SFT 与 RL，但论文没有报告拦截规则命中率、误杀率或被剔除轨迹的比例。

第三步是两阶段 SFT。模型从中期 checkpoint 初始化，优化 assistant 响应（含 tool-call token）的自回归交叉熵，mask 用户指令与工具观察；Stage 1 用 240B+ tokens、学习率 5×10−55\times10^{-5}5×10−5，Stage 2 用 50B+ tokens、学习率 1.5×10−51.5\times10^{-5}1.5×10−5，各自做 cosine decay，多条样本打包并用 attention mask 防止跨样本注意（§4.3）。论文没有说明两个阶段的数据构成差异，也没有解释为什么模型合并从 SFT Stage 1 出发、而 MOPD 学生从 Stage 2 初始化；这两个选择对后文的能力合并很关键，但当前材料无法确认其理由。

第四步是领域 RL。每个 episode 指定任务域、harness 及其版本、环境和 evaluator；策略在不同 harness 中交互，只看到公开指令、工具和执行反馈，参考解与隐藏检查保持隔离。GRPO 在固定 harness/evaluator 版本下比较同一任务的多次 rollout，采样时平衡 domain–harness 组合并保留回归案例（§4.4）。奖励由独立 verifier 判定最终正确性；长轨迹的辅助 segment reward 只奖励可测量的进展，惩罚多余计算、约束违反和 reward hacking；模型生成的诊断必须有执行记录作证据。失败会先归因：策略造成的错误进入学习信号，与环境/harness 有关的故障被 mask，evaluator 故障则阻断该样本；token 级更新通过 Token-In, Token-Out（TITO）管线使用记录的 rollout 概率（§4.4）。论文没有给出 RL 的任务数、rollout 预算、奖励权重或训练 token 量。

第五步是 MOPD。学生从 SFT Stage 2 初始化，四个冻结教师分别负责 agentic 用户体验、multi-harness、long-horizon 和 general agentic 能力。对每个任务，学生先自己 rollout，得到 BBB 条轨迹；再按任务域 did_idi​ 选择对应教师 qdiq_{d_i}qdi​​，由教师对学生生成的每个 token 打分。设 pkp_kpk​ 为当前学生策略，qdiq_{d_i}qdi​​ 为任务域 did_idi​ 对应的冻结教师，得到截断的对数比率优势：

这个优势的含义是：如果教师比当前学生更倾向于生成这个 token，就给它正权重；反之给负权重，再用 [−c,c][-c,c][−c,c] 截断控制方差。作者用 reverse-KL 风格的、按长度归一化的 surrogate 来更新学生，只对模型生成的 token（含 tool-call token）计算损失，指令和工具观察只作为上下文；重复的 rollout 会被 mask 掉（§4.5）。这仍然是一种 on-policy 蒸馏：数据由学生自己产生，教师只提供 token 级信号，因此能覆盖学生实际会走到的状态，而不是只模仿教师的离线轨迹。

第六步是模型合并。作者从 SFT Stage 1 出发，在训练过程中穿插 residual model merging：每次合并先计算某个 checkpoint 相对指定 reference checkpoint 的参数增量，按预设权重和全局 ℓ2\ell_2ℓ2​ 范数校准后加回 reference，最终把专家分支和 MOPD checkpoint 合入 IQuest-Q1（§4.6）。这相当于在参数空间做「按范数归一化的任务向量相加」，目的是缓解不同阶段/专家之间的参数冲突；但论文没有给出合并权重、reference 的选择规则，也没有报告单独去掉合并后的结果。图 3 把后训练的四个环节串在一起。

3.5 基础设施与推理：长上下文、异步教师与工具格式

训练基础设施要解决两个瓶颈。第一个是长上下文下的负载均衡：序列打包用 best-fit 策略，在全局打乱的数据流上维护一个最多 2BS2BS2BS tokens 的有限前瞻窗口（BBB 为全局 batch，SSS 为序列长度），当前窗口装不下的样本会带到下一轮并优先处理；打包后的序列还会跨 data-parallel replica 重排，以 micro-batch 粒度平衡文档长度差异带来的计算不均（§2.3）。第二个是上下文并行：full attention 用 ring-based K/V exchange；SWA 只交换所需的 halo，并把交换与前后向计算重叠。每个 rank 先用自己的本地 K/V 算出内部 query 的完整输出，以及边界 query 的部分输出和对应的 Log-Sum-Exp（LSE，对数求和指数）统计；halo 到达后再算边界 query 的补集，并用 LSE 重新归一化合并两部分（§2.3、论文 Fig. 10）。这样边界 query 不必等远端 K/V 到齐就能开始计算，同时保持滑动窗口的语义。

后训练运行时是另一套系统。它要在一个训练 run 里支持多个 harness 和版本：每个实例指定 scaffold、任务环境和 verifier，运行时在隔离沙箱中执行对应配置，保留工具编排、上下文管理和交互流程，并把不同 API 协议映射到统一的 policy 接口（§4.7）。rollout 与训练的一致性靠 TITO：在模型服务边界保留 session 级 prefix tree，复用跨轮次、跨分支的 token 历史，返回 scaffold 期望的结构化响应，并在序列结束时把轨迹、奖励和 token mask 一起保留（§4.7）。MOPD 用全异步训练：周期性同步学生参数、显式控制样本 staleness，教师前向与训练引擎走同一条执行路径以减少 log-prob 偏差；教师权重存在分布式存储里按需加载，只把当前教师需要的 shard 放进 GPU，并在当前前向中预取下一个教师的权重（§4.7）。这套设计让四个教师不必各自常驻一份 GPU 副本，但代价是存储、IO 和调度复杂度。

最后是人机回路的开发流程。作者把 IQuest-Q1 接入内部模型开发基础设施，让 agent 通过统一接口读取训练与评测记录、定位失败、提出数据清洗或配置修改；人类专家审批关键决策与昂贵实验，并控制哪些改动进入后续迭代（§6.2）。论文给出的一次案例是：agent 追踪 6,054 次工具调用、定位 35 次 schema 相关错误，发现训练数据偏向单一 tool-call schema 且部分工具定义与调用参数不一致，提出清洗与增强方案；审批后用 2.35B tokens、938.7 GPU hours 训练新 checkpoint，并在 held-out 与熟悉 schema 上评估。这个流程把模型用于改进下一代模型，而不是推理时的 agent loop；论文只给一次案例，没有把它与人类工程师的独立诊断做对照，因此「RSI」在这里是流程愿景，不是已被验证的闭环。

推理阶段，模型输出 IQuest 专用格式的 tool call，必须配兼容的 serving parser 和 agent harness 才能被结构化执行；模型是纯文本输入，没有原生图像、音频或视频能力（Limitations）。递归 MTP 用于投机解码，长上下文训练扩展到 512K；论文没有报告推理吞吐、首 token 延迟、draft 接受率或不同 harness 下的平均工具调用次数，因此无法判断这些系统设计在真实部署中的性价比。

4.3 机制证据

先把证据类型分开。Table 2 与图 5 的分数是原文事实；作者把提升归因于 CLI 中心课程、Stable SplitNorm/Muon/μP、多 scaffold RL、MOPD 和模型合并，是作者主张；我认为这些实验还不足以把总榜提升归因到某个组件，是审稿人判断；各后训练组件的消融、训练种子、总算力和数据配比属于论文未报告，当前材料无法确认。下面的机制证据主要是三类：架构层面的受控 scaling 对比、学习率稳定性分析，以及定性的 CLI 案例。

图 6 先解释作者如何定义「稳定」。在附录 A 中，作者对学习率做网格搜索，把训练损失轨迹分成 stable、warning、collapsed 三类：stable 持续下降；warning 先反弹再恢复；collapsed 反弹后维持高损失。ηsafe\eta_{\rm safe}ηsafe​ 定义为被判定为 stable 的最大学习率，ηopt\eta_{\rm opt}ηopt​ 是在固定预算下优化效率最高的学习率；两者之比的对数 HN=log⁡(ηsafe/ηopt)H_N=\log(\eta_{\rm safe}/\eta_{\rm opt})HN​=log(ηsafe​/ηopt​) 就是稳定裕度，HN≤0H_N\le 0HN​≤0 表示优化已被稳定性约束（§2.2、Appendix A）。图 6 展示的是这三类轨迹的代表曲线，而不是某个组件的消融：它证明作者有一套可操作的分类标准，但不能证明 Stable SplitNorm、Muon 或 μP 中哪一个扩大了稳定区间。

图 6（论文 Fig. 8）：三条 LM loss 曲线分别对应 stable、warning、collapsed 三种训练状态；稳定曲线单调下降，警告曲线在约 250 步反弹后恢复，崩溃曲线反弹后维持高 loss。论文把最大稳定学习率定义为 ηsafe\eta_{\rm safe}ηsafe​，并用它和 ηopt\eta_{\rm opt}ηopt​ 的比值定义稳定裕度；这张图是分类标准的示例，不是组件消融。它说明作者为什么强调「宽稳定区间」，但不能单独证明 Stable SplitNorm/Muon/μP 中哪一个带来了该区间。

最接近受控实验的是 §2.2 的 scaling efficiency 对比：作者按 Qwen3-30B-A3B 的配置构造一个 Qwen3-MoE 风格基线，用相同训练数据比较，报告 IQuest-Q1 在相同训练 FLOPs 下训练交叉熵更低，整体 scaling efficiency 高 1.93×，也就是达到同样训练损失只需约 52% 的算力（§2.2、论文 Fig. 4a）。这个对比有价值，因为它控制了数据和训练预算；但它比较的是「整套 IQuest 设计」与「Qwen3-MoE 风格基线」，差异同时包含混合注意力、query-aware sink、QKNorm/Clip、Partial RoPE、首层 dense MLP、Stable SplitNorm、Muon 和 μP。论文没有做 leave-one-out 消融，因此不能把 1.93× 归给 Stable SplitNorm，也不能证明 Muon + μP 是必要的。作者说这是「cumulative benefit」，这个措辞是准确的；但如果读者把它理解成「Stable SplitNorm 带来 1.93×」，就超出了原文。

稳定性方面，作者报告在测量尺度上 ηsafe\eta_{\rm safe}ηsafe​ 始终高于 ηopt\eta_{\rm opt}ηopt​，并外推 Critical Model Size 约为 572B 激活参数 / 12T 总参数，说明在当前 recipe 下还有 scaling 余量（§2.2、论文 Fig. 4b）。μP 的证据是：在一个 896 宽、18 层的 proxy 上选学习率，零样本迁移到目标模型；在 4× 宽度和 4× 深度范围内，最优学习率保持一致（§2.1、Table 3、论文 Fig. 9）。这些是优化器层面的证据，能支持「训练稳定、超参可迁移」，但论文没有把这些稳定性指标与下游 benchmark 提升做相关分析，也没有证明 572B 的外推在真实 572B 模型上成立。572B 是外推值，不是实测模型。

后训练组件的机制证据更薄。MOPD 只报告了最终模型，没有报告「不用 MOPD」「只用单个教师」「换教师组合」「去掉 reverse-KL/clip」的对照；模型合并没有报告「不合并」「只合并 SFT 阶段」「改变 ℓ2 校准」的对照；两阶段 SFT 没有报告「只做 Stage 1」「只做 Stage 2」的对照；预训练的两阶段课程没有报告「Stage 2 不提高代码比例」的对照；长上下文扩展没有报告 32K/128K/512K 各阶段的 agent 能力对照；多 scaffold/version 的 RL 也没有按 scaffold 拆分的对照，无法判断跨 scaffold 训练是否真的比单 scaffold 更稳。论文也没有给出 RL 的任务数、rollout 数和奖励权重，因此无法判断 RL 与 MOPD 各自贡献多少。按现有材料，只能说「整套后训练流程产出了一个有竞争力的模型」，不能说「MOPD 或模型合并是有效的」。

定性证据方面，论文 Fig. 7 展示了模型从自然语言规格生成交互式前端应用（游戏世界、场景编辑、科学可视化），用 §6.3 报告了三天防御性安全部署中专家借助模型产出 30 份漏洞报告、经同行复核并负责任披露。这些例子说明模型能完成真实工件和真实安全分析，但它们没有对照组、没有成功率、没有用户研究，不能替代对「CLI 交互体验」的定量评估。§6.2 的 RSI 案例同样是一次性的：agent 追踪 6,054 次工具调用，定位到训练数据偏向单一 tool-call schema、部分记录的工具定义与调用参数不一致，提出清洗与增强方案；人类专家审批后，用 2.35B tokens、938.7 GPU hours 训练新 checkpoint，并在 held-out schema 与熟悉 schema 上评估。论文没有报告这个 checkpoint 相对基线的具体提升，也没有与「人类工程师独立完成同样诊断」做对照，因此它证明的是「agent 可以参与一次数据诊断与训练实验」，不是「递归自我改进已经形成闭环」。

综合起来，本文的效果证据（benchmark 分数）比机制证据强。Table 2 覆盖广、与闭源/开源基线并列，能支持「这是一个有竞争力的开源 agentic 模型」；但 1.93× 是整套架构的对比，稳定性分析是优化器层面的，MOPD/合并/课程/长上下文都没有消融。数据质量与规模、SFT 的 290B+ tokens、四个教师模型、不同 harness 的评测预算，都是可能解释总榜提升的替代因素，当前实验无法把它们与论文强调的机制分开。

4.4 成本与适用范围

训练成本方面，论文报告预训练 + 中期训练共 29T tokens，SFT 两阶段 240B+ 与 50B+ tokens；没有报告 GPU 型号、数量、总 GPU 小时、能耗或费用，也没有报告 RL 与 MOPD 的 token 量/rollout 量（§3.1、§4.3–§4.5）。唯一给出的算力数字是 RSI 那次实验的 938.7 GPU hours（§6.2），它只是后训练中的一个小实验，不能代表总成本。数据方面，预训练来源是网页、GitHub、书籍、论文、新闻和领域材料；中期训练有超过一百万个容器化实例；后训练使用 RapidAPI、Smithery 的 API/MCP server、公开技能、GitHub 仓库、工业数据和清洗后的使用日志（§3.1、§3.3.2、§4.1）。论文没有给出各来源的 token 数、采样比例、许可证、去重阈值，也没有说明如何检查评测集污染；工业数据和内部 CLIBench 也不公开。

推理与系统成本方面，模型是纯文本、需要专用 tool-call parser 和兼容 harness；长上下文训练扩展到 512K，但论文没有报告推理延迟、吞吐、显存占用或不同 harness 下的平均工具调用次数（Limitations）。递归 MTP 和异步教师加载是为效率设计，但前者没有 draft 接受率/加速比，后者没有 GPU 副本数、存储 IO 或调度开销的量化。后训练运行时要在同一 run 中支持多个 scaffold/version、隔离沙箱、verifier、TITO prefix tree 和四个教师的按需权重加载，系统复杂度明显高于单 harness SFT；论文没有报告这些基础设施的故障率或运维成本。人工方面，任务合成主要靠 agent 和规则，RSI 案例中有人类专家审批关键决策，但没有标注工时或人力成本。

适用范围应收缩为：在论文自报的 coding-agent、通用 agentic 与推理基准上，IQuest-Q1 在开源模型中具有竞争力，在 CyberGym、NL2Repo、DeepSWE、AutomationBench 等任务上超过同代开源基线；但它仍明显落后于 Claude Opus 5/GPT-5.6 的多个项目（SWE-Bench Pro、Terminal-Bench 3.0/4.0、HLE、APEX-Agents、JobBench、BrowseComp），在长程终端任务上尤其明显。它不能支持「通用 CLI 已解决」「跨所有 scaffold 稳定」「真实工程环境可无人监督」这些更大的结论。作者自己在 Limitations 中也承认：输出可能错误、代码需要测试复核、工具调用依赖专用 parser/harness、真实 CLI 任务仍需人工监督。这些限制与报告的数字并不矛盾，但会显著缩小读者对「开箱即用的 CLI agent」的预期。

  • 原文依据：CyberGym 84.5 衡量的是在大型开源代码库中复现和验证真实漏洞的能力（§6.3）；三天防御性部署中，人类安全专家借助模型产出 30 份漏洞报告，全部由同行独立验证，影响开源项目的发现被负责任披露（§6.3）。论文没有报告漏洞报告的精确率/召回率、误报率、专家节省的时间、模型在攻击性任务上的拒答率或红队结果，也没有说明开放权重后的滥用防护。Limitations 承认：纯文本输入、输出可能错误、工具调用依赖专用 parser/harness、真实 CLI 任务可能需要人工监督、模型仍会漏约束/重复失败/留下未解决问题。
  • 为什么重要：这是一篇要开放权重的网络安全能力模型。防御性部署案例能说明有用性，但不能说明安全性；没有误报率与红队评估，读者无法判断模型在真实安全流程中的可靠性，也无法判断开放权重后的风险是否被充分管理。真实 CLI 任务的失败率同样影响「agentic foundation model」的部署预期。
  • 当前能够得出的判断：原文事实是模型在 CyberGym 上得分较高，且有一次三天部署与 30 份报告；作者主张它对防御性安全有实质帮助；审稿人判断是这些证据是定性的，缺少精确率、召回率、失败率和红队数据。开放权重下的 dual-use 风险没有被量化，论文的安全讨论相对于能力展示明显偏薄。
  • 如何验证或补强：报告漏洞报告的精确率/召回率与专家复核结果，区分模型独立发现与人类引导的贡献；做红队评估与滥用测试，说明拒答/监控/许可策略；在真实 CLI 任务上报告失败率、人工接管率与平均修复时间；如果开放权重，提供负责任使用指南与漏洞披露流程。
  • 严重程度：次要问题。

6. 审稿式总评

作者认为通用模型在长程、跨 scaffold 的真实 CLI 任务中不够专、不够稳，因此提出 IQuest-Q1：用 320B/15B 的稀疏 MoE、混合注意力与 Stable SplitNorm/Muon/μP 做稳定预训练，用 29T tokens 的两段课程和中期训练把 agentic 轨迹与长上下文灌进去，再用两阶段 SFT、领域 RL、四教师 MOPD 和模型合并把多个专家能力合成一个模型。实验在 20 余个自报基准上表明，它在 DeepSWE v1.1（64.6）、NL2Repo（63.0）、CyberGym（84.5）、AutomationBench（52.7）等项目上超过同代开源基线，但在 SWE-Bench Pro（57.5）、Terminal-Bench 3.0/4.0（17.9/22.7）、HLE（39.2/55.7）、APEX-Agents（50.9）、JobBench（55.7）与 IQuest-CLIBench（53.7）上仍落后于 Claude Opus 5/GPT-5.6；其中「模型在多个 agentic 基准上有竞争力」的证据较强，「各组件为何有效」「CLI 体验是否真的优化」「RSI 是否成立」仍缺少充分支持。本文最有价值的部分是把一个 320B CLI 基座的完整训练管线、数据合成、后训练与基础设施摊开给读者看；最大的审稿风险是缺少组件消融、评测协议不齐、数据/算力不透明，以及把一次内部案例写成 RSI 路径。

  • 问题定义清晰度：中。CLI 作为通用接口、长程/跨 scaffold/真实环境三类困难交代得清楚，具体子问题（训练一个 CLI 中心的开源 MoE）也能辨认；但作者没有用受控研究证明通用模型失败的根本原因，RSI 的定义也偏宽，领域一般问题与本文实际解决的子问题需要读者自己拆开。
  • 创新性证据：中。320B/15B 规模、混合注意力与 Stable SplitNorm/Muon/μP 的组合、跨 scaffold 后训练与四教师 MOPD 是有辨识度的系统工作；但 SplitNorm、Muon、μP、MTP、GRPO、MOPD、EAGLE-3 都是已有组件，论文没有消融证明组合的必要性，也没有独立文献检索支持「首次」。
  • 方法可信度：中。架构、优化器、数据阶段、SFT/RL/MOPD/合并流程交代得较细，训练稳定性分析也有可操作的定义；但数据配比、总算力、RL 细节、两阶段 SFT 的差异缺失，后训练组件没有隔离，机制解释主要停留在「整套 pipeline 有效」。
  • 实验支持力度：中。覆盖 20 余个基准，与闭源/开源基线并列，能说明模型在开源队列中的位置；但结果多为作者自报，harness/预算/评分来源不统一，图与表基线集合不一致，没有方差或置信区间，内部 CLIBench 不可复核。
  • 可复现性：弱。论文没有给出代码/权重链接，没有数据卡、数据配比、污染检查和主训练算力；只有架构、部分超参和训练阶段可复现，无法从论文重建模型或复核榜单。
  • 综合阅读价值：中。作为现代 agentic foundation model 的工程管线与基准全景图，本文对理解「预训练→中期→SFT→RL→蒸馏→合并」很有帮助；但作为机制论文，它的消融与可复现性不足，适合批判性阅读，不宜把 Table 2 当作通用 CLI 能力的证明。
