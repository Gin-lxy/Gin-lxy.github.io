0. 一句话结论

Recursia 要解决的是“单独能成功的机器人技能组合后会失败”，作者把持久改进的单位从单个任务程序改成共享可执行栈（shared executable stack，含工具、带执行契约的技能、交接（handoff）机制和验证器（verifier）），用源任务失败归因（failure attribution）驱动编码智能体修栈，再以通用性检查、机制测试和配对选择/回归门筛选，最后冻结整个栈、用声明式任务适配器（declarative task adapter）执行未见过的长程组合。论文在 LIBERO-Pro Long 上报告 Pos 0.284、Task 0.534，相对 ASPIRE 高 5.8 与 15.1 个百分点；物理 Franka FR3 三个组合目标平均 66.7% 对 SD-only 的 26.7%，但这些结果只支持“同一 embodiment 内、源侧调试过的共享栈可以零样本迁移到新组合”这一有限结论：源侧诊断依赖仿真真值，物理实验每目标只有 10 次试验，附录承诺的逐任务表在 PDF 与 HTML 中都没有出现，尚不足以支持普遍的长程组合泛化。

1. 论文具体想解决什么问题？

长程机器人操作（long-horizon robot manipulation）不是“把若干会做的动作串起来”那么简单。论文的出发点是：技能库里的每个技能可以单独成功，但组合成长序列后，失败往往发生在技能之间的共享接口上，而不是发生在某个技能内部（§1）。这条路线属于“代码即策略”（code as policies）传统：语言模型生成调用感知与控制 API 的程序，程序里可以有反馈循环和过程抽象（§1、§4）。已有工作大致分两类。一类是视觉—语言—动作模型（vision-language-action model，VLA），如 OpenVLA、π0、π0.5，直接把观测和指令映射成动作；另一类是程序化智能体与技能库（skill library），如 Code as Policies、ProgPrompt、RoboCodeX、CaP-X、Voyager、ASPIRE、Lifelong Robot Library Learning 和 Uni-Skill（§1、§4）。ASPIRE 是最接近的前驱：它把执行反馈、程序修复、技能发现和进化搜索放进一个持续的机器人编程循环，并把验证过的修复蒸馏成可迁移的技能库（§4）。

论文指出，这些方法主要改进“生成的任务程序”或“技能库里的单个技能”，但组合是否可靠还取决于程序调用的共享接口：工具、技能契约、技能间的状态传递、验证逻辑（§1）。作者据此列出四类障碍，并各给了一个具体例子：

  1. 工具不足（tool insufficiency）：任务需要的能力在初始 API 中不存在。例如源任务需要“物体前方/中部”的参照关系，而初始关系分发不支持；N=10 的迭代增加了共享的实例选择与关系分发，指令分发覆盖从 81/90 提升到 84/90（§3.7、Table 2）。
  2. 语义失配（semantic misalignment）：工具正常返回，但没有真正到达后继技能要求的位姿或语义目标。一个具体表现是“松手”已经执行，物体却还没有被目标支撑面稳定支撑；Fig. 2 因此把 ready_to_release（可松手）与 placed（已放置）拆成两个声明，工具层也把“到达”与“完成移动”分开报告（§1、§2.2、Fig. 2）。
  3. 状态不兼容（state incompatibility）：前一个技能的终态违反后一个技能的前置条件。论文给的直观例子是：完成“释放”动作后还需要一次“后退”，下一次抓取才可执行（§2.2）；mug–pudding 序列里，mug-on-plate 谓词在 10 个 Pos episode 中全部为真，但完整合取只成功 1 次，seed 42 在 step 573 完成 mug 目标后，pudding 绑定返回 not_found（§3.4、论文 Fig. 4）。
  4. 验证脆弱（verification brittleness）：错误的检查会放行未完成的任务，或扰动已完成的目标。book-transfer 的 N=8 案例属于另一种表现：机器人已经抓起并抬起了目标书，但抬升后的视觉查询选中了桌上另一本相似的书，低重检位置被当成“抬升失败”，夹爪于是打开，后续抓取失败（§3.6、Fig. 6）。

这四类障碍分别对应分层控制器里的工具执行、技能完成、技能间状态传递和验证器（§1）。作者主张，这篇论文的新观察不是“组合会失败”这一早已存在的现象，而是把它重新定位为共享接口的失效：已有系统会从经验中获取和复用技能，执行引导的自调试也证明失败程序能提供修复证据，Darwin Gödel Machine 更把自我修改推到编码基准上；作者称“多层共享接口的修复如何被验证并跨任务保留”此前没有被单独研究（§1、§4）。作者的核心假设是：修共享接口应该同时改善多个组合，而只针对某个任务轨迹打的补丁只应让那条轨迹受益（§1）。

需要把问题边界说清楚。论文用 LIBERO-90 做源侧调试，用 LIBERO-Pro Long 和三个物理组合目标做目标侧评测；所谓零样本组合迁移（zero-shot compositional transfer）在 §2.1 被定义为：目标组合不为栈修改提供反馈，冻结的栈执行时不做目标特定代码修复；源任务和目标可以共享物体、关系和单个技能。这不是“未见过的物体”或“未见过的机器人”意义上的零样本。论文用案例说明了四类障碍，但没有统计各失败模式在源任务中的出现频率，也没有用对照实验证明“共享接口是组合失败的主要原因”；这一点在 §5 会继续讨论。

2. 创新点是什么？

真正的技术增量不是新的网络、损失或训练算法，而是改进对象的重新定义和一套围绕它的验收流程。论文没有训练策略或世界模型，基础模型在比较内固定，改进发生在可执行代码层（§2.1、§2.3）。以下三点分别对应“改什么”“怎么筛”“怎么复用”。

第一，把共享可执行栈（shared executable stack）作为持久改进单元，对应 §1 的工具、技能、交接、验证四类接口失效。栈写成 Sk=(Tk,Kk,Hk,Vk)\mathcal{S}_k=(\mathcal{T}_k,\mathcal{K}_k,\mathcal{H}_k,\mathcal{V}_k)Sk​=(Tk​,Kk​,Hk​,Vk​)，分别存放工具、带执行契约的技能、交接机制和验证器；每个接受过的修改都带代码版本、失败类别和验证证据（§2.1、§2.2）。与 ASPIRE 把修复蒸馏进技能库、Voyager 式技能库只存过程不同，这里把工具、技能完成证据、技能间状态传递和验证逻辑放在同一个可版本化对象里，并允许在缺少能力时生成新工具（§2.2、§3.7）。证据上，冻结栈的迁移收益见 §4.2 的图 3 与表 1，共享工具被生成并实际调用的记录见 §4.3 的 Table 2。这更接近问题表述与系统抽象的贡献，而不是新的学习算法；是否“首次提出”还需要更完整的文献检索。

第二，失败归因（failure attribution）驱动的递归改进流程与多维验证门（multidimensional validation gate），对应“如何把失败证据变成可验收的共享修复”这一问题。源侧执行轨迹定位“最早被违反的执行要求”，编码智能体只改一个共享模块槽位，候选修改要同时通过通用性检查、机制测试、配对选择门和回归门（§2.3、§2.4、Algorithm 1）。与 Darwin Gödel Machine 在编码基准上修改自身代码相比，这里把自我修改约束到机器人共享接口，并用源任务上的配对执行和逐任务损失上限来防止“平均值变好但丢掉已成功状态”；与 ASPIRE 的程序修复相比，这里显式区分“缺少能力”和“实现错误”，并把修复定位到四层中的具体一层（§2.3、§4）。这套流程是已有组件（失败归因、代码修复、回归测试、beam search（束搜索））的新组合，创新性主要来自约束设计和应用场景；门在两个记录案例中的接受/拒绝行为见 §4.3，但其因果贡献仍需消融（§5）。

第三，冻结整栈后的声明式复用，对应“源侧修好的接口如何在新组合上生效”这一问题。源侧改进完成后，工具、技能实现、交接逻辑和验证器一起冻结；目标侧只提供一个声明式任务适配器（declarative task adapter），描述物体、支撑面、关系类型和目标依赖，由共享执行器组合调用，不做目标侧代码修复，也不用目标反馈更新知识（§2.1、§2.4、§3.3）。这使“源侧改一处、目标侧多处受益”成为可执行的工程流程；证据在 §4.2 的 LIBERO-Pro Long 与物理三任务上，具体数字与边界留在那里展开。

3. 作者如何解决？

直觉上，作者把机器人长程任务看成一棵调用树：叶子是工具，中间节点是技能，节点之间靠交接传递状态，边上还有验证器检查“是否真的完成”。如果同一棵子树被很多组合复用，那么修子树比修某一条完整轨迹更可能迁移；反过来，如果只在一个任务程序里打补丁，换一个组合就失效。图 1 把这个思路放在一个系统视图里：目标侧只做观察—组合—执行，源侧用执行器（executor）、提议器（proposer）和验证器构成改进循环，候选栈以版本树的方式与父栈比较，四层共享栈是循环作用的对象。图 1 的读法是“源侧失败驱动栈演化，目标侧只消费冻结栈”，而不是“一个端到端策略在目标上继续学习”。

图 1（论文 Fig. 1）：这张图把论文的三段论证连成一条数据流。目标侧，系统观察场景、用声明式适配器把指令拆成有序子目标、在冻结栈上执行，栈本身不允许改代码；源侧，执行器记录动作、观测、机器人状态和失败，失败归因把问题定位到工具、技能、交接或验证器中的一层，提议器据此提出一个共享模块的补丁，验证器用通用性检查、机制测试和配对回归决定是否接受；接受者成为下一轮的父栈，拒绝者保留原父栈。版本树说明改进是“有向、可追溯”的：候选不是直接覆盖父栈，而是在隔离版本里比较。读图时应抓住“源侧闭环”和“目标侧开环”的分工：目标侧没有任何箭头回到栈，这正是论文所说的冻结复用。

先看输入和栈的定义。源侧输入是源数据集 Dsrc\mathcal{D}_{\mathrm{src}}Dsrc​（实验中是 LIBERO-90）、当前栈 Sk\mathcal{S}_kSk​、一个任务适配器 aτa_\tauaτ​ 和执行历史 ht=(o0,u0,…,ot)h_t=(o_0,u_0,\ldots,o_t)ht​=(o0​,u0​,…,ot​)；目标侧输入是未见组合的适配器和冻结栈。栈的四层如下：

Sk=(Tk,Kk,Hk,Vk) \mathcal{S}_k=(\mathcal{T}_k,\mathcal{K}_k,\mathcal{H}_k,\mathcal{V}_k) Sk​=(Tk​,Kk​,Hk​,Vk​)

其中 Tk\mathcal{T}_kTk​ 是工具集合，Kk\mathcal{K}_kKk​ 是技能集合，Hk\mathcal{H}_kHk​ 是交接机制，Vk\mathcal{V}_kVk​ 是验证器。工具暴露可复用的感知、几何、规划或执行操作，接口要写清输入、坐标约定、可观测完成条件和资源上限；工具集可扩展，但新工具只能由允许的底层操作组装，注册前要验证，且不能引入部署时不可得的感知或改动外部评估器（§2.2）。这解释了为什么“工具不足”不是让适配器里塞一个任务专用绕行，而是要求生成一个共享工具：绕行只救一条轨迹，共享工具才可能被多个组合调用。

技能的表示是执行契约（execution contract）：

Ki=(Prei,πi,Posti,Bi) K_i=(\mathrm{Pre}_i,\pi_i,\mathrm{Post}_i,B_i) Ki​=(Prei​,πi​,Posti​,Bi​)

Prei\mathrm{Pre}_iPrei​ 是可观测前置条件，πi\pi_iπi​ 是参数化程序，Posti\mathrm{Post}_iPosti​ 是完成时要求的证据，BiB_iBi​ 是资源上界。前置/后置条件针对任务参数和测量几何，而不是基准任务的身份；执行返回证据和终止原因，让调用者区分“动作做完了”和“任务关系建立了”；契约是可执行检查，不是在未观测状态下的形式化正确性保证（§2.2）。图 2 把四层接口的具体样子展开：工具层用公共机器人状态报告到达/停滞/不可达等状态；技能层把放置拆成“可松手”与“已放置”两个阶段；交接层要求同一实例、已验证的抓握和观测到的抬升；验证层用当前帧与冻结参考帧比较身份，并在不确定时返回 unsure 而不是硬判。

图 2（论文 Fig. 2）：这张图不是四个孤立模块的截图，而是同一套执行语义在四个责任层上的接口样例。工具层关心的是一次操作是否真的到达并完成，返回值区分 reached、stalled、unreachable、budget_exhausted 等状态，后继动作依赖的是完成状态而不是“命令已发出”；技能层把放置拆成 ready_to_release 与 placed 两个声明，前者只说明可以松手，后者才说明支撑几何、间隙和两帧稳定性都满足；交接层在“抓取→运输”之间要求同一物体身份、已验证的抓握和至少 5 cm 的抬升，避免把“抓到了东西”误当成“抓到了目标”；验证层在物体被移动后用冻结参考帧和当前帧比对身份，输出 identity_verified、identity_mismatch 或 identity_unknown。四层连起来的数据流是“动作状态→技能完成证据→交接前置条件→跨帧身份/关系验证”，读者应理解为什么单看某一层的成功信号不够。

交接层处理的正是状态不兼容。论文明确写出 Posti(ht)⇏Prei+1(ht)\mathrm{Post}_i(h_t)\not\Rightarrow \mathrm{Pre}_{i+1}(h_t)Posti​(ht​)⇒Prei+1​(ht​)：前一个技能完成，不自动意味着后一个技能可以开始。交接要更新后继使用的状态、检查后继前置条件，还要检查“之前已经达成、但后续动作可能破坏”的关系；根据观测到的失败，执行器可以重新观察、执行有界恢复或停止，恢复必须先建立缺失的前置条件才能继续（§2.2）。例如释放动作完成后要先后退，下一次抓取才可执行。这个设计与传统的“技能返回成功就进入下一步”不同：它把技能间的状态转移当成一等对象，而不是调用者脑中的隐式约定。

验证层则要避免“到达位姿”被误当成“任务完成”。论文要求验证器只用允许的观测和执行历史判断物体身份与任务相关关系；外部评估器独立测量自己的错误，内部验证器的输出永远不被当作真值（ground truth）成功标签；外部评估还要看支撑几何和跨观测的物体身份，因为“到达一个位姿”不等于“目标物体被目标支撑面支撑”（§2.2）。这一点是方法可信度的关键：它防止系统自己给自己发成功证书。但实现上有一个重要折扣：Appendix B.4 说记录版把放置验证器设成 enforce=False、corrections=False 的影子监视器（shadow monitor），外层 run() 也不要求影子判定为 success，所以论文自己提醒“不应把实现描述成在每个技能边界都强制执行放置后置条件”。这说明四层栈在概念上完整，在记录版实现里验证层的强制力并不均匀。

接下来是改进闭环，也就是论文所说的递归自改进（recursive self-improvement）。一轮迭代的输入是当前栈、源开发任务、选择任务和预算 BBB；执行器先跑源任务，记录动作、观测和机器人状态；失败归因用仿真真值区分失败机制，找出“最早有证据支持的执行要求违反”，记录发生阶段、证据和受影响组件，并区分“缺少能力”与“实现有错”（§2.3、Algorithm 1）。编码智能体拿到归因后提出一个候选修改 δ\deltaδ：说明失败类别、要改的栈层、预期修复和验证测试；每个迭代只选一个共享模块槽位，其他共享组件、诊断流程、检索、搜索代码和数据划分保持不变（§2.3）。候选在隔离版本里应用，例如接受新工具时 T′=Tk∪{tnew}\mathcal{T}'=\mathcal{T}_k\cup\{t_{\mathrm{new}}\}T′=Tk​∪{tnew​}；拒绝的候选不替换父栈，接受的候选保留代码哈希、源失败、测试和配对结果（§2.3、§2.4）。

候选要过三道关。第一道是通用性检查（generality checks）：拒绝共享代码里针对基准任务、种子、物体或场景的特化分支，几何常数必须有文档来源，例如机器人标定、测量几何或声明的物体无关构造（§2.4）。第二道是机制测试（mechanism tests）：感知和验证补丁可以在记录观测上回放，运动补丁必须做实机/执行测试，因为旧轨迹不能揭示新控制器会怎么做；还要检查接口兼容性、下游动作是否尊重失败返回；新工具既要证明目标能力，也要证明对不支持请求的有界处理（§2.4）。第三道是配对选择（paired selection）与回归：父栈和候选在相同源任务初始状态、同一资源政策下比较，考虑源任务成功、其他源任务的回归和资源使用；接受条件是 G(δ)∧U(δ)∧R(S′,Sk;Dsel,B)G(\delta)\land U(\delta)\land R(\mathcal{S}',\mathcal{S}_k;\mathcal{D}_{\mathrm{sel}},B)G(δ)∧U(δ)∧R(S′,Sk​;Dsel​,B)（§2.4）。Appendix A.2 给出记录版门槛：开发集净增至少 2 个状态、选择集至少 1 个；每个任务每个角色的损失至多 1 个，回归角色至多 1 个；最多允许 4 次干净的 horizon timeout。通过数值门还不够，评估者还要检查新成功是否真的完成了物理任务、新回归失败是什么（Appendix A.2）。

这套流程还有一个容易被忽略的层次：改进策略本身也会变。论文说验证门设置和用于调试的数据类型可以跨迭代调整，并会保留到后续迭代；把补丁选择从 top-1 扩到 top-nnn，就把顺序链变成了 beam search（§2.3）。这意味着“自改进”不只改栈，也改搜索/验收程序。它增加了方法的表达力，但也让不同迭代之间的比较不再完全同分布；后文 §5 会把这一点作为机制证据的混杂因素。

源侧完成后，所有共享实现冻结。目标侧适配器只声明请求的组合，执行日志记录每个子目标调用了哪个版本；适配器提供物体描述、支撑/目的描述、关系类型和目标依赖，执行器用适配器和观测历史组合调用（§2.1、§2.4）。论文强调目标侧不修代码、不用目标反馈；源侧诊断用的评估器真值从不进入部署策略的输入（§2.1、§3.1）。这就是“零样本”的全部含义：不是物体或机器人未见过，而是目标组合不为栈改进提供信号，冻结栈直接执行。方法不需要训练，基础模型在比较内固定；被学习/被修改的是代码和版本化栈，而不是模型权重（§2.1、§2.3）。

4. 解决得怎么样？

4.1 实验设置

仿真侧用 LIBERO-90 做源侧调试，包括失败诊断、修复生成和候选选择；所有源侧开发在目标评测前完成，选中的栈连同工具、技能实现、交接逻辑和验证器一起冻结（论文 §3.1）。主评测是 LIBERO-Pro Long 的 10 个长程任务，沿两个轴扰动：Pos 改变初始物体位置，Task 改变任务规格；每个任务—轴组合用 seeds 1–50，每轴 500 个 episode；指标是官方评估器的完整任务成功率，先对每个任务的 50 个状态求成功率，再对 10 个任务做不加权宏平均，失败、超时和程序错误都留在分母里（论文 §3.1、Appendix D.3）。论文报告 Overall 是 Pos 与 Task 宏平均的均值，但正文只给两个轴的数字（论文 §3.1、§3.2）。

基线是 OpenVLA、π0、π0.5、CaP-Agent0 和 ASPIRE。协议并不一致：CaP-Agent0 的公开协议在每个 seed 上重新生成程序，并带测试时推理和重试；ASPIRE 每个任务固定一个程序，不做目标侧调试；论文说比较时保留这个差异（论文 §3.1）。Fig. 3 的图注还明确说基线成功率是从已有比较中复用的，不是在同一套代码上重跑（论文 Fig. 3）。此外，Appendix C.1 承认仿真实验用 Contact-GraspNet，而用于对比的 ASPIRE 配置用 AnyGrasp，抓取提议质量可能同时影响单个操作和长程完成，直接比较的公平性受限。

物理侧是 Franka FR3 + Franka Hand，六个源任务：把杯子或牛奶盒放进篮子、把白杯和蓝杯放到左右盘子、把塑料碗放到盘子、把杯子放进碗；每个源任务保留 3 条开发 rollout（轨迹采样）。SD-only（skill document only）基线用 ASPIRE 的工具实现，但只更新一份自然语言技能文档；Recursia 更新共享 Python 栈。两者都用 GPT-6 Astra、前后腕部观测、同样的六个机器人工具（含 SAM3 与 Contact-GraspNet）（论文 §3.3）。目标有三个：T1 把杯子和牛奶盒放进同一个篮子；T2 把蓝杯放左盘、白杯放右盘，反转源任务的左右分配；T3 先把碗放盘上，再把杯子放进移动后的碗。每个目标每种方法评测 10 次，每次最多 20 个代码块，成功由人工判定（论文 §3.3）。源知识在评测前冻结，试验内的反馈修正不更新持久知识（论文 §3.3）。

机制分析分布在几处：§3.4 用回溯案例区分“单个技能变好”和“组合变好”；§3.5 比较三种推理驱动（inference driver）；§3.6 用两个验证门案例说明接受/拒绝；§3.7 用 Table 2 说明工具修复和工具生成；Appendix D.2 给出随源经验 NNN 的迁移 scaling。它们回答的是“哪些局部机制在动”，不是“每个设计都被消融过”。论文没有报告置信区间或具体 McNemar 值；Appendix C.5 只说“报告的精确 McNemar 比较使用不一致结果”，并要求置信区间考虑任务内状态分组，但可见正文没有给出这些统计量。

4.3 机制证据

先把证据类型分开。主结果的成功率是原文事实；作者把增益归因于“共享接口修复可迁移”“验证门挡住了局部/聚合假改进”，是作者主张；我认为这些实验还不足以把共享栈的贡献与迭代次数、人工审查、基准选择和数据泄漏分开，是审稿人判断；每轮候选拒绝率、总 token/时间成本、逐任务表在可见材料中缺失，属于无法确认。

第一组机制证据是“单个技能变好不等于组合变好”。N=11N=11N=11 时，standalone 的 stove-on 操作在开发和选择两个面板上都从 0/10 提升到 10/10，但 stove–pan 组合仍是 0/10；检查开发 rollout 发现 stove-on 谓词变真后，后续抓取尝试把 pan 弄丢了，其他候选又因逆运动学工作空间之外被拒（§3.4）。N=6N=6N=6 的 mug–pudding 序列更直接：mug-on-plate 谓词在全部 10 个 Pos episode 中为真，但完整合取只成功 1 次；seed 42 在 step 573 完成 mug 目标后 pudding 绑定返回 not_found，seed 41 则在 step 552 和 1440 分别完成两个目标且保留第一个（§3.4、论文 Fig. 4）。论文由此区分“后继执行失败”和“后继就绪条件未建立”，并说这正是 handoff 机制要处理的缺口。这个证据支持“孤立成功与链式成功之间有差距”，但它来自回溯案例，不是受控实验：没有报告所有 episode 的 Δchain\Delta_{\mathrm{chain}}Δchain​ 分布，也没有证明 handoff 修复就是后来成功的唯一原因。

第二组是验证门案例。N=8 时，book-transfer 的开发摘要报告 10 个 episode 中有 8 个出现候选过滤拒收；检查发现机器人已经抓起并抬升了目标书，但抬升后的视觉查询选中了桌上另一本相似的书，低重检位置被当成“抬升失败”，夹爪打开，后续抓取失败（§3.6）。N=9 的修复改变了 book insertion 的运输—下降边界，使进入开口仍在接触感知控制下；开发集的侧向走廊拒收从 8 降到 2，大多数测试通过，但官方完成只从 0/10 到 1/10，选择集仍是 0/10，低于预先声明的 2 和 1 个成功，因此被选择门拒绝（§3.6、Fig. 6）。N=11 的候选把开发完成从 2/50 提到 3/50、选择完成从 7/50 提到 11/50，但一个 basket-placement 任务的选择总数保持 5/10 的同时“新增 2 个成功、丢掉 2 个旧成功”，超过每任务 1 个损失的 cap，被回归门拒绝（§3.6、Fig. 6）。图 5 把这两个门的判定记录在同一张图里。这两个案例确实说明门能拒绝“局部机制变好但整体没变好”和“平均值变好但丢掉旧成功”的候选；但它们不能说明门相对于“不过门、直接接受”或“只比聚合分数”更好，因为没有消融。

图 5（论文 Fig. 6）：这张图把一次验证门判定拆成证据链，而不是只给一个拒绝标签。它先用 N=8 的初始/执行帧说明“系统已经抓起目标书”与“系统认为抬升失败”可以同时发生，再用开发集与选择集上的官方成功数显示同一修改对两个数据集的影响，最后记录 N=9 与 N=11 两次候选的完整结局：N=9 把走廊拒收从 8 降到 2，但完成只从 0/10 到 1/10、选择集 0/10，因未达到预先声明的增益被选择门拒绝；N=11 把选择集总成功从 7/50 提到 11/50，却在 basket 任务上新增 2 个、丢掉 2 个旧成功，超过每任务 1 个损失的上限，被回归门拒绝。读者应从这条链里理解验证门到底在比较什么：局部失败机制减少不算成功，聚合均值上升也不算成功，只有开发/选择两端都达到预声明增益且没有超过逐任务损失上限，候选才会成为下一父栈。

第三组是工具修复/生成。Table 2 的 N=10 针对“缺少 front/middle 参照关系”增加共享实例选择与关系分发，指令分发从 81/90 到 84/90，front-of-mug 在开发集从 0/10 到 8/10、选择集从 0/10 到 7/10；N=11 生成共享 run_rotary 驱动，服务 turn-on 与 turn-off，修正 pinch frame，并把旋转增量重新锚定到执行后的工具位姿，20 个测试通过，在 standalone stove 激活和 stove–pan 序列中都被调用（§3.7、Table 2）。这些是“源任务上工具确实被调用并改善”的证据，但不是目标迁移的因果证据；Appendix C.5 自己说，调用痕迹只能说明使用，要把成功增益归因到某个组件，还需要匹配的移除测试，而论文没有报告这种移除测试。

第四组是 scaling 与推理驱动。N=0N=0N=0 时目标成功为 0，N=18N=18N=18 时 one-shot 推理下 Pos 0.232、Task 0.434，说明源经验确实在目标上留下了痕迹；但曲线非单调、每点只跑一次、不同 checkpoint 的验证门设置还可能变化（§2.3），所以它不能证明“每一轮共享修复都有效”。§3.5 的推理驱动比较则说明：在 N=13N=13N=13 的冻结栈上，rule-based、one-shot、closed-loop 的 Pos 成功率是 12%/16%/16%，Task 是 24%/30%/32%，大部分增益在 one-shot 编排阶段就已经拿到，继续加反馈主要改善 Task、对 Pos 没有总体增益（§3.5、Fig. 5）。这更像“推理驱动也很重要”的混杂证据，而不是共享栈机制的干净证据。

综合起来，论文的机制证据是“案例支持 + 存在性 scaling”，不是“逐组件消融”。四层栈中的工具、技能、交接、验证器没有被逐一移除或替换；验证门没有被关闭；共享修复与任务特定补丁没有直接对照；推理驱动和迭代预算也没有被固定成同一水平。作者在 §3.4 和 §3.6 自己把这两节称为回溯案例研究（retrospective case studies），这个限定是准确的。

4.4 成本与适用范围

材料层面有一处需要更正：HTML 页面没有给出代码/项目页，但论文 PDF 首页实际列出 GitHub（https://github.com/cocacola-lab/Recursia）和项目页（https://cocacola-lab.github.io/Recursia-website/）；仓库 README 说明物理实验代码与运行脚本可用，仿真代码“将放在 recursia/sim/ 下”，当前仓库里仿真目录是预留的，原始日志、协议文档和模型检查点被排除。因此可复现性不是“完全没有代码”，而是“物理侧部分公开、仿真侧尚未公开、关键实验记录缺失”；代码/项目页的准确信息应以 PDF 与仓库为准。

成本披露不完整。论文在 §3.1 说会把源侧改进成本与目标执行成本分开报告，包括模型输入/输出 token、墙钟时间和感知调用；但在可见的正文、附录 A–D 中没有出现这些总数，也没有每个接受修改的平均 token/时间成本、候选拒绝率或工具生成数量。Appendix C.5 甚至明确说“在对应账本缺失时，不推断总成本、重复次数或工具数量”。验证门的门槛在 Appendix A.2 有一部分数字（开发净增 ≥2、选择净增 ≥1、每任务损失 ≤1、最多 4 次 timeout），但每轮预算 BBB、候选总数、被拒比例、人工审查耗时都没有报告。编码模型在物理实验明确是 GPT-6 Astra；模拟侧只说“在受控比较内固定”，可见正文没有给出模型名。推理侧的定位/身份查询用 claude-opus-5-5、effort=low、默认 3000 token 响应上限（Appendix B.4），这是一项外部模型依赖，论文没有报告其调用成本。

推理成本有一个清楚的反直觉结果。N=13N=13N=13 冻结栈上，rule-based、one-shot、closed-loop 的平均端到端时间是 Pos 5.28/6.88/7.22 分钟、Task 5.20/5.95/7.15 分钟；相对 rule-based，one-shot 用多约 96 秒（Pos）和 45 秒（Task）换来 +4/+6 个百分点；相对 one-shot，closed-loop 再用多约 21 秒（Pos）和 72 秒（Task）只换来 0/+2 个百分点（§3.5、Fig. 5）。图 6 把成功率和耗时放在同一组坐标里。这说明“反馈条件化编排”的边际收益集中在 Task 轴，Pos 轴没有总体增益；大部分成功提升已经由一次性任务程序编排拿到。论文没有报告生成阶段的 token 数、感知调用次数或失败重试的分布，因此无法判断这些时间差在更大模型/更长任务上是否成立。

图 6（论文 Fig. 5）：这张图把同一冻结栈（N=13N=13N=13）上的三种推理驱动放在一起比较，成功率的柱状图与端到端耗时并列呈现，因此可以直接看出“多花的推理时间买到了多少成功”。rule-based→one-shot→closed-loop 的成功率（Pos/Task）从 12%/24% 升到 16%/30% 再到 16%/32%，平均端到端时间（Pos/Task）从 5.28/5.20 分钟升到 6.88/5.95 分钟再到 7.22/7.15 分钟。关键不是三个驱动谁最高，而是边际收益的形状：one-shot 相对 rule-based 提升最大，closed-loop 相对 one-shot 只在 Task 上再涨 2 个百分点，却要多花约 72 秒；Pos 上 closed-loop 没有总体成功率增益，只是更慢。这里的 one-shot 指任务程序只生成一次，执行中仍可重新观察并使用闭环低级控制，并不是开环执行。这张图支持“反馈不是免费午餐”，也提醒把主结果与推理驱动设置对齐后再比较。

适用范围需要收缩。仿真侧是 LIBERO-Pro Long 的 10 个任务、每轴 50 个种子，源侧是 LIBERO-90；物理侧是 6 个源任务、3 个组合目标、每目标 10 次、人工判定。所有源侧和目标侧实验都用同一个机器人 embodiment（具身形态）和同一套执行接口，论文明确说没有做跨 embodiment 泛化，共享修复可能依赖运动学、夹爪几何、控制器约定或标定细节（§5）。源侧诊断用仿真真值，真机上重置场景可能很慢、不安全或不可能，识别“最早被违反的要求”所需证据往往不完整或昂贵（§5）。目标侧不做代码修复、不用目标反馈，这是方法的优点，但也意味着它只能验证“源侧已经修好的栈能否迁移”，不能验证“目标侧还能不能继续自改进”。

还有一个零样本边界问题。Appendix C.4 说，冻结执行本身不证明评测任务在开发时从未被观察过；记录版推理比较复用了评测行，协议还标明了历史上对 Scene5 的暴露。主 LIBERO-Pro Long 面板是否完全隔离，论文没有给出 split 清单或状态级证据。声明式适配器不含任务 ID、场景 ID、种子或仿真状态，但它必然包含目标物体、支撑面和关系描述；这些描述是否含目标特有信息、是否由评测方提供，论文没有展示适配器全文或生成过程。因此“零样本”在这里是一个很窄的操作定义，不能外推成“未见物体/未见环境/未见机器人”的泛化。

综合来看，本文能支持的范围是：在 LIBERO-Pro Long 与三个物理组合目标上，源侧对共享栈的改进可以冻结后迁移，平均成功率和若干案例显示共享接口修复比只更新自然语言技能文档更有用；同一个冻结栈配合不同推理驱动时，one-shot 编排已经能拿到大部分增益，额外闭环反馈的收益有限。它不能支持“通用长程组合泛化”“真机上的递归自改进”“跨 embodiment 共享修复”或“验证门已经被证明是迁移的原因”。

  • 严重程度：主要问题。

6. 审稿式总评

作者发现单独可用的机器人技能在组合后失败，且失败常发生在工具、技能契约、交接和验证器这些共享接口上；因此提出 Recursia，把共享可执行栈作为持久改进单位，用源侧失败归因驱动编码智能体修栈，再以通用性检查、机制测试、配对选择门和回归门筛选，最后冻结整栈、用声明式适配器做目标侧组合。实验在 LIBERO-Pro Long 的 10 个任务（每轴 500 episodes）和 Franka FR3 的 3 个物理组合目标上表明：仿真 Pos 0.284、Task 0.534，相对 ASPIRE 高 5.8/15.1 个百分点；物理平均 66.7% 对 SD-only 26.7%，其中 T3 的 2/10→10/10 贡献了约三分之二的均值提升。其中“共享栈可以把源侧修复带到新组合”的方向性证据和“验证门能拒绝局部/聚合假改进”的案例证据较强；但“共享修复优于任务特定补丁”“验证门是迁移成功的原因”“真机也能递归自改进”“零样本边界干净”仍缺少充分支持。本文最有价值的部分是把组合失败拆成四层共享接口，并给出一个可版本化、可验收、可冻结的工程闭环；最大的审稿风险是核心比较的基线/后端不一致、逐任务结果表缺失，物理样本过小，以及机制证据主要是回溯案例而非消融。

  • 问题定义清晰度：强。四类障碍、四层栈和零样本的操作定义都写得清楚，失败案例能对应到具体接口；边界（同 embodiment、共享物体/技能、目标不反馈）也有明确限定。
  • 创新性证据：中。把共享栈作为改进单位、用失败归因和验证门约束自我修改，是有辨识度的组合；但工具、技能、交接、验证器、回归测试、beam search 都是已有概念，论文没有证明“首次提出”，也没有直接对照任务特定补丁。
  • 方法可信度：中。栈的接口、契约、交接条件和验收流程交代得较具体，内部验证器不被当作外部成功标签这一点尤其重要；但源侧诊断依赖仿真真值，记录版放置验证器还是影子监视器，验证门和共享修复都没有消融。
  • 实验支持力度：中。LIBERO-Pro Long 每轴 500 episodes、10 个任务，规模不小；但基线是复用的、抓取后端不一致、逐任务表缺失，物理只有每目标 10 次且由 T3 主导，统计强度有限。
  • 可复现性：弱。PDF 首页和公开仓库提供了物理侧代码与项目页，这是加分项；但仿真代码尚未加入、原始日志/协议/检查点被排除、逐任务表和候选账本缺失，独立复现核心仿真结果很难。
  • 综合阅读价值：中。对做机器人编程、技能组合和 agent 自改进的读者，本文提供了一个清晰的“共享接口 + 验收门”设计范例，四类失败模式也适合作为系统设计检查表；但阅读时应把 +40 pp 和 +15.1 pp 当作有边界的实验信号，而不是已被独立验证的通用能力。
