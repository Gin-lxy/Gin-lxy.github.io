0. 一句话结论

论文解决的是”token 级路由（token-level routing）算法已被证明有收益、但现有 LLM 服务系统跑不动它”这一问题：SGLang、vLLM 等建立在单模型同步假设上，token 级路由会带来步级失同步（step desynchronization）与频繁的批次准入延迟（batch admission delay）。TokenRouter 的核心思路是”请求中心编程、模型中心执行”——开发者只写 route/send/receive 三个按单请求视角描述路由的函数，运行时为每个 LLM 启动一个自治子服务器（subserver），用三段解耦循环异步执行、靠 handoff-resume（交接-恢复）机制保持请求状态，并用延迟批处理（delayed batching）把稀疏到达聚成大批，其最优阈值 B∗B^*B∗ 由离散时间马尔可夫链（Discrete-Time Markov Chain, DTMC）吞吐模型解析求出。在论文报告的五种路由算法、三种负载、四组模型对上，吞吐比”更强基线”高 2.01–64.15×（Abstract、§5.2），消融与模型-实测对照支持各组件确有效用；但区间两端点高度依赖比较对象（对最强的 R2R 官方实现仅约 2.0–2.6×），结论应限定在论文覆盖的 A100 单机、并发 1–16、至多 3 个合作模型的范围内。

1. 论文具体想解决什么问题？

研究背景与具体任务。 大模型服务通常把请求分派给规模、专长不同的模型，以推进成本-质量帕累托前沿（Pareto frontier）。session 级与 query 级的粗粒度路由已在生产系统（如 ChatGPT、Cursor）与学术系统（如 RouteLLM）中广泛使用，但一旦路由完成，整段回复由单一模型生成。新近算法工作把粒度推到 token 级：R2R 只把约 5% 的 token 路由到 32B 模型即可逼近其质量，而 query 级路由需要把约 40% 的请求整单交给 32B；token 级路由还能让专长互补的模型在同一段回复内协作，并提供连续可调的成本-质量工作点（§1）。问题是：这类算法的收益依赖每个解码步都可能切换模型的执行模式，而现有服务系统并不支持。论文的任务因此落在系统层：为 token 级路由推理设计一个高效、对开发者友好的服务系统，使算法收益在真实系统上兑现，而不改动算法本身。

现有方法通常如何处理。 vLLM、SGLang 等服务系统面向单模型：同一批活跃请求在每一步解码保持同步推进，连续批处理（continuous batching）、分页 KV 缓存（paged KV cache）等机制都以”请求不离开本模型”为前提（§2）。多模型场景下，speculative decoding 虽然也协调两个模型，但草稿生成与目标验证是固定、可预测的周期性模式；token 级路由则是数据依赖的随机模型访问（§2、§4.2）。

现有方法具体在哪些条件下表现不好。 论文在 §1 给出三条：

  1. 步级失同步（step desynchronization）：不同 LLM 每步延迟差异很大，把请求保持在同一个同步批次里意味着每步都要等最慢的模型，快模型被迫空转；
  2. 批次准入延迟（batch admission delay）：token 级路由导致频繁的模型切换，一个被路由的请求到达目标模型时，对方常常正在处理上一批，请求只能等到下一批才开始执行，产生气泡并使批次碎片化；
  3. 实现复杂度：现有系统没有暴露”逐步路由决策”的编程接口，在其内部实现 token 级路由需要大规模修改代码库，还要与连续批处理、前缀缓存（prefix caching）等紧耦合特性小心协调。

支撑问题判断的证据。 前两条的直接展示是 Fig. 4 的四种调度策略对照：Step-Sync 用步屏障（平均延迟 13.33 个 SLM 批单位）、Model-Sync 一次只跑一个模型（13.00）、Eager-Async 一有请求就到就处理（10.83），TokenRouter 的延迟批处理把平均延迟降到 8.67——注意这是示意性时间线（以 SLM 批为单位），不是硬件实测。真正的实测证据在 Table 10：作者自建的、无状态保持的 SGLang 基线（Std. Serving）在 SLM 侧每个解码步中，前缀匹配 7.78 ms（20.94%）、锁缓存节点 6.49 ms（17.47%）、释放锁 5.13 ms（13.81%）、更新 RadixCache 12.12 ms（32.62%）合计约 84.8% 的时间花在与路由状态保持无关的记账上，SLM 推理本身只占 1.56 ms（4.20%）。也就是说，论文观察到的现象是”系统侧开销吞掉了路由算法的收益”，且这一归因有单点实测支撑；但失同步与准入延迟的因果演示仍以示意图为主（审稿人判断）。

作者认为问题产生的原因。 根因是”单模型同步假设”：请求进入批次后被假定不会离开，返回的 token 被当作全新请求处理，于是每次切换都要重做前缀匹配与 KV 缓存分配。TokenRouter 的对策是把”路由算法描述”与”系统执行优化”彻底解耦：算法只在单请求视角描述流动，系统以状态保持的异步跨模型调度执行。

论文最终要验证的核心假设。 若把每个合作 LLM 当作自治子服务器独立推进、请求以消息在子服务器间异步迁移（迁移只需追加 token，不重建服务状态）、并用延迟批处理把稀疏到达聚成大而满的同模型批次，则：（a）token 级路由的算法收益能在真实系统上兑现为吞吐与延迟优势；（b）该优势随输出长度与并发扩大而保持；（c）系统可作为标准单模型服务器的替代品（drop-in replacement），不要求算法作者理解底层调度。

三类问题的区分：

  • 领域早已存在的一般问题：LLM 服务中的批调度与 KV 内存管理、多模型协同的选择策略；
  • 本文发现的新观察：token 级路由在单模型同步假设下产生的两类系统级病态（失同步、准入延迟），以及”把返回 token 当新请求”造成的可量化开销（Table 10 的逐项分解）；
  • 本文实际解决的具体子问题：在 8×A100-80G 单机（另有跨节点变体）上，为 5 种已有 token 级路由算法提供统一运行时，在并发 1–16 的负载下把吞吐与端到端延迟做到显著优于官方实现与自建 SGLang 基线，同时保持算法本身的输出行为。

2. 创新点是什么？

总括。 TokenRouter 不是新路由算法，而是服务系统设计，技术增量可分为四块：(i) route-send-receive 请求中心编程接口与”请求中心编程、模型中心执行”原则；(ii) 三段解耦循环的异步执行 + handoff-resume 状态保持机制；(iii) 延迟批处理调度 + 基于 DTMC 稳态吞吐模型推导最优阈值 B∗B^*B∗；(iv) 一组 token 路由特有的工程适配（共享 GPU 的 KV 联合分配、extend 模式 CUDA graph、进程内路由、全局状态跟踪）。其中 (ii)(iii) 是系统论文的主体机制；(i) 是抽象层设计；(iv) 提供单项最大增益（Fig. 1a）。按规范判据，本文没有”更大基础模型”或”更换数据集”式伪创新，但多数组件属于已有执行模式的显式化与工程改造，真正有研究成分的是 (iii) 的建模。

创新点 1：route-send-receive 接口与请求中心编程原则。

  • 新增内容：三个函数。route(result) 在每个解码步后基于前向结果（hidden states、下一 token logits、采样 token）为批内每个请求输出目标索引，0 表示本地继续，非零指向对应 peer 模型；send(req) 在被委派时构造 PeerReq，携带请求 ID、peer 尚未见过的 token 后缀、是否结束的状态字段，以及位置锚点 req.loc（供接收方决定最小的回传后缀，刚采样的 token 是否算入由算法决定）；receive(peer_req) 把 PeerReq 转成本地请求格式，默认提交全部转移 token，只有交接语义特殊的算法需要覆写（§3.2）。开发者只追踪”单个请求如何在协作 LLM 间流动”，即生命周期 receive → decode → route → send → peer receive → peer decode → …（§3.1）。
  • 与最接近做法的差异：现有服务系统没有 per-step 路由接口；speculative decoding 的接口是固定草稿-验证模式。论文指出各种 token 级路由算法其实共享同一执行生命周期（§2 末段），本接口即对该生命周期的显式抽象。
  • 类型：抽象与 API 设计（已有执行模式的显式化），不是新的路由思想。
  • 证据：5 种路由信号互不相同的算法（CITER 置信度、R2R 预测分歧、R-Stitch 熵、Co-LLM 延迟得分、ME 集成权重，Table 1）都在同一运行时上以 scheduler 子类实现（Appendix C）；Fig. 3 的 R-Stitch 小模型侧示例展示了”高熵 token 交给大模型、send 丢弃不确定 token 让对端重生成、receive 默认全接受”如何映射到三个函数。
  • 移除后变化：接口无法消融；替代证据是算法覆盖广度。论文未声称该接口为首次提出（§2 把生命周期归为已有算法的共同模式）。

创新点 2：三段解耦循环异步执行 + handoff-resume。

  • 新增机制：标准单模型服务器有两个异步循环——client-server 循环（请求进入与响应流式返回，Fig. 2b 紫色）与 decoding 循环（调度与模型执行，蓝色）；TokenRouter 增加第三个 inter-model 循环（黑色）在子服务器间收发 peer 请求。被路由的请求离开本地批、在对端处理期间本地其余请求按自己的节奏继续执行；对端返回后调度器把请求恢复回本地批（§4.2）。恢复时引入 pending 状态（介于 running 与 finished 之间的中间态）：调度器跳过 pending 请求但保留其服务状态；恢复时按对端输出把 pending 切回 running 或 finished，未结束时直接追加新 token 回批，跳过前缀匹配与 KV 重分配，交接开销近似于一次 token 追加。
  • 与最接近做法的差异：naive 做法把返回请求当全新请求，重做前缀匹配与 KV 分配——作者自建的 Std. Serving 基线正是如此，其开销被 Table 10 量化。
  • 类型：工程机制设计（在已有系统结构上增加循环与状态机），不是新研究思想。
  • 证据：Table 6 消融在 N=4 时，加入异步执行带来 1.12×（143.88→161.26 token/s），加入延迟批处理再带来 1.31×（161.26→210.61）；Table 10 的延迟分解支撑”免去重复前缀匹配/记账”的机制解释。
  • 移除后变化：即 Table 6 的 “- Async execution” 行，N=8 时从 296.86 掉到 230.79 token/s。

创新点 4：token 路由特有的工程适配（四项）。

  • 新增内容（Appendix B）：(a) KV 缓存内存自动分配——多模型共置同一 GPU 时把各模型的 KV 预留当作联合分配问题，按权重占用与每 token KV 单元大小计算共享预算下的最大公共容量，避免人工调参导致的 OOM 或闲置；(b) extend 模式 CUDA graph——单模型系统只给 decode 批抓图，而 token 路由下 peer 返回全部是 extend 批，因此对一定范围的 extend 批大小与 token 长度抓图、超范围回退；(c) 进程内路由（in-process router）——route 每步每请求都调用（比 query 级路由高频几个数量级），跨进程会引入每 token 一次 IPC 往返，故与 scheduler 同进程；(d) 全局状态跟踪——延迟批处理阈值依赖系统级活跃请求数，各子服务器通过 peer 消息通道捎带控制消息共享计数，避免中心协调者。
  • 证据：Fig. 1a 的增益分解显示，仅 extend CUDA graph 一项就把 base 实现（132.78 token/s，≈R2R 官方 134.9）提到 230.79 token/s（1.71×），是最大的单项工程增益；Table 6 给出全部逐项消融。
  • 类型：工程实现改进。

原创边界说明。 根据本文 related work 与实验对比，只能确认作者声称的差异（接口抽象、tri-loop 异步执行、延迟批处理+DTMC 建模、四项工程适配）；是否构成各自方向上的首次提出，还需要更完整的文献检索。论文本身未使用”首次提出”表述，其定位是”把算法层面的理论收益转化为对成熟单模型服务系统的实际加速”（§1 末段）。

3. 作者如何解决？

直觉。 TokenRouter 把一件事拆成两半：”路由算法是什么”由开发者用三个函数描述，”如何高效地把它跑起来”由运行时接管。运行时把每个参与协作的 LLM 变成一个自治子服务器：请求像邮件一样在子服务器之间投递，每个子服务器只管一件事——尽快把自己模型上的批次跑满、跑满后把请求按路由规则寄出去。这样，算法作者不需要理解批调度与异步执行，系统则获得了对跨模型执行与批调度的完全控制权（§1）。

运行流程（按实际执行顺序）。

  1. 输入：客户端通过一个与标准单模型服务器（vLLM/SGLang）完全一致的外部接口发送请求（OpenAI 风格协议），Server Interface 将其转发给指定的入口子服务器（entry subserver）（§4.1）。
  2. 子服务器内部：每个子服务器持有调度器（scheduler）、带私有 KV 缓存池的 LLM runner，以及用户定义的三函数构成的 router/sender/receiver（§4.1，Fig. 2b 右侧方框）。三者的布局完全一致，增加 LLM 只需再起一个子服务器。
  3. 单个请求的流转：receive 进入本地解码 → 每个解码步后 route 决定去向（0 本地继续 / 非零指向 peer）→ 若委派，send 打包 PeerReq（对端未见过的 token 后缀 + 位置锚点 + 状态）→ 经 peer 消息通道（本地 ZeroMQ IPC，Appendix C）到达对端 → 对端 receive 转成本地请求继续解码，如此往复直到 finished。
  4. 哪些由用户定、哪些由运行时定：路由语义（何时切、切给谁、传什么后缀、如何接受回传）完全由用户的 route/send/receive 决定；批调度、异步执行、KV 内存分配、CUDA graph 捕获等全部由运行时按固定策略控制——这正是”请求中心编程、模型中心执行”的分工（§3.1）。
  5. 训练：系统本身无需训练。评测中的部分路由算法带有各自的训练成分（CITER 需训练 router、Co-LLM 需微调 Qwen3-0.6B、阈值/权重如 CITER τ=0.98\tau{=}0.98τ=0.98、R-Stitch τ=0.03\tau{=}0.03τ=0.03、Co-LLM η=0.15\eta{=}0.15η=0.15、ME 权重 0.5/0.3/0.2，§5.1）——这些属于直接使用的现有算法，不是本文贡献。
  6. 推理阶段的关键变化：(a) 三段循环解耦——请求在对端处理时本地照常推进，实现”各子服务器按自己的节奏走”；(b) handoff-resume——离开的请求标记 pending，返回时直接追加 token 回批，跳过一次前缀匹配与 KV 重分配；(c) 延迟批处理——每批攒到 BiB_iBi​ 个请求才启动，BiB_iBi​ 取模型推出的吞吐最优值 B∗B^*B∗（详见创新点 2/3 与 Appendix D）。
  7. 输出：与单模型服务器相同的 token 流；对客户端而言，背后有几个 LLM 参与路由是透明的（§4.1）。

4. 解决得怎么样？

4.1 实验设置

路由算法与模型对。 评测五种 token 级路由算法：CITER、R2R、R-Stitch、Co-LLM、ME（Table 1）。前四种在 Qwen3-0.6B 与 Qwen3-32B 之间路由，ME 在 Qwen3-0.6B、Qwen3-8B、Qwen3-32B 之间路由（§5.1）。另外每种算法还用各自原始论文的模型对与数据集复测（Table 4）：R2R 用 DeepSeek-R1-Distill-Qwen-1.5B/32B + AIME、CITER 用 Qwen2-1.5B/72B + CommonsenseQA、Co-LLM 用 LLaMA2-7B(tuned)/70B + GSM8K、R-Stitch 用 L1-1.5B-Short/QwQ-32B + AIME。

硬件与部署。 全部实验在一台 8×A100-80G 上运行。两模型算法：小模型占 1 GPU，大模型占 2 GPU（张量并行 tensor parallelism，TP=2），两个模型通过 CUDA MPS 共享 2 块 GPU（”重叠部署”）；ME 每个模型占 1 GPU（§5.1）。附录另测非重叠部署（小/大模型占不同 GPU，Appendix A.3.1）与跨节点部署（两节点经 RoCE 3.7 GB/s 互联，Appendix A.3.2）。

基线。 两个：(1) Official Code——算法官方开源实现（R-Stitch 未开源，记为 N/A；Co-LLM 官方用 per-model vLLM 服务器带连续批处理，CITER 与 R2R 官方是无连续批处理的推理引擎）；(2) Std. Serving——作者自建的标准 SGLang 基线：每个 LLM 一个 SGLang server、每次只返回一个 token、由外部 dispatcher 在服务器之间转发，代表”成熟单模型系统 + 外部路由胶水”的朴素做法（§5.1）。Table 2/5 中还列出 LLM-only 参照行（只部署大模型、不路由）。

负载。 三种：(1) Low-effort reasoning（短输入短输出）：AIME2024 提示（约 100 token），最大输出 2048；(2) High-effort reasoning（短输入长输出）：AIME2024，最大输出 8192，只保留 Qwen3-32B 解答超过 8192 token 的题；(3) Agentic（多轮）：SWE-Smith 轨迹，输入约 8192 token，最大输出 1024（§5.1）。

指标与协议。 吞吐 = 生成输出 token 总数 / 总耗时；同时报端到端请求完成延迟与 TTFT（首 token 时间，time-to-first-token）。注意协议差异：对推理引擎（Official Code）是打包一批 NNN 个请求一起处理；对服务系统（Std. Serving、TokenRouter）是启动 NNN 个 worker、每个 worker 完成上一个请求立刻发下一个（闭环）。主要并发点为 4（Fig. 5/6）与 8（Fig. 1a）；附录补并发 1（Fig. 8/9、Table 5）。

各实验分工。 主实验（§5.2）回答”比现有系统快多少”；§5.3 与 Appendix A.2 的消融回答”增益来自哪个组件”；Appendix A.3 回答”部署方式（重叠/非重叠、单节点/跨节点）影响多大”；Appendix A.4 回答”与自建基线的差距从何而来”（延迟分解）；§5.4 回答”对成本-质量帕累托前沿的推进”；Appendix D.4 回答”DTMC 模型能否预测最优阈值”。

4.3 机制证据

结论先行。 本文的证据链分成两层：效果层（Fig. 5/6、Table 2/3——“更快”）与机制层（Table 6/Fig. 1a 的组件消融、Table 10 的延迟分解、Fig. 10 的模型验证——“为什么快”）。机制层证据在同类系统论文中属于比较扎实的一档，但仍有明确边界（等价性未验证，见质疑三；模型验证范围窄，见质疑二）。

组件消融（Table 6、Fig. 1a）。 每个组件移除后吞吐按预期方向下降：N=8 时完整系统 372.48 → 去延迟批处理 296.86 → 去异步执行 230.79 → 去扩展 CUDA graph 约 132.78，且 base 132.78 与官方 R2R 134.89 基本持平——这个”base≈官方”的控制很有价值，它使 2.76× 的整体增益可以归因到四个具体改动，而不是”换了起点”。局限：消融是逐层累加式的，组件间交互（例如 CUDA graph 与异步执行的叠加效应）未被单独分析；N=1 时异步与延迟批处理增益为零（73.02 不变），这与机制解释一致（无批可攒、无跨模型并发），但也说明两项机制的收益完全依赖并发负载。

延迟分解（Table 10，Appendix A.4）。 对自建 Std. Serving 基线剖析 2048-token 生成最后 128 步的 SLM 侧单步耗时：前缀匹配 7.78 ms、锁缓存节点 6.49 ms、SLM 推理 1.56 ms、释放锁 5.13 ms、更新 RadixCache 12.12 ms、其他 4.08 ms。与”没有状态保持 → 每次返回被当作新请求 → 重做前缀匹配与 KV 记账”的解释吻合，是”handoff-resume 为什么必要”的直接证据。局限：只剖析了一个算法场景（R2R）与自建基线，未对官方实现做同样分解。

4.4 成本与适用范围

成本侧（论文报告）。 系统本身无训练成本；推理阶段：吞吐增益 2.01–64.15×、端到端延迟降低 2.03–63.64×，TTFT 与官方实现持平或略好（Table 2/5）；单用户速度在并发 16 时仍保有并发 1 时的 51.7%（官方 R2R 为 31.3%，Fig. 1b）。额外开销与复杂度：多子服务器进程 + ZeroMQ IPC 通道 + 共享 GPU 的 KV 联合分配 + extend 范围 CUDA graph 捕获（Appendix B/C）；跨节点部署吞吐比同资源单节点略降（Table 9，N=4 时 CITER 308.36→277.56，约 −10%）；非重叠部署反而平均 +6.43%（Appendix A.3.1）。

论文未报告的成本项。 DTMC 求解 B∗B^*B∗ 的耗时与内存（仅说明用 BFS 枚举可达状态，Appendix D.2.1，未给复杂度）；主实验各场景实际采用的 B∗B^*B∗ 数值；GPU 时耗/能耗对比；失败率。

适用范围。 结论适用于：(a) 遵循”选下一个模型 → 转移请求状态 → 接收 token/分布”生命周期的 token 级路由算法（论文的抽象本身以该生命周期为界，§2）；(b) 至多 3 个合作模型（ME 是验证到的上限）；(c) 单机 8×A100-80G，并发 1–16（跨节点变体亦验证）；(d) 模型规模覆盖 0.6B–32B（标准设置）与 1.5B–72B（各算法原始设置）。仍未解决/未验证：违反几何分布假设的路由模式（§6 自认的开放问题）；>3 模型与更高并发下的调度与模型有效性；服务输出与官方实现的逐 token 等价性；生产环境（多租户、真实到达过程、尾部延迟）表现。

  • 原文依据：§4.2 的异步三段循环与 §4.3 的延迟批处理都改变请求在何时、与谁一起被解码；论文只论证吞吐/延迟，没有给出任何”TokenRouter 与官方实现产生相同 token 序列/路由决策序列”的对照实验；§5.4 的 Fig. 7 仅以准确率-吞吐曲线形式呈现质量。
  • 为什么重要：服务系统的基本契约是”承载算法而不改变其行为”。批组成与执行时序变化会改变浮点归约顺序与 kernel 选择，在非贪心解码下可能改变采样结果，进而改变后续路由轨迹——哪怕概率极小，也需要证据而不是默认。若输出不一致，§5.4”推进帕累托前沿”的准确率数字与官方 R2R 的对比就失去同基准前提。

  • 如何验证或补强：固定请求与随机种子，逐一对比各系统输出的 token 序列与每步路由决策；给出不同 BBB 与不同并发下准确率的差异（把调度不变量当作实验假设检验）。

  • 原文依据：全部实验在单台 8×A100-80G 上（跨节点仅附录小规模，Appendix A.3.2）；并发上限 16（Fig. 1b）；合作模型数上限 3（ME）；帕累托结论仅基于 AMC23 单数据集（§5.4）；所有结果为单次运行点值，无方差、置信区间或显著性检验（Table 2/3/5–10 均无）。
  • 为什么重要：摘要的”drop-in replacement for standard single-LLM servers”是关于部署与兼容性的强主张，但：没有真实生产轨迹、没有多租户/多副本、没有 H100 等其他硬件、没有并发 32+ 的数据（延迟批处理在极高并发下收益可能反转，因为准入延迟的绝对值会上升）；缺少方差也意味着无法判断小差距（如 1.99×、2.01× 这类端点）是否稳定。

6. 审稿式总评

作者发现 token 级路由算法的收益在现有单模型同步服务系统上被两类系统级病态（步级失同步、批次准入延迟）与”无状态切换”的记账开销吞掉，因此提出 TokenRouter：用 route-send-receive 接口把算法描述与执行优化解耦，用三段循环异步执行 + handoff-resume 保持请求状态，用延迟批处理聚批并以 DTMC 模型推出最优阈值。实验在 5 种算法、3 种负载、4 组模型对（0.6B–72B）与各算法原始设置下表明，吞吐最高提升 64.15×、且 base≈官方的控制显示增益来自四个可分解的具体改动；其中组件消融（Table 6）、延迟分解（Table 10）与阈值模型验证（Fig. 10）证据较强，但头条数字的口径选择性、DTMC 假设的窄验证与主实验 B∗B^*B∗ 未披露、服务输出等价性未验证仍缺少充分支持。本文最有价值的部分是”请求中心编程、模型中心执行”这一接口抽象与 Tri-loop + handoff-resume + delayed-batching 的完整工程闭环，把一个新兴算法方向的系统支撑补齐了一大块；最大的审稿风险是把”对未优化研究代码的加速”与”对成熟系统的加速”混在一个区间里呈现，以及对模型外推范围的低调处理。

  • 问题定义清晰度：强——三类挑战（失同步、准入延迟、实现复杂度）在 §1 界定明确，且每类都有对应的失败场景描述（Fig. 4）与部分实测（Table 10）。
  • 创新性证据：中——接口抽象与异步机制多为已有执行模式的显式化/工程组合，论文自己以”complementary”而非”首次”定位；DTMC 建模是实打实的增量但已有应用范式；组件消融充分，然”接口不可替代性”类证据天然缺失。
  • 方法可信度：强——机制与证据链自洽（base≈官方的控制、逐项消融、延迟分解、模型-实测最优阈值一致），假设均显式声明并标注边界（§6 限制、Appendix D.1 假设）；输出等价性未验证属于其外沿边界（质疑三）。
  • 实验支持力度：中——覆盖面广（算法×负载×模型对×原始设置×部署变体），方向性结论一致；但全部为单机、单次运行点值，无方差/置信区间，区间端点又依赖比较对象选择（质疑一、四），因此不宜按”无保留的强”理解。
  • 可复现性：强——官方代码已发布（GitHub thu-nics/TokenRouter，仓库标注 NeurIPS’26 官方实现，本次已核验可访问），系统构建于 SGLang 0.5.1，实现细节（ZeroMQ IPC、内存联合分配、CUDA graph 范围）与全部模型公式在 Appendix B–D 给出；扣分项是主实验 B∗B^*B∗ 未披露与对 A100/CUDA graph 的硬件依赖，精确复现仍需与作者对齐配置。
  • 综合阅读价值：高——对一个正在升温的方向（token 级路由/多模型协同解码）给出了第一个较完整的服务系统设计与系统-算法联合测量，抽象（route-send-receive）可复用，测量方法（base≈官方的消融设计、DTMC 验证）也可借鉴；对做推理服务、模型路由与多模型协同的读者都值得精读，但引用其加速倍数时应按基线分层折算。
