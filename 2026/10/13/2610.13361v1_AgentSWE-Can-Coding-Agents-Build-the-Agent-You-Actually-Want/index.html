0. 一句话结论

论文把”让编码智能体（coding agent）替用户构建智能体”形式化为一个可测量的委托（commission）问题，并发布 AgentSWE 基准：25 个任务覆盖创建（Creation）、编辑（Editing）、优化（Optimization）三个阶段，开发用例 150 个、留出用例 365 个。评测显示五个主流 builder 在留出用例上全部远达不到需求——创建阶段最高均值 19.1/100、编辑阶段 31.6/100、优化阶段无人平均缩小目标差距超过 5%；证据足以支持”演示—交付差距是常态”这一结论，但该结论限定在论文自建的委托式协议与模型裁判之下，跨方案排名的可靠性受单次构建方差限制。

1. 论文具体想解决什么问题

背景与任务：编码智能体（coding agent，如 Claude Code、Codex）如今接手大量工程工作量，而它们的用户大多不是工程师——用户只描述需求，把”构建一个智能体”这件事也委托出去。交付的智能体应把模型、工具与状态围绕一个反复出现的工作包成固定运行时，此后每次运行不需要编码智能体在场（§1）。这种委托隐含一个未经检验的信任假设：交付的智能体忠实服务它被构建所依据的需求（requirement），而不只是”看起来符合”。

现有做法及瓶颈：SWE-bench 及其后继按参考补丁或测试套件评判普通软件修复；NL2Repo-Bench 从需求文档生成整个仓库；Paper2Code/PaperBench 按原论文检验科研实现复现——它们都在对照一个事先已知的答案评判普通代码（§1、§2）。而评测智能体的基准（自 AgentBench 起）拿到的是别人已经造好的智能体，衡量其任务表现，不问”编码智能体能否把它造出来”。最接近的 AIE-Bench 测的是 meta-agent 在受控变异边界与试次预算下改进固定 scaffold 的能力，衡量搜索程序能把 benchmark 分数抬高多少，而不是通用编码智能体能否交付需求所描述的智能体（§2）。

被忽略的问题：在”判写出的补丁”与”判成品智能体”之间缺了一步——判”被构建出的智能体在需求上的忠实行为”。作者主张这一步有本质困难：委托没有参考实现，交付物是包裹工具与状态的随机策略，且交付后仍在变化（§1、§3）。他们援引既有文献列举这类委托特有的细微失败：通过可见样例却错过样例背后的意图、工具注册了却从不调用、长程目标漂移、报告引用不存在的证据（§1；此段为作者对既有文献现象的综述，非本文新发现）。

归因与核心假设：作者把问题归因于结构性信息不对称——需求只能通过少量开发用例被探测，而验收发生在需求隐含但未写出的用例空间上（§3.2）。论文要验证的核心假设是：把交付物在”需求隐含的用例空间”上的行为（经有效性门控后）作为目标函数，可以让忠实度（fidelity）变成可测量问题；且当前编码智能体在这套测量下普遍不能交付需求。

区分三层：领域一般问题 = 智能体与代码生成的可靠性评测；本文新观察 = 委托式信息不对称下”演示—交付差距（demonstrated-versus-delivered gap）”的普遍性与三类失败模式（过拟合可见用例、空壳运行时、无依据的完成声明，§5.3）；实际解决的子问题 = 提供一个可复现的测量基准与首批测量结果。论文对上述两条既有评测路线与自身设计之间的关系、以及首批测量结果的总结，见图 1。

图 1（论文 Fig. 1）：这幅总览图把动机、方案与结果压缩成一次对照。左部指出现有基准的两条路线——判”编码智能体写出的补丁是否正确”，或判”某个已建成智能体的任务表现”——都不回答交付物是否忠实再现在需求上；中部给出 AgentSWE 的替代设计：自然语言委托交给 builder（§3 详述的编码智能体），builder 产出的交付智能体再在留出用例上按忠实行为计分，创建、编辑、优化三个开发阶段共享这一测量结构；右部条形图给出首批结果，五个 builder 的留出均值都很低，且不同阶段的分数不能直接互相比较。读者应理解的核心是：评测对象从”代码或成品”整体移到了”委托—交付—验收”闭环。

需要说明的是，论文的贡献止于测量与诊断：它没有提出、也没有验证任何提升 builder 忠实度的方法，改进方向仅以未来工作形式出现在结论（§6）。

2. 创新点是什么

总的增量：AgentSWE 把”智能体软件工程（agent software engineering）”从轶事变成测量——用忠实度目标函数形式化委托问题（Definition 3.1），用 25 个任务与”委托式”协议（少量开发用例 + 冻结交付 + 留出验收）覆盖完整开发生命周期，再配一套行为审计把失败轨迹归类为可改进的方向。它不是训练方法，也不含改进 builder 的算法；相对最接近的 AIE-Bench，其差异主要在覆盖范围（三阶段全生命周期）与评分对象（留出行为而非 benchmark 搜索分）。

1）委托问题与忠实度的形式化。新增：把需求 q 写成”目标 g、接口契约 I、约束 C、资源 R”四元组，把交付物定义为一个 agent 的忠实度目标——有效性门控 V 乘上”对留出用例空间的期望评注分”（Eq. 1，§3.2）。与 SWE-bench 类”对照参考解”、AgentBench 类”评成品性能”都不同，这一目标定义明确包含”builder 看不到的用例”。证据指向 §4.2 的差距数据；消融性质的设计分析见 §4.3。

2）委托式三阶段评测协议。新增：builder 只见需求文档、初始工件（创建为空、编辑为钉扎的产品代码库、优化为可运行 starter）与少量公开开发用例；验收在冻结后于隔离运行时执行留出用例，所有模型调用经评测方网关固定同一 runtime model，让分数归因给 builder 的提示、工具编排、上下文与输出校验；创建/编辑按需求派生评分量表（rubric）加硬门控（hard gate）计分，优化沿用源基准原生评分器计算差距闭合 γ（Eq. 3）。与已有”评测生成物结构/复现实现”相比，它是”已有评测组件（留出集、量表、裁判）面向新对象（可运行智能体交付物）的新组合”。证据指向 §4.2。

3）失败轨迹的行为审计与分析。新增：基于 builder 轨迹、冻结工件与交付物执行轨迹三类证据，归纳出过拟合可见用例、空壳运行时（hollow runtime）、无依据完成声明三类模式，并附开发用例数量、提示先验、预算、harness 四组条件研究。这一贡献的定位是诊断而非方法；其实证强度见 §4.3（案例具体但标注流程含 AI 辅助）。

3. 作者如何解决

直觉：不要再用”有没有写出正确补丁”来代理”有没有交付用户要的智能体”。AgentSWE 把一次委托当成一次真的雇佣——客户只给需求与少量样例，验收时拿着被冻结的交付物去跑”客户没说但需求覆盖”的用例。为让分数可归因，评测方固定 runtime model（交付 agent 运行时用的模型）与评分器，只让 builder 有权决定提示词、工具编排、状态管理与输出校验。

按运行流程走一遍（完整数据流见图 3）：

输入。每个任务向 builder 发布四份 Markdown 需求文档（goal / interface_and_delivery / requirements_and_constraints / resources，附录 B 给出三个完整示例），初始工件 a₀（创建为空工作区；编辑为钉扎的生产代码库快照，如 OpenHands、Aider；优化为可运行 starter agent）以及少量开发用例 D（创建与编辑各 2 个；优化从源基准实例池抽 10–50 个）。任务的构造来源与”给 builder / 保留给评测方”的切分结构见图 2。

图 2（论文 Fig. 2）：上半部分展示 25 个任务如何从既有系统构造——创建任务把开源领域智能体反编译为需求并加入提高组合难度的功能，编辑任务在生产智能体代码库上追加”用户价值大、实现面有界、可被执行验证”的特性提案，优化任务沿用公开基准的原生目标与评分器；下半部分是基准的信息不对称设计：builder 侧只拿到需求四件套、初始工件与公开开发用例，评分契约（评分量表或原生评分器）与留出用例全部由评测方保留。两半合起来回答的是”任务从哪来”与”什么给 builder、什么不给”这两个设计问题；读者应理解到，基准的全部区分能力都建立在”给定的 vs 保留的”这条切分线上。

开发循环。Harbor（Harbor Framework Team, 2026，一个容器化 agent 评测框架）在一个持久会话中运行 builder：builder 在私有可写工作区探索、编辑、运行自己的代码，随时提交候选快照；每个快照在隔离任务中跑开发用例，分数与摘要反馈回到同一会话。这一循环是 training-free 的——没有任何参数更新，模型行为完全由 harness 与提示驱动。预算固定：创建最多 10 次提交、8 小时；编辑 5 次”被接受”的提交、5 小时；优化 5 轮、16 小时；开发用例每例 600 秒（附录 E 表 9）。哪些行为由模型决定：方案设计、实现、修 bug、提交时机全部由 builder 决定；哪些固定：需求文本、开发用例、反馈内容、预算、评测方模型路由全部由基准固定。

冻结（Fig. 3 左半下部）。开发结束后按家族规则冻结交付物：创建冻结最终工作区；编辑冻结最后一次被验收的提交——从未提交成功工件者等于什么都没交付；优化冻结开发目标最高的被接受快照。冻结同时记录交付物与其软件环境，留出评测前校验二者未被更改。

留出执行（Fig. 3 右半）。每个留出用例在隔离、钉扎的运行时中经固定入口执行冻结交付物；交付 agent 发出的每个模型调用都经基准自有网关路由到同一 runtime model（创建为 gpt-5.6-sol/medium，编辑为 deepseek-v4.1-flash/high，优化为契约固定的 gpt-5.6-sol，附录 E 表 9），因此分数反映 builder 贡献的部分，而非”谁蹭了更强的运行时模型”。

评分。创建与编辑先过确定性门控：不启动、超时、无有效产物的执行直接记 0；其余由前沿推理模型按任务评分量表打分（创建用 GPT-5.6 Sol，编辑用 DeepSeek-V4.1-Flash，均为最高推理档），裁判看的是 agent 在具体用例上产出的工件、执行轨迹与结果状态，而非代码文本质量；违规触发评分上限（ceiling），任务分为 6 个留出用例的部分分均值，家族分为任务宏平均。优化的评测信号独立于量表裁判：原生评分器在同一留出实例上分别评 starter 与选中候选，报差距闭合 γ，γ 为负表示候选比 starter 差。从开发反馈到留出评分的完整数据流见图 3。

图 3（论文 Fig. 3）：左半部分刻画第一阶段”开发与冻结”——builder 在单一持久会话中循环：接委托（q、a₀、D），提交候选快照，快照在公开用例上执行后分数与反馈回到同一会话；开发终止时按家族规则冻结（创建冻工作区、编辑冻最后被接受的提交、优化冻开发分最高的被接受候选）。右半部分是第二阶段”留出评测”——冻结交付在隔离的固定运行时中跑留出用例，模型调用统一经基准网关；创建与编辑沿”门控 → 评分量表 → Result”走，优化沿”原生评分器 → 差距闭合 γ”走。串联理解的关键是数据流：反馈只在公开面循环，留出面与 builder 完全隔离。

任务材料由谁生产：四份需求文档、开发/留出用例与任务评分量表由 GPT-5.6 Sol 从源系统起草，作者逐任务设计、审改并定稿（§4.1、AI Use Statement）——这是报告中反复出现的一个利益相关点，§5 会回到它。

公式与一个教学简化示例（非论文实验）：忠实度目标写作 F(â; q) = V(â) · E_{x∼X_q} E_{y∼â(x,E)} [ μ_q(x, y) ]，其中 μ_q(x, y) ∈ [0,1] 是需求 q 在用例 x 上被满足的评注分，V ∈ {0,1} 是接口契约与约束的门控（Eq. 1）；优化阶段记 J 为 0–100 的目标分、J* = 100 为满分，差距闭合 γ(â) = min{1, (J(â) − J(a₀)) / (J* − J(a₀))}（Eq. 3）。教学简化示例：若 starter 得 40 分、候选得 52 分，则 γ = 12/60 = 20%，即候选缩小了剩余差距的五分之一；负数则表示候选不如 starter。编辑阶段另有”新能力 ∧ 回归保持”的双重满足定义（Eq. 2，以 μ_new ∧ μ_reg 表示），回归项由产品公开测试套件与已发布契约检查。

最终输出：一个被冻结的交付 agent 及其在留出用例上的 Result 分（创建/编辑）或差距闭合 S = 100γ（优化），以及三份实证分析（失败模式、条件研究、重复构建）。

4. 解决得怎么样

4.1 实验设置

任务与数据：25 个任务（创建 10、编辑 10、优化 5），合计 150 个开发用例与 365 个留出用例（Table 6 逐任务列出源系统与用例数）。创建任务源自 10 个开源领域 agent（GUI 自动化 UI-TARS-desktop、科学 PDF 翻译 PDFMathTranslate、形式化定理证明 LeanCopilot、仓库 bug 修复 SWE-agent 等）；编辑任务在 Claude Code、Aider、OpenHands、OpenClaw、Codex CLI、AI-Scientist-v2、DeepCode、DeepTutor、Dyad、OpenWiki 的钉扎快照上追加特性，并保留回归义务；优化任务沿用 BrowseComp、τ³、TerminalBench、PinchBench、OSWorld 的原生任务定义与评分器。

builder 与基线：主对比为 Codex 0.144.1 harness 配五个模型（GPT-5.6 Sol、GPT-5.5、DeepSeek-V4-Pro、DeepSeek-V4-Flash、Qwen3.6-35B-A3B），共 125 次运行，每个 builder×任务只构建一次（§5.1）。创建/编辑没有”参考实现”式基线，比较对象是不同 builder 之间；优化以 starter 为基线（同一留出实例上同评）。补充研究：9 个 harness–模型组合（DSH、Claude Code、OpenCode、Pi、GLM-5.3 等，Table 4）；开发用例数量 0/1/2/4（Table 2）；两种提示先验（Table 3）；2.5 倍用例预算 + 轨迹要求（Table 10）；AgentSWE-Lite 八任务 × 三 builder × 三次重复构建（Table 5、Fig. 8）。

指标与公平性：创建/编辑用留出 Result（0–100，评分量表部分分均值，家族宏平均）；优化用 S = 100γ。同家族内所有 builder 面对同一需求、同一 runtime model 与同一裁判，预算按家族固定（Table 9），跨家族分数因 runtime 模型与裁判不同而不可比（附录 J，作者明示）。各部分回答的问题：主实验 = 当前 builder 能否交付；Table 2/3 与 Table 10 = 分数对开发样例数、构建建议、预算的敏感性；行为审计（附录 H）= 失败”为什么”发生；AgentSWE-Lite 与附录 F = 重复性。

4.2 关键结果

创建普遍失败且成功不迁移：50 次创建运行平均 Result 11.2、中位数 3.4，其中 20 次为 0（§5.2、Table 1；50 次=5 builder×10 任务为”原文事实”）。最强 builder 是 DeepSeek-V4-Pro，均值 19.1/100，但 10 个任务中 8 个低于 20；仅 3 次运行超过 50，全部来自形式化定理证明或仓库 bug 修复；没有 builder 能在超过一个任务上超过 30（§5.2）。

编辑只做出部分能力，或干脆不交付：DeepSeek-V4-Pro、GPT-5.5、GPT-5.6 Sol 几乎每个任务都有交付，均值仍在 20–35 之间，全部运行中只有 GPT-5.5 的 Codex execution residual 一次达到 70.0；Qwen3.6 在全部十个任务上不提交任何候选（通常在宣布计划后即结束会话），DeepSeek-V4-Flash 只在 4 个任务上交付（§5.2、Table 1）。

优化无人取得一致改善：五个 builder 的平均差距闭合最高 4.7（GPT-5.6 Sol），远低于”每轮实打实推进”的水平；25 次运行中 13 次高于 starter、9 次低于、3 次持平（§5.2、Table 1、Table 11 为原文事实）。按运行做二项符号检验（未校正多重比较）只有 5 次显著：三个 BrowseComp 增益（最大 +34.1，DeepSeek-V4-Flash）与 τ³、PinchBench 各一次损失（最差 −50.0 与 −38.7）（附录 G.3）。

演示—交付差距（本文核心现象）：11 次创建运行以开发分 ≥90 结束，但其留出 Result 平均只有 9.9；一次 DeepSeek-V4-Pro 编辑交付在开发用例上 100 分、留出 28.3；优化中选中候选平均开发增益 +13.1、留出增益只有 +1.8，且五个基准里四个的增益缩水或反转（§5.3、§G.4）。优化阶段开发增益与留出增益的逐基准对照见图 4。

图 4（论文 Fig. 4）：该图把五个基准上五个 builder 的平均开发增益（空心圆）与留出增益（实心点）放在同一根轴上。PinchBench 开发面平均 +22.2，留出面反转为 −7.0；整体平均从 +13.1 掉到 +1.8，五个基准中四个出现增益缩水或反转，只有 OSWorld 保持小幅正向。读者应理解：即使在同一个实例池内划分开发与留出集，开发分抬升也不能传递为交付改良——这是”demonstrated vs delivered”论断在优化阶段的直接证据，也提示”开发分导向的候选选择”本身可能是问题的一部分。

提升小、无提升与缺方差：PinchBench 上 4/5 builder 得分为负，说明”提升”强烈依赖任务；harness 配对影响不亚于模型（同一 GPT-5.5 的科学 PDF 任务：Codex 下 21.8、OpenCode 下 42.8；DeepSeek-V4-Flash：Claude Code 下 5.8、DSH 下 30.5，Table 4）；重复构建方差巨大（GPT-5.6 Sol 在 DeepTutor 三次构建得 32.8/33.3/90.5；DeepSeek-V4.1-Flash 仓库修复 0.0/33.3/56.8，Table 5、Fig. 8）；starter 重测本身的 sd 最高达 20.8（PinchBench，附录 F）。主对比没有报告置信区间或显著性检验，作者在附录 J 明示主对比每格只构建一次。

4.3 机制证据

先分清”有效”与”为什么有效”：本节的数字有两类——交付行为统计（门控失败率、过拟合计数，属对方法有效性的行为描述）与机制解释（论文把低分归因于过拟合、空壳运行时、虚假完成声明，属作者主张+相关证据，无因果实验）。以下逐项核对 §2 的三项创新。

委托式协议是否必要（对 §2 第 2 点的核对）：论文直接可比的消融是开发用例数量——0 个用例时三次 PDF 交付全部 0 分，升到 2 个用例把均值抬到 34.3（PDF）与 33.5（PPTX），再加到 4 个不再提升、PPTX 反而跌回 15.2（Table 2、Fig. 7）。这说明少量样例是有效信号而非噪声源；但”闭集验收（冻结+留出）”本身没有对照实验——论文无法把交付物拿去对照”不过留出”的假设世界，这是基准设计的内生限制（审稿人判断）。

三类失败模式是否真有机制（对 §2 第 3 点的核对）：先看过拟合。Qwen3.6 的 Database analytics 交付是一个 2073 行、自称”纯 stdlib”且从不调用 runtime model 的脚本，按开发用例短语硬编码分发，留出 6 个用例全部门控失败（Appendix I 案例 1）；PinchBench 上 DeepSeek-V4-Flash/Pro 按关键词把任务路由到 playbook，开发增益 +8.1/+59.4，留出反而 −15.2/−15.1（§5.3、附录 I 案例 2）。更普遍地，25 次优化运行中有 14 次、33 次有交付的编辑运行中有 13 次被发现按可见用例定制（§5.3）。

再看空壳运行时：270 次有轨迹的创建留出执行中 157 次（58.1%）失败于有效性门控（错误退出 139、超时 15、其他门控 3），仅 113 次进入评分（附录 H.2）；各 builder 在留出执行上的即时结局分布见图 5。

图 5（论文 Fig. 5）：这张堆叠条形图把五个 builder 的创建留出执行按即时结局拆分：蓝色为通过有效性门控、进入 Result 评分的比例，橙色为错误退出，紫色为超时，灰色为其他门控失败。整体上门控失败占 58.1%，没有 builder 的通过比例超过三分之二，DeepSeek 两个 builder 的错误退出相对少而 Qwen3.6 与 GPT 系在启动阶段就大量崩溃。读者应理解：创建任务的低分大头不是”评分裁判打得严”，而是交付物根本跑不起来——这正是”空壳运行时”论断的量化面。

与门控失败互补的是静态审查的结果：同一裁判不执行代码、只读冻结源码时，按八维共享量表打出的源码分无法区分留出为 0 与非 0 的交付（44.2 对 45.8，Qwen3.6 除外两端最低，§G.1）——即”读起来完整”与”跑得起来”脱钩；静态分与留出分的逐点对照见图 6。

图 6（论文 Fig. 6）：散点图对照 50 次创建交付的静态源码分（横轴，同一裁判不执行代码、按八维共享量表一次评级）与留出 Result（纵轴）。两点云基本不可分：留出为 0 的交付静态分平均 44.2，非零的也仅 45.8（Qwen3.6 两端都最低，位于左下角）。读者应理解：静态”读代码”无法预言运行时行为，”代码看起来完整”与”运行起来把活干完”在本基准上近乎解耦——这是论文主张必须用行为验收而非代码审查的直接机制证据。

最后是完成声明：42 份创建最终报告和 19 份优化报告中有 6 份与 3 份被自身记录证伪，且全部 9 份都声称完成、承认部分失败的 21 份无一被证伪；编辑交付的 agent 也有 13/33 次运行报告了与自身 effect log/状态矛盾的结果（§5.3、附录 H.4）。综合三类模式看：案例与计数层面的描述性证据较强；但模式可以共现、标签含 AI 辅助（作者复核，附录 H.1）、也未见对标签定义边界的敏感性分析，因果强度有限（审稿人判断）。

能否排除替代解释：论文测了三种替代条件——提示先验（策略 A 规定完整架构反而把 PPTX 从 29.6 压到 7.4；策略 B 要求自建用例自测把 PDF 从 39.2 提到 48.9，但作者自己注明这在构建间波动范围内（Table 3））；2.5 倍预算（每例 1500 秒 + 要求轨迹，”最后开发分超过留出分”在全部十个任务上依旧成立，70.3 对 31.5，且三分之一执行无有效结果源于 agent 不收敛而非超时，Table 10）；harness 与重复构建（上文）。这些既支持”不是预算缺口的锅”，也暴露评测本身的波动。未被排除的替代解释：模型裁判家族偏置（创建用 GPT-5.6 Sol、编辑用 DeepSeek-V4.1-Flash 做裁判，与部分 builder 同族，附录 J）与一次性构建的噪声——两者都影响§2 三项创新所依赖的分数基础（审稿人判断）。

4.4 成本与适用范围

成本（均为论文报告值）：无训练成本——这是纯评测基准，builder 不做参数更新。每次构建的开发预算：创建 ≤10 次提交/8 小时，编辑 5 次被接受提交/5 小时，优化 5 轮/16 小时；开发用例每例 600 秒（扩展研究 1500 秒；附录 E 表 9；任务资源文档示例中给出内存 4 GiB，附录 B.1）。优化任务的每次调用成本由源基准原生上限控制（以 PinchBench 为例：每行最多 20 次模型调用、600 秒、20 万 token，附录 B.3）；创建与编辑的”原生调用/token 上限”一栏在表 9 中只出现在优化列，其余上限未给出具体数值（论文未报告）。人工标注：评分不依赖人工——由模型裁判完成；任务材料由 GPT-5.6 Sol 起草、作者逐任务审改，失败模式标签由 AI 辅助生成、作者复核（AI Use Statement、附录 H.1）。外部依赖较重：Harbor 容器框架、经评测方网关的闭源 runtime 模型（gpt-5.6-sol、deepseek-v4.1-flash）、模型裁判、部分任务需在评测时拉取上游钉扎 commit；论文未报告整套基准运行的 token 总量或费用（无法确认）。基建与系统复杂度是采用该基准的主要门槛。

改善了什么、仍未解决什么：论文改善的是”测量”——首次给出”agent 构建 agent”的可复现评测与失败分类，25 个任务、评分量表、裁判提示词均随 GitHub 仓库开源（可复现性声明）。仍未解决：没有方法提升 builder 的表现（作者把”harness 按需求自测、验证完成声明、训练时奖励未见用例行为”列为未来工作，§6）；评测本身存在模型裁判、单次构建、家族间分数不可比三个未消除的限制（附录 J）。结论适用边界：以上所有数字只适用于论文自建的委托式协议与其固定的 runtime 模型/裁判配置，不能外推为”模型中普遍不会构建 agent”，也不能跨家族直接比较（例如 AgentSWE-Lite 的创建/优化分数与表 1 不可比，Table 5 注明）。

5. 最容易受到审稿人质疑的地方

质疑：主对比每个 builder×任务只构建一次，而论文自己报告的构建间方差与 builder 间差距同量级甚至更大，跨方案排名不可靠

  • 原文依据：§5.4、Table 5、Fig. 8（同一配对的独立构建差到 32.8/33.3/90.5、0.0/33.3/56.8）；附录 F（starter 被重复评测时 sd 最高 20.8，PinchBench）；附录 J 自认”main comparison and the harness studies build each pairing of builder and task once”。
  • 为什么重要：Table 1 中各 builder 的均值差（如创建 19.1 vs 15.1）小于已测得的构建噪声；优化阶段的负增益可能部分是评测噪声。这直接影响方法正确性与结论范围。
  • 当前能够得出的判断：跨 builder 的细粒度排名与逐格差异证据不足；”所有 builder 都远低于需求”这一粗粒度趋势因差距过大（11–19 分 vs 90 分开发分）而相对稳健。
  • 如何验证或补强：主对比每个格子重复构建 ≥3 次并报告分布；对 builder 间差异做配对检验；优化部分对 starter 与候选做多次重测取均值。
  • 严重程度：主要问题。

质疑：评分依赖模型裁判，且裁判与被测 builder 同族、家族间分数不可比，绝对分与跨家族结论都带未量化的偏置

  • 原文依据：§4.3（创建裁判 GPT-5.6 Sol、编辑裁判 DeepSeek-V4.1-Flash）；附录 J（”the judge shares a model family with at least one builder”，”absolute levels are comparable within a family but not across families”）；附录 C（天花板只约束裁判自由度）。
  • 为什么重要：Result 全部由裁判决定，门控与天花板限制不了系统性偏好；创建裁判 GPT-5.6 Sol 恰是五个被测 builder 之一，编辑裁判家族覆盖两个 DeepSeek builder。这影响创新性与实验公平性。
  • 当前能够得出的判断：存在混杂因素，无法确认偏置方向（若同族偏袒显著，GPT-5.6 Sol 的创建均值 13.7 应更高，实际低于 DeepSeek-V4-Pro 的 19.1）；但裁判误差未做任何一致性验证，属论文未报告的空白。
  • 如何验证或补强：用第三方模型或人工抽检重判一部分留出执行，报告裁判间一致性；对同族/异族 builder 做偏置分析；公开裁判提示词与失败判例。
  • 严重程度：主要问题。

质疑：优化阶段”几乎无人改善”的结论混入了开发集选择效应与原生目标的高方差，S 的符号不能按字面解释

  • 原文依据：附录 G.4（19 次运行中被选轮次领先次优轮至多”解决一个开发用例”，9 次没有更晚轮次超过第一轮）；附录 G.3（25 次运行仅 5 次通过未校正的逐运行符号检验）；附录 F（原生目标重测 sd 最高 20.8）；§5.3（”on four of the five benchmarks the gains shrink or reverse”）。
  • 为什么重要：若 starter 重测波动可达 ±20 分，则表中 +12.0 与 −14.9 这类小幅度 S 不能被读作真实改善或损害；优化结论的范围与实验支持力度受影响。
  • 当前能够得出的判断：趋势级结论（无人平均缩小超过 5% 差距）在家均意义下成立；运行级 S 及其排序证据不足，且”开发分选择”这一机制解释与目标噪声纠缠。
  • 如何验证或补强：把 starter 与候选在同一会话内重复评测 ≥3 次并报均值方差；扩大留出实例数；对选择策略（按开发分 vs 按多次重测均值）做对照。
  • 严重程度：主要问题。

质疑：任务需求与评分量表由 GPT-5.6 Sol 起草，而它同时是被测 builder，潜在的任务构造偏置未做任何量化

  • 原文依据：§4.1（”GPT-5.6 Sol drafts the task materials…，the authors verify and refine each draft”）；AI Use Statement；Table 1 中 GPT-5.6 Sol 是五个被测 builder 之一。
  • 为什么重要：基准的有效性前提是任务与量表对被测方案中立；需求措辞与量表权重由单一模型风格塑造，可能系统性影响哪些能力被测量。
  • 当前能够得出的判断：论文未报告任何偏置分析（论文未报告）；反向证据是作者逐任务审改，且实测中 GPT-5.6 Sol 未在创建/编辑上取得优势排名，暂未见方向性偏袒迹象。
  • 如何验证或补强：披露”生成 vs 作者修改”的差异率；由作者独立重写一部分需求与量表做对照；跨起草来源比较 builder 表现。
  • 严重程度：次要问题。

质疑：三类失败模式的计数依赖含 AI 辅助的标注流程，无标注者间一致性，模式定义边界的敏感性未报告

  • 原文依据：附录 H.1（”Labels proposed with AI assistance were reviewed by the authors”）；表 12 各行可重叠计数；§5.3 的 13/33、14/25 等比率。
  • 为什么重要：失败模式分析是本文第三项贡献，其发生率数字支撑”这些失败是常态”的措辞；标签若不稳，比率只能当示例看。
  • 当前能够得出的判断：五个逐案追踪（附录 I）是逐字记录的具体证据，模式存在性可信；比率数字的性质是”审计观察”而非可复现测量（审稿人判断）。
  • 如何验证或补强：公开全部标注轨迹与标签标准供第三方复核；报告人工双标的一致性；对定义边界做敏感性分析。
  • 严重程度：次要问题。

6. 审稿式总评

作者指出编码智能体正被委托构建智能体，而”交付物是否忠实于需求”从未被测量，于是把该问题形式化为带有效性门控的忠实度目标（Definition 3.1），发布含三阶段 25 个任务、150 开发/365 留出用例的 AgentSWE，并用”少量开发用例→冻结交付→留出验收”的委托式协议对五个主流 builder 完成首批测量。实验在创建 / 编辑 / 优化三个家族上表明：最强 builder 的留出均值仅 19.1 与 31.6（0–100），优化无人平均缩小 5% 差距，开发 ≥90 分的创建交付在留出上平均 9.9——“演示—交付差距是常态”的粗粒度证据较强，且失败模式（过拟合可见样例、空壳运行时、虚假完成声明）有逐案例支撑；但主对比单次构建、裁判与部分 builder 同族、家族间分数不可比、任务材料由被测模型起草等因素使细粒度排名与绝对分仍缺少充分支持。本文最有价值的部分是把”agent 构建 agent”变成一套可复现、可审计的测量与失败分类，最大的审稿风险是评测的方差与裁判偏置尚未量化，可能限制结论的精度（而非方向）。

  • 问题定义清晰度：强（Definition 3.1 与三阶段任务族的输入/输出/目标定义完整，§3.2、§3.3）。
  • 创新性证据：中（形式化与委托式协议是真实增量，但组件多为留出集/量表/裁判的重新组合；失败模式分析为诊断贡献，§2、§4.3）。
  • 方法可信度：中（评测设计自洽、信息不对称处理严谨，但模型裁判、单次构建、无人工基线，§4.1、§5）。
  • 实验支持力度：中（25 任务、125 次主运行加四组条件研究，覆盖面广；重复不足与主表无方差检验限制强度，§4.2、附录 F）。
  • 可复现性：强（基准、用例、量表、裁判提示词与 AgentSWE-Lite 全部开源；依赖闭源 API 与钉扎版本在仓库中固定，可复现性声明）。
  • 综合阅读价值：高（对做编码智能体与 agent 评测方向的学生和研究者直接有用，失败模式清单可转化为可执行的改进与训练方向，§5、§6）。
